SD-020 · Chapter 1 of 12

Define continuity before choosing a rollout strategy

Zero downtime is a workload contract

A deployment replaces processes, configuration, data interpretation, or model behavior while users continue doing useful work. Zero downtime should describe a defined customer capability under declared load and failure assumptions. It does not mean no process restarts, no connection ever moves, or no internal error occurs. Specify eligible operations, latency, correctness, and allowed degradation before choosing a rollout mechanism.

A stateless request, a ten-minute streaming response, a background training job, and a paid external action have different continuity needs. A retry may repair a failed idempotent read while duplicating an unprotected purchase. A stream can remain on an old process during drain while new requests go elsewhere. A job may need a compatible checkpoint rather than a live process handoff. Treat these as separate migration paths.

The deployment changes a distributed system while multiple versions coexist. That period can last longer than the rollout itself because workers pause, clients cache, queues retain messages, and regions disconnect. Compatibility must cover the real coexistence window. An old binary returning after a pause is still an old writer, even if the dashboard declared the rollout complete yesterday.

Separate release, deployment, and migration

Deployment places executable components or configuration in an environment. Release exposes behavior to a selected population. Migration changes durable state, schema, format, or ownership. A feature flag can decouple deployment from release, but it does not make an incompatible schema change safe. A rollback of traffic can hide new behavior while leaving new-format data behind.

Define a release identity that includes executable digest, configuration revision, schema compatibility, model and tokenizer versions where relevant, and the intended traffic policy. An image tag alone is too weak if it is mutable or if critical behavior also comes from separately changed configuration. Reproduce the actual bundle used by a request during incident analysis.

This lesson develops an original hypothetical release platform. Public company sources provide context, while all numerical examples and interview exercises are invented teaching cases. We will preserve availability through bounded capacity and compatibility, then explain when rollback cannot restore the previous world and forward repair becomes necessary.

The first whiteboard

Draw old and new versions, their shared database, queue, cache, clients, and external providers. Mark every read and write format. Name which changes are reversible, which are only compensatable, and which are irreversible. Then identify the smallest cohort that can expose the relevant risk without violating the customer contract.

A safe deployment strategy is a sequence of legal states, not a button labeled rollback. Each state needs preconditions, evidence, a next step, and a stop condition. The rest of the lesson makes those states concrete.

SD-020 · Chapter 2 of 12

Budget useful capacity during rolling replacement

Readiness is not mere process existence

A new process is not useful capacity until it has loaded artifacts, established required connections, passed meaningful readiness checks, and can serve the intended capability. A health endpoint returning two hundred from an empty HTTP handler does not prove model readiness, database compatibility, or tenant routing. Avoid checks that create a new global dependency or overload a struggling backend.

Separate liveness, readiness, startup, and rollout progress. Restarting a slow but healthy process repeatedly can turn temporary warmup into permanent failure. Removing readiness should stop new traffic through the routing contract, while drain handles work already admitted. The load balancer and process need compatible timing; setting a flag locally does not instantly erase every cached route.

Reserve headroom for load variation, a concurrent failure, and resource contention during warmup. New replicas can consume CPU, GPU memory, cache bandwidth, and database connections before they contribute useful throughput. A nominal surge can therefore reduce old-fleet capacity. Test the actual coexistence resource budget, especially for large models and shared accelerator hosts.

Worked example 1: a rolling update with a capacity floor

Assume twenty replicas each sustain one hundred eligible requests per second at the required latency. Peak demand is sixteen hundred requests per second. The nominal minimum is sixteen healthy replicas, but running exactly at that boundary leaves no room for variance or another failure. For this exercise, set a required useful floor of eighteen replicas, or eighteen hundred requests per second.

Choose maxUnavailable equal to two and maxSurge equal to four. At the declared readiness boundary, the rollout should maintain at least eighteen available replicas relative to the desired twenty and may create up to twenty-four non-terminating replicas under the simplified rollout budget. Actual Kubernetes terminating processes and resource use can temporarily exceed a naive count, so the infrastructure capacity plan must inspect lifecycle behavior rather than treating this bound as a universal process limit.

Start four new replicas. They load a model and pass readiness. Remove two old replicas from new admission and drain them. Continue in bounded steps, checking useful capacity and error rates. If new replicas fail readiness, do not keep removing old ones merely because the desired version exists. A progress deadline should stop the rollout and surface the failure for an explicit recovery action.

The failure variation is a zone loss removing three otherwise useful replicas while only eighteen remain. The fleet now has fifteen hundred requests per second of assumed useful throughput, below demand. The original rollout budget did not promise survival of that concurrent loss. Add stronger headroom, a zone-aware rollout constraint, or a stated degradation policy if that failure must be tolerated.

The final design ties replica transitions to useful serving capacity and resource reserve. Correctness means requests remain within their contract, not merely that the deployment controller reports progress. The interview takeaway is to compute the floor, show a transition sequence, and distinguish controller availability counts from measured throughput and physical resource use.

Blue-green and traffic switches

Blue-green keeps two environments and switches admission between them. It simplifies one part of rollback if the old environment remains ready and compatible. It can double some capacity cost and still shares databases, queues, keys, and external effects. A green environment writing incompatible data can make blue unsafe even before the traffic switch is complete.

Traffic routing is itself distributed state. Changes propagate through gateways, caches, connection pools, and persistent sessions. Measure effective traffic by version rather than assuming a control-plane acknowledgment means every request moved. A safe switch includes old connection handling, capacity, and the ability to identify work admitted on each version.

SD-020 · Chapter 3 of 12

Use canaries as experiments with explicit limits

Cohort selection and comparable evidence

A canary exposes a bounded population to a new version while retaining a comparison population. The purpose is to detect a harmful change before expanding its impact. Routing five percent of traffic is not automatically a representative experiment. Tenant mix, request complexity, region, cache state, model size, and time can confound the comparison.

Choose cohorts that exercise the changed behavior and remain ethically and operationally acceptable. For a low-volume enterprise tenant, a global random five-percent sample may barely test the relevant feature. For a safety-critical tool, the smallest safe cohort may require synthetic or shadow evaluation before any real effect. Shadow traffic must suppress external writes and protect sensitive data.

Define stop, hold, and promotion conditions before rollout. Stop means evidence or a hard invariant requires rollback or mitigation. Hold means evidence is insufficient, delayed, or unavailable. Promotion requires the declared exposure, observation window, and guardrails. Missing telemetry is not equivalent to zero failures. Neither a green aggregate dashboard nor a p-value substitutes for a business correctness invariant.

Worked example 2: compare rates and uncertainty

The baseline serves one hundred thousand eligible requests with one hundred errors, an observed error rate of 0.1 percent. The canary serves five thousand requests with twenty errors, an observed rate of 0.4 percent. The observed ratio is four, and the excess is 0.3 percentage points. These are descriptive calculations; they do not alone prove causality or future behavior.

For a rough independent Bernoulli approximation, the standard error of the difference is the square root of p1 times one-minus-p1 divided by n1 plus p2 times one-minus-p2 divided by n2. Substituting the observed rates gives about 0.000898 as a fraction, or 0.0898 percentage points. A rough 1.96-standard-error interval around the 0.3-point difference is approximately 0.124 to 0.476 percentage points. The approximation and independence assumptions must be stated; exact or better-designed analyses can be appropriate.

If the canary disproportionately receives difficult requests, this comparison may attribute workload differences to the release. Stratify or randomize appropriately and inspect cohort balance. If requests share tenant-level failures, independence is weaker and the simple interval can overstate certainty. Repeatedly checking until one result looks significant also changes the interpretation. Predefine the decision procedure or use a suitable sequential method.

The failure variation is a correctness defect that appears once in a rare paid action. A low average error rate does not excuse violating a hard invariant. Stop on duplicate charge evidence under the release policy, reconcile effects, and investigate. Statistical promotion rules govern uncertain rate comparisons; they do not override known safety violations.

The final decision in this teaching example is to stop expansion and investigate the observed regression with cohort-aware evidence. Correctness includes protecting users while preserving diagnostic identity. The interview takeaway is to calculate clear rates, state uncertainty and confounders, and distinguish insufficient evidence from evidence of safety.

Canary cost and observation windows

Some regressions emerge only after cache expiry, compaction, token refresh, daily traffic changes, or queue backlog. A ten-minute canary cannot prove the absence of a twenty-four-hour resource leak. Choose observation windows from the failure mechanism and maintain post-promotion monitoring. A release can pass its initial gate and still require later mitigation.

Canaries also consume engineering and infrastructure resources. Automate repeatable checks, retain a clear human override path, and record the evidence behind decisions. Avoid a gate so noisy that operators routinely ignore it. Evaluate false alarms, missed incidents, and time to safe recovery together.

SD-020 · Chapter 4 of 12

Migrate schemas through compatible intermediate states

Expand, migrate, contract

An expand-migrate-contract sequence first adds a compatible representation, then moves and validates data, then removes the obsolete representation only after all relevant consumers and rollback needs have changed. The intermediate states are the essential design. Renaming a column in one step can break old binaries, background jobs, scripts, and delayed messages that still use the old name.

Expansion can include a nullable new column, a new table, an optional message field, or a versioned object format. Compatibility is directional. A new reader understanding old records does not prove an old reader understands new records. A new writer preserving an old field does not prove both fields remain equivalent under every concurrent update.

Database operations have engine- and version-specific locking, rewrite, validation, and failure behavior. PostgreSQL documentation distinguishes relevant ALTER TABLE operations and deferred validation for supported constraints. A generic statement that an operation is online is too vague. Verify lock acquisition, lock duration, scan work, replication impact, and the cancellation or retry plan on the deployed version.

Worked example 3: split a display name safely

The initial schema has display_name as a single string. The new product needs given_name and family_name, but splitting arbitrary human names is not reliably reversible or semantically correct. The objective is compatible rollout without inventing information. Expand the schema with optional structured fields and a representation version while retaining display_name for old consumers.

Deploy readers that understand both representations and prefer an explicitly supplied structured value when valid. Deploy writers that preserve display_name according to a declared display policy and record whether structured fields came from user input or a limited migration rule. Historical rows without reliable structure remain unclassified rather than being silently split at the last space.

A backfill populates only rows whose conversion is valid under an approved rule, or marks them as needing user review. It uses row version conditions so an old snapshot cannot overwrite a newer user's edit. Validation counts eligible, converted, skipped, conflicted, and invalid records separately. A count of rows touched does not prove the new representation is correct.

During coexistence, an old writer can change display_name without updating structured fields. Either route those writes through a compatibility adapter, use a transactionally enforced synchronization policy, or keep the new fields marked stale until reconciled. Two independent writes from application code are not atomic merely because they occur next to each other.

Contract only after old readers and writers, delayed jobs, retained messages, and the rollback horizon are handled. The final result preserves user meaning and compatibility rather than claiming every legacy value can be transformed perfectly. Correctness includes provenance and conflict behavior. The interview takeaway is that schema migration includes semantics, not just columns and row counts.

Constraints, indexes, and rollback boundaries

Adding or validating a constraint can scan data and consume I/O even when ordinary writes remain possible. Creating an index may need a version-specific concurrent procedure and cleanup after failure. Monitor replica lag, lock waits, transaction age, disk reserve, and query latency. Set bounded lock acquisition behavior so a deployment does not wait invisibly behind a long transaction and then block new work.

A schema downgrade is not always safe after new writes begin. Keep the expanded representation until the compatibility window closes. If a new field contains information the old schema cannot represent, reverting a binary may still be possible through an adapter, while dropping the field would lose data. State these limits before the rollout.

SD-020 · Chapter 5 of 12

Backfill incrementally without corrupting concurrent writes

Backfill is a long-running production workload

A backfill competes for database I/O, CPU, cache, transaction logs, replication bandwidth, and locks. Use bounded batches, stable progress identity, idempotent transformations, and adaptive throttling based on customer impact. A fixed high row rate is not a virtue if it saturates the primary or creates hours of replica lag.

Choose a progress mechanism that does not skip records when the dataset changes. A simple offset scan can become unstable under insertions and deletions and gets expensive at large offsets. Keyset pagination, snapshot boundaries, change capture, and reconciliation can be useful, but each has assumptions. The migration must account for new writes during and after the historical scan.

Keep transformation version, source version, and result state explicit. A retry should either repeat the same safe transformation or detect that the row changed. Do not mark a batch complete before its effects are durable. A worker crash between data updates and progress advancement must not lead to silently omitted or doubly applied non-idempotent work.

Worked example 4: rate, conflicts, and catch-up

Assume a table has one hundred twenty million eligible rows. The backfill safely processes ten thousand rows per second when customer traffic is normal. Ignoring retries and pauses, the scan takes twelve thousand seconds, or three hours twenty minutes. If throttling allows work only half the time at that rate, wall time becomes six hours forty minutes under the simplified duty-cycle assumption.

During the scan, live writers update five hundred rows per second. A naive two-write path that updates old and new stores independently can fail between writes. Instead, use one transaction when both representations share a transactional boundary, or a durable change record with idempotent application and reconciliation when they do not. State how ordering and deletes are preserved.

For row R, the backfill reads source version ten. A user writes version eleven before the migration commits. The backfill condition requires source version ten; it fails and retries or defers using the new value. It must not overwrite version eleven with a transformation of version ten. Record the conflict as expected concurrent behavior rather than treating every conflict as data corruption.

If the change stream arrives at five hundred updates per second and the catch-up consumer applies eight hundred, net backlog drain is three hundred per second while that load remains steady. A nine-million-event backlog then needs thirty thousand seconds, or eight hours twenty minutes, before it reaches zero under these assumptions. A fast historical scan does not imply the migration is ready to cut over.

The failure variation is a deleted row reappearing because a delayed backfill insert ignores the deletion version. Preserve tombstone or version ordering in the target protocol. The final result is a target whose historical scan and live changes reconcile under a stated ordering rule. The interview takeaway is to quantify scan and catch-up separately, then explain conflicts and deletes.

Validate meaning, not just counts

Compare source and target using stable identities, transformation semantics, sampled deep checks, and complete invariant checks where feasible. Equal row counts can hide one missing row and one duplicate. Equal checksums can be meaningless if the fields are normalized differently or if the comparison excludes the changed data. Design the validation to catch the failure you care about.

Before cutover, identify the high-water mark through which live changes are applied, remaining exceptions, and the freshness bound acceptable to readers. Keep a reconciliation path after cutover. The migration is not complete merely because the historical worker finished its last page.

SD-020 · Chapter 6 of 12

Drain long work and preserve effect identity

Admission and completion are separate

Removing an instance from admission stops new work only after routing changes take effect. Existing requests, streams, queue leases, and background tasks need a completion or transfer policy. A fixed sleep before termination is a weak substitute for observing actual in-flight work and enforcing a bounded deadline.

For HTTP-style requests, retries need a clear idempotency contract. For a streaming response, a client may have received partial output and cannot safely pretend nothing happened. Resume tokens, request identity, and a documented reconnect protocol can help if the product supports them. Some operations must be allowed to finish on the old version, which extends the compatibility window.

Queue workers add ownership and acknowledgment boundaries. A message may be processed but not acknowledged before the worker stops. Its redelivery must not duplicate an external effect. Stable business idempotency and reconciliation belong at the effect boundary, independent of the deployment system. Process restarts are routine; logical actions must survive them.

Worked example 5: terminate a worker after a paid effect

Worker A running version one receives message operation P with attempt A1. It sends a payment request using stable idempotency key P. The provider commits the payment, but A is terminated before it records the response and acknowledges the queue message. The objective is to complete the operation without charging twice during the deployment.

The queue redelivers P to worker B running version two as attempt B1. B must use the same logical effect identity and reconcile the provider outcome under the provider's actual idempotency contract. If the provider returns the existing result, B records that durable outcome and acknowledges P. A new attempt identifier is useful for diagnostics but must not replace the business idempotency key.

If the provider's idempotency retention window has expired, blindly sending again may be unsafe. Query authoritative payment state, use a supported business lookup, or route to explicit reconciliation. The deployment controller cannot manufacture an exactly-once payment guarantee from a rolling update. State the unresolved outcome and the operational response.

Now consider a ten-minute inference stream. The route layer stops new admission to A but allows the stream to finish within a twelve-minute drain bound, assuming resources and policy remain valid. A forced deadline can interrupt it, requiring a documented client outcome. If an emergency security change invalidates the old policy, the stream may need to stop earlier. Availability and security constraints must be resolved explicitly.

The final result preserves logical identity across versions and separates queue delivery from effect commitment. Correctness means one intended business result under the provider contract, or an explicit unresolved state. The interview takeaway is that graceful drain reduces interruptions while idempotency and reconciliation protect effects when drain is insufficient.

Chapter summary

A deployment deadline is an operational choice, not proof that all old work finished. Track in-flight count, oldest age, pending effect reconciliation, and active version. Do not delete old schemas, keys, or artifacts while valid old work still requires them. A process can be gone while its messages and external effects remain part of the migration.

SD-020 · Chapter 7 of 12

Know when rollback has stopped being a safe inverse

Binary rollback, traffic rollback, and data repair

A binary rollback changes which executable runs. A traffic rollback changes which version receives new work. A data rollback changes durable state, often losing or transforming work. A compensation creates a new business action intended to counter an earlier one. These operations have different safety and availability properties. Calling all of them rollback obscures what is actually recoverable.

Before release, create a compatibility matrix for old and new readers and writers against every intermediate schema or format. Mark the last state in which the old binary can safely resume. This rollback boundary may occur before the rollout reaches all users. Once new writers emit an incompatible durable format, routing back to old readers can produce failures or silent misinterpretation.

A rollback plan includes the capacity and readiness of the old environment, artifact retention, key availability, configuration compatibility, and the handling of in-flight work. If the old fleet has been scaled to zero, restarting it may take minutes and depend on management services. A button that changes a route does not restore missing warm capacity.

Worked example 6: a lossy format change crosses the boundary

Version one stores account balance in integer cents. Version two introduces a higher-precision representation for a new product. The objective is to deploy the new behavior while retaining a safe mitigation path. Expansion adds the new representation and readers able to interpret both. During the initial phase, writers preserve values exactly representable in cents so version one remains compatible.

At a later release gate, version two begins accepting fractional-cent values. An account now holds a value that version one cannot represent exactly. Simply rolling back the binary would either reject the data or round it, changing business meaning. The old executable is no longer a safe general fallback for this new state.

A compatible mitigation can disable new fractional-cent operations while keeping a reader and ledger implementation that understands the new representation. Existing higher-precision values remain intact. If a defect affected calculations, repair through auditable forward ledger entries under the product's accounting rules rather than rewriting history blindly. This is a hypothetical engineering example, not financial advice or a claimed production accounting policy.

The failure variation is an asynchronous old worker returning and writing a cent-only value over the higher-precision balance. Exclude unsupported old writers through a schema or capability epoch, version-aware API, or equivalent enforcement at the authoritative write boundary. A dashboard saying the old deployment has zero replicas does not prove no stale writer exists.

The final result distinguishes rollback before incompatible writes from mitigation after them. Correctness preserves durable meaning and auditability. Production implications include retaining compatibility code, tracking format adoption, and planning forward recovery. In an interview, identify the exact transition that removes the inverse instead of promising every deployment can always be undone.

Feature flags and emergency mitigation

A feature flag can stop new behavior while leaving compatible code deployed. Treat the flag service, cached values, propagation, and authorization as part of the operational design. An emergency flag that requires a failing global lookup on every request can introduce its own outage path. State which policy may be cached and how quickly a change must become effective.

Flag removal is a migration too. Old clients or queued jobs may still refer to the earlier behavior. Track ownership and retirement criteria so temporary compatibility paths do not accumulate forever. The goal is an explicit safe lifecycle, not permanent complexity disguised as flexibility.

SD-020 · Chapter 8 of 12

Apply rollout discipline to models, agents, and public systems

AI releases have behavioral compatibility

An inference release can change weights, tokenizer, prompt templates, retrieval schema, tool definitions, safety policy, and serving runtime. A model loading successfully does not prove that the product remains correct. Build a versioned compatibility bundle and evaluate the tasks and populations that matter. Latency and HTTP success can remain healthy while answer quality or tool behavior regresses.

Offline evaluation, shadow execution without effects, limited canary exposure, and post-release monitoring provide different evidence. A deterministic test corpus cannot cover every production prompt. A canary may miss rare harmful behavior. Use hard safety invariants where possible, retain human escalation for uncertain privileged actions, and make the release's limits explicit. Do not equate absence of observed failures with a universal safety guarantee.

NVIDIA's public Triton model-management documentation provides concrete product lifecycle context. It does not by itself implement the lesson's product-quality gates or cross-service compatibility. A model repository update, a loaded instance, route readiness, and a safe customer release are distinct stages. Pin request versions when needed and define how long old artifacts remain available for streams and rollback.

Agents and long-lived workflows

An agent run can span a release and retain a plan, context, approvals, tool results, and unresolved external effects. Migrating it to a new runtime requires compatibility for that durable state. A new model may interpret an old plan differently. A previously approved scope does not automatically expand because the new version has more tools.

Anthropic's public multi-agent research article provides production workflow context, not a disclosed universal deployment protocol. Our original design exercise is to preserve run identity, approval scope, effect identity, and schema version across upgrades. If a paused workflow cannot be safely resumed by the new version, drain it on a compatible runtime or perform an explicit migration with validation.

For training infrastructure, a runtime update may alter checkpoint compatibility, communication behavior, or hardware assumptions. A canary needs representative topology and load. Successfully training on one small node does not prove a multi-node job will survive restart and restore. Separate the ability to start new jobs from the treatment of already running ones.

What the public sources do and do not prove

Google's SRE workbook grounds canary reasoning and release evaluation. Meta's historical rapid-release article grounds public release-engineering context. OpenAI's PostgreSQL article includes public schema-management and operational concerns. These sources support disciplined change management, but they do not reveal private current rollout thresholds or interview questions. All rates, replicas, migration states, and questions here are original.

GitHub's gh-ost repository describes a MySQL online schema-migration tool. It is not a generic PostgreSQL procedure. PostgreSQL and Kubernetes documentation are version-sensitive references for their actual operations. In a cloud architecture discussion, translate these principles into the chosen platform and verify its guarantees. A managed rolling-update feature cannot decide your application's compatibility or business compensation policy.

SD-020 · Chapter 9 of 12

Defend a complete release and migration platform

Requirements and component responsibilities

Design a hypothetical platform deploying a multi-tenant inference and tool service across three regions. It needs continued eligible request service at declared peak load, bounded rollout blast radius, compatible long-lived workflows, auditable schema changes, and a tested mitigation path. Confirm whether a concurrent zone failure must also be tolerated and which actions have irreversible effects.

An artifact builder produces immutable signed executable and compatibility bundles. A release registry records versions, provenance, schema ranges, and rollout policy. A rollout controller advances a durable state machine with stable change identity. Regional admission layers route cohorts. Worker readiness reports actual capability. An evaluation service joins release identity to customer-impact and model-quality evidence. A migration controller performs bounded backfills and records validated progress.

The authoritative data services enforce write compatibility and operation identity. The release controller cannot rely only on fleet observations to exclude old writers. A schema or capability epoch can reject unsupported mutations where they commit. A separate approval path governs destructive contract steps and privileged emergency actions according to the platform's operator policy. This is an original architecture proposal, not a requirement to ask the learner for approval during this lesson.

Follow a release through legal states

The release starts prepared but receives no customer traffic. Compatibility tests verify old and new readers and writers against the expanded schema. Capacity checks confirm warmup and surge can fit without starving old workers. The controller starts a limited cohort and waits for meaningful readiness. It then exposes the canary under a declared traffic selection and observation policy.

The evaluator can stop on a hard invariant, hold for insufficient data, or permit the next stage after its predeclared conditions pass. Promotion advances by region and cohort with useful-capacity checks. The controller records the evidence and exact bundle identity for each decision. A crash and restart resumes from durable state rather than reissuing every external action without identity.

Schema expansion precedes incompatible application use. A throttled backfill handles historical data while a transactional or durable-change path preserves live updates and deletes. Validation establishes a high-water mark and exception policy. Read cutover happens only when the target contract is satisfied. Contracting old fields waits for old writers, delayed jobs, retained messages, and rollback requirements to end.

During a failure, traffic rollback is allowed only if the destination remains ready and understands current data. Otherwise disable the new capability, keep compatible readers, or perform forward repair. Queue redelivery retains business idempotency across versions. Streams drain within their declared bound unless security requires termination. The platform reports unresolved effects rather than inventing a successful inverse.

Observability, security, cost, and evolution

Track effective traffic by release, useful capacity, readiness delay, warmup resource pressure, error and latency cohorts, model-quality guardrails, in-flight age, migration lag, conflicts, lock waits, replication lag, format adoption, and rejected obsolete writers. Keep change identity in diagnostic events without indiscriminately logging prompts or secrets. Correlation with a deployment is an investigation lead, not automatic causal proof.

Security includes signed immutable artifacts, scoped deployment authority, tenant-safe canary routing, protected migration credentials, and auditable flag changes. A compromised release controller is powerful; separate routine rollout capability from destructive data authority. Preserve access controls during schema and cache migrations. New code must not accidentally expose data simply because its schema is easier to query.

Cost includes surge capacity, duplicate blue-green environments, model artifact staging, retained old runtimes, shadow evaluation, backfill load, and engineering complexity. Start with staged rolling updates and explicit compatibility if they meet the contract. Add blue-green or specialized traffic controls when their rollback or isolation benefit justifies the cost. No strategy removes the need to understand durable data and external effects.

The complete defense names the legal states, their evidence, the rollback boundary, and the recovery action after that boundary. It also states limitations: low-volume canaries may require longer observation, a rare quality defect may escape tests, and a provider without reliable idempotency limits effect recovery. A mature platform makes these limits visible and improves them through incident evidence.

SD-020 · Chapter 10 of 12

Execute a compatibility and rollout state model

Model and assumptions

The executable Python below models release stages, available capacity, a compatible expanded schema, and a contract boundary that excludes old writers. Its gate distinguishes hold, stop, and promote. A backfill uses a source version condition so stale work cannot overwrite a newer edit. Assertions include the arithmetic from the lesson.

The model is local and deterministic. A production controller requires durable transitions, authenticated observations, retries with stable identity, fencing or equivalent ownership, and transactional enforcement where state commits. The code does not implement a statistical sequential test, a database engine, or an actual orchestrator. It exposes a few rules so they can be inspected and challenged.

Read the gate order: a known hard violation stops the rollout even if the sample is small. Missing evidence holds. An observed rate regression stops under this exercise's simple declared threshold. Passing the gate only means these conditions passed; it is not a universal proof of release safety.

Experiments and code

PYTHON · executable standard-library model
from dataclasses import dataclass
from math import sqrt

def capacity_ok(useful, floor=18):
    return useful >= floor

def gate(observed, hard_violation=False):
    if hard_violation:
        return 'stop'
    if observed is None:
        return 'hold'
    baseline, canary = observed
    return 'stop' if canary > baseline + 0.002 else 'promote'

@dataclass
class Row:
    source_version: int
    value: str
    migrated: str | None = None

    def backfill(self, expected_version, transformed):
        if self.source_version != expected_version:
            return False
        self.migrated = transformed
        return True

class Schema:
    def __init__(self):
        self.minimum_writer = 1

    def contract(self):
        self.minimum_writer = 2

    def accepts(self, writer):
        return writer >= self.minimum_writer

def main():
    assert not capacity_ok(17) and capacity_ok(18)
    assert gate(None) == 'hold'
    assert gate((0.001, 0.004)) == 'stop'
    assert gate((0.001, 0.001), hard_violation=True) == 'stop'
    assert gate((0.001, 0.001)) == 'promote'
    row = Row(11, 'new user value')
    assert not row.backfill(10, 'stale transformation')
    assert row.backfill(11, 'valid transformation')
    schema = Schema()
    assert schema.accepts(1)
    schema.contract()
    assert not schema.accepts(1) and schema.accepts(2)
    baseline, canary = 100 / 100_000, 20 / 5_000
    se = sqrt(baseline * (1-baseline) / 100_000
              + canary * (1-canary) / 5_000)
    assert 0.00089 < se < 0.00091
    assert 120_000_000 / 10_000 == 12_000
    assert 9_000_000 / (800 - 500) == 30_000
    print('Capacity, gates, stale backfill, compatibility, and arithmetic checks passed.')

Interpretation and chapter summary

Test the real integration using representative warmup, long streams, delayed jobs, lock contention, replica lag, telemetry failure, and a controller crash between external actions. Keep blast radius bounded and use realistic tenant permissions. An isolated happy-path deployment says little about compatibility under coexistence.

The model's value is a precise conversation about preconditions. A safe transition needs enough useful capacity, compatible state, valid authority, and sufficient evidence. If one is absent, hold or stop according to the contract. Automating an unsafe transition more reliably does not make it safe.

Speaking scripts, concept checklist, and drills

Thirty-second explanation

I define zero downtime as continuity of a specific correct customer capability. I keep enough useful capacity while old and new versions coexist, then gate exposure using comparable canary evidence. Data changes follow expand, migrate, validate, and contract. Long work drains under a bound and retains effect identity across retries. Before release I identify the rollback boundary; after incompatible state or irreversible effects, mitigation may require compatible code and forward repair.

Two-minute explanation

I start with the request contract and the coexistence window. A rollout is safe only if old and new readers, writers, queued work, and clients can interact with every intermediate state. I compute useful capacity rather than just process count, including model warmup, surge contention, and the concurrent failure requirement. Readiness must correspond to the actual capability.

I separate deployment from release and migration. A canary exposes a bounded representative cohort with predeclared stop, hold, and promotion conditions. Missing telemetry holds; a known correctness violation stops. Error rates need denominator, cohort, uncertainty, and observation-window assumptions. Model releases also need behavioral quality and safety evidence beyond latency.

For durable changes, I expand compatibly, migrate historical data with version-aware bounded work, preserve live updates and deletes, validate semantics and catch-up, then cut over. Contracting old fields waits until old consumers and rollback needs are gone. A binary rollback cannot safely interpret every new data format, so I identify the boundary before crossing it.

Finally, drain long work and protect business effects across redelivery. A process can stop after a payment committed but before acknowledgment. The next version must reconcile using the same logical identity. The release platform makes these states visible and automates legal transitions; it cannot make arbitrary external actions reversible.

Five-minute architecture explanation

I will design a hypothetical release platform for a multi-tenant inference and tool service. I first confirm peak demand, latency and correctness objectives, long-stream behavior, external effects, schema compatibility, and whether a zone failure must be tolerated during rollout. These requirements decide the necessary headroom and the permitted migration sequence.

The build system creates immutable signed bundles containing executable, configuration, model, and compatibility identities. A release registry records provenance and supported schema ranges. A durable rollout controller advances through prepared, limited exposure, evaluation, expansion, and completed states. Regional routing selects cohorts and readiness reports real serving capability. An evaluator joins release identity to customer-impact and model-quality evidence. A migration controller handles bounded data work separately from request serving.

For capacity, suppose twenty replicas each sustain one hundred requests per second, demand is sixteen hundred, and our chosen useful floor is eighteen replicas. Two unavailable and four surge is a candidate rolling budget, but it is not a promise to survive losing three more replicas. I would add zone-aware reserve or explicitly degrade if that concurrent failure is required. Warmup can consume shared resources before new replicas are useful, so the measured resource budget matters as much as the controller count.

For canaries, I predefine cohort, exposure, observation window, guardrails, and decisions. A baseline with one hundred errors in one hundred thousand requests is 0.1 percent. Twenty errors in five thousand canary requests is 0.4 percent. That descriptive regression warrants investigation under our policy, but causal interpretation still depends on workload balance and correlation. Missing evidence holds. A duplicate paid effect is a hard violation even if the aggregate rate is low.

Schema evolution uses compatible intermediate states. Expand first, deploy readers and writers that honor both representations, then backfill with stable identity and row-version conditions. A stale backfill must not overwrite a newer user edit. Live changes and deletes use a transaction or ordered durable-change protocol. Validate meaning, not just counts. A historical scan finishing does not imply catch-up is complete; net drain rate can make the live backlog the dominant schedule.

Cutover requires a verified freshness boundary and exception policy. Contraction waits until old writers, retained messages, paused jobs, and the rollback horizon are handled. Enforce unsupported-writer rejection where data commits. A fleet dashboard cannot prove that an old paused process will never return. Compatibility epochs or equivalent checks turn that assumption into a protected boundary.

For long requests, stop new admission and drain observed in-flight work within a declared bound. Streaming clients need a clear interruption or resume contract. Queue workers preserve logical business identity across attempts and versions. If an external provider committed a payment before the worker died, the successor reconciles that outcome rather than sending a new unprotected action. Graceful shutdown reduces disruption but is not the correctness mechanism for effects.

Before release, I name the last state where old code can safely resume. After new-format data or irreversible effects, traffic rollback may be insufficient. Disable the new capability while keeping compatible readers, or apply auditable forward repair. Keep old artifacts and capacity only for the horizon actually needed, since blue-green and retained runtimes cost resources.

The observability plan includes effective traffic by version, useful capacity, readiness and warmup, cohort errors, model quality, migration lag, conflicts, lock waits, format adoption, and stale-writer rejection. Security includes scoped rollout authority, signed bundles, protected data migrations, and tenant-safe evaluation. I would start with staged rolling updates and explicit compatibility, adding more elaborate strategies only when requirements justify them. The defense is a sequence of safe states with honest recovery limits.
