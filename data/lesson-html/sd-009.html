SD-009 · Distributed Systems Foundations · 01

What survives the worker?

A database provider accepts a promotion. Before the recovery worker records the returned operation identifier, its machine disappears. A replacement has the customer's intent, an expired attempt, and no result. Which facts can it recover?

Worked example 1 · The invisible success

At 10:00, a recovery request for application group G names target region East and expected generation 17. The coordinator persists the request, picks worker A and sends it a promotion task. A calls the database provider. At 10:01 the provider creates operation P and sends a response. A crashes before persisting P. Worker B now sees a task that has no recorded completion. Sending a fresh promotion might start a competing operation; declaring the old one failed could provoke an operator into forcing another recovery. The local state is compatible with two external histories. In one the provider accepted A's call and in the other the call never reached the provider.

Give the logical promotion its own durable identity K before either worker calls the provider. Bind K to the tenant, workflow, logical step and intended immutable input. The provider agrees to serialize duplicate requests with K, reject conflicting payloads under the same key, and return the existing operation or an authoritative status during the recovery window. B can now replay the request with K and discover P. The next durable transition records that P was accepted. A separate observation must establish whether the database actually became the target primary. Seeing a provider operation identifier proves acceptance under that provider's contract. It cannot by itself prove service readiness or absence of an old writer.

Change just one assumption. The provider accepts a key but discards its mapping after ten minutes. A regional incident delays B for twenty. The same string K may now create another operation. Retention of the binding, the semantics of an absent lookup, and the maximum age at which automatic retries are permitted belong in the workflow design. A recovery service should expire its permission to retry before its ability to distinguish outcomes expires. Past that boundary it needs stronger evidence, a different recovery action or an explicit unresolved state. An operator screen that merely says retry available silently transfers a correctness decision from the designer to the person on call.

Define a durable promise

Durable execution means that a declared execution can make progress across process lifetimes using persistent evidence about its inputs, decisions, waits and outcomes. A thread's stack, open network connection and partially executed instructions may vanish. An implementation can restore logical progress using an explicit state machine, replay from an ordered history, or a combination of snapshots and subsequent events. The API can resemble an ordinary sequential program. Its failure semantics still depend on the storage boundary and every external system it touches. Ask which failures the service acknowledges surviving, what unit of work it retries, and how a replacement decides which next action is permitted.

Distinguish three identities immediately. A workflow ID selects one business operation, such as recovering G for a particular approved request. A logical step ID names one intended action within it. An attempt ID names one delivery or execution of that step. Use the attempt for logs, deadlines and stale-result rejection. Use the logical step identity for external deduplication when all attempts represent the same effect. Reusing one key for different generations can hide a legitimate second action; generating a fresh key on each transport retry can duplicate the first. Define the identity domain before choosing a retry library.

The proof you can give an operator

Ask what the replacement could prove if you removed every worker log. It should be able to identify the last durable decision, the set of permitted outstanding effects, and the evidence required to advance. If losing diagnostic logs would make those facts unknowable, the logs are secretly serving as your recovery database. Promote that evidence to a durable, access-controlled record. Retain logs for investigation and use the workflow's own authoritative state for decisions. The distinction becomes especially important in a region outage when the missing application's logs often live in the same unavailable region.

SD-009 · Distributed Systems Foundations · 02

The engine's smallest recoverable transaction

A scheduler sees that a step became runnable. It must ensure that losing a process at this instant neither strands the step nor grants two incompatible successors.

Worked example 2 · The scheduling hole

Imagine two independent writes at workflow revision 31. The worker updates next step to VerifyHealth, commits, and then publishes a message to a queue. Crashing between those calls leaves revision 32 describing pending work that no worker will receive. Reversing the calls creates a different window. A consumer can receive VerifyHealth and act before the state transition becomes durable. If the state write fails, a real action has escaped from a workflow that never authorized it. A reliable message broker cannot fix a missing atomic relationship between two different stores merely by guaranteeing redelivery of messages it did receive.

In one design, the database transaction conditionally advances the workflow revision, appends the decision event and inserts an outbox row for the next task. A relay delivers pending rows to the queue. It records successful delivery only after publishing. If it dies after publishing but before marking the row delivered, a later relay can publish again. Duplicate delivery is intentional. The receiver identifies the task by its stable identity and checks whether it can still be claimed. The workflow transaction has turned a possible omission into a controllable duplicate. An alternative scans state for due tasks and treats the queue as a low-latency hint. The scanner must eventually cover every shard and handle deadlines without starving quiet tenants.

Now let workers A and B process revisions 31 and 32 concurrently. A began from 31 and proposes VerifyHealth. B has already applied a cancellation signal at 32. A's commit must test its expected revision. If it loses, discard its speculative decisions and recompute from the new durable state. Performing external I/O during that speculative computation is dangerous because a rejected transaction cannot retract a completed provider mutation. Have the decision stage emit a command; have the authority atomically admit that command before a separate activity attempts the effect. This gives the process a testable point at which it may first interact with the outside world.

Design records a successor can interpret

A useful baseline schema has execution rows indexed by tenant and execution identity, an ordered event stream per execution, immutable command intents, attempt records, durable timer or wake-up records, and an inbox for external signals. Keep a uniqueness constraint on execution identity and client request key at admission. Keep event sequence allocation inside the transaction that advances the execution. A mutable status projection can speed lookup, but the authoritative representation and its consistency with the journal must be documented. Treat changes to this schema as changes to the recovery protocol. Any field needed to reject a future stale message may outlive the worker or binary that originally wrote it.

If the event and the outbox live in different partitions that cannot transact together, consider colocating them by execution ID or deriving dispatch entirely from the committed stream. In the latter design a consumer advances its read cursor only after safely handing off every command before it. Sharding by execution means separate runs can progress independently, while a single extremely large run may become hot. A secondary index on resource identity is useful for investigation, but must not become an accidental source of authority when it lags the execution store. In particular, absence from an eventually consistent search screen proves very little about whether a command already exists.

Durable wait and visibility

A waiting workflow should release worker compute. Persist a wake condition, such as a timer deadline, operation callback or child completion, and reconstruct the runnable task when the condition is durably observed. A timer can fire late due to queue delay, throttling or a region outage. Define whether its deadline means earliest eligible time, latest acceptable completion or the time at which a competing business event becomes invalid. Those meanings require different state checks. For an approval deadline, a delayed scheduler must still evaluate whether the approval was received in time under the documented authority clock. A slow timer thread should not quietly extend a customer's approval authority.

SD-009 · Distributed Systems Foundations · 03

Replay decisions without repeating an effect

A replacement opens a history of 46 events. The source program appears to run from the top once more. Understanding which operations consume recorded facts and which create commands is the difference between recovery and accidental re-execution.

Worked example 3 · The new branch on an old history

Suppose version one receives a recovery request, schedules CheckReplica, waits for its recorded result, then schedules Promote. After the check completes you deploy version two, which inserts CaptureDiagnostics before Promote. When a fresh worker replays an existing execution, it reaches a position where the history records Promote but its code now proposes CaptureDiagnostics. A replay-based engine must have a compatibility rule for its command sequence. It may detect a nondeterminism error. Silently pretending that the old promotion result belongs to diagnostics would produce a meaningless decision. Matching only the number of emitted commands would miss this corruption.

Replay reconstructs local variables by re-evaluating decision logic against durable inputs and outcomes. When it encounters a previously completed activity, the runtime can supply the recorded result instead of invoking the activity a second time. Once replay reaches the end of the available history, a newly generated command can be admitted. A decision worker can crash repeatedly while computing a branch; only accepted commands have durable standing. Replay of workflow code and redelivery of an activity are separate phenomena. The first rebuilds the coordinator's reasoning. The second can actually call a provider again and therefore needs a side-effect contract.

Read the current wall clock inside an ordinary branch and an old execution might choose a different path on Tuesday than it chose on Monday. Unordered iteration over a collection, changing environment variables, direct random generation and reading the latest feature flag can likewise affect command order. Use the runtime's recorded or replay-aware APIs when provided, or obtain a value through an activity whose result becomes a durable input. Sorting loop inputs is helpful if the set itself is stable; it does not fix a query that returns different members each time. Record the exact materialized membership or a stable immutable version that can be retrieved during recovery.

Version the decision and the data

Routing old executions to compatible code is one strategy. Persist a plan or behavior version at admission and ensure the workers for it remain available until all relevant histories are safe to retire. Another strategy uses a framework-specific version marker so replay follows the old command path for old histories and a new path for eligible ones. A plain global feature flag that changes during replay cannot provide this distinction. Migration is also possible through an explicit recorded transition with a defined cut point, input transformation and recovery path. These mechanisms have different costs in worker fleet size, retained binaries and long-term auditability.

Command compatibility is only one dimension. An activity result persisted three months ago may omit a field that newer code expects, or use a different unit. Make result schemas versioned and preserve semantics when upgrading them. A decoder defaulting missing bytesPerSecond to zero may turn unavailable information into a false capacity estimate. Replay representative old histories against the new decoder as part of release testing. Include histories whose uncommon branches were last executed several releases ago. A canary starting only fresh executions can succeed while thousands of dormant workflows become unrecoverable when their timers finally fire.

Distinguish a graph from a program

A stored state-machine definition with explicit state IDs can avoid replaying arbitrary application code, but it still needs compatible transition definitions and durable task outcomes. Its advantage is that migration and audit may be easier to express for bounded, declarative plans. Code-as-workflow systems make loops, reusable abstractions and nested orchestration convenient but require engineers to learn the replay restrictions. For an OCI-style recovery product a versioned declarative plan could contain provider-specific activities whose implementations evolve separately. The interview decision should include the skills of the teams authoring plans and the lifespan of executions, in addition to the developer experience of writing the first workflow.

SD-009 · Distributed Systems Foundations · 04

Make retries earn their right to run

One activity can time out while its provider is still executing. A replacement attempt improves progress only if the design can explain what happens to the original one.

Worked example 4 · Three kinds of waiting

A training cluster repair task enters the queue at 12:00 and is claimed at 12:04. Its provider submits a replacement node at 12:05, but initialization takes eighteen more minutes. The queue wait, the runtime of an individual activity attempt, and the total time budget for all attempts answer different questions. A short queue deadline can surface a worker-capacity issue before the provider was contacted. An attempt deadline after submission leaves an uncertain provider outcome. A total operation deadline can exhaust while a remote action is still making progress. Mixing these under a single error named timeout makes automatic recovery almost impossible to justify.

Split the action into SubmitReplacement and ObserveReplacement. Submission uses the stable logical key and records a provider reference. Observation checks authoritative state and schedules a durable timer for a future poll when the provider remains busy. A long operation then occupies very little orchestration compute between polls. Polling too frequently can overwhelm a recovering provider, while sparse polling adds a known detection delay. If 6,000 repairs poll every thirty seconds with independent phases, their mean load is about 200 polls a second. If they all wake together after a restart, the instantaneous burst can be much larger. A jittered, bounded polling schedule and a provider-wide concurrency limit address different parts of that problem.

Callbacks can reduce polling, provided the receiver authenticates the source and binds the event to the precise resource, tenant and submitted operation. A callback is often a hint that a state change deserves verification. It might be delayed behind a newer callback, duplicated or fail delivery entirely. Record a durable inbox entry, deduplicate on the provider's event identity if one exists, and preserve a fallback reconciliation path for missing notifications. If the provider guarantees authenticated, ordered terminal callbacks with a specified durability contract, you can rely on more of their contents. Write down the exact contract before removing the fallback.

Heartbeats and progress cursors

A heartbeat tells the scheduling service that a worker recently communicated. Optional heartbeat details can capture a resumable position, such as the last verified chunk number. A cursor is safe only if everything it skips was durably completed. If a worker advances the cursor to chunk 19 before chunk 19 reaches object storage, a restart at 20 quietly loses data. Record progress after durability and validate the association with the exact input manifest and attempt. If the last heartbeat was lost, the next worker may repeat some work. Content-addressed immutable chunks or idempotent per-chunk updates can make that replay safe while avoiding a very large journal for every byte.

Two attempts may run at once after a pause or network partition. The scheduler can reject an obsolete completion using an attempt token; the provider can still accept late mutations from that attempt unless it independently checks authority or deduplicates the operation. Put attempt freshness at the engine's history boundary and resource freshness at the provider's mutation boundary. Use metrics that report each separately. A large count of rejected stale completions may indicate a misconfigured timeout even if downstream deduplication successfully prevented harmful effects. Lowering retry intervals in that situation can increase the stale work competing for already constrained resources.

Decide when to stop

Classify failures by what changed and by what evidence is missing. Invalid credentials may require reauthorization. A schema contradiction generally requires a software or data correction. A jittered retry may help with transient provider overload, but only while a bounded deadline and retry budget remain. An ambiguous write needs same-intent reconciliation. If a user modifies the recovery plan to choose a different target, that is a new intent requiring its own preconditions and audit trail. Calling all four conditions retryable encourages the system to turn a local failure into a distributed retry storm precisely when the on-call team needs a stable picture.

SD-009 · Distributed Systems Foundations · 05

Concurrent branches, cancellation and human decisions

A recovery plan contains three independent checks, a human approval and a promotion. Two checks succeed, one reports late, and the operator requests cancellation while the provider is accepting the promotion. Which state should the customer see?

Worked example 5 · A signal races a timeout

An approved change requires a signed operator response before 18:00. At 17:59:59 a gateway receives a response, stalls before committing it, and resumes at 18:00:02. Meanwhile a durable timer has become eligible. Specify which moment governs validity. If durable receipt by the authority is required, the gateway's local receive timestamp alone is insufficient. If acknowledged receipt at the gateway is the agreed cut point, that gateway must persist verifiable evidence before acknowledgment and arrange later delivery under that policy. A distributed system cannot distinguish two near-simultaneous events by comparing loosely synchronized log timestamps with no declared ordering rule.

Use an inbox record containing tenant, execution, signal identity, signer, intended plan version and permission scope. Atomically deduplicate the signal and append its acceptance or explicit rejection according to the current workflow state. If the workflow is already terminal, the result should explain whether the action was too late or was a replay of an already accepted decision. Signals may arrive before a waiting worker has started listening. A durable inbox or signal facility can preserve them across that window. A transient callback that requires the worker to be in memory at receipt forces the business protocol to inherit process availability.

For parallel tasks, record a durable fan-out manifest defining the exact children required. Name children by stable logical identities such as volume UUID and plan step rather than loop iteration over an unordered service response. Each child completion contributes at most once to its join. A counter incremented for every delivered success message is incorrect if notifications can repeat. Store a set or bitmap of completed child identities, or condition each child's terminal change on its previous state in the same domain as the aggregate update. At dashboard time distinguish 17 completions from 17 unique successes for 20 expected resources.

Where cancellation becomes effective

Cancellation is a request to stop future work under a defined policy. It might arrive before a task is admitted, while it is waiting, after a provider accepts it, or after the business effect becomes irreversible. Treat these positions differently. If no command exists, closing admission can prevent dispatch. If a task is queued, the consumer must consult its current authorization before dispatch; a queue tombstone alone leaves a race. After acceptance, call provider cancellation if supported and observe its terminal outcome. If the effect completed before cancellation took hold, returning canceled as though nothing happened misleads the operator.

A useful response can say cancellation accepted, draining pending activity, promotion already applied, and awaiting verification. Model these as structured fields or stages that communicate the remaining work. For a safety-sensitive operation, define whether clean cancellation requires both no new submissions and positive evidence that every in-flight command has reached an accounted-for terminal condition. An interface that must respond promptly can acknowledge the cancellation request immediately and expose a separate completion state later. Estimate how long that later state might remain uncertain and what the user can still do safely during the interval.

Compensation is another external action with its own intent, preconditions, retries and ambiguous outcomes. Suppose a newly promoted database has already accepted customer writes. An automatic compensation that switches the route back to an old primary can strand those writes. Design compensations from the actual known state and permitted business semantics, and record prerequisites such as draining clients and confirming replication. If the corrective action requires domain authority, expose a manual gate with the evidence and constraints an operator needs. Manual intervention can select an authorized policy under uncertainty; it cannot make a lost external observation reappear.

def observe_children(expected, messages):
    # Static join manifest; reject foreign children.
    completed = set()
    for child in messages:
        if child not in expected:
            raise ValueError("unknown child")
        completed.add(child)
    return expected - completed

manifest = frozenset(["disk-a", "disk-b", "disk-c"])
assert observe_children(manifest, ["disk-a", "disk-a"]) == {"disk-b", "disk-c"}
assert not observe_children(manifest, ["disk-c", "disk-b", "disk-a"])

Size the concurrency boundary

A plan covering 20,000 disks is an inappropriate place to append a synchronous heartbeat per disk every second to one hot execution history. Partition by a stable resource group, run bounded child workflows, and have the parent consume aggregate terminal outcomes or selected progress updates. The parent still needs a way to drill into a particular failed child. Preserve identifiers and query paths rather than copying all payloads into the parent. Ensure a cancel issued at the parent traverses children durably and that a child discovered after cancellation cannot enter an excluded phase simply because it missed a best-effort broadcast.

SD-009 · Distributed Systems Foundations · 06

Design a recovery control plane that can explain itself

Build a hypothetical multi-tenant service that can promote a database, validate compute health and shift traffic. An application group may span regions and each provider exposes a different contract. The customer wants a resumable plan and an honest answer about when the application is serving again.

State the success criteria and irreversible boundary

Assume 4,000 registered application groups, up to 500 concurrent recovery executions during a regional event, and plans containing 40 logical steps on average. Users can submit, inspect, pause, approve, request cancellation and resume. A request accepted under the promised failure domain must remain discoverable by its stable identity. At most one conflicting promotion may be authorized for a group generation. A terminal success must include a verified application endpoint and a recorded recovery target. Durability of the control plan says nothing about the recovery point of user data. Store the source replica's observed recovery position and let the customer assess the data-loss tolerance separately.

At admission authenticate the tenant and authorize the initiating principal for the specific plan revision and group. Persist an immutable plan version, an input fingerprint, the expected resource generation and a request key in one transaction. For a duplicate key with the same fingerprint return the established run identifier. For a different fingerprint report a conflict. Expose GetRun by tenant and run identity and GetByRequestKey for the lost-admission-response case. A fresh run after manual repair may intentionally reference the same plan version, but it must explicitly bind to the prior run, a current group generation and a new business operation where appropriate.

Use an execution store sharded by tenant and run, a group authority for conflicting operations, a timer service, task dispatchers, provider-specific workers, a signal inbox and an evidence store. If a run and a group record live in different transactional domains, the run cannot assume exclusive authority on creation. Model acquisition of a group grant as a separate recoverable step with its own identity. A grant protects only resources that enforce it. A router supporting compare-and-set on route version can check a generation during cutover. A provider without equivalent fencing must serialize conflicting submissions through a durable adapter that can account for already accepted work, or expose an unresolved state that blocks a conflicting automatic promotion.

Worked example 6 · Walk the happy path into a bad night

Run R starts against group generation 12. It binds a verified plan digest and checks the replication watermark, compute inventory and target-network readiness in parallel. Child results carry dependency identities, observation times and resource revisions. Successful checks establish evidence at a point in time; they do not freeze the world. Before the promotion the workflow validates the current group grant and the important provider preconditions. It records promotion intent K, dispatches through the provider adapter, reconciles its result and confirms that the target database is writable under the agreed policy. Only then does it request a versioned route update and probe the application through the customer-facing endpoint.

Crash the orchestrator immediately after the route update but before it records completion. The router has already changed revision 64 to 65. A replacement reads the run history and recovers the same route intent and expected revision. It consults the router's outcome binding or strongly consistent state. If the router confirms the precise intended revision and request provenance, the replacement can record completion and resume probes. A state already pointing at the target can be useful evidence, but it may also have been set by an operator or another run. Decide whether the business contract requires observed convergence or proof that this request caused the change. Those requirements produce different answers to the same lookup.

Now the health probe fails. Routing moved successfully, the database is writable, and the customer endpoint is returning an error. Mark the application degraded and preserve the exact evidence. A blind restart of the entire run could attempt to promote again, change routing twice and overwrite diagnostics. A targeted repair might fix a security group, certificate or backend membership and rerun the probe. The repair is a new command under current authority. Store its change approval and input alongside the original immutable plan. If product requires a one-click retry, its implementation must still specify what is rechecked, what is preserved and which effects are never automatically repeated.

Budget the control path

Five hundred simultaneous plans with forty steps create 20,000 logical step instances. Assume six journal entries per step, averaging 1.5 KiB each after encoding. That gives 120,000 events and about 176 MiB of logical journal payload before replicas, indices and snapshots. If they all finish within ten minutes, the average event rate is 200 per second. Synchronizing an entire phase of twenty provider checks per plan at the same instant can still produce 10,000 submissions in one wave. Design around provider-specific quotas, regional fairness and the worst admitted burst. Reserve worker capacity for reconciliation and cancellation even when new submissions are saturated.

Suppose one provider permits 80 concurrent operations and the mean operation occupies a slot for 45 seconds. An optimistic steady-state upper bound is about 1.78 completions per second. If all 500 plans require one such operation, a full drain takes at least about 281 seconds using the rate approximation; discrete batches with identical durations would need seven waves or 315 seconds. Additional retries, skew and priority rules stretch the tail. A product promise of complete recovery for every plan within two minutes cannot be met under those assumptions. Preprovisioning, increasing quota or reducing the number of operations per plan changes the physical bound. Adding workflow workers alone does not.

Make recovery observable and isolate tenancy

Measure age of oldest admitted execution without progress, queue delay by provider and tenant, age of unknown external outcomes, replay time, conflicting grant attempts and time to verified endpoint. Separate engine availability from provider health and customer recovery success. Link logs and traces across attempts using the logical identity, but retain the attempt identifier to diagnose replay and duplicate dispatch. Store large diagnostic payloads and snapshots by immutable digest outside the hot history. Protect sensitive evidence with scoped access, encrypt at rest and define a retention policy that respects both customer needs and the workflow's ability to recover. Avoid persisting credentials in history; resolve narrowly scoped credentials at activity execution time.

A production rollout should start with read-only validation plans, graduate to reversible actions and exercise one controlled disruptive operation before broad availability. Test provider quota exhaustion, region evacuation, worker image rollback and loss of an operator approval response. In a post-incident review compare the run's recorded conditional decisions with actual customer observations. An incident that completed every activity but restored an unusable endpoint exposes a missing success predicate. The unit of value is the customer's verified application recovery under the stated data and failure contract, even when the control plane itself behaves exactly as implemented.

SD-009 · Distributed Systems Foundations · 07

AI infrastructure introduces a second kind of checkpoint

An execution checkpoint can restore which orchestration decision to make next. A training checkpoint can restore model, optimizer and associated training state. The two records live in different systems and advance under different rules.

Worked example 7 · Eight ranks finish writing and one verification is lost

A training job at step 8,000 writes eight shard objects under immutable names for checkpoint generation C. Seven ranks report success. The eighth uploads bytes but crashes before notifying the controller. The scheduling history contains seven positive observations and one missing acknowledgment. A recovery worker should verify the expected manifest and actual immutable object versions to decide whether the checkpoint is complete. Counting seven notifications plus one assumed success could expose a partial checkpoint. Restarting the entire training job from scratch would waste valid computation and may leak the completed objects. Reconcile the missing evidence at the storage boundary.

After verification, publish a recoverable-checkpoint pointer through a conditional transition scoped to job lineage and attempt epoch. A delayed old training attempt might still finish uploading immutable objects. If only the current attempt can advance the pointer, those uploads can be garbage-collected later without confusing restore clients. The workflow journal records the published manifest identity and verification result. When restarting, the training system must also support loading that checkpoint's topology and data-state representation. A valid set of weights can be insufficient if the software cannot recover optimizer state or the data cursor required by the training contract.

Imagine a new planner replaces a failed run on a smaller GPU pool. The scheduler can restore its own durable workflow and know that checkpoint C is published. That says nothing about whether C is compatible with a different tensor-parallel layout. Treat compatibility checks and any required transformation as explicit steps with immutable inputs and outputs. A failed transformation should leave the previous recoverable pointer intact. During a board interview, ask which dimensions of progress the customer is paying to preserve. The answers might include completed optimizer steps, output tokens already streamed to a user or a tool call already performed by an agent, each with a different persistence boundary.

A durable agent tool call

An agent selects a tool to create an expensive training reservation. If decision replay simply calls the model again with the conversation, a small model change or nondeterministic sampling can choose a different tool, quantity or region. Record the selected tool and normalized arguments as a durable intent, subject to policy and human approval when required. Only then dispatch the activity. A later model invocation may be allowed to propose a new plan after observing failure, but that proposal is a new recorded decision, not a replacement for the earlier tool outcome. Keep authorization effective at the boundary where the real reservation is made.

A text summary saying the agent probably created the reservation is valuable context for a human but inadequate recovery evidence. Store the authoritative request key, committed policy decision, tenant, budget debit, provider result and any outstanding reconciliation requirement. If the model emits the same normalized intent again, decide whether it is referring to the prior action or deliberately requesting another. Content similarity alone cannot establish this distinction. The UI may require a deliberate new logical action indicator for operations such as allocating a second GPU pool. Workflow identity and explicit intent semantics give the application a basis for that decision.

Design for partial output

An inference service may have streamed 120 tokens to a customer before its worker crashed. Persisting a run history can record the last durable output sequence but cannot erase text the customer already saw or prove which bytes a remote client consumed. If clients need resumable delivery, expose ordered chunks with stable sequence numbers, an acknowledgment or resume cursor and a retention window. A resumed model invocation may produce different continuations unless the system can restore the relevant decoding state under a compatible model and policy. Define whether resume promises identical bytes, access to recorded prior bytes or a visibly new generation. Those are product contracts; orchestration durability is one building block in their implementation.

SD-009 · Distributed Systems Foundations · 08

Migrate, replay and audit under real failure

A platform can have an excellent steady-state workflow engine and a dangerous recovery procedure. The revealing tests start with old histories, missing acknowledgments and duplicated deliveries.

Worked example 8 · Recover a region without resurrecting yesterday's action

Execution R's primary journal acknowledges a promotion and then the entire region becomes unreachable. A secondary journal is asynchronously replicated and still shows the step as pending. The provider in another region can continue performing the promotion. Starting R from the secondary copy with an unguarded fresh request creates a path to conflicting action. Define the workflow history recovery point separately from the provider's effect history. If a previous authorization may survive and the recovery point can omit its key, automatic failover requires independent evidence for the identity and outcome or a trusted fence over old activity.

One option is to synchronously protect critical intent and authorization records across the failure domain before dispatching an irreversible action. Lower-value logs and progress samples can replicate asynchronously. This moves a wide-area durability cost onto the smaller subset of operations that need it. Another option is to derive a stable logical identity from an independently durable admission record and immutable plan so the successor can query an authoritative provider after a history gap. Deterministic derivation alone does not recover whether the user changed or canceled the plan, so reestablish the current authority and plan lineage before acting. A third policy restores an isolated read-only dashboard and blocks new mutations until evidence is recovered.

For a controlled test, freeze the history replica just before intent K appears, let the provider accept K, isolate the primary, and present the secondary to the recovery tool. The correct result depends on the promised contract. It may discover the existing operation by K, wait for synchronized records, or explicitly block for reconciliation. A green dashboard that says failover completed because the new worker is up proves none of these. Include a test in which the old region returns after new authority has been granted. Make sure its queued work and timer fire events cannot reopen a discarded line of execution.

Replay tests and invariants

Build a fixture library from sanitized histories representing early failures, odd branches, canceled runs and recent schema versions. Replay them against the candidate code with external networking disabled in the decision stage. Check that the same historical decisions match and that new commands arise only beyond the known prefix. Exercise activity adapters separately against provider doubles that can commit, drop a response, delay a lookup, return an obsolete observation or accept two requests with different keys. A replay test can prove command compatibility for the selected histories. It cannot by itself test real provider idempotency behavior, which needs its own integration and contract qualification.

Add fault injection at every durable boundary. Crash before intent persistence, after persistence before queue delivery, after provider acceptance before result capture, after result persistence before acknowledgment, and after verification before terminal success. For each cut, state the lawful next actions and the forbidden customer outcome. Then delay an old attempt until after its replacement commits. A core invariant might say there is at most one authorized active target per group generation. Another says every terminal success has a verifiable provider state and an endpoint probe tied to the same generation. Check both the durable history and the observable provider state to avoid validating only the engine's self-report.

Capacity and history retention

Long-lived workflows need bounded history strategies. An execution may roll into a fresh history with a compact summary at a quiescent boundary, preserving the linkage, outstanding intents, deduplication state and signal delivery semantics. Taking a snapshot of local variables while activity completions remain unaccounted for can strand a result addressed to the old run identity. Quiesce or explicitly transfer every outstanding dependency and test signal arrival during rollover. Retain the original audit evidence for as long as the customer contract and regulations require. A short operational history can coexist with longer audit retention if recovery metadata remains available to the components that enforce it.

Replays consume CPU and storage bandwidth. A cached hot workflow may look cheap until a rolling restart evicts all worker caches at once. Estimate cold-start replay cost from measured history sizes and command processing rates, then stagger evacuations and admission. If one history contains 60,000 events and a worker replays 10,000 events per second under test, its idealized replay time is six seconds before fetching data or executing new work. Four hundred such histories landing on forty equally capable workers require at least about sixty seconds of aggregate replay service in the ideal case. A runbook should account for this recovery load before it opens all incoming traffic.

Defend the failure contract in an interview

Each question is original practice. Sketch an execution, choose the earliest crash that makes the answer uncertain, and then name the evidence that resolves that uncertainty.

Twelve Senior Staff questions

A provider returns an operation ID only after submission. What should a worker persist before sending?

Evaluates ambiguous remote success. Persist an immutable logical action identity under the run's authority, a request key bound to that action, its input fingerprint and relevant generation preconditions. The provider must support safe same-key replay or an authoritative lookup capable of resolving the uncertain acceptance. The server-generated operation ID is useful once recovered. It cannot be the only recovery key because the crash window begins before the worker learns or persists it.

Follow-up. What if lookup briefly returns absent? Specify its consistency semantics and deduplication window before authorizing another send.

Common mistake and tradeoff. Generating new keys on transport retries changes the business operation. Keeping results longer increases storage while covering longer outages.

Can replaying workflow code produce two external calls?

Evaluates the boundary between replay and activity retry. Decision code replay should consume recorded results and reconstruct the same command sequence. Direct external I/O inside that code breaks the model because replay would perform it again. Properly isolated activities may still be executed more than once after lost completions. Thus I inspect both the decision runtime's replay contract and the provider's effect contract. A passing replay test establishes very little about whether the external effect tolerates duplicate dispatch.

Follow-up. Can workflow logs appear twice? Yes. Ordinary logging during replay may repeat even when durable decisions and provider effects do not.

Common mistake and tradeoff. A duplicated log line is weak evidence of a duplicated action. Correlate logical identity and actual provider state.

Why write an outbox when your broker guarantees durable delivery?

Evaluates atomic scheduling and acknowledgment. Durable delivery applies after the broker has accepted a message. It says nothing about an application crashing between a database transition and publication. I put the intent and dispatch obligation in one transaction, then allow a relay to deliver at least once. If a separate scanner reliably derives work from committed state, it can play a similar recovery role. In either case ownership of the persistent obligation must be unambiguous.

Follow-up. Can the relay publish duplicates? Yes. A consumer must safely check the task's identity and continued eligibility.

Common mistake and tradeoff. A separately committed sent flag cannot bridge the database and broker unless a protocol coordinates those commits.

Is a heartbeat every five seconds sufficient evidence the activity is progressing?

Evaluates liveness versus useful progress. It proves recent communication within the heartbeat mechanism. A worker can heartbeat indefinitely while waiting on a blocked driver. I would attach a validated progress cursor when meaningful and measure age since last verified state change. For an external provider I also need its actual operation status. Deadlines should accommodate legitimate long stages and define the safe recovery action under uncertainty. The workflow must account for an old attempt that resumes after its heartbeat timeout.

Follow-up. Where do you store the cursor? In a durable boundary that never advances beyond verified effects and binds to a specific input version.

Common mistake and tradeoff. Aggressive heartbeat deadlines can create overlapping attempts under load while a relaxed one delays replacement.

How can you avoid counting the same child twice at a fan-in?

Evaluates set membership and transactional aggregation. I first materialize the child identity set for this plan revision. Each child may transition from pending to exactly one terminal contribution, conditionally in the same transaction as its contribution to the aggregate, or via a projection that deduplicates by child identity and event version. The parent succeeds only when the required predicate over that complete set is satisfied. A queue of successful messages does not define the expected population.

Follow-up. What if new children can be discovered later? Record explicit membership transitions and define when the set closes.

Common mistake and tradeoff. A simple success counter is cheap but insufficient if redelivery can increment it or membership remains open.

What does cancel mean for an operation that already moved traffic?

Evaluates irreversible effects and user-visible status. I would acknowledge the cancellation request separately from its outcome. Freeze admission of new mutations under that run, identify already accepted commands, and reconcile their actual effects. If routing already changed, expose that fact and check whether policy permits a compensating change. Any reversal must satisfy current generation and application data constraints. Only declare cancellation complete under the documented drain or accounting condition.

Follow-up. Can an operator override a block? A properly authorized operator may select a different policy, with evidence and an audit trail.

Common mistake and tradeoff. Returning a single canceled flag can hide a real customer-visible cutover or an outstanding provider action.

How do you roll out a new command in the middle of a workflow definition?

Evaluates historical compatibility. I would replay representative old histories against candidate code, including dormant and failed paths. Add the new command through a supported recorded version distinction, route older runs to compatible workers, or explicitly migrate execution at a known safe boundary. A global feature flag that changes between execution and replay cannot distinguish historic decisions. Version payload interpretation and keep a path to load old dependencies while any relevant history can still resume.

Follow-up. When may old code retire? Once live and restorable histories no longer require it under the retention and restore policy.

Common mistake and tradeoff. Testing only newly created executions can leave dormant runs unable to resume weeks after a successful deployment.

What happens if the workflow journal fails over with a nonzero recovery point?

Evaluates cross-system recovery and authority. The restored journal might forget an intent whose provider effect survived. I would reestablish exclusive mutation authority, recover an independent identifier and reconcile provider state, or suspend conflicting automatic actions. For stricter service classes I would synchronously protect critical intent records before dispatch across the required failure domain. The customer's data recovery point, the orchestration recovery point and the provider's own history may all differ.

Follow-up. What if the old region returns? Its queued tasks and credentials need enforceable stale-ownership handling.

Common mistake and tradeoff. Asynchronous journal replication alone does not justify a claim that every acknowledged external action is represented after regional failover.

When does storing a snapshot actually bound recovery time?

Evaluates cold replay and tail load. A snapshot must cover a known durable history position and include the state necessary to reconstruct outstanding commands, waits, grants and deduplication. Recovery loads it and applies a bounded valid suffix under a compatible schema. If hundreds of workflows resume together, total I/O and scheduling can dominate per-workflow replay time. I would benchmark cold workers under a region evacuation workload and examine both the snapshot path and retained historical formats.

Follow-up. Can you drop the old history? Only after satisfying recovery, audit, compatibility and outstanding dependency requirements.

Common mistake and tradeoff. A snapshot of final application fields can look correct while omitting unresolved work or duplicate suppression.

Should an agent simply call its model again when resuming an unfinished tool request?

Evaluates nondeterministic decisions and permissions. I would distinguish a recorded tool intent from a genuinely new planning turn. If the earlier turn authorized a reservation, resume the recorded arguments, tenant, policy and request identity and reconcile its outcome. A fresh model call could choose a new tool or region and thereby turn recovery into a new business action. New planning may be useful after recovery but should become its own durable, authorized decision.

Follow-up. What if the text summary says the tool failed? Query the authoritative provider or durable outcome before accepting that conclusion.

Common mistake and tradeoff. A model-generated progress note aids context. It is insufficient evidence about a real allocation or payment.

Would you use a workflow engine to process every output token?

Evaluates granularity and economics. I would order high-value control decisions durably and choose a separate output delivery protocol for high-volume token streams, with chunk sequence numbers, recorded payloads and resume cursors if required. Persisting a history event for every token can overwhelm the coordination store and impose latency disproportionate to the decision value. If the product promises exact recoverable output, build a data path capable of meeting that promise and budget for retention.

Follow-up. What should resume do after a model upgrade? Define whether to replay stored chunks or start a distinguishable new generation.

Common mistake and tradeoff. A durable control plane alone cannot reproduce a nondeterministic continuation or prove a client consumed every transmitted byte.

What do you measure to decide whether recovery improved?

Evaluates end-to-end operational evidence. I would measure time to the user's verified success condition, such as a working endpoint with the promised data recovery point. Split that into engine admission, provider queueing, active work, ambiguous-outcome reconciliation and application verification. Include the fraction of runs blocked safely and the age of their oldest unresolved command. Compare failure drills before and after the proposed change with the same scale and failure model. A faster worker restart may leave customer downtime unchanged.

Follow-up. Which one metric would you put on the incident summary? Time to verified customer recovery together with affected count and observed recovery point.

Common mistake and tradeoff. Optimizing engine completion can reward premature success if the final verification predicate is weak.

Whiteboard the lost acknowledgment

Put the customer, execution store, worker and provider on the board. Mark the last durable evidence held by each participant before submission, after provider acceptance and after local result persistence. Ask a colleague to erase one participant and predict which facts a replacement can still establish. Then reverse the direction of the lost response. An admission timeout for the client, an activity timeout for the worker and a missing provider completion notification are distinct recovery cases. Explain why the identifying key and authoritative lookup must exist on the appropriate side of each gap.

Speak through a recovery decision

Choose the scope of the answer first. A short definition should identify durable progress. A longer architecture answer must say exactly what happens to effects outside the engine.

Thirty seconds · What durable execution buys

Durable execution lets a new worker continue a logical operation from persisted evidence after the old worker disappears. I record inputs, decisions, waits and outcomes, then use compatible replay or an explicit state machine to recover. For external actions I persist an intent before dispatch and require a provider contract for ambiguous success. A durable workflow can therefore explain what it knows and why the next action is safe, including when the only safe action is to wait.

Two minutes · The interrupted promotion

I would start with a recovery request for one application group. The system durably accepts the exact plan revision, target and request identity. An initial response means the run can be found and resumed. It cannot mean the application is already accepting traffic. The durable plan checks replica readiness, acquires authority for the expected generation and records an immutable promotion intent. Each worker attempt uses the same logical key for that promotion.

Now crash the worker immediately after the provider accepts the request. A replacement has no local success response. With a documented provider deduplication or outcome-lookup contract, it can recover the existing operation and observe its status. If provider evidence is unavailable past the retention window, the workflow exposes an unknown outcome and blocks conflicting automatic actions. That is an operational state with a recovery procedure, not a reason to invent a failure and issue another promotion.

After the provider confirms the database transition, the plan performs an authorized route change and verifies the endpoint. Durable timers and the event history let the system wait without holding a server thread for the whole recovery. My dashboard separates the time spent waiting for workers from the time spent inside providers and the time spent resolving uncertainty. The final business metric is recovery of a usable application with the stated recovery point.

Five-minute architecture defense

I would ask which failures the customer expects acknowledged progress to survive. Worker loss, a zone outage and a total region outage need different durability placements. I would also ask which external effects are irreversible, because that determines which records must be recoverable before dispatch. For ordinary progress observations asynchronous replication may meet the contract. For a promotion that can change where customers write data, I want stronger evidence at the point of authorization.

The control plane admits an immutable plan and assigns a run identity under a tenant-scoped request key. A decision worker reconstructs state from its journal, verifies the expected revision and submits commands. In one transaction the engine advances the history and records its task dispatch obligations. An outbox relay can send a duplicate, so the activity consumer checks the stable logical task and its present eligibility. A fresh attempt receives its own diagnostics identity while reusing the business request key for a repeated effect.

Consider a lost reply from the database provider. From the engine's perspective there may be two possible worlds. The provider could have accepted the promotion, or the packet could have disappeared on the way out. No number of retries inside the workflow database distinguishes those worlds. I need the provider to identify a previous matching request, return its operation or expose authoritative evidence adequate for reconciliation. Once I know what the provider accepted, I must still verify what actually became active and whether the old writer is excluded.

For long-running waits I use durable timers or authenticated callbacks with durable receipt. A callback may race cancellation or arrive out of order, so the same authority that serializes the execution decides which transition is valid. Parallel checks operate on a recorded membership set and contribute to a join only once per child. The completion rule specifies the required observations and whether they are fresh enough for promotion. A receiving worker that cannot reestablish these preconditions must pause before creating a new external effect.

I would capacity-test a regional event, not just a steady stream of independent requests. Hundreds of plans can all reach the same provider at once. Separate queueing from provider throughput, bound concurrency by provider and tenant, and protect reconciliation from starvation by new work. Then test cold replay after worker evacuation, run old histories on the candidate worker version and restore from a secondary copy deliberately missing a recent intent. The expected outcome of each test should be expressed in customer terms.

In a training platform the same distinction applies to a job restart. Restoring the planner's execution history tells us which checkpoint it intended to publish. Restoring a usable training job additionally requires complete, compatible shard data. In an agent platform we must similarly preserve which tool action was actually authorized rather than re-asking the model and accepting a different answer. Across these cases I defend the same principle: each durability claim needs a named boundary, a specific failure model and an observable recovery test.

Final interview cheat sheet

  • Admission. Persist a stable run identity and input binding before acknowledging the request.
  • Intent. Make the next permitted external action discoverable before dispatch.
  • Attempt. Use a distinct diagnostic identity for each execution of a logical step.
  • History. Persist the facts that let a replacement reconstruct decisions.
  • Replay. Consume prior results and match historical commands.
  • Outbox. Commit the dispatch obligation with the state that authorized it.
  • Effect. Define how the provider resolves uncertain acceptance.
  • Timer. Treat firing as a durable opportunity to evaluate a condition.
  • Join. Track unique results against a recorded manifest.
  • Cancellation. Account for in-flight effects before declaring the documented terminal condition.
  • Version. Keep old histories executable or migrate them explicitly.
  • Recovery. Verify the customer outcome across the promised failure domain.
