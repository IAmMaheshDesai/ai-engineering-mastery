SD-001 · Distributed Systems Foundations · 01

Which promise did the operator actually receive?

A recovery coordinator has just lost contact with its primary site. Two operators click Promote, each from a different region. Both requests are reasonable. Only one may choose the next recovery destination.

Start with the observable mistake

Suppose Oregon and Virginia each hold a database row that says generation seventeen, primary unavailable, recovery destination undecided. Oregon accepts a request to promote Phoenix. Virginia accepts one to promote London. Their clocks differ by three milliseconds, so a last-writer-wins merge eventually selects London. A dashboard that looks at the converged row can easily report success. A customer routed to Phoenix during those intervening seconds may already have acknowledged writes there. Discarding the Phoenix row cannot retract those acknowledgments. The business error happened when the service made two incompatible promises. Fixing the eventual display value is too late.

Write the promise as a predicate. Within one recovery group and generation, at most one destination may be authorized for promotion. The next generation can choose a different destination through an explicit transition. This framing makes an engineering difference. A global mutex around all recovery groups would satisfy the narrow exclusion requirement, but an unrelated database failover in Mumbai would now wait behind a slow file-system recovery in Chicago. A useful ordering boundary is the set of commands that can invalidate each other's preconditions. Start there and enlarge it only when the business invariant demands it.

Consensus chooses a value for a decision instance despite failures. To run a service, assign instances to successive log positions and have replicas execute the resulting sequence through the same transition function. The proposed value can be a command whose application returns a rejection. Both promotions might legally occupy different log positions. If the first command changes generation seventeen to eighteen, the second command expecting seventeen fails its comparison everywhere. A unique log alone does not preserve the one-destination promise. The conditional transition supplies the application rule, while the log makes its evaluation order consistent.

Worked example 1 · Follow two requests through one generation

At index 200 all three replicas agree that payments has generation seventeen. The first operator sends request P with expected generation seventeen and target Phoenix. The second sends request L with the same precondition and target London. The leader orders L at index 201 and P at 202. At application of 201 each replica records generation eighteen, target London, and an accepted result for L. At application of 202 the comparison sees eighteen and records a conflict for P. The client receives the winning generation in the response so it can decide whether to reread or start a separate administrative action.

Reverse the order and Phoenix wins. Both outcomes meet the specification because the invocations overlapped. If the London client had already received a success before Phoenix even issued its request, an implementation that claimed the reverse order would violate real-time ordering. Recording receive timestamps cannot establish that property when messages take different routes. The service can use the actual committed order and a read path that respects completed writes. The appropriate test records client invocation and completion intervals alongside results, then asks whether some legal sequential execution respects those intervals.

Now sever the link to the automation worker immediately after London wins. A commit still means exactly what the service promised at the metadata boundary. It does not mean a database in London is accepting traffic. Expose an operation resource with separate accepted, applying, verified and failed states. An operator who sees accepted can safely look up the existing operation. An operator who sees a timeout may have no idea whether the request reached the leader. Preserve the request identity across this uncertainty. A fresh identity with a relaxed precondition can authorize a different operation entirely.

How I would explain this in an interview

I start by writing down what would hurt a customer if two controllers were briefly correct according to their own local views. In this case it is acknowledging writes at two independently promoted destinations. I would order the promotion decisions per recovery group, condition each one on the observed generation, and store the winning request's outcome. I would then separately explain how the selected destination enforces its right to serve. That last boundary tells me whether I have designed a reliable metadata service or a reliable failover system.

Why a majority needs a memory

Three votes can decide a proposal among five replicas. To explain why the decision survives a leadership change, follow the information that one voter must carry between two different majorities.

Worked example 2 · Build the smallest intersection

Label five voters A through E. A decision reaches A, B and C before the sender loses power. A replacement can communicate with C, D and E. The combined size of those two sets would be six if they did not overlap, but only five voters exist. At least one participant therefore belongs to both sets. In this example C carries the history that the new coordinator could otherwise miss. If A and B are the only ones that remember the decision, the second group need never hear about it. Requirements about when to acknowledge persistence are part of the proof.

Let a first set have size w and a later set have size r in a universe of n distinct members. Their overlap is at least w plus r minus n, since their union is no larger than n. To force one common member, require w plus r to exceed n. To tolerate f missing members while continuing with equal majority quorums, use at least two f plus one voters. With five voters and two crashes there are exactly three survivors. If one survivor is doing a disk repair, six healthy application processes on other machines cannot vote in its place. Membership is a statement about identity and durable state.

Give C a persistent record but program it to vote for whichever candidate contacts it first, regardless of the candidate's log. The sets still intersect. The replacement can still omit an acknowledged entry. Intersections are channels for constraints, and the protocol specifies which constraints must travel through them. In Raft a voter checks log freshness before granting its one vote in a term. In Paxos an acceptor promises to exclude lower ballots and reports its accepted history. The details differ because one protocol constrains the choice of leader while the other constrains what a proposer may issue after obtaining promises.

Timeouts, crashes and silence

The failure model here allows processes to stop, restart from durable storage, and exchange messages that may be delayed, reordered, duplicated or lost. Participants execute the protocol faithfully. Media that silently returns yesterday's term after a successful durability acknowledgment violates a foundational assumption. Operators should remove and rebuild such a voter through the documented membership procedure. Restarting it under its old identity with an empty disk and letting it vote immediately can erase the only intersection a future majority depends on. The same reasoning explains why cloning a live voting disk into two active processes is dangerous.

A timeout changes the local assessment of progress. It cannot prove another node has stopped. An overloaded leader waiting for a disk flush and a disconnected leader may look identical through a heartbeat monitor. A follower can start an election after its timer expires because the election protocol itself preserves safety if the suspicion is wrong. Randomized timeouts reduce repeated ties among candidates. Liveness still needs sustained periods in which enough members can communicate and perform durable work. A scheduler that always pauses each prospective leader at the wrong instant can keep a safe group from deciding anything.

Consider the incremental cost of moving from three voters to four. The quorum changes from two to three while the number of unavailable members tolerated remains one. Placement may still provide operational advantages, and a four-member configuration can be a temporary transition. Present those as explicit goals. Counting failure domains matters as much as counting processes. Three replicas on independent instances behind a single power feed lose the ability to decide after one power failure. A placement diagram should annotate shared disks, racks, zones and control-plane dependencies wherever they can remove several votes at once.

from itertools import combinations

def minimum_overlap(voters, first, later):
    # Enumerate small configurations for a whiteboard proof.
    pairs = ((set(a), set(b)) for a in combinations(voters, first)
             for b in combinations(voters, later))

Stop and defend an assumption

If a product manager asks for successful promotions from both halves of any network partition, ask which half can safely order an irreversible customer-visible change. In a five-voter layout one side of a clean split can have three or more voters. The other side may serve an explicitly historical view or queue an unaccepted request with a visible status. Promising both sides independent successful promotions changes the service contract. A good defense offers an operation that can continue, a precise description of its weaker semantics, and a recovery procedure when connectivity returns.

SD-001 · Distributed Systems Foundations · 03

Raft from the first vote to the client response

A Raft leader sends commands to followers in log order. The most revealing moment is when a follower has persisted an entry but still cannot tell its clients that the command succeeded.

Election and matching prefixes

Each voting server has a current term, a vote within that term, and a log of entries labeled by creation term. Persist the current term and vote before sending a response that depends on them. Suppose A times out, advances from term six to seven, votes for itself and solicits votes. A voter whose current term exceeds seven rejects the request. A voter learning of a higher term updates its term and steps down as appropriate. To grant a vote it must be eligible to vote for that candidate and find the candidate's log at least as up to date as its own. Compare the last entry's term first, and its index second.

If A's last entry is at index 40 in term six and B ends at 42 in term five, A has the fresher Raft log for this comparison. Raw length measures positions and misses the history encoded in term changes. Receiving a higher term alone does not entitle a candidate to lead. It takes votes from a majority of the active configuration. A previous leader may still think it is in charge until it learns about the election. This is compatible with election safety, which states that at most one leader wins in a given term. Terms describe protocol history independently of wall-clock time.

A newly elected leader records, for each follower, a next index to send and the highest index known to match. AppendEntries includes the index and term immediately before the transmitted entries. That pair is a testable claim about the common prefix. If the follower lacks the predecessor or finds the wrong term there, it rejects the append. The leader backs up its probe, potentially using conflict hints to skip entire terms. Once the predecessor matches, the follower replaces a conflicting suffix with the leader's entries. An empty heartbeat must still perform the predecessor check. Merely hearing from a leader is insufficient evidence that two logs match.

Worked example 3 · A slow follower and a lost reply

All three replicas have applied index 40. A, the term-seven leader, receives command Reserve with identity R9. It persists entry 41 and sends it to B and C. B checks predecessor 40, appends 41 durably and replies. C is performing a lengthy storage operation. A now knows its own durable copy and B's copy cover a majority. Entry 41 belongs to its current term, so A advances its commit index. A applies the command, stores the resulting reservation alongside R9 in its state machine and returns the result. B may still advertise commit index 40 until it receives a message carrying the leader's newer commit index.

Drop the client response and crash A. B contains entry 41, while C stops at 40. In an election involving only B and C, B will refuse to vote for a candidate whose log is behind. B can win, append a current-term entry and establish its commit boundary. As it applies the committed prefix, its state machine materializes the reservation and the result for R9. A retry with the original identity then returns that result. If implementation code sends B's acknowledgment before the append reaches durable storage, a simultaneous power loss can defeat the argument. A network trace of two acknowledgments is inadequate evidence of durable replication.

Consider a variation in which A and B persist 41, B's acknowledgment is lost, and A dies before it learns whether it has enough copies. The future protocol history continues to constrain what successors can choose. The client's ability to discover an outcome differs from the underlying fact that sufficient replicas accepted an entry. Do not build a compensating action on the belief that an RPC timeout canceled the original command. Reconcile using authoritative state, retain deduplication results through the supported retry horizon and reject ambiguous reuse of the same identity for a different request body.

Deterministic application

A log containing the instruction choose a random free GPU can produce disagreement even when every replica receives identical bytes. Have the command name the proposed GPU, or use a deterministic allocation rule over replicated inputs. Read the wall clock before proposal if a timestamp must become a business input, then replicate that timestamp and specify what it means. An external policy lookup from inside application also risks replaying against changed permissions. Decide which checks belong at admission and which versioned authorization facts must be part of the committed decision. Recovery should be able to explain yesterday's allocation without reconstructing yesterday's network.

When a majority of old entries can disappear

An entry can sit on three out of five disks while a legal successor can still erase it. The missing information is the term in which the leader is trying to establish commitment.

Worked example 4 · Construct the counterexample yourself

Begin with five voters and a committed prefix ending at index ten. A leads term two. It appends X at index eleven to its own disk and B's disk. Before reaching any other replica it becomes isolated. E wins term three with C, D and itself, all still ending at index ten. E appends Y at eleven only to its own disk. E then goes offline. A returns, obtains votes sufficient for term four, and sends its old X to C. At this instant A, B and C have the same term-two entry X. Concluding that X has become committed by counting these replicas would permit the service to expose X.

Pause before counting again. D still ends at ten. E returns with its last entry in term three. If A now disappears, E can enter term five and obtain votes from voters ending in term two or earlier. Their latest entries precede E's latest term even if they have the same length. E can replicate its term-three Y over X at index eleven. Both prior elections were legal. The incorrect step was treating the newly counted majority of an earlier term's entry as the commit condition in term four. The majority intersection at C exists, but C is allowed to vote for E under the log freshness rule.

Return to the moment before A's second disappearance. This time A appends a term-four no-op at index twelve and replicates it to B and C. Those appends require the term-two X as predecessor. A can now advance its commit index to twelve using a majority for its own term. That action commits the entire prefix, including X. E's latest entry is still in term three. To win a new election it needs at least one of A, B and C, whose term-four logs make E ineligible. The current-term entry changes the proof about future elections. It is much more than a heartbeat or a cosmetic audit marker.

How this becomes an implementation review

When reviewing a commit loop, locate the exact data used in its comparison. An optimistic next-send index can jump forward before any follower reply. The match index represents established agreement through a position. Counting the optimistic value is a correctness error even if a fast network makes it work on most tests. Count distinct eligible voting identities, include the leader's durable match position, check the active configuration rules and restrict direct advancement to a current-term entry. Keep commit index monotonic. Receiving an older response after a newer one should not convince the implementation to uncommit an entry or to acknowledge a write prematurely.

A deterministic test can hold messages in named queues and deliver them in the order of the counterexample. Use explicit barriers before and after durable writes and before and after replies. At each step record current term, last log term and index, commit index and application results. A test that simply terminates a random process every minute may never create the narrow window between the stale majority and the new-term no-op. Add an assertion over the complete observed history. Once any client receives a successful command result, no future authoritative read of that history may replace its effect with a conflicting decision at the same position.

Diagnose an incident without confusing the watermarks

The log end measures what has been appended locally. The commit index bounds the prefix known safe to apply. The applied index measures how far the local state machine has executed that prefix. An operator sees log end one million, commit nine hundred thousand and applied eight hundred thousand. These gaps point to different bottlenecks. Check peer communication and durable acknowledgments for the first gap. Check application, compaction and database writes for the second. Truncating the log at the applied index to save disk space can remove recovery information. A snapshot needs a durable, internally consistent state at a precise included index and term.

Paxos recovers a value before it issues a new one

Imagine taking over a one-slot register labeled next routing generation. Several acceptors remember earlier proposals. No coordinator can tell you whether one of those proposals already succeeded.

Worked example 5 · Adopt an inconvenient value

Use three acceptors A, B and C. A proposer with ballot ten sends a prepare request and obtains promises from A and B. Neither reports a previously accepted value. The proposer chooses blue and sends accept requests. A and B persist the pair ten and blue. Blue is now chosen even if every reply disappears on the return path. Neither the routing service nor a learner has to be alive for this fact to hold. Chosen describes a condition on acceptor state and protocol history. Learned describes the information available to some observer.

A successor wants green. It obtains promises for ballot eleven from B and C. C reports no accepted value and B returns ten and blue. The successor must propose blue in this slot. It has no evidence about whether A accepted blue. From where the successor sits, B alone could have accepted blue or a whole majority could have accepted it. Recovering blue is safe in both histories. Choosing green would be unsafe in the second. The application's preference for green can be proposed later as a separate command with a different position and an appropriate precondition.

What if the successor hears two different prior values? Take five acceptors and suppose its prepare quorum reports red at ballot four, nothing from a second responder, and blue at ballot seven from a third. It adopts blue, the value from the highest accepted ballot reported in that quorum. The rule does not count the most frequently reported color. Under the protocol's induction, any higher issued ballot following a chosen value must preserve it. If the earlier red had already been chosen, a valid proposal at ballot seven could not have introduced a different blue. This reasoning assumes uniquely ordered ballots and consistent behavior by each proposer within a ballot and slot.

Now delay an old accept message at ballot ten until after C has promised eleven. C rejects that request. Persisting a promise before responding is what makes the rejection survive a restart. Persisting only the accepted pair while forgetting a higher promise allows a recovered node to break an exclusion on which a concurrent proposer depends. Persistence ordering is part of the algorithm under crash recovery. When teaching the two phases, distinguish the questions they answer. Prepare discovers and constrains prior history. Accept attempts to make one permitted proposal chosen. A promise by itself chooses no application value.

From one decision to a replicated service

A single-decree protocol is an incomplete answer to the question of how a scheduler processes a thousand submissions per second. A log needs many slots, recovery of holes, orderly application and a way to distinguish a client retry from new work. In a stable-leader Multi-Paxos design the leader can establish a ballot over a range of slots and amortize the prepare work. The familiar fast path then asks acceptors to accept entries under that ballot. The promised scope and recovery procedure must cover the slots actually used. Skipping prepare for a slot outside that scope loses the premise for issuing the value.

If slot fifty-two is chosen but fifty-one has an unknown outcome, a learner can record fifty-two without executing it out of order in a general state machine. A new leader recovers earlier slots and may fill a genuinely unconstrained empty slot with a no-op. Guessing that a missing entry is empty because a local log has a hole would confuse ignorance with evidence. Command pipelining improves throughput because slots can be in flight together, but application must preserve the dependencies built into the service contract. You might separately optimize commuting operations after specifying the different execution model and demonstrating equivalent results.

Choosing an implementation

Raft and Paxos share the central discipline of carrying durable evidence through leadership changes. They organize the recovery work differently. If a team has an audited service implementing one protocol, switching because the other has a shorter textbook description is difficult to justify. Compare the actual read API, snapshot recovery time, membership operations, testing tools, supported deployments and availability of expertise. Measure how quickly an on-call engineer can determine which nodes are eligible voters. A sophisticated consensus algorithm wrapped in an ambiguous administrative interface can have a poor production failure record for reasons no quorum proof addresses.

SD-001 · Distributed Systems Foundations · 06

Reads, checkpoints and moving a voter

Consensus protects the decisions in a log. A user reading from a stale leader, or an administrator replacing the wrong membership configuration, can observe behavior outside that guarantee.

Worked example 6 · Read after a successful promotion

Client M promotes revision 22 and receives success from leader B in term twelve. Old leader A is still alive in term eleven, reachable through an outdated DNS entry. A has revision 21 in its applied state. A request for the current primary arriving at A after M's success cannot legally return revision 21 under a linearizable API. The read must take effect at some instant between its invocation and response. Every such instant falls after M's completed write. A's local role label says leader, but there is no valid instant in the allowed interval at which 21 was still current.

One approach orders the read through the replicated log. A different approach allows a leader that has committed an entry in its current term to establish a read barrier through communication with a quorum. It retains a safe read index and waits until its state machine has applied at least that index before answering. A delayed application worker can make the second wait dominate even when the quorum is healthy. An implementation can batch concurrent readers behind one confirmation if it preserves each invocation's ordering constraints. Attaching a new reader to a confirmation completed before its invocation needs a separate proof.

A bounded leader lease can reduce the quorum round trips at read time. It introduces timing assumptions and discipline around elections, renewal and pauses. A wall clock that can jump backward is unsuitable as the sole justification for continuing to serve. If your service cannot establish the assumptions, a quorum-confirmed read is easier to defend. Alternatively offer a read API explicitly requesting historical or potentially stale data. Return an applied revision, and allow a client to require at least its last observed revision when a monotonic session view is sufficient. Document what happens if the local replica cannot catch up before the deadline.

Worked example 7 · Replace a failed site

An active configuration consists of A, B and C. The target consists of C, D and E. Directly switching some nodes to the new set lets A and B form a legal old majority while D and E form a legal new majority. They share no voter. Each configuration individually satisfies majority arithmetic, yet a client might receive contradictory promises while different machines believe different rules are active. The step that broke the proof was changing the universe underneath the intersection argument. Cycling process addresses or updating a load balancer is quite different from changing which durable identities count toward a decision.

In Raft joint consensus, the transition configuration requires a majority of the old membership and a majority of the new membership. For example, B and C satisfy the old side, and C and D satisfy the new side. C can count on each side because it belongs to both configurations. A set containing just A, B and D would have three distinct nodes, but it would fail the new-side requirement. Obey the implementation's log rules for when the joint and final configurations take effect. A single static majority threshold on the union cannot express this predicate.

Catch up new replicas as nonvoting learners when the implementation supports it. Suppose a learner must transfer a 60 GiB snapshot over a sustained 80 MiB per second channel. Ignoring protocol overhead, that transfer alone costs 768 seconds. During those minutes the leader continues to create new log entries. If the learner replays changes more slowly than the leader creates them, it never reaches a safe promotion threshold. Measure both the remaining lag and its slope. Reserving bandwidth for catch-up may slow some foreground traffic but prevents a long repair from becoming the normal state of the cluster.

Restore after losing a quorum

Distinguish temporarily losing contact with a majority from permanently destroying enough durable state to make the old group unrecoverable. In the first case, reconnecting valid voters may recover the original history. In the second, creating a fresh cluster from an older backup starts another lineage. It may discard acknowledged writes. An operator who forces a new cluster during a mere partition can create two live histories. Require evidence about the failed sites, isolate prior writers, record the recovery point and describe the data loss explicitly. Include outstanding external effects in reconciliation because cloud resources created after the snapshot can still exist.

When taking snapshots, include state machine results needed for retries and the metadata identifying the applied prefix. Publish the snapshot only after data and metadata agree durably. A reader of a partially transferred snapshot should continue using the last valid one or fail recovery safely. Compact enough log to control storage while retaining a recovery window for routine follower outages. Very aggressive compaction can transform a short network incident into a costly snapshot-transfer storm.

SD-001 · Distributed Systems Foundations · 07

Design a publication service for training checkpoints

A training job produces hundreds of immutable shard objects. Its recovery controller needs one authoritative answer to the question, “Which complete checkpoint should my next attempt load?”

Requirements, API and data ownership

In this hypothetical design, 2,000 jobs share a regional pool. Each publishes a checkpoint every five minutes. Some jobs restart on another rack and two attempts may briefly write at the same time. A successful publish must identify a complete, immutable manifest for the currently authorized attempt. An older attempt must be unable to advance the pointer. Readers that ask for the latest version after publication completes must see that version or a later one. A lost publication reply must be recoverable. These are metadata requirements. A separate storage service must provide durability and access to the large shard objects across the failures the recovery plan promises to tolerate.

Define Publish with tenant, job, attempt epoch, expected pointer revision, immutable manifest digest and client request identifier. Derive the tenant from an authenticated identity and check authorization for that job. Store an active epoch, pointer revision, current manifest digest and accepted request outcomes in replicated state. Record the digest of significant request fields with each outcome. Reusing an identifier with a different digest is a client error. Provide GetLatest with a strong read option, and GetPublication for a stable request identifier. A request that loses an epoch race returns a conflict containing the current revision according to the documented information-disclosure policy.

Writers upload shards under immutable object identities. A manifest specifies the complete expected shard set, sizes, checksums, training step, model format and compatibility metadata. A verifier checks completeness and seals a manifest under a tenant-scoped identity. To keep the replicated transition deterministic it consumes a validated immutable manifest reference, rather than contacting storage during log replay. The system must bind the verification to the exact object versions and guarantee their retention. Checking that objects exist at noon and deleting them at one minute past noon would make a correct pointer useless to a worker restoring at two minutes past.

Worked example 8 · Recover the publisher at the worst moment

Job J is at epoch eight, pointer revision 30 and step 4000. Attempt eight finishes a manifest for step 4100, seals it and sends Publish with expected revision 30 and request K. Replica A appends K and durably replicates to B. The command applies and revision 31 now points at the new manifest. The response is lost. A replacement worker starts before the original worker receives any reply. It first checks the stored outcome for K and discovers the exact accepted revision. The operation can now be reported as complete even if a still newer checkpoint has since advanced the current pointer.

Compare this with a restart before K reached the log. A new attempt acquires epoch nine through a conditional committed transition. Delayed K then arrives carrying epoch eight. If the matching K outcome exists, return its historical result with its revision. Otherwise reject the obsolete epoch, leaving any uploaded blobs orphaned. Keeping historical lookup separate from granting new authority is important. An old success is evidence about a past decision. It is never permission to publish another checkpoint. Periodic garbage collection can remove unreferenced objects after considering active uploads, retention leases and recovery grace periods.

Where should the version check happen? Two API servers may both read revision 30 and locally approve different writes. Put the comparison inside the applied command, with epoch validation and the pointer update in the same state-machine transition. Deduplication and result persistence belong to that boundary too. A client should receive a definitive success only after it can be recovered under the promised failure model. If the runtime separates log durability from materialized database durability, make sure replay reconstructs the same outcome after a crash and that client-visible reads satisfy the contract during recovery.

Capacity, availability and scope

At 2,000 jobs per 300 seconds the mean publication rate is about 6.67 per second. At 256 shards of 64 MiB each, one checkpoint occupies 16 GiB. The aggregate average payload rate is roughly 106.7 GiB per second before storage replication. A 2 KiB pointer command at the same publication rate contributes about 13.3 KiB per second of logical log payload. Compare those numbers before debating a faster consensus implementation. Putting the actual checkpoint bytes in the consensus group would bind leader failover and follower catch-up to training data transfer at a radically different scale.

The average hides synchronized checkpoint bursts. If 2,000 jobs publish within five seconds, the service must admit 400 pointer publications per second and verify over one hundred thousand shard references per second if it does an individual check for each shard. Measure digest verification, object metadata throttling, auth checks and queue growth separately. Seal per-job manifests ahead of the final pointer write, cap verification concurrency per tenant, and use bounded queues. Backpressure should arrive before client timeouts produce a second wave of identical requests. Classify an overload response by whether the request could already be accepted, so clients know when to reconcile.

Use three voting replicas across independent zones within a region if zone loss is the stated failure objective. Synchronous cross-region voting adds network latency and shifts which partition can commit. Asynchronous export of a recovery manifest may be a good option for a different recovery objective, but a separate region cannot advertise zero loss solely because the pointer was replicated locally. State an objective for the availability of the referenced bytes in the destination. A disaster recovery operator needs a restore-ready checkpoint, not merely a recent metadata sequence number whose objects are still in flight.

Architecture defense under conflicting objectives

Suppose product now asks for a fifteen-millisecond p99 publish, zero acknowledged checkpoint loss on total regional failure, and regions separated by a minimum eighty-millisecond round trip. Ask what the publish acknowledgment means. If it means the checkpoint is recoverable across that failure, some remote durability evidence has to exist before success. Pre-staging the bulk bytes can reduce the amount remaining at commit, but an authoritative new ordering decision that requires a remote vote still pays the WAN round trip. A latency objective should state where the client is, what prior staging is allowed and whether a competing writer can appear in the other region.

I would offer a fast regional publication with a separately observable geographically protected watermark, or a geographically synchronous publication with a measured, achievable tail objective. If the customer insists on the stronger contract I would pick the latter and test failover while client retries are in flight. I would evolve the service by sharding groups on tenant and job only after measuring leader or apply contention. A job migration between groups then needs a fenced directory epoch and explicit handoff of the last pointer and deduplication state. Splitting for throughput creates a new recovery protocol that must itself be designed and tested.

SD-001 · Distributed Systems Foundations · 08

Operate the group you designed

A dashboard shows all five voters responding and client writes timing out. Decide which waiting stage is expensive before proposing a larger cluster.

Worked example 9 · Calculate a latency budget

Assume the leader's durable append finishes in four milliseconds. In this design it issues replication in parallel with that append. Peer acknowledgments, measured from dispatch and including their durable writes, arrive after three, eight, fifteen and forty milliseconds. With five voters and a majority of three, the leader needs two follower acknowledgments plus its own durable copy. The earliest commit in this trace occurs at eight milliseconds. Add two milliseconds of deterministic application and three of combined client transit. The resulting illustrative end-to-end latency is thirteen milliseconds. Pipelining changes when work starts, so draw the dependency graph before adding numbers.

Now let the fastest follower stall until seventy milliseconds. The two fastest follower replies arrive at eight and fifteen. Commit now occurs at fifteen and the same client path takes twenty. Lose the leader's local disk performance instead and assume its flush takes fifty milliseconds. Under this design its own durable append gates client success even while the other disks are healthy. The critical path moves again. A graph of average peer latency could look excellent throughout the incident. Measure leader fsync, peer round trip including persistence, quorum completion, application, client queue time and client-observed latency as distinct distributions.

Do not claim a p99 by adding individual p99 measurements from these stages. Tail events can be correlated or occur on different requests. Record same-request traces or histograms of full operations and annotate which quorum members completed first. Aggregating over healthy and degraded placements may hide that a zone evacuation uses a very different path. A service-level objective for available commits under a single zone outage should be measured during an actual controlled outage. Counting healthy ping responses verifies far less than a conditional write followed by a strong read through an independently routed client.

Scheduling, fairness and load shedding

A group can be under its nominal throughput limit and still miss every election timeout during a burst of large snapshots. Prioritize heartbeat and replication traffic appropriately, limit snapshot bandwidth and bound the number of proposals admitted but not yet committed. A large batch amortizes disk and network overhead. Waiting to fill it imposes latency on a quiet service. Put a time bound on batching, test small and large request distributions and track oldest outstanding proposal age. Increasing a queue's capacity often converts fast rejection into longer tail delays with no additional useful throughput.

Consider an AI serving fleet sending periodic liveness messages. Most samples describe observations that a later heartbeat supersedes. Persisting each observation through the ownership ledger competes with the few decisions that genuinely need durable ordering. Keep ephemeral telemetry in a different path. Commit decisions that grant or revoke exclusive capacity, or change the desired configuration. On recovery, rebuild observational state from agents and reconcile it against the journal. This partition of responsibilities does require a policy for what happens while observations are unknown. Treat missing telemetry as missing information until the resource enforcement rule authorizes reclamation.

PYTHON · executable model
def commit_time_ms(local_flush, follower_replies, voters):
    # Static majority, parallel dispatch, one distinct reply per follower.
    needed = voters // 2
    if voters < 1 or len(follower_replies) > voters - 1:
        raise ValueError("invalid group or replies")
    if needed > len(follower_replies):
        return None
    threshold = sorted(follower_replies)[needed - 1] if needed else 0
    return max(local_flush, threshold)

assert commit_time_ms(4, [70, 8, 15, 40], 5) == 15
assert commit_time_ms(4, [3], 5) is None

Incident drill and rollout

An on-call engineer sees election counts surge after a storage-class migration. Start by correlating term changes with fsync tails and scheduler pauses. Check whether packet loss affects multiple peer pairs, then inspect leader changes by availability zone. If writes time out, sample the durable request outcomes before retrying administrative commands. Freeze further membership changes while the quorum is marginal. Adding a voter can increase the number of acknowledgments required at the exact moment an existing replica is struggling. A clearly labeled learner and a measured promotion threshold are operationally different from simply adding another IP address.

Defend the design under questioning

Each question below is original interview practice. Read the question first, draw the smallest execution that could break your answer, then expand the model answer.

Twelve Senior Staff design questions

A write times out. Would you immediately retry it against another region?

Evaluates ambiguity and client contracts. I would first ask which authority the second endpoint consults. A different ingress for the same logical group is safe if the request carries its original identity and precondition and the service durably records its outcome. An independently writable recovery copy can authorize a contradictory action. If the old commit is recoverable, query its outcome or replay the identical request through the same authority. If the authoritative history was lost, reconcile externally visible effects and make the recovery-point decision explicit.

Follow-up. What if deduplication records expired? A missing record no longer proves absence. Bound retries by contract or use an enduring business identity.

Common mistake and tradeoff. A second transport attempt does not require a new business decision. Longer result retention trades storage for a longer safe retry window.

Could five nodes survive the loss of any two sites?

Evaluates failure domains and placement. Five voters survive loss of any two individual voters under a static majority rule. To survive any two whole sites, inspect how many voters those sites could remove together. A placement of two, two and one across three sites loses four if the two largest sites fail. Even losing the two smaller sites removes three. Five across five independent sites meet the voter count, subject to connectivity, storage and shared dependencies. Write down the required surviving service, including access by clients and to its data.

Follow-up. Would one voter in a cheap witness site help? Check exactly what durable state the implementation requires a voting participant to retain.

Common mistake and tradeoff. Adding an arbitrary witness to a paper diagram can invalidate the protocol. More distant voters can also become latency-critical during degradation.

Why can an isolated old leader answer a stale read after returning a recent heartbeat?

Evaluates read linearizability. A heartbeat at one instant does not prove leadership at all subsequent instants. Another majority can elect a successor and commit a write before the read arrives at the old node. I would establish a read barrier that covers that invocation, satisfy the current-term commit prerequisite and wait for the local applied index. If we use a lease, I would spell out its timing assumptions, how overlapping authority is excluded and what the implementation does after a long pause.

Follow-up. Can we direct dashboard reads to followers? Yes, with an explicit freshness contract, a revision and an appropriate fallback.

Common mistake and tradeoff. Confusing a responsive process with an authoritative read source hides stale decisions. Read barriers consume quorum work, while weaker reads shift reasoning to callers.

Your successor sees one accepted Paxos value. Why preserve it?

Evaluates indistinguishable histories. The one responder could be the only surviving intersection with an earlier deciding majority. It cannot tell the new proposer which other messages arrived. Phase one collects promises and the accepted pair from a quorum. The proposer carries forward the value associated with the highest accepted ballot among those replies. It may select its own value only when none report a prior acceptance. This rule works even when nobody managed to disseminate the old decision to learners.

Follow-up. What if one node reports a higher promise and no accepted value? A promise excludes lower proposals but is not itself an accepted value.

Common mistake and tradeoff. Taking a majority vote over returned values is incorrect. Recovery costs a round of communication to constrain all subsequent proposals safely.

An engineer counts three replicas of an old Raft entry. What evidence do you request?

Evaluates leader completeness and commit advancement. I would ask which term created the entry, which term the leader is in, which voter configuration is active and whether the count is based on durable matches. A current leader can establish a commit boundary by quorum replication of a current-term entry. That commits its preceding prefix. If the only evidence is a new count for an earlier term, a successor with a more recent last log term might still be elected without the entry. Show the competing candidate's last term before promising success.

Follow-up. Why append a no-op? It can establish the current-term boundary before the next application write arrives.

Common mistake and tradeoff. A no-op consumes a log position but simplifies recovery and enables safe read paths. A term number alone proves no replication.

Can a scheduler issue a GPU launch immediately after recording its intention?

Evaluates external effects and recovery. An applied intent supplies a durable work item and its authorized generation. A dispatcher may now send a launch request, but sending it and recording the response span different failure domains. I would require a provider-supported idempotency key, an inspectable operation handle or an enforcement point that can reject duplicate launches. The worker must recover unresolved requests and compare observed placement with desired placement. If none of these contracts exists, ambiguous completion needs reconciliation before issuing conflicting work.

Follow-up. What if the worker can check its own lease? It may pause after the check and send later. Validate authority at the mutation boundary.

Common mistake and tradeoff. A replicated log can replay an instruction. Replaying a non-idempotent external call can repeat the effect.

Where would you put consent to publish a new model revision?

Evaluates control-plane versus serving-path design. The rollout controller commits desired model revision, rollout policy and generation. Serving replicas fetch immutable artifacts, verify their digest, warm capacity and report readiness. A routing component switches per the committed policy once sufficient serving capacity exists. I would keep per-token inference outside the agreement group. For a strict cutover I would define the boundary precisely, such as new sessions after a committed routing revision, and decide what existing streaming sessions may finish.

Follow-up. How do you roll back? Publish a new generation that references a known retained artifact and reconcile serving readiness again.

Common mistake and tradeoff. Ordering a pointer is inexpensive compared with moving weights. It does not synchronize every in-flight request at the moment of commit.

How do you know a replacement voter can catch up?

Evaluates capacity during repair. Measure its installed snapshot revision, replication lag, sustained replay throughput and the ongoing write rate. If replay processes 2,000 entries per second while new writes add 1,500, a backlog of one million takes roughly 2,000 seconds to drain after snapshot installation. Background compaction or bursty traffic may stretch that estimate. I would promote a learner only once the implementation's safety and operational criteria are met and the remaining voters retain margin for another fault during the change.

Follow-up. How could you shorten repair without buying a larger leader? Rate-limit foreground writes temporarily or use a newer valid snapshot.

Common mistake and tradeoff. An absolute lag threshold alone can briefly look healthy even when the follower is falling behind. Repair consumes resources needed by customers.

What belongs in a snapshot besides the customer-visible rows?

Evaluates replay and durable boundaries. Capture an internally consistent image corresponding to one applied index, the metadata needed to resume log matching, and membership state as required by the implementation. Include deduplication results, authorization epochs and any protocol-relevant application metadata at that boundary. Publish and verify the image before deleting covered log entries. Test restoration on a clean machine and replay a duplicated request that originally completed before the snapshot. It should return the same recorded result under the supported retention contract.

Follow-up. What if an object store upload is partial? Keep the prior valid image and publish the new manifest only after validating all components.

Common mistake and tradeoff. A backup that lists the right rows but grants an old worker permission can recreate an excluded failure.

What would make you reject a single global consensus group?

Evaluates scope of invariants and operational isolation. I would enumerate which operations must have a common order. Different tenants publishing independent checkpoints need no cross-tenant order. Partitioning by job can isolate noisy tenants, improve throughput and confine recovery. A global quota shared across jobs changes the problem. We might preallocate bounded quota to regions or serialize quota transitions in a separate authority. Neither choice is free. Unused reservations reduce utilization, and global serialization adds a dependency to allocation. Measure the frequency and value of the invariant before paying for it on every command.

Follow-up. Can we hash solely by request ID? Successive commands touching the same invariant could then land in different groups.

Common mistake and tradeoff. A convenient partition key can destroy the very correctness condition consensus was chosen to enforce.

After a region disappears, should an operator force a new majority?

Evaluates disaster recovery judgment. First determine which valid voters and durable histories remain. A control-plane outage may hide a healthy majority that is still serving a different client population. Forming a new cluster from a snapshot creates a new history and needs an explicit decision about acknowledged data loss, isolation of old writers and fencing downstream. Preserve evidence, inventory external effects and define a safe cutover before authorizing new mutations. If the original majority can return within the recovery objective, restoring connectivity is often simpler.

Follow-up. What if the customer requires immediate read access? An isolated, clearly dated snapshot can support an explicitly historical read service.

Common mistake and tradeoff. Treating quorum loss as permission to override quorum turns an availability incident into possible customer data divergence.

What evidence would convince you a new implementation is safe enough for rollout?

Evaluates validation strategy and scope of proof. I would combine a small executable model or formal specification with deterministic schedules covering elections, persistence barriers, stale replies and membership changes. At the API boundary, record histories and check them against the specified sequential model. Exercise crash recovery from actual files and compare application state after log replay. Stage upgrades through mixed-version groups and validate snapshots written by the previous release. Operational drills should include a slow disk and asymmetric connectivity. Passing an ordinary load test gives little information about these cases.

Follow-up. Does passing a history checker prove the protocol? It checks the histories observed, within its model and search limits.

Common mistake and tradeoff. Use counterexamples to improve the specification. Spend the highest test effort on paths able to acknowledge impossible outcomes.

Draw a vertical line through the page. On the left write the last fact the client can prove from its own response. On the right write the last fact a replacement can prove from durable records. Speak, rehearse and revise

Use a stopwatch for the three explanations. Rebuild the argument from its invariants when speaking, and change the example to match the question you were asked.

Thirty seconds · Explain one durable decision

Consensus lets a group agree on one decision even if some members fail. In a recovery service, I would use it to choose which destination can receive a promotion grant. A majority matters because future decision makers must encounter durable evidence of earlier choices. The protocol specifies how they honor that evidence. After the grant commits, a separate enforcement step ensures that an old controller cannot keep writing to the protected resource.

Two minutes · Explain a failover without losing the client

Take a three-replica group with two concurrent operators. Each asks to promote a different destination based on the same observed generation. The leader orders their commands. Once a current-term entry is durably replicated on a majority, the state machine can apply it. The first command satisfies its precondition and advances the generation. The second sees the changed generation and fails its comparison. Every healthy replica replaying that prefix reaches the same outcome. The system has resolved a real business conflict in addition to ordering two messages.

Now lose the response to the winning operator. From the operator's perspective, a timeout tells us only that no timely response arrived. From the successor's perspective, the committed prefix contains a request identity and an outcome. Retrying the same identity returns the same result. I also distinguish authorization from completion. The database provider might have received a promotion request while the dispatcher crashed before saving its response. The dispatcher needs an external idempotency or reconciliation contract. This is the point where a replicated decision becomes a production workflow.

The main operational question is which failures we promise to tolerate. Zone placement, durability acknowledgments and the recovery point of external data all affect the customer. I would measure accepted decisions and verified recovery separately. Ask me to defend the system during a partition, and I can say exactly which side may authorize writes and which observations the other side may still serve.

Five-minute architecture rehearsal

I would start by asking what the training owner expects a successful publication to buy. If every worker fails a moment later, the next job attempt should be able to recover the entire selected checkpoint. A pointer to incomplete weights does not meet that promise. The complete checkpoint includes the model and optimizer shards and the metadata the training framework needs to reproduce its progress. I would specify the failure domain for that recovery and distinguish a local publication from one protected against the loss of an entire region.

The data path writes immutable shards and a manifest that names their exact versions. Each training attempt has a monotonically increasing epoch for this job. A verifier checks the expected shard inventory, version and integrity, then issues a seal tied to the manifest digest. The pointer service accepts a command containing the digest, seal, attempt epoch, expected revision and stable request key. The deterministic application step checks this command against the current job record, persists its outcome and conditionally advances the pointer. For a thousand parallel jobs, different jobs can use different groups because their checkpoint pointers do not conflict.

Now consider a failure during publication. The submitter has the last shard on disk but loses connectivity before that shard reaches shared storage. The verifier cannot issue a valid seal and the restore pointer stays at the last complete manifest. In a different execution the entire publication succeeds and the submitter crashes before receiving the reply. The successor queries the stored outcome using the original key. Repeating the exact command preserves the earlier result. Changing the payload under the same key is an error. A late operation from the old attempt must pass the epoch comparison at the writer boundary.

I would next draw the three-replica metadata group. One follower can fail and the other two can still durably order a current-term command. The new leader needs the committed history, and a read of the latest pointer must also establish current authority and wait for local application. Local reads of an older revision are fine for an explicitly historical view. A restore operation asking for a specific immutable digest has a different requirement again. Giving those reads different API contracts avoids paying a quorum round trip on every shard fetch.

Finally I would ask the interviewer to remove a zone while many jobs checkpoint together. The average publication rate can look modest while synchronized verification requests overwhelm object metadata. I would watch queue age, quorum latency, checkpoint seal errors and the age of the last verified restore point. If the requirement changes to survival of a region, I must redesign both placement of voting members and durability of the objects. The most important test is starting a real restore from the acknowledged checkpoint under that failure and verifying that the training job resumes at the intended step.

Final interview cheat sheet · Twelve distinctions to carry forward

  • Decision. Define exactly which conflicting actions must share an order.
  • Validity. A chosen value must be permitted by the protocol specification.
  • Safety. No admissible execution may expose incompatible decisions.
  • Progress. Specify the timing, storage and membership conditions under which the group can decide.
  • Intersection. Identify the durable evidence carried by the common member.
  • Freshness. Compare Raft last-entry term before index when judging a candidate.
  • Commitment. Count a current-term majority to advance the Raft commit boundary directly.
  • Application. A replica can know an entry committed before executing it.
  • Adoption. A Paxos successor carries the highest accepted ballot value in its prepare quorum.
  • Reconfiguration. A joint decision must satisfy both memberships independently.
  • Read barrier. Establish authority during the read and wait for local application.
  • Effect. The external resource needs its own contract for duplicate or stale requests.
