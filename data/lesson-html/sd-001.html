01 · Foundations

Why consensus exists: the split-brain problem

Five voters record a decision. Two disappear. Which survivor carries enough evidence to protect the decision during recovery?

Why distributed consensus exists

Imagine three replicas storing the identity of the active scheduler. A network partition makes two groups disagree about which machine is the leader. Without a coordination protocol, both might schedule the same GPU or trigger the same failover.

Consensus is a way for cooperating processes to agree on an ordered sequence of decisions despite some failures. It is not a magical guarantee that every operation will finish.

  • Replicated state machines apply the same committed commands in the same order.
  • Consensus chooses an agreed log; application logic determines what those commands mean.

Failure model and assumptions

Machines may crash, messages may be lost, duplicated, reordered or delayed, and partitions may temporarily isolate replicas. Raft assumes crash faults rather than arbitrary Byzantine behavior.

In a fully asynchronous system, a deterministic consensus algorithm cannot guarantee termination under even one crash in all executions (FLP). Practical systems use timeouts and partial synchrony for progress.

  • Do not confuse a slow node with a dead node.
  • Safety must survive delayed and duplicated messages.

Safety versus liveness

Safety means conflicting decisions never both become committed. Liveness means the system can eventually commit new decisions under appropriate conditions.

A minority partition should generally stop committing rather than violate safety. If a majority remains connected, it can often continue after an election.

Majority quorum mathematics

For N voting replicas, a majority is floor(N/2)+1. Any two majorities intersect, so they cannot be entirely disjoint.

For five voters, quorum is three. A five-node cluster can tolerate two failed voters while still retaining a reachable majority. It does not tolerate an arbitrary partition that leaves no connected majority.

Replication is not automatically consensus

Asynchronous replication can create divergent copies if multiple leaders accept writes. Consensus provides rules for selecting an ordered log and safely committing entries.

A replicated database might use consensus for metadata while using different mechanisms for bulk data. Choose the coordination scope deliberately.

How I Would Explain This in an Interview

I would ask what must survive the next leader. For this scheduler it is the order of exclusive GPU reservations. The quorum protects that order within the metadata service. A worker still needs a durable admission check before it starts a process.

The agreement problem is not merely selecting a leader

Consider an AI scheduling control plane with replicas A, B, and C. The active scheduler writes an assignment saying that training job J owns eight GPUs on worker W. Suppose A acknowledges the assignment and crashes before the other replicas record it. If B becomes leader and allocates the same GPUs to another job, the system has created a conflicting ownership history. The central question is not which process is currently alive. It is which decisions are durable and which new leader is permitted to act on them. Consensus solves agreement about an ordered log; separate resource-level fencing is still required to prevent an old owner from acting outside that log.

A replicated state machine begins with a deterministic transition function. Given identical initial state and identical committed commands in identical order, all healthy replicas compute the same logical result. That is why a consensus protocol orders commands rather than simply copying whichever memory image appears newest. Commands may include assigning a lease, changing a configuration, creating a workflow, or recording a failover epoch. The state machine should avoid nondeterministic behavior such as reading local wall clocks during application unless the chosen time is explicitly recorded in the command.

Safety is the requirement that two legitimate replicas do not decide incompatible histories. Liveness is the requirement that the system eventually makes progress when the network and membership assumptions allow it. A design can preserve safety while becoming unavailable: a minority partition must refuse to commit new writes. This is a deliberate tradeoff, not a software bug. In an interview, first state the failure model and consistency requirement, then explain what you intentionally sacrifice during partitions.

Worked example 1

The one voter that remembers

Five servers start with slot 48 open. In classic Paxos, three acceptors named A, B, and C accept the same promotion command in ballot ten. A and B lose power before any client learns the result. D and E have received no messages about slot 48. Count the smallest possible intersection between two sets of three in a universe of five. The sets contain six memberships altogether, but only five distinct machines exist. At least one machine must appear twice. For the surviving quorum C, D, E that machine is C.

Now try a deliberately incomplete recovery rule. Suppose D asks only which value is most popular among the three survivors. Two report an empty slot, so D concludes it may choose cancellation. That rule loses a chosen promotion. A correct proposer asks for durable promises and prior accepted proposals. C’s reply at ballot ten requires the proposer to carry promotion forward when the other two report none. If C also becomes unavailable, two machines cannot complete this recovery. In production, monitoring must distinguish the number of healthy processes from the number of mutually reachable voters capable of accessing their durable state. In an interview, identify C and then name the rule that forces D to heed its evidence.

02 · Raft

Raft from first principles: roles, terms and elections

Two candidates have different log histories. Follow the vote that lets one of them lead.

Raft in one picture

Raft organizes servers into followers, candidates and leaders. At a given term, a leader normally handles proposals and replicates log entries.

Terms are monotonically increasing election epochs. They help replicas reject messages from obsolete terms.

Leader election walkthrough

A follower that does not hear a leader within its randomized election timeout becomes a candidate, increments its term, votes for itself and requests votes.

A candidate wins only after obtaining votes from a majority. Voters also enforce a log freshness condition to prevent electing a candidate with an outdated log.

  • Randomized timeouts reduce split votes.
  • A node votes at most once per term.
  • A higher term causes a server to step down.

Terms and the stale leader

Consider a leader in term 8 that becomes isolated. The majority elects a new leader in term 9. The old leader might still think it owns the role.

Raft prevents that old leader from committing new entries without a majority, but external systems that do not check ownership may still accept stale actions. This is where fencing or idempotent external APIs matter.

Why terms matter

A term is a logical epoch, not a wall-clock timestamp. When a node sees a higher term, it updates its term and steps down. Terms help nodes reject stale leadership claims; a term alone is not a substitute for fencing at an external storage or compute resource.

Trace a complete Raft election

Imagine a three-member Raft group with A, B, and C at term seven. A is leader and sends periodic AppendEntries heartbeats. A crashes. B waits for a randomized election timeout, increments its current term to eight, votes for itself, persists that vote, and sends RequestVote to C. C checks that the request term is current, that it has not voted for someone else in term eight, and that B’s log is at least as up to date as C’s log. If these conditions hold, C grants its vote. B now has two votes, a majority of three, and becomes leader for term eight.

Why randomize election timeouts? If B and C always begin elections simultaneously, each can vote for itself and neither obtains a majority. Randomization reduces repeated collisions. It does not guarantee that an election always finishes within a fixed deadline under arbitrary network delays. Once elected, B immediately sends AppendEntries messages to establish authority. A delayed heartbeat from old term seven cannot demote B because receivers compare terms. If B encounters a higher term, B steps down.

The log freshness test matters as much as the vote count. A candidate with an obsolete log must not replace a leader if doing so could lose committed entries. Raft compares the last log term first and then the last log index. A candidate with a higher last-log term is considered more up to date; with equal terms, the longer log wins. This rule works with the leader completeness property and Raft’s commitment restrictions to preserve committed history across elections.

For communication practice, describe the election as a timeline rather than a glossary: the leader stops sending heartbeats, a follower times out, the candidate advances the term, a majority votes based on log freshness, and the winner begins replication. Then explain the failure case: if the network divides three nodes into a group of two and a group of one, only the group of two can elect a leader and commit.

Worked example 2

A long log loses an election

Five voters share a prefix through index 19. In term six, A appends entries through index 24 on A and C alone. In term seven, B wins with B, D and E, then appends index 20 locally. A has the longer log, but B’s last log term is seven. A later asks B for a vote. B denies it even though A has four more entries. Suppose A obtains only C’s vote in addition to its own, and its election fails. B then starts a higher term and wins with B, D and E. The two copies on A and C were a minority in the five-voter group. Nothing in this history required B to preserve their uncommitted suffix.

Once B wins, a normal append at index 21 includes the term at index 20. C’s entry there belongs to term six, so it rejects the append. B backs up to a matching prefix. C then replaces its conflicting suffix with entries supplied by B. A dropped success response may cause B to resend entries. An already matching entry does not require truncating an otherwise matching suffix merely because a heartbeat carried no new entries. For an operator, an apparent fall in a replica’s last log index can be legitimate repair. A decrease in the applied committed history of a serving replica would demand a different investigation.

03 · Replication

Replicated logs, commitment and client retries

Three disks contain the same entry. To decide whether it is committed, reconstruct when the third copy arrived.

AppendEntries and log replication

The leader appends a command to its log, sends AppendEntries with the preceding log index and term, and followers reject inconsistent prefixes.

Followers can truncate conflicting uncommitted suffixes and catch up. The log matching property ensures that equal index-and-term entries imply identical preceding entries.

Commitment and application

A leader tracks replication progress and advances commitIndex according to Raft commitment rules. For current-term entries, majority replication permits the leader to commit; earlier entries can become committed indirectly.

Once committed, replicas apply commands in log order. Do not tell an interviewer that any arbitrary old-term entry becomes committed solely because a majority currently stores it.

Leader crashes before replying

A client sends a command. The leader may commit it and crash before returning the response. The client cannot know whether the command took effect.

Retrying blindly may execute a business action twice. Include a client request ID and durable deduplication state in the replicated state machine for logical operations. External APIs still need their own idempotency mechanisms.

The critical crash window

Consider an API call that succeeds, followed immediately by a worker crash before its result is persisted. Consensus for the worker metadata cannot retroactively tell you whether the external call succeeded. Persist an operation ID before the call and require the target API to deduplicate or expose a way to reconcile the outcome.

Commit is not the same as apply

A log entry can be committed but not yet applied to a state machine on a lagging follower. Reads therefore require an explicit consistency strategy, such as a leader read barrier or a suitable lease under stated timing assumptions.

Trace an append, a crash, and a retry

Suppose the leader of a three-voter group has a log with entries one through twelve committed. A client submits Allocate(job-42, gpu-7) with idempotency key req-901. The leader appends entry thirteen locally, sends AppendEntries to followers, and waits for a majority acknowledgement. When a follower persists the entry, the leader can advance its commit index according to Raft’s term-aware commitment rules. It then applies the command to its deterministic state machine and responds to the client. The order of persistence, replication, commitment, and application is essential; an entry appearing in one log does not mean it is committed.

Now change the timeline. The leader commits entry thirteen and crashes before returning the response. The client sees a timeout and retries. The new leader must not interpret the retry as a completely new business request. Store a stable request identifier and the resulting decision in replicated state so repeated submissions can return the same logical outcome. Consensus makes the deduplication record durable, but the application still needs a deduplication policy and retention window.

Consider a more difficult variation: the leader appends entry thirteen to its own disk but never replicates it to a majority. A different leader may overwrite that uncommitted suffix. Therefore an API must not promise successful execution based only on the leader’s local append. Explain the distinction between accepted, replicated, committed, applied, and externally completed. Each stage answers a different question and has different failure semantics.

If a committed command triggers an external API, a second challenge appears. The state machine might record an intent, then a worker calls a GPU control API and crashes before recording success. After recovery, the system cannot infer whether the external call took effect. Use an operation ID created before the call, require idempotent or queryable downstream behavior, and reconcile until the durable desired state matches the observed state. Raft cannot make an arbitrary external API atomic with its log.

Worked example 3

A majority containing an old entry

Five replicas share index one. In term two, A stores X at index two on A and B alone. A fails. E wins term three with votes from C, D and E, whose logs still end at index one. E appends a conflicting Y at index two to its own disk and fails. A returns, wins term four with votes from A, B and C, then copies X to C. Stop here. Three replicas now hold X, but the entry is stamped term two. Can A declare victory by counting three disks?

Trace the counterexample. If A fails now, E can request votes in term five. Its last entry has term three, which is newer than term two on C. E can win C, D and E and replace X with Y. The third copy of X appeared under a later leader. That copy did not retroactively satisfy the current-term commitment condition for a term-two leader. The calculation looked persuasive because it discarded the history of how the three copies arose.

Run the alternative ending. Before failing in term four, A appends a no-op at index three in term four and replicates it to A, B and C. That entry now meets the current-term rule. Its prefix, including X, commits with it. E’s request can no longer win C’s vote with its term-three tail, and D and E alone cannot elect it. On a whiteboard, change just the last entry on the majority and rerun the election. The operational consequence is precise: after a leadership change, progress on a current-term entry can establish commitment of inherited history.

04 · Recovery

Snapshots, reconfiguration and safe recovery

Move from one voting configuration to another while clients continue submitting writes.

Snapshotting and log compaction

A long-lived replicated log cannot grow forever. Periodically snapshot the applied state and retain metadata required to resume replication.

A follower far behind may receive a snapshot rather than millions of individual log entries. Snapshots must be consistent with applied state and include index and term boundaries.

Membership changes

Changing voters carelessly can create disjoint majorities. Raft uses carefully designed configuration transitions, commonly joint consensus, to preserve quorum overlap across membership changes.

Operationally, replacement of failed voters and zone migrations must be treated as correctness-sensitive workflows.

Why membership transitions require quorum overlap

Changing from one replica set to another is itself a distributed-systems problem. Naively switching configurations can create two disjoint majorities. Production protocols use safe reconfiguration mechanisms, such as joint consensus in Raft, so the transition preserves quorum overlap.

Operational design

Test restore from snapshots, checksum integrity, disk exhaustion, corrupted state, slow followers, and replacement of failed nodes. Backups are not a substitute for verifying the consistency of restored metadata.

Snapshots and membership changes are safety-sensitive

Long-running Raft clusters cannot retain every historical log entry forever. A snapshot stores the state machine’s materialized state at an included log index and term. The snapshot must be internally consistent with committed state. A follower that falls far behind can receive an InstallSnapshot transfer rather than replaying millions of old commands. The snapshot reduces recovery time, but does not eliminate the need to persist the latest term, vote, and remaining log correctly.

Membership changes are not equivalent to editing a list of server addresses. Suppose a five-node cluster is replaced with a different five-node cluster in one uncoordinated step. Two disjoint majorities might each believe they can commit. Raft joint consensus is one technique that requires agreement under overlapping old and new configurations during transition. Other production implementations use carefully constrained single-server changes. The correct interview response is to name the implementation’s membership algorithm and explain how quorum intersection is preserved.

A common operational failure is restoring a stale snapshot into an active cluster as if it were authoritative. Snapshots carry an index and term and must be installed through protocol-aware mechanisms. Restoring an arbitrary disk image from backup can violate the cluster’s identity and membership assumptions. For disaster recovery, distinguish restoring a replicated metadata service from restoring the resources managed by that service. The two recovery workflows have different correctness and RPO considerations.

Worked example 4

Change the voters while writes continue

The old voters are A, B and C. The new voters will be C, D and E. Before starting, transfer snapshots and subsequent log entries to the incoming replicas so they can catch up. Now imagine directly changing a configuration flag at each node. A and B could keep writing under the old configuration while D and E write under the new one. Each pair has a majority in its own configuration, and the two pairs share no member. Having C listed in both configurations does not force either pair to hear from C.

In Raft’s joint configuration, decisions governed by the joint rule require a majority of the old voters and a majority of the new voters. A, C and D satisfy both requirements. A, B and D have three out of five machines but only D from the new set, so they fail. Losing C need not stop every joint decision: A, B, D and E still cover both majorities. Once the joint configuration commits, the leader can append the final configuration using the protocol’s configuration rules. Membership entries themselves obey Raft’s special rules for adopting configurations. Treating the transition as two administrative file edits would reintroduce the very race we set out to prevent.

Pause at the point where D cannot finish snapshot installation. Removing a working voter to accelerate the move could erase your margin for the next failure. Check the replication gap, disk throughput, and available quorum under both configurations. If necessary, defer the planned change while serving on the original healthy group. A learner that has copied bytes is distinguishable from a voter entitled to decide a command.

05 · Paxos

Paxos and Multi-Paxos: the agreement mechanism

Follow a single slot through three ballots and decide which value the next proposer must preserve.

Basic Paxos: actors and promise

Paxos uses proposers, acceptors and learners. A proposer first asks acceptors to promise not to accept lower-numbered proposals.

Acceptors report any previously accepted value. The proposer must preserve the highest-numbered accepted value it learns, preventing incompatible choices.

Prepare and accept phases

Phase 1: proposer sends Prepare(n); a quorum promises and reports previously accepted proposals. Phase 2: proposer sends Accept(n,value) consistent with those reports; a quorum accepting chooses the value.

Unique increasing proposal numbers matter. A chosen value remains safe even when different proposers compete.

Multi-Paxos versus Raft

Basic Paxos decides one value; Multi-Paxos optimizes repeated decisions with stable leadership. Raft structures leader election and log replication explicitly for understandability.

Both require careful engineering around recovery, configuration changes and client retries. Do not assume one is universally faster or safer.

Quorum intersection is necessary, not sufficient

In classic Paxos both phases normally use majorities. The essential intersection is between a later prepare quorum and any earlier accept quorum for the same slot. Those phases perform different jobs. An ordinary application read is neither phase. A cache read that touches three servers still needs a specified consistency protocol before we can promise that its result reflects the latest completed write.

From one value to a log

Basic Paxos chooses a value for one instance. Multi-Paxos extends the pattern to a sequence of instances and typically uses a stable leader to avoid repeating expensive preparation for every command. Raft makes a leader-oriented replicated log explicit and packages membership and recovery rules in an approachable form.

Understand Paxos as promises and accepted values

Basic Paxos chooses one value among competing proposals. A proposer sends Prepare with ballot number n. Acceptors promise not to accept proposals with lower ballot numbers and report previously accepted proposals. If the proposer obtains a quorum, it must propose the value associated with the highest-numbered accepted proposal reported by that quorum, if one exists. It then sends Accept(n, value). When a quorum accepts the same proposal, the value is chosen. This rule prevents a later successful proposal from choosing a conflicting value.

Consider three acceptors A, B, and C. Proposer P obtains promises from A and B for ballot ten, and proposes value X. A and B accept X, so X is chosen. A competing proposer Q later obtains promises from B and C for ballot eleven. B reports that it accepted X at ballot ten. Q must carry X forward rather than selecting Y, even if Q originally preferred Y. The intersecting member B transfers information about the earlier choice. The intersection alone is not sufficient; the prepare and value-selection rules are what make the intersection useful.

Basic Paxos selects one value, whereas a replicated service needs an ordered stream of decisions. Multi-Paxos commonly uses a stable leader to avoid running a full prepare phase for every slot. Raft integrates leader election, log replication, and safety rules into a more directly understandable design. Do not claim that Paxos is inherently unsafe or that Raft is universally faster. Compare the exact variants, storage implementations, batching, networking, and operational characteristics.

An excellent interview explanation separates three layers: consensus chooses a value, a replicated log sequences many values, and the application state machine interprets those values. This prevents confusion between protocol-level agreement and business-level effects.

Worked example 5

A value can be accepted without being chosen

Start with three acceptors and one open slot. In ballot twenty, P obtains promises from A and B but only A receives its accept request for blue. In ballot twenty-one, Q prepares with B and C. Both report no accepted proposal, so Q proposes green. B and C accept it. Green is now chosen even though A remembers blue. Seeing one prior acceptance therefore does not prove that its value was chosen. What matters is the precise quorum and what the proposer learned in its prepare phase.

Next, R starts ballot twenty-two and prepares with A and B. A reports blue at twenty and B reports green at twenty-one. R must carry green, even if R prefers blue and even if blue arrived first. Choosing the highest reported ballot is meaningful only among actual acceptances for this slot. A promise with a large ballot number and no accepted value supplies no candidate value. If R’s accept request loses a race to a higher promise, it must back off and try a higher ballot. Durable promises across restart are essential here. Forgetting a promise could let a delayed lower-ballot message undo the reasoning that kept green safe.

Multi-Paxos turns this recovery problem into a per-slot exercise within one leadership ballot. An incoming leader may learn about activity in slots 51 and 53 while slot 52 appears empty. It must recover potentially chosen commands, and can fill a proven free slot with a no-op. It can buffer a learned command at 53 while waiting for 52. Executing 53 first could read state that command 52 was meant to change. A high throughput pipeline therefore needs separate indicators for accepted slots and the contiguous applied prefix.

06 · Production

Designing a consensus-backed control plane

A former leader can answer quickly with an obsolete value. Trace the checks behind a linearizable read.

Consensus service architecture

A practical coordination service exposes a small strongly consistent key-value or log API, stores durable WAL records, and replicates metadata across zones.

Applications watch committed changes, acquire logical ownership and perform side effects through guarded APIs. Keep consensus state small and avoid placing large model checkpoints directly in the replicated log.

Leases versus fencing

A lease limits ownership to a time window, but clock skew and long pauses can make an old owner dangerous. A fencing token is a monotonically increasing epoch checked by the protected resource.

For example, storage accepts writes only when token ≥ highest token previously observed. An old worker with token 41 is rejected after token 42 has been accepted.

  • A fencing token works only if the resource actually enforces it.
  • Do not equate an expiring lease with safe rejection of stale writes.

Fencing design

In this design a change of scheduler ownership increments the shard’s ownership epoch. A Raft leadership change alone need not change that grant. The scheduler includes the epoch with a resource mutation. The resource must remember the highest accepted epoch and reject lower ones. A fencing token works only if the resource enforces it; simply logging the token does not protect the external boundary.

Reliability signals

Track leader changes, election duration, proposal latency, commit latency, quorum health, log lag, snapshot duration, rejected stale epochs, and operations stuck in reconciliation. Tie alerts to user-facing availability and recovery objectives.

Define the API before drawing boxes

For a production coordination service, begin with operations such as CompareAndSwap(key, expectedVersion, newValue), Get(key, consistency), Watch(prefix, resumeRevision), and GrantLease(ttl). Each write should have a stable request ID and a documented response semantics. A successful linearizable write means its result can be placed at a single point between invocation and response in a total order consistent with real-time precedence. A watch stream may be eventually delivered and should not be confused with the consistency of the underlying write.

Partition the system into an API gateway, consensus-backed metadata shards, a watch distribution layer, durable snapshot storage, and an operations plane. The leader of each shard proposes writes; followers persist and replicate. The service must authenticate clients, enforce quotas, handle slow watchers, and expose cluster health. Most applications do not need to run a bespoke consensus implementation. Prefer a proven coordination service unless a measured requirement justifies owning protocol complexity.

For recovery, specify what is persisted before acknowledging a write, how replicas bootstrap after restart, how the cluster detects membership drift, and what operators do when quorum is lost. Avoid a dangerous manual override that simply forces two isolated groups to act as leaders. A production runbook should distinguish a recoverable follower outage from catastrophic quorum loss and require explicit operator decisions when data loss is possible.

Worked example 6

A read from the former leader

At 10:00, A is leader and its state machine says the active region is Phoenix. A becomes isolated. B and C elect B, commit Ashburn, and return success to the operator. After that response a second operator asks A for the current active region. A’s disk is healthy and its local state unchanged. Returning Phoenix would violate real-time order because the completed change preceded the new read. An authenticated connection to A and a low local query latency tell us nothing about that ordering.

For a quorum-confirmed leader read, first establish commitment of a current-term entry. Capture a safe read index, confirm leadership for this read through current-term contact with a majority, and wait for the local state machine to apply through that index before serving. Implementations may batch compatible read requests behind one confirmation. A partitioned former leader cannot gather the confirmations. If the client instead requests a stale observation for a dashboard, a local replica can serve its applied revision and the API can name the weaker guarantee. Never silently downgrade the read used to authorize a promotion.

Name the consistency of each read path and define the retry contract for each write path.

07 · Geography

Multi-region latency, partitions and alternatives

Price the normal write path, then remove a region and calculate which acknowledgment now sets the latency.

Multi-region tradeoffs

A global quorum may require long-haul round trips and can make every control-plane write expensive. Regional consensus groups with carefully designed ownership boundaries may offer lower latency.

For disaster recovery, decide which metadata must be globally authoritative, which can be eventually replicated, and what happens when regions cannot communicate.

When not to use consensus

Consensus is unnecessary for many immutable blobs, cache entries, analytics events and independently partitioned workloads.

Use consensus for critical shared decisions requiring ordered agreement, such as ownership, membership and authoritative configuration. Avoid making every request dependent on a global coordinator.

Failure-domain tradeoff

A five-node cluster tolerates two failed voters for majority availability, but only if the remaining three can communicate. Correlated failures, network partitions, and poor placement can eliminate quorum even when three machines are technically running.

Alternatives

Use a regional consensus cluster for strongly consistent control-plane state and asynchronous replication for distant read replicas when the product allows it. For high-volume telemetry or immutable blobs, consider logs, object storage, or eventually consistent systems instead of routing everything through consensus.

Reason quantitatively about regions and quorums

A five-node cluster needs three votes to form a majority. It tolerates two node failures only if the remaining three can communicate and maintain required storage durability. If replicas are spread across three regions with placement two, two, one, loss of the two-replica region leaves three replicas and a quorum. Loss of either other region leaves at least three. However, latency depends on which peers acknowledge and where the leader runs; geographic fault tolerance and write latency must be considered together.

If a write requires a leader-to-follower round trip and local durable persistence, a cross-region quorum may impose tens or hundreds of milliseconds of coordination latency depending on geography and storage. Batching can improve throughput but does not remove the latency floor of synchronous quorum acknowledgement. For high-volume model inference, do not place a consensus round trip on every token-generation operation. Use consensus for infrequent control-plane decisions, while allowing the data plane to operate from validated configuration and fenced ownership.

If you require active-active writes across distant regions, clarify whether the application truly requires linearizable ordering across all writes. A single global consensus group is conceptually simple but can become a latency and availability bottleneck. Shard independent metadata, localize ownership where possible, and use asynchronous replication for data whose semantics tolerate staleness. Describe the tradeoff explicitly rather than saying multi-region is automatically more reliable.

Worked example 7

Price a regional failure in milliseconds

Place voters A and B in Phoenix, C and D in Ashburn, and E in a third region. A leads. For a simple worked estimate, assume its own durable write completes in two milliseconds, overlapping follower activity. The elapsed times for durable follower acknowledgments are three, forty-one, forty-six and seventy milliseconds respectively. A needs two follower acknowledgments in addition to itself. The second fastest is forty-one milliseconds. The estimated replication barrier is the larger of two and forty-one, or forty-one milliseconds. Add four milliseconds for the client and application path and the rough result is forty-five. This models one write under explicit parallelism assumptions.

Now lose Ashburn. A, B and E remain, and E’s seventy milliseconds are on every successful write path. With the same overhead the estimate becomes seventy-four milliseconds. A fifty-millisecond objective that held on the normal path will fail in the degraded topology, even though every committed decision remains safe. These are illustrative samples. The percentile of the second-fastest response is generally not the second-smallest of the individual peers’ published percentile numbers. Replay joint latency samples or measure the actual commit distribution. Correlated disk stalls and cross-region congestion are especially important in the tail.

08 · AI infrastructure

GPU scheduler ownership and agent execution

Trace a database promotion whose provider handle disappears before the worker can save it.

GPU scheduler ownership

Two schedulers must not simultaneously assign the same exclusive GPU allocation. Store authoritative placement decisions in a consistent control plane, and give assignments epochs or generations.

Workers validate the current generation before acting. The execution plane remains separate so that the consensus layer does not sit on every token-generation request.

Agent orchestration and durable execution

Consensus can establish which worker owns a workflow and where its checkpoint metadata lives. Durable execution records step transitions so a new worker can resume after a crash.

Neither alone guarantees exactly-once payment, email, failover or cloud API side effects. Use stable operation IDs, API idempotency, reconciliation and compensating steps.

OCI FSDR control-plane analogy

Imagine an FSDR failover orchestration whose coordinator dies after issuing an external failover API call. Before the call, persist a stable operation ID and intent. After recovery, query operation status or retry using the same idempotency key.

Consensus can protect authoritative workflow ownership, while the durable workflow engine handles checkpoints and replay. Keep the recovery behavior explicit and test crash boundaries.

Separate ownership decisions from resource enforcement

An AI workload scheduler might use a consensus-backed record that maps GPU worker W to ownership epoch 142 and job J. When scheduler S1 loses its lease, scheduler S2 acquires epoch 143. If S1 later wakes up and sends a delayed Allocate command with epoch 142, the GPU agent must reject it. The important property is monotonicity at the resource that performs the side effect. Merely checking the epoch in the scheduler is insufficient because the scheduler itself can be stale.

An agent workflow may similarly store the next action and checkpoint in a durable log. Consensus can protect the authoritative workflow state, but a remote payment, ticket creation, or infrastructure mutation requires its own idempotency or reconciliation contract. Explain why the correct abstraction is often at-least-once delivery plus effectively-once business effects, not a blanket exactly-once claim.

At scale, keep coordination traffic proportional to changes in ownership and durable state rather than per-token or per-GPU-kernel work. If a model-serving cluster has thousands of workers, the consensus group may manage partitions, leases, and desired configurations while workers stream telemetry independently. This separation improves throughput and limits the blast radius of coordination latency.

Worked example 8

The provider returns a handle that nobody saves

Imagine a recovery orchestrator modeled on the problems faced by a full-stack DR control plane. A committed intent records request key K17, database incarnation D9 and target Phoenix. A worker sends the promotion. The database service records K17 and creates operation O19. The worker crashes before saving the response. Its successor can see K17 in the log but cannot calculate O19. No number of additional replicas for the intent journal would reproduce a response received by nobody who survived.

Require a documented provider contract that binds K17 to tenant, resource and payload and returns the same result or handle on replay. Within that contract’s retention period the successor resends the identical request and recovers O19. It can observe progress and commit completion before activating a dependent routing step. If the provider offers neither durable deduplication nor lookup by stable intent, keep the outcome unknown and reconcile authoritative evidence. A status of primary can be ambiguous if an operator separately promoted the database. In an agent runtime, substituting create-ticket for promote-database gives the same failure. Record the tool’s request identity before crossing its boundary.

Worked design: resilient AI workload scheduler

Design a scheduler for 10,000 GPUs across three zones while keeping exclusive allocations safe.

Worked architecture: resilient scheduler

Design a three-zone scheduling control plane: five coordination voters, stateless API frontends, elected scheduling owners, a durable workflow store, and workers enforcing assignment generations.

Walk through a leader crash, partition, delayed worker, duplicated request and a region outage. Explain what is safe, what remains available, and which components are the bottlenecks.

Senior Staff tradeoff discussion

The best answer starts with requirements: fault model, latency budget, write volume, geographical topology, recovery time and cost.

Defend why the critical coordination path uses consensus, why bulk data does not, and how you measure operational health. Discuss migration, rollout, observability and incident response, not just boxes and arrows.

Requirements and APIs

Define createJob(jobId, specification, idempotencyKey), getJob(jobId), cancelJob(jobId), and watchJob(jobId). Nonfunctional goals include no conflicting allocation, recovery after worker crashes, bounded scheduling latency, auditability, and isolation between tenants.

Data model

Job: ID, tenant, desired state, observed state, version. Allocation: resource ID, job ID, ownership epoch, expiration policy. Operation: stable ID, type, attempt, state, external request ID, result reference. Store the small authoritative state in a consensus-backed metadata service; store large artifacts elsewhere.

Failure walkthrough

Leader A commits an allocation intent and crashes. Leader B is elected, reads the committed intent, and checks whether the executor already acted. B retries with the same idempotency key if needed. If A later resumes, its old epoch is rejected by the executor. This is how coordination, fencing, and reconciliation work together.

Defend the scheduler design under pressure

Assume a hypothetical fleet of 10,000 GPUs across three availability zones. The scheduler must place training jobs, avoid double allocation, recover within thirty seconds after a leader crash, and tolerate a single zone failure. Begin by clarifying whether allocations are exclusive, whether running jobs can survive scheduler failure, and whether capacity reservations must be durable before execution. These questions reveal the required consistency boundary.

Choose a five-replica metadata quorum with zone-aware placement, and store job intent, allocation records, and ownership epochs in the replicated state machine. Separate the leader’s planning loop from the worker agents that enforce allocations. Each allocation includes job ID, worker ID, monotonically increasing epoch, stable operation ID, and expiration or explicit release semantics. Worker agents reject stale epochs and deduplicate operation IDs. The scheduler reconciles actual GPU state with durable desired state after crashes.

Failure test one: the leader commits an allocation and crashes before responding. The new leader reads the committed record and returns the existing result when the client retries. Failure test two: the old leader is partitioned but still connected to one worker. The worker refuses its old epoch after accepting a newer one. Failure test three: a zone is lost and quorum remains. Scheduling continues if sufficient capacity exists; already running jobs follow the separate data-plane failure policy.

Capacity is not only a count of GPUs. Placement may depend on GPU model, topology, interconnect bandwidth, memory, locality, and tenant quota. A good Senior Staff answer separates the correctness-critical allocation transaction from optimization heuristics. The heuristic can be changed without weakening the exclusive-ownership invariant.

A production contract for a three-zone scheduler

Place two voters in zone one, two in zone two, and one in zone three. Dispatch and inference do not share a thread pool with metadata replication. The placement planner can tolerate stale worker telemetry because its plan is only a proposal. The replicated command validates the device incarnation, the expected reservation version and tenant quota before recording the assignment. On conflict the planner rereads state and tries another placement. Bind the request key to tenant and canonical payload and retain the successful result in the same transition. A client retry with a different payload should receive a conflict, even if the device happens to be available again.

Suppose ten thousand GPUs average two allocations per GPU per hour. That produces about 5.6 allocations per second. A disruption that reschedules two thousand devices in ten seconds drives two hundred allocations per second, before releases or retries. At two kilobytes per log command that burst is roughly four hundred kilobytes per second of logical writes, and about 1.6 megabytes per second of leader payload sent to four followers in steady replication. Add framing, snapshots, acknowledgments, retry amplification, quota mutations, and durable disk overhead before turning this estimate into a capacity plan. Batch independent decisions with a bounded wait so interactive launches retain a latency budget.

Authenticate every API caller, scope journal keys to tenants, and permit only the worker for the device incarnation to report its observed allocation. An internal worker report is evidence to reconcile, not authority to rewrite the plan. Keep tenant secrets and model weights out of replicated command payloads. Measure the fraction of eligible leader failures for which the first safe new placement occurs within thirty seconds, and separately report unavailable GPU capacity and disruption to already running jobs. Exercise one-zone loss while a snapshot transfer is in progress. If disk contention depresses quorum acknowledgments, rate-limit catch-up and reserve resources for voting traffic.

Architecture defense. Product asks for thirty-second recovery during a partition and no duplicated allocation. Clarify whether a reachable majority and reachable device are assumptions, and what counts as recovery for a running job. My design continues already admitted jobs while quorum is missing and withholds conflicting new admissions. With a healthy majority but an unreachable device, it offers another eligible device if policy allows. A first implementation can keep a single small metadata group. Split groups by allocation pool after measuring contention. Cross-pool gang placement then needs explicit reservations and an all-or-release coordinator; a pile of individually committed allocations does not give a job its entire gang.

10 · Interview mastery

Concepts you must remember and explain

Rehearse one design at three speaking lengths, from the invariant to the production tradeoffs.

Important concepts to remember

Consensus chooses a safe order of decisions; replicated state machines apply those decisions. Majorities overlap, but protocol-specific rules establish safety.

Raft terms are election epochs. A leader without majority cannot safely commit new decisions. Client retries need deduplication. External side effects require independent guards.

  • Consensus chooses a value per slot. The application interprets it, so a committed allocation request can still return a version conflict.
  • Safety preserves compatible decisions across executions. A period with zero committed writes can be safe and still breach an availability objective.
  • Liveness means progress under the stated conditions. Count reachable durable voters and inspect latency before predicting a recovery time.
  • A quorum is a sufficient set for a given protocol phase. Overlap preserves information only when the participants use the protocol’s durable rules.
  • A term identifies a Raft election generation. A new term can begin without a winner, so a rising term counter may indicate churn.
  • Log matching ties equal index and term to the same prefix. An equal index alone cannot validate a follower’s contents.
  • Leader completeness means later elected leaders include committed entries. A follower can help enforce that property while unaware of the commit index.
  • A Paxos promise bars lower ballots. Persisting it before replying protects the proposer from a lower ballot after an acceptor restarts.
  • A chosen proposal has quorum acceptance. A learner may still have insufficient evidence to report the choice, so timeouts remain ambiguous.
  • A read barrier establishes an ordering point. Wait for the required applied index before exposing the local materialized state.
  • A snapshot represents a committed applied prefix. Include configuration and deduplication state needed to resume service correctly.
  • A fence rejects an obsolete generation at the resource. Installing the floor has its own ordering point after the ownership decision.

Explain it in 30 seconds

Distributed consensus lets replicas agree on an authoritative sequence of decisions despite failures. Raft elects a leader and replicates a log, committing decisions under quorum and term rules. In AI infrastructure, I would use it for scheduler ownership and critical metadata—not for every inference request—and protect external actions with fencing and idempotency.

Explain it in two minutes

I would start with a concrete decision. We have a GPU and two jobs that want exclusive use of it. The scheduler replicas can each make a reasonable local choice and still disagree. I want a durable order for claims and a deterministic rule that awards the device only if the recorded version is still free. In a three-voter Raft group, the leader appends a command in its current term, one follower makes the entry durable, and the leader can commit. Applying the command decides whether the claim succeeded. A rejected claim can itself be a perfectly valid committed command.

If the leader crashes after commitment, a future elected leader must contain the entry. The caller may have seen only a timeout, so I record its request key and the original result. I also distinguish assigning the GPU in metadata from starting a process on the host. The host must validate the assignment generation and handle duplicate submissions. If the network splits, the majority can continue under stable conditions and reachable workers can honor existing assignments. That gives the business a precise availability promise while preserving exclusive ownership.

Explain it in five minutes

Picture an operator asking whether it is safe to promote Phoenix while Ashburn is unreachable. I would start by separating three questions. Which control plane can authorize promotion? Which copy of the database meets the recovery point objective? And what prevents the old primary from accepting writes? Consensus answers the first question. The data replication policy and a write fence address the other two. Putting five voters around a promotion log alone cannot recover missing database transactions or isolate a primary that still serves clients.

I would store proposed transitions in a small replicated state machine. A request includes the plan identity, its expected version, target region, and a caller-generated key. Two operators can race to submit different requests. The log orders them. When the state machine applies them, it checks each expected version against the state left by the previous command. One succeeds and the other sees a conflict. Both outcomes can be replicated safely. That distinction matters because engineers sometimes describe consensus as a service that makes business decisions on its own.

Take a leader in term twelve that receives a request for slot forty-eight. It persists the command and a second member of the three-voter group persists it. The leader can now commit this current-term entry. It applies the transition and fails before answering. The client’s timeout is consistent with success. A follower that has the entry can protect the decision through its election vote even before learning the commit index. A successor can commit a current-term entry to establish the inherited prefix. On retry, the replicated request record returns the first result. I would test this exact crash window with a delayed reply.

Paxos reaches a comparable safety result through a different recovery path. A proposer gathers promises, discovers the highest accepted ballot reported for a slot, and carries that value forward. Intersecting quorums give it a witness to a potentially chosen value. The promise limits what older proposers can still accomplish. A stable Multi-Paxos leader amortizes preparation over successive slots. Whichever implementation I choose, the operational questions include durable storage, handling slow followers, safe membership changes, snapshot installation and a tested restore.

Finally, I would place the consensus group where its quorum survives the required fault. I would measure the actual durable acknowledgment path after losing a zone. If the new control plane cannot fence the previous writer, promotion waits. If promotion has already been submitted, the successor reconciles it with a provider-recognized idempotency key. The service reports that state explicitly and keeps independent work moving. I would defend this design by showing a trace of accepted operations during the failure and the customer-visible time until the first safe write.

11 · Interview

Senior Staff interview questions and model answers

Use the twelve questions to practice answering aloud before revealing each model answer.

What happens when a leader is partitioned from its quorum?

It may continue believing it is leader, but cannot commit new log entries. The majority side may elect a new leader. External systems must enforce fencing to reject stale operations.

The interviewer is evaluating whether the candidate separates authority from reachability.

Suppose an isolated former leader accepts a client connection after its replacement commits a write. A stale local read may violate the client’s expectations even when the old leader never commits a write. Offer a bounded or explicitly stale status API separately from the strongly consistent path. An old TCP connection proves reachability only.

Follow-up for the whiteboard: Would you continue serving reads?

Why do majorities intersect?

For N voters, two sets larger than N/2 must share at least one member. Consensus protocols use this overlap with additional voting and value-selection rules to preserve agreement.

The interviewer is evaluating whether the candidate can prove the counting argument.

For quorums of sizes q and r in a fixed set of N, the intersection has at least q plus r minus N members. For five and two majorities of three the bound is one. The overlap matters only if that member persists the state the recovery protocol asks about. Counting processes that silently lost their disks breaks the proof.

Follow-up for the whiteboard: What changes if a voter forgets its promise?

Can Raft guarantee exactly-once API calls?

No. Raft orders durable decisions; external effects can be ambiguous after timeouts. Use stable operation IDs, downstream idempotency, reconciliation, and durable completion records.

The interviewer is evaluating the boundary between replicated state and a side effect.

Commit an intent keyed by the client before sending. A provider that deduplicates identical payloads and returns the original operation handle permits safe replay. A local outbox can reliably deliver the intent but cannot alone deduplicate the remote mutation. Set retention to cover the advertised retry horizon and define the outcome after it expires.

Follow-up for the whiteboard: What if the provider forgets keys after a day?

What is the difference between an accepted and committed entry?

An entry can exist on one or more logs without being committed. Raft uses majority replication plus its term-aware commitment rule to establish commitment.

The interviewer is evaluating reasoning about a change of term.

Draw five disks with an old entry on three and a conflicting entry of a later log term on another disk. Ask when the third copy arose. If a subsequent leader copied it, that majority alone cannot establish commitment. A current-term entry committed on a majority protects its entire prefix. Acknowledging the inherited entry early improves apparent latency by breaking the guarantee.

Follow-up for the whiteboard: Why might a newly elected leader append a no-op?

How do you prevent stale leaders from controlling GPUs?

Persist a monotonically increasing ownership epoch and require each GPU agent to reject commands with older epochs. The enforcement must happen at the resource boundary.

The interviewer is evaluating whether enforcement occurs at the actual mutation.

Atomically install the verified successor generation at the worker and compare it in the reservation transaction. If the worker is unreachable, its availability for new work is unknown. Quarantine it rather than reuse its capacity elsewhere under an assumption that the old job stopped. Reading a coordinator key before sending a command leaves a race.

Follow-up for the whiteboard: What if the old process is still running?

What is a linearizable read?

A read whose result can be placed at a single instant between invocation and response, respecting real-time order. A Raft leader needs an appropriate current-leadership check or read protocol.

The interviewer is evaluating the separation between leadership confirmation and state-machine freshness.

A quorum read barrier may establish that a leader can serve a read, yet its apply loop may lag the captured index. Wait for application before reading. Under high read volume batch barriers or offer explicitly stale reads to monitoring clients. Returning immediately after a heartbeat ignores local lag.

Follow-up for the whiteboard: What if the apply queue is a thousand entries behind?

What changes when a quorum spans regions?

Synchronous write latency rises with network round trips, while failure-domain resilience may improve. Placement must balance latency, region loss scenarios, and quorum survival.

The interviewer is evaluating cost and availability under correlated loss.

Compute the required follower response under normal placement and after a zone outage. A fast local voter may mask a slow distant path until that voter fails. Provision for the degraded path or narrow the latency objective. Adding remote nonvoters can improve read locality, but nonvoters cannot rescue a missing write quorum.

Follow-up for the whiteboard: Which acknowledgment sets the latency floor?

Why use joint consensus during reconfiguration?

It prevents a transition in which disjoint old and new voting groups can independently commit incompatible histories.

The interviewer is evaluating membership-specific reasoning beyond ordinary majority math.

With old voters ABC and new voters CDE, an old majority AB and a new majority DE are disjoint. A safe transition accounts for both until the change commits. Scheduling a membership change while an incoming member is far behind can prolong joint-mode unavailability. Catch it up before making its vote necessary.

Follow-up for the whiteboard: Does sharing one server across configurations suffice?

How does Multi-Paxos differ from basic Paxos?

Basic Paxos chooses one value; Multi-Paxos extends the mechanism to repeated log slots, often using stable leadership to amortize preparation.

The interviewer is evaluating whether the candidate understands recovering a sequence.

A new ballot must account for all prior accepted values in the range it will lead. Recover holes before applying later commands. A stable ballot saves round trips, yet leader churn brings the recovery work back. Compare throughput with a stable leader and tail latency during turnover instead of ranking algorithms from their names.

Follow-up for the whiteboard: Can a learner apply slot 53 before slot 52?

How would you recover a lost quorum?

First establish which durable state survives and which members can be trusted. Follow protocol-specific recovery procedures; never blindly force two partitions into independent leadership.

The interviewer is evaluating operational judgment when normal progress is impossible.

First distinguish a network isolation from actual destruction of durable state. If a majority may still exist elsewhere, isolate it before any forced restore. If a majority of the original history has been destroyed, restore under a new identity with an explicit recovery point and reconcile external effects. Choosing the longest surviving log is insufficient evidence of commitment.

Follow-up for the whiteboard: Which acknowledged writes could a backup omit?

What is the FLP result?

In a fully asynchronous model with even one possible crash, deterministic consensus cannot guarantee termination in every execution. Practical systems rely on timing assumptions for progress.

The interviewer is evaluating whether impossibility results can guide an SLO.

A timeout turns uncertainty into a new attempt. It cannot establish that a peer died. Randomized retries and a period of sufficiently timely communication allow practical progress; loss of timing assumptions leaves the safety rules intact. Test a period of delay followed by recovery. A hard universal election deadline is a stronger claim than the model allows.

Follow-up for the whiteboard: What evidence would support a thirty-second recovery objective?

When should you avoid consensus?

Avoid it for high-volume data-plane operations that do not require global ordering. Use local decisions, partitioned ownership, or eventual consistency when business semantics allow.

The interviewer is evaluating whether strong consistency is placed narrowly.

Keep the routing manifest strongly ordered if contradictory rollouts are costly. Serve inference from locally applied validated configuration and measure convergence separately. Immutable model shards can replicate asynchronously and be verified by hash. The risk is referencing shards before they exist, which a publication readiness check can address.

Follow-up for the whiteboard: What belongs in the log for a model rollout?

Important concepts

Common mistake: confusing election and ownership

Electing a leader does not instantly revoke a stale process’s ability to reach external resources. Fencing must be enforced by the resource.

Common mistake: calling a replicated write committed too early

A local append alone cannot commit a new entry in a three-voter group. One durable follower acknowledgment suffices there for an entry from the leader’s current term, provided the leader also persisted it.

Common mistake: promising availability during every partition

A minority partition deliberately loses write availability to protect consistency.
