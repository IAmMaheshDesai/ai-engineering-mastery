SD-001 · Distributed Systems Foundations · 01

Two operators start one failover

Payments runs in Ashburn. Phoenix is its standby. When Ashburn stops responding, two operators open the same OCI Full Stack Disaster Recovery plan in Phoenix and click Execute. What should each person see?

What the operators need to know

Imagine you are the incident lead. Your first question is “Has someone already started the Payments failover?” If the answer is yes, you want the execution you can follow. A minute later, someone from customer support asks a different question. “Can customers make payments in Phoenix yet?” You could confidently answer yes to the first question while you are still waiting for evidence for the second.

In OCI Full Stack DR, a DR Protection Group represents the resources you protect together. In our example the Ashburn group has the primary role and its Phoenix peer has the standby role. The operators use the failover plan in the standby group. Both intend to recover the same application in the same place.

For the rest of this lesson, we will design a small coordinator behind that familiar workflow. The version numbers, voter names, and execution ID are teaching examples. Oracle’s public walkthrough describes protection groups, plans, and roles. The coordinator is our design for learning how consensus works. Oracle’s DR walkthrough

Worked example · Follow requests A and B

Imagine a shared record for Payments. It says “Version 17. No failover in progress.” A version is simply a number that changes when the record changes. Alice (operator A) reads version 17 and sends request A. Ben (operator B) reads the same version and sends request B. Each request means “Start this plan if Payments is still at version 17 and ready for failover.”

The coordinator puts A first. It checks the record, creates execution DR-42, and records version 18. These changes happen together. When it checks B, it sees version 18 and the existing execution. B’s request to start a new run no longer meets its condition. Both operators can follow DR-42.

Here is why ordering matters. If two independent coordinators each saw version 17 and each approved a run, two workers could begin the same plan. Merging the records later would tidy up the dashboard. It could leave an extra worker changing real resources. We want the decision to happen before either worker gets permission to act.

Consensus lets several servers agree on which command belongs at each place in a shared history. They all apply A and then B. The version check supplies the rule that lets only A start a run. If B had come first, B could have started the run instead. Both outcomes are sensible when the requests overlap.

What if the screen times out?

Suppose A’s connection drops just after the coordinator records DR-42. A sees a spinning screen and then an error. B sees that DR-42 exists. The two screens look different even though the service made one decision. A lost the reply. That is different from losing the decision.

How to respond during the Payments incident
What you seeWhat to do
The request was acceptedOpen DR-42 and follow its progress.

The request timed outCheck execution history. In our design you can also look up the outcome using the original request ID.

A request ID identifies one attempt by a caller. An execution ID identifies the run the service created. A knows its request ID before sending anything. That is what makes it useful after a lost reply. If the design supports resending that same request safely, A can recover the original result even when the browser never received DR-42.

What would prove recovery?

Here is a quick way to practice the handoff. Alice has the execution open. Ben has the alarm open. Ask Alice to read the execution ID and the last completed step. Ask Ben to read the time of the last successful Payments test through the customer address. If the test ran before the outage, nobody has yet checked whether the recovered application works. The two people are looking at different evidence. Putting both observations in the incident notes lets the next shift see exactly what still needs checking.

Now imagine Ashburn starts answering again while the Phoenix execution is running. A fresh green light tells you that Ashburn is reachable. It does not tell you which database is allowed to accept a payment. First check the agreed recovery record, then check the actual database roles. A monitoring signal is a reason to investigate. It should never silently reverse the recovery decision.

Recording DR-42 authorizes the recovery work. The database may still be changing roles, application instances may still be starting, and traffic may still be going to Ashburn. Describe each result in words the incident lead can act on. “We accepted DR-42.” “The database step finished.” “Our test payment succeeded through the Phoenix endpoint.” Each statement needs its own evidence.

In an interview, I would start with one sentence. “For this Payments incident, both operators must end up following one failover execution.” Then I would follow the harder part. “Before declaring recovery, I would verify that Phoenix can serve Payments and the old primary cannot accept conflicting writes.” The next chapter shows how several servers can remember that first decision even if one goes down.

Why two out of three can decide

The coordinator has accepted DR-42. Now one server goes quiet. How can the servers that remain tell whether the Payments failover was already authorized?

Meet the three voters

Picture three servers that keep the coordinator’s decision history. We will call them R1, R2, and R3. A server that participates in the protocol is a voter. These servers keep small records such as “the next Payments command is A.” The Payments database itself can be much larger. We are talking about the servers that remember what the recovery system decided.

Our group has three members and uses majority votes. Its smallest majority is two. That gives us three possible pairs. R1 can work with R2. R1 can work with R3. R2 can work with R3. A sufficient group of participants for a protocol step is called a quorum. The two operators’ clicks have nothing to do with the count. Two operators can send a hundred requests and still contribute zero protocol votes.

Why use three servers when one could store a row? A single server is easy to understand until it fails just after replying to the operator. If every server must reply, one slow server can stop all decisions. With three voters and a working majority, the coordinator can keep its promise through one server failure. The surviving servers still need to communicate and store their records successfully.

Worked example · Watch the two pairs overlap

Suppose R1 is the Raft leader. It puts A’s command in its log in its current term, which is its numbered period of leadership. R1 saves the command, and R2 saves a copy and replies. With these two durable copies, R1 can commit the command. In this lesson, applying it creates DR-42 and moves Payments from version 17 to 18. R3 has been slow and has yet to receive the entry.

The first pair was R1 and R2. The only pair that can work while R1 is down is R2 and R3. R2 belongs to both. It need not have seen the client reply or even know yet that R1 declared the command committed. The entry itself is in its log. If R3 asks R2 to elect it while its log is behind, Raft’s election rule makes R2 refuse. R2 has a sufficiently up-to-date log and can seek election instead.

The overlap explains where the information survives. The protocol explains how to use it. If R2 erased its disk whenever it restarted, it could forget A. If R2 voted for any candidate that asked first, R3 could win with an incomplete history. A useful question to ask about any quorum design is “What does the shared member remember, and which rule makes that memory count?”

Try the overlap in Python

Keep the first pair fixed at R1 and R2. List every pair that could act later. The code prints the name of at least one voter that appears in both groups. Try changing the first group to just R1. The last line of output will then show an empty list. That is the missing link when a lone server is allowed to authorize a run.

PYTHON · Compare three possible pairs
from itertools import combinations

voters = ("R1", "R2", "R3")
first_pair = {"R1", "R2"}

for later_pair in combinations(voters, 2):
    shared = first_pair.intersection(later_pair)
    print(later_pair, "shares", sorted(shared))

This small exercise checks a property of sets. It cannot tell whether a disk flush completed, whether a server voted twice, or whether an old client request was replayed. Those questions belong to the implementation and the tests. For our example, the exercise shows exactly why a later pair has a chance to recover the earlier decision.

What can one voter do on its own?

Now suppose R1 is cut off from both peers. It might still receive requests and it might still think it leads the group. It cannot collect the second durable copy required to commit a new command. An operator connected only to R1 might see a timeout. An operator who can reach the other two may still make progress after they establish leadership. A request reaching a server is only the start of the operation.

If every voter can reach only itself, new decisions wait. Existing Payments traffic might continue elsewhere because this decision service and the application have separate jobs. During the incident, report precisely what is impaired. “We cannot authorize a new failover right now” tells the on-call engineer what to investigate. It also avoids claiming anything about the health of Payments before someone actually checks it.

Remember the arithmetic for a fixed majority group. Three voters need two and can lose one. Five need three and can lose two. Two voters need both, so a two-server decision group cannot lose either and still authorize new work. The two OCI regions in our story describe where Payments runs. They do not tell us how many voters Oracle uses or where those voters live.

How Raft records the failover

Payments needs to move from Ashburn to Phoenix. Two people click Execute. Follow request A from that click to the moment the coordinator can say, “Your execution is DR-42.”

Who gets to put requests in order?

Imagine building the part of a Full Stack DR coordinator that keeps track of Payments failovers. Give it three voting copies called R1, R2, and R3. They hold a small record of decisions. The Payments database holds customer data. Those are different jobs. When R2 votes, no customer rows move and no application server starts. The three voters in this example are a way to learn Raft. Their names and locations are our design choices.

Raft gives one voter the job of ordering requests. That voter becomes the leader. Suppose the voters have lost touch with their previous leader. R1 waits for its election timer, starts a new election, and votes for itself. Call this election round term 7. R1 asks R2 and R3 for their votes. R2 sees that R1 has a sufficiently recent decision history and grants its vote. R1 now has two of the three votes and can act as leader in term 7.

Why check a candidate’s history? Imagine choosing a new coordinator that has forgotten a decision already promised to an operator. It might approve the failover a second time. A Raft voter checks the term of the candidate’s last log entry first. If the terms match, it compares how far the logs extend. It also saves its vote before replying, so a restart will not let it vote for two different candidates in the same term.

Keep two numbers separate as you read. Term 7 tells the three voters which leadership round they are in. Version 17 tells the operators which Payments recovery record they saw. A change of leader can advance the term while the Payments record stays at version 17. An accepted Payments failover can advance the record to version 18 while R1 remains leader in term 7.

Follow request A through three copies

Both operators saw version 17. Request A arrives at R1 first in this example. R1 gives A the next place in its decision history, slot 201. The entry says to start the Phoenix failover if Payments is still at version 17. It includes the proposed execution ID DR-42 so every copy will record the same ID if the request succeeds.

The previous-slot check matters. R1 tells R2 which entry should come immediately before A. R2 compares the slot number and term with its own copy. If they match, the two copies agree on the history leading up to A. If they differ, R2 asks R1, through a failed append response, to try an earlier point. R1 can then supply the missing entries in order. A follower that was offline can catch up this way.

R1 has now saved A and heard that R2 saved it. That is two durable copies of an entry from R1’s current term. R1 can mark slot 201 committed. It applies A to the Payments record, finds version 17, changes it to 18, and records DR-42. Now it can answer the first operator. R2 learns how far the leader has committed in a later message and applies the same command. R3 can catch up after the operator receives a reply.

What the second operator sees

Request B, from the other operator, takes slot 202. It also asks to start the failover from version 17. Once slot 202 is committed, each voter applies it after slot 201. Each finds version 18. Each leaves DR-42 as the one authorized execution. The history can therefore contain both requests even though only one creates work.

Imagine reading these two lines aloud to an incident commander. “Alice’s request to start the Phoenix failover was accepted. Ben’s request referred to the older version, so he should follow DR-42.” Both operators now know what to watch. To find out whether Payments is serving customers, the incident commander still needs execution progress and an application check in Phoenix.

Try pausing the story when R2 saves A but before R2 hears which slots R1 committed. Can R2 tell Ben that DR-42 exists merely from looking at its local log? It still needs to know that slot 201 is committed and apply it to the record. Seeing a proposed command, knowing the command is final, and knowing its application result are three separate moments.

What happens when the leader stops

Alice clicks Execute on the Payments failover from Ashburn to Phoenix. Her browser waits, then shows a timeout. Suppose R1, the Raft leader in our example, has stopped. Is DR-42 already under way?

Two crashes that look the same to Alice

Replay request A and pause it at two different moments. In the first run, R1 saves A in slot 201 and stops before sending it anywhere. R2 and R3 have only the history through slot 200. They can elect a new leader without R1. Their history still says Payments is at version 17. They may later use slot 201 for a different command. The new leader has made no promise to execute the copy of A left on R1.

If Alice sends A again with the same request identity and the same version check, the new leader can consider it. Suppose it arrives before Ben’s competing request B, just as it did in our original run. A can still create DR-42 and move Payments to version 18. The new leader reached that outcome by accepting the retry. A single copy from a crashed leader was never enough evidence to start work.

In the second run, R1 and R2 both save A in term 7 while R1 leads that term. R1 learns that R2 saved it, commits it, applies it, and stops just before Alice receives the reply. Slot 201 is final. Any future Raft leader must keep A there. Alice sees the same timeout as before. This time, starting an independent second failover would duplicate a decision the service already made.

How the next leader learns what is final

Continue the second run. R2 saved A, but R1 stopped before telling R2 that slot 201 had been committed. R3 never received A. R3 asks R2 for a vote. Its history ends earlier in this example, so R2 refuses. When R2 asks R3, R3 can grant the vote. With its own vote and R3’s, R2 wins term 8. The new leader has A in its log, even though it may still need to learn how far that log is safe to apply.

Here is a Raft rule worth remembering. To advance the commit point by counting copies, the leader counts an entry from its own term. Suppose R2 now sends A to R3. R2 sees A on two voters, but A was written in term 7. Seeing two copies today does not tell R2 when those copies were made or whether they ever formed a majority under the term-7 leader. Other election histories can produce the same count for an old entry that was never committed.

R2 can settle this without asking Alice to start anything. It writes a small entry from term 8 immediately after A. Think of it as a bookmark saying “we have reached this point.” This entry makes no change to Payments. Once R2 and R3 both save that term-8 entry, R2 can commit it and every preceding entry in its log. That includes A. R2 can apply the history through the bookmark and give Alice a reliable answer about DR-42.

Notice what R2 recovered. It has the original request, the expected version, and enough history to reconstruct the answer. It still needs information from the execution worker to know which recovery steps have actually run. A new leader should never infer that Phoenix is ready simply because it recovered a record authorizing the failover.

How to answer the operator after a timeout

In our coordinator design, Alice’s client keeps the identity of request A. It can ask the current service about A or resubmit the same request with that identity. The service checks saved request results before it tests the version. That order matters. If A already succeeded, the answer should still name DR-42. Reporting a version conflict to Alice would hide the fact that her own earlier request advanced the version.

Ben’s request B is different. He also saw version 17, but his request identity has no saved success. If A already created DR-42, B reaches its version check and finds 18. Ben can follow the running execution. The difference between Alice and Ben is easy to explain during an incident. Alice is asking again about her original click. Ben is asking to authorize another execution.

Finally, imagine both reachable voters lose touch with each other while R1 is down. Neither can form a majority alone. Alice may have to wait for a reliable answer, and a new decision must wait for a majority. What she can safely record in the incident notes is simple: “We lost contact while starting the Phoenix failover. We are checking DR-42 and the plan execution history before taking another action.”

How Paxos remembers the choice

Suppose two voters have saved request A, but the coordinator crashes before it can tell either operator. Operator B still wants to start the Payments failover to Phoenix. How can a replacement coordinator find out what it can safely do?

A decision with a missing reply

Keep the OCI Full Stack DR example. Payments has its primary in Ashburn and its standby in Phoenix. Two operators submit requests A and B, both based on version 17. For this chapter, imagine building their coordinator using Paxos. We are exploring a design for the exercise. The details about voters and messages describe that design.

Think of the shared log as a book with numbered lines. Earlier lines say that Payments is at version 17. Paxos answers a small question about the next blank line. Which command belongs there? Request A and request B can each ask for that space. Once a command has been chosen for a line, every later coordinator must preserve it.

There are three voters, R1, R2 and R3. In Paxos these voters are called acceptors. The coordinator suggesting a command is the proposer. Each attempt has a unique number called a ballot. A higher ballot gives the next proposer a way to take over. Ballot numbers track attempts to fill a log line. Version 17 tracks the Payments recovery record. The two numbers do different jobs.

The first proposer opens ballot 10. It asks the voters what they have already accepted for this line. R1 and R2 each save a promise to ignore lower ballots and reply that their line is empty. Two replies are enough. The proposer sends them request A under ballot 10. Both save it. A majority has accepted the same proposal, so A is now chosen.

Now the proposer crashes. The console shows a timeout. One operator thinks the click failed. The other is ready to try B. Neither operator saw the reply, but the crash took away only the messenger. The decision is still on two disks.

The replacement asks before it acts

The replacement can reach R2 and R3. It starts ballot 11 for the same line. R3 has never heard of A. R2 replies, “I accepted A in ballot 10.” Both promise to ignore lower ballots. These two replies give the replacement enough information to continue safely, even though R1 is unavailable.

Here is the rule the replacement follows. Among the replies from its majority, it takes the value with the highest accepted ballot for that line. If none of the replies includes a value, it may suggest a new one. Here the only reported value is A, so it must propose A. R2 and R3 save A at ballot 11. The replacement can now announce the result.

Why carry A forward when just one reply mentioned it? R2 cannot tell whether R1 saved A as well. From the replacement’s point of view, the case where only R2 saved A looks exactly like the case where both saved it. Carrying A forward works in both cases. Replacing A with B could erase a decision the earlier majority already made.

Imagine that a delayed message from ballot 10 reaches R3 after its ballot 11 promise. R3 turns the old message down. A crash and restart must preserve that promise. Otherwise, an old message could appear fresh to the restarted voter. Saving the promise before replying is a small step with an important consequence for Payments.

From one log entry to DR-42

When replicas apply A, each sees version 17 and records version 18 with execution DR-42. The execution ID belongs to the shared decision, so all replicas use the same ID. Request B can still appear on a later line. When replicas apply it, they see version 18. B asked to start from version 17, so it cannot create another execution.

In a system with many log entries, a stable proposer can often do the initial ballot work for many lines and then send new proposals as requests arrive. This approach is commonly called Multi-Paxos. Each line still needs its own decision. If the proposer changes, its successor must check for earlier accepted values in the lines it will fill.

If you are on call, the practical conclusion is straightforward. The missing reply leaves the client uncertain. It does not undo the work already recorded by the voters. Look for the original execution before making another request. Finding DR-42 answers “Did we authorize the failover?” Its progress and the application checks in Phoenix answer “Has Payments recovered?”

How to read and preserve the decision

The first operator has an execution ID, DR-42. A second operator refreshes the Payments page and sees version 17 with no execution. Before anyone clicks again, we need to know what that page actually read.

A status page can fall behind

Return to the three-voter Raft example. R1 and R2 recorded the decision for Payments. Request A created DR-42 and advanced the recovery record from version 17 to 18. R3 lost its connection before it received the entry. A status page that reads directly from R3 can still show “ready to start.” R3 is faithfully showing what it knows. Its information is old.

For a trend chart, showing the last sample with its timestamp may be fine. For an operator deciding whether to start a failover, that answer could be costly. If the service offers a current read, a read started after the first operator received success must include that change or a later one. Engineers call this guarantee linearizability. Two operators do not have to compare their clocks to use it.

One way a Raft leader serves that read is to first commit an entry from its current term. For the read, it records the committed log position it needs and exchanges fresh messages with a majority to confirm it still has authority. It then waits until its own copy of the Payments record has applied entries through that position. Only then does it answer. The last wait matters. A server can have the decision saved in its log while the record used by its status page still says 17.

Suppose the old leader can still answer the operator’s HTTP request but cannot reach another voter. A current read through the method above may have to wait or fail. An honest “current status unavailable” is actionable. The operator can keep the execution ID and check again. An empty execution list presented as current would encourage a duplicate start.

What a snapshot must remember

Months later, the log has grown. To speed up restarts, a replica saves a snapshot. Picture a saved copy of the records after applying a known log entry. A restart can load that copy and replay what came later. This snapshot belongs to our example coordinator. It serves a different purpose from a backup of the Payments database.

For example, take the snapshot just after A was applied. It must capture version 18 and DR-42 together. It should also include the saved result for request A if the service allows clients to retry that request and look up its result. Store the log position and term covered by the snapshot and the applicable voter configuration. Those details let the replica connect the saved state to the right place in its history.

Try the restart on paper. Load the snapshot, then apply request B from the next entry. B still expects version 17 and sees version 18. It cannot start another execution. Now imagine saving only version 18 and dropping the link to DR-42. B is still refused, but the first operator can no longer find the execution through the saved request. A backup can preserve a number and still lose a promise made to a person.

Replace one voter safely

R3 needs a replacement after a disk failure. R1 and R2 are healthy. In our design, a fresh machine joins first as a learner. It receives a snapshot and subsequent log entries. While it catches up, it has no vote. Giving a blank machine a vote too early makes it easier to lose availability during the repair.

For a Raft design using joint consensus, the old voting group and the proposed voting group overlap during a planned transition. The protocol temporarily requires a majority from each group. Once that transition has been committed, the leader can record the final voting group. The old voter then leaves. Simply editing three local configuration files would give each machine a different answer to “Who can vote today?”

A voter replacement changes who stores the coordinator’s decisions. It does not change where the Payments application runs. During this repair, DR-42 still refers to the failover from Ashburn to Phoenix. The operator should be able to find the same execution after the replacement catches up.

When the records disagree

If only R3 survives and it shows version 17, it cannot tell whether R1 and R2 already chose A. Assigning R3 two new empty partners would give three machines the same stale view. First aim to recover a quorum with its saved history. If that history is permanently lost, recovery requires an explicit operational decision. Keep the old group from resuming independently and reconcile the surviving records with the actual state of Payments in both regions.

Ask two separate questions during that review. “What is the latest decision we can prove?” directs you to the log, snapshot and execution records. “Where can Payments safely accept writes?” directs you to the database role, the old writer and the traffic path. Both answers matter before an operator can declare recovery complete.

SD-001 · Distributed Systems Foundations · 07

From one decision to a working application

The recovery record now points to DR-42. Payments still needs a writable database, healthy servers, and a route that brings customers to Phoenix. Who does each job?

Draw the path from the console to a customer

Start with the view from the Phoenix standby DR Protection Group. The operator selects the Payments failover plan. A plan describes the work to do. A plan execution tracks one run of that work. You can prepare a plan well before an outage. During the outage you need to know which execution is handling this particular recovery.

In our design exercise, the three voters R1, R2, and R3 keep the decision record. Request A asked to start at version 17. The accepted change creates DR-42 and advances the record to version 18. Request B also expected version 17, so it cannot create another execution. The voter names, versions, and short execution ID are teaching labels. Oracle documents protection groups, plans, executions, groups, and steps. They are the parts an OCI operator can work with.

Put dependent work in the right order

Suppose your Payments servers need a writable database before they can accept orders. Starting every server quickly sounds helpful. But if those servers point to the wrong database, a green process light tells you very little. First establish which database may receive writes. Then configure the application to use it, start the application, and test it. Only move customer traffic when the runbook’s readiness conditions are met.

OCI Full Stack DR runs plan groups in sequence. Steps within a group run in parallel. Imagine that Payments has two independent application servers in Phoenix. They can start in one group once their shared database is ready. Putting the database promotion and both application starts in that same group would allow all three to start together. A dependency should be visible in the group order, instead of relying on a server usually taking longer to boot.

The actual groups depend on the resources and plan you configure. Review which tasks the generated plan covers and where Payments needs a custom step. For example, an application-specific check might open the normal Payments endpoint and look up a known test order. A plan precheck can catch configuration problems before execution. The application check asks a later question that matters to customers: can this running copy of Payments do its job?

Recover a worker that loses its reply

Follow one step inside DR-42. A worker sends a request to change the database role. The database service receives it, but the worker loses its connection before it can save the answer. The next worker sees an unfinished step. Should it send the same command immediately? First it needs to find out what the first worker did.

In a design where the downstream service supports a request key, save a stable key for the step before making the call. For example, DR-42/database-promotion identifies this one intended change. If a reply gets lost, look up the existing operation when the service supports that lookup. If retrying with the same key is supported, use it within its documented time window. Each downstream API has its own contract. Check that contract before assuming another call is safe.

If the API supplies neither guarantee, inspect the database role and operation history. A database already writable in Phoenix may be evidence that the change took effect. Confirm the database identity and that it is the intended writer. If the evidence is incomplete, pause the step for investigation. Guessing can turn a missing reply into a second real action.

Check the whole path before declaring recovery

Imagine the dashboard now shows the database and both servers are ready. One final check fails. The public Payments address still routes to Ashburn. Customers still see an error, even though all three Phoenix machines look healthy. Check from the customer side of the routing boundary. A direct request to a Phoenix server bypasses the very part that failed.

The opposite failure also matters. Phoenix answers correctly, but an isolated copy of Payments in Ashburn can still accept writes. Losing contact with Ashburn does not prove it has stopped. The recovery design needs a database or storage mechanism that prevents the old side from accepting conflicting writes. Identify that mechanism with the database owner and test what happens when Ashburn reconnects. An execution ID by itself cannot turn off an old writer.

For the incident handoff, write down three facts. Which execution authorized the change? What proves Phoenix can serve Payments? What prevents Ashburn from accepting conflicting writes? A colleague who can answer all three can explain the recovery from the operator’s first click to the customer’s next request.

SD-001 · Distributed Systems Foundations · 08

Running the failover during an outage

At 09:00, the Payments monitor loses contact with Ashburn. What do you watch first? Use the time of each event to find where the recovery is actually waiting.

Read one incident timeline

These times are made up for practice. Think of them as entries in the incident notes. At 09:00, the alarm sounds. At 09:01, an operator starts the Phoenix failover. A moment later the decision record shows execution DR-42. At 09:04, Phoenix reports that the Payments database can accept writes. At 09:06, the first check through the ordinary customer endpoint succeeds.

The six minutes cover several different waits. One minute passed before anyone started the plan. The decision to start took a small part of the next minute. Most of the remaining time went into changing the database role, preparing the application, and reaching it through the customer route. If the team wants quicker recovery, measuring only the time for two voters to agree will point them at the wrong place.

Tell a slow voter from a stuck plan step

Suppose R1 is leader in our teaching model. R1 saves a new entry locally and sends it to R2 and R3. R2 saves it and replies quickly. R3 is slow. For a new entry in the leader’s current term, R1 and R2 make the necessary majority. Waiting for all three would add a delay that this decision does not require. R3 can catch up later.

Now imagine R2 becomes unreachable while R3 is still slow. R1 has to wait for R3 to save and acknowledge the entry. The same slow disk or long network trip now matters. Look for a change in which voters are reachable, as well as how long each takes to save an entry. These are signals an engineer might expose in a coordinator they own. An OCI customer can instead start with the execution details that the service exposes.

Say DR-42 already exists and its database step has been running for three minutes. That observation tells you more than a general message that failover is slow. Inspect the active step and the target resource. A second operator clicking Execute cannot shorten the database role change. If a failed step needs attention, open that execution, inspect the reported failure, and correct its cause before considering a retry.

Practice choosing an honest status message

You are updating the incident channel. The message should tell people what succeeded and what is still being checked. Suppose the plan succeeded but the customer check has no result yet. “Payments is back” would send the support team away too soon. The short Python example gives different messages for those two observations. Its input strings are local labels for the exercise.

Run the example once. Then change the last argument in the call from “unknown” to “passed” and print the result instead of running the assertion. You should get a different message without changing the plan state. That is why the dashboard should show both pieces of evidence.

PYTHON · practice model
def recovery_message(plan_state, customer_check):
    if plan_state == "failed":
        return "Inspect the failed step in DR-42."
    if plan_state != "succeeded":
        return "Follow DR-42. Recovery is still in progress."
    if customer_check != "passed":
        return "Plan complete. Payments still needs verification."
    return "Payments passed the customer check in Phoenix."

What should the customer check actually do? A simple homepage might come from a cache even when the database is unavailable. Use a safe check agreed with the Payments team, such as reading a known test order through the normal endpoint. If the recovery promise includes accepting new writes, also use an approved test transaction that proves the write path works. Keep real customer charges out of the test.

Handle a failed step without losing the story

Suppose the Phoenix application step fails because its configured database address still points to Ashburn. First record the execution ID, failed step, and error. Check which earlier groups finished. A successful database promotion is an important fact to preserve. Starting from the beginning could repeat work that already changed the environment.

Update the incorrect setting through the approved procedure. Before retrying, inspect the application and its dependencies so you know whether the first attempt did anything useful. OCI Full Stack DR supports retrying a failed step in an execution. Use the recovery action appropriate to that step and its effects. Follow DR-42 as it progresses, and rerun the Payments checks when the application is ready.

Afterward, ask what would have shortened this particular outage. A rehearsal using the same Phoenix configuration could have exposed the wrong address. An earlier customer-path test could have revealed a routing error sooner. More voters would solve neither problem. Keep the incident notes specific enough to distinguish a slow decision, a slow resource change, and a healthy resource behind the wrong route.

Interview practice with the Payments failover

In these original practice questions, Payments usually runs in Ashburn. Phoenix is its standby. Two operators try to start the same failover. Answer each question out loud before opening the answer.

Two operators and one plan

1. Why does it matter if both operators chose Phoenix?

Imagine both callers get a different execution ID. One operator sees a failed step and pauses their execution. Meanwhile, the other execution continues and moves traffic. Who is actually in control? In our design, one Payments recovery attempt has one execution record. Both operators can find that record and make decisions from the same history.

2. Could we pick the click with the earliest timestamp?

A clicked first on one screen. B’s request reached the service first through a faster connection. The two requests overlapped, so either order could be safe. What matters is that all copies use the same order. In our example A wins. If A already received success before B clicked, the service must respect that completed decision.

3. Why do we need version 17 if Raft already orders the requests?

Ordering tells each copy to process A and then B. The version check tells it what to do with B. A sees version 17, starts DR-42 and changes the record to 18. B expects 17 and finds 18. Without the check or an equivalent rule, both copies could faithfully follow the same order and still start two executions.

4. What if A loses the reply and clicks again?

A timeout tells us the operator stopped waiting. The service may already have created DR-42. Give the original request a stable ID and keep its outcome. The caller can look it up or retry with the same ID under that agreement. Check the stored result before testing the old version again, so A gets the result of A’s first attempt.

What the voting rules buy us

5. Why use two votes when we have three copies?

Write down two possible majorities. R1 and R2 can form one. R2 and R3 can form another. R2 belongs to both. That overlap gives the next group a way to find evidence from the first. The protocol also needs rules for saving that evidence and following it after a restart. Counting replies alone cannot do that.

6. R1 sees the outage but cannot reach R2 or R3. Should it approve the request?

R1 cannot tell whether the other two stopped or whether only its own connection broke. R2 and R3 might still be working together. Letting R1 authorize a failover by itself would give two separate groups authority. R1 waits. If R2 and R3 can communicate and satisfy the protocol, they can still make progress.

7. The Raft leader crashes after it replies to A. What must its replacement preserve?

The replacement must keep the committed command that created DR-42. Raft limits who can win an election based on the candidates’ logs. A replacement catches up on committed work, applies it, and can then serve a fresh lookup. An operator may wait during the election, but a successful reply must still mean something after the wait.

8. How would Paxos protect A’s choice if a reply went missing?

Suppose R1 and R2 both accepted A for the same log position in the same round. A is chosen there even if no one saw both replies. A new proposer asks a majority about earlier rounds. It must carry forward the value with the highest accepted round those replies report. Following this rule keeps the chosen value safe.

When the record meets the real application

9. Phoenix shows an old status. Is it safe to click Execute again?

A copied status screen may be behind. Check the authoritative execution history for Payments. If your design promises a current read, the server must establish that it still has authority and has applied the required committed entries. Waiting for that read costs time, but it prevents an old “ready” screen from becoming permission to start another run.

10. Does a decision to start DR-42 guarantee that Payments works in Phoenix?

DR-42 tells us the failover was authorized. The database, application and traffic path each still have work to do. Ask for the plan step results, then send an approved test request through the normal Payments entry point. A process can be running in Phoenix while clients still reach the old endpoint.

11. What if a worker restarts after it sent a database request?

Read the saved step record for DR-42. The worker might have sent the call before it stopped. Reconcile the database role and any recorded operation ID. A service that supports a stable retry key can recognize a repeat. If the outcome is still uncertain, pause the step for review before repeating a change with real effects.

12. How would you check that Ashburn can no longer accept writes?

Ask which component actually accepts a Payments write. A healthy-looking Phoenix console cannot answer for a disconnected writer in Ashburn. The design needs an enforcement mechanism at the write path, such as a database role transition with documented protections. Verify what that mechanism guarantees during a partition before declaring it safe to reopen writes.

Walk through the incident yourself

Keep a pencil handy. For each drill, write down one fact you know and one fact you still need. Use the same Payments failover from the first chapter all the way through.

Say it in thirty seconds

“Payments normally runs in Ashburn. When Ashburn becomes unreachable, two operators ask to start the Phoenix failover. In our design, three copies keep the recovery record. They agree to process A before B. A starts execution DR-42 and changes the record from version 17 to 18. B expected 17, so it cannot start a second run. Both operators can follow DR-42. We still have to verify that Payments actually works in Phoenix.”

Now say it again without using the words Raft, Paxos or quorum. Imagine you are speaking to the person handling customer calls. They need to know whether there is one recovery in progress, where to see its progress, and what evidence will let them tell customers that service has returned.

Drill 1 · Cover one voter

Draw three circles on paper and call them R1, R2 and R3. These are imaginary copies of the decision record. Ashburn and Phoenix tell you where Payments runs. The circles tell you who records the decision. Keep those labels separate, because knowing which application region is down does not tell you exactly which voters can communicate.

Cover R3 with your hand. Can R1 and R2 still record A? Now uncover R3 and cover R2 as well as R3. What changed for R1?

Reveal the answer

With R1 and R2 connected, there are two voters available. A Raft leader among them can commit a new entry from its current term after both have stored it. With only R1 available, R1 can record what it observed, but it lacks the votes to commit a new failover command. Check connectivity before assuming a machine needs replacement.

Drill 2 · Lose the answer

The console times out just after A clicks Execute. B says, “My screen still shows version 17. I can try it from here.” Decide what you would ask B to do. Then run the exercise again with an extra fact: an authorized, up-to-date lookup finds DR-42 and shows that it belongs to A.

Reveal the answer

First ask B to check the execution history for Payments. A timeout and an old screen leave several possibilities open. After the lookup finds DR-42, both operators can follow it. If A retries using the same request ID in this design, the stored result points back to DR-42. B’s distinct request still carries expected version 17, so it fails the check against 18.

Drill 3 · Read the incident board

Cover the last column. At each point, decide what you would tell the incident commander. Use the narrowest claim the evidence supports.

Now add a fourth observation. A Phoenix server answers its local health check, yet the normal customer endpoint still times out. Which team would you involve first?

Reveal the answer

Follow the path between the customer endpoint and the healthy server. Check where that endpoint sends traffic and whether the intended backends are reachable. The successful local check gives you a place to start. Repeating the whole failover would change several things at once and make the original fault harder to see.

Drill 4 · Give the handoff

You are leaving the incident call. The next operator sees version 18 and a completed database step. The Payments test is still pending. Write a handoff short enough to read on a phone. Include what was authorized, what has finished and who owns the next check.

Read one possible handoff

“Payments failover from Ashburn to Phoenix is running under DR-42. The database step finished. We are keeping the incident open while the application owner checks the normal customer endpoint. Follow DR-42 for progress. If you see a different execution ID, bring it to the incident call before taking action.”

Finally, ask the next operator to explain what would change their answer. A failed test calls for diagnosis. A successful test gives evidence about the path exercised. Confirmation that the old writer is fenced and the remaining recovery checks are complete can support a return-to-service decision. Each update should tell a customer or teammate something they can safely act on.
