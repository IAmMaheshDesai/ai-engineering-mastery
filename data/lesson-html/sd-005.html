SD-005 · Distributed Systems Foundations · 01

What exactly gets bigger when you add a machine?

A model registry times out on deployment day. The SRE team proposes doubling its replicas. The storage team proposes splitting it into shards. Each proposal can be right for a different saturated resource.

Worked example 1 · A misleading average

Imagine a registry with one primary database and two asynchronously updated followers. Each node can execute roughly 6,000 of the benchmark's point reads per second when it has spare CPU. The service receives 9,000 reads and 1,500 writes each second. Most reads go to the followers. Each write changes a model revision and updates three indexes at the primary. Followers must replay the resulting changes. The primary's storage flush latency spikes while read replicas have spare query capacity. Adding a third read replica could reduce queueing on the first two followers; it cannot divide the primary's stream of ordered writes among three independent primaries. It can even add outbound replication work at the source.

First ask what a replica copies. In this example each copy holds the same logical data at some execution position. A read replica can serve many reads because the work of evaluating one query need not be repeated at all replicas. A replicated write, by contrast, eventually needs some representation on every copy promised by the system. The units of storage and recovery increase with replica count. The number of independently writable partitions is unchanged. If your bottleneck is the global write stream or the capacity of one volume, adding copies may leave the constraining dimension untouched.

Now divide the registry into four horizontal partitions by model identity. Each holds a disjoint subset of records and has its own replicated write stream. A client resolves the model ID to one partition and writes only there. All four leaders can process independent changes concurrently if CPU, storage and failure domains permit. Splitting the data does introduce new work. A query asking for the most recently updated model across all tenants may now need multiple partitions, a separate index or a materialized view. A transaction that moves ownership across two partitions can require a coordination protocol. Before proposing sharding, label the operations that lose locality and decide who pays that cost.

The third operation people call scaling out is moving an existing partition between machines. Its logical key range can stay exactly the same. You are changing physical placement to balance load or replace hardware. A fourth operation splits an existing partition into smaller independently routable pieces. You may split without moving any bytes immediately if both new pieces still reside on the same storage engine. Only later might one piece migrate to another node. Distinguishing a change of boundaries from a change of owners makes failures easier to describe. If a move fails, clients still need a valid answer about who owns each key.

State the contract before the topology

In a recovery control plane I would begin with a short list of invariants. A model revision acknowledged to a client must survive the stated failure. An authoritative routing update must have one order per model. A reader must either receive the promised freshness or receive a meaningful error. A retry must resolve the fate of its original command across a move. A placement change cannot make two independent histories authoritative for the same key. These are testable properties. Four shards with three replicas each is just a topology until you explain which promise each choice supports.

Suppose a noisy tenant submits training artifacts to every model within its own registry. You can partition by model ID, group by tenant, or split especially hot tenants separately. The business API matters. If a transaction must atomically enforce a single tenant quota on every new revision, distributing models without addressing that quota creates a shared serial resource. Options include a transactional quota service, bounded per-shard reservations or a deliberately approximate quota with explicit overage semantics. Moving rows around cannot by itself parallelize a truly global invariant. Draw the shared invariant alongside the shard map before claiming a throughput improvement.

How I would explain this in an interview

I would ask which path saturates first and measure it with representative operations. Replication gives additional copies and may buy read capacity or failure tolerance. Sharding gives independent units of data and ordering. Rebalancing changes their assignment as demand or hardware changes. I would spend my first design minute mapping customer operations and invariants onto those units. Then I can explain whether another machine adds useful capacity, another copy of the same bottleneck, or new work on the migration path.

SD-005 · Distributed Systems Foundations · 02

Replication transfers both bytes and obligations

A replica can possess a log record, know it is committed, apply it to its local index and serve it to a user at four different moments. Your API must decide which moment counts.

Worked example 2 · Three acknowledgments that mean different things

A client publishes revision 104 of model Aspen. The primary appends the change to its local write-ahead log. Follower East has received it in a network buffer, follower West has flushed it to stable storage, and neither has yet applied the record to its queryable index. If the primary replies after a local durable write alone, a failure that destroys the primary before the other copies become durable may lose an acknowledged publication. If the system's specified consensus protocol commits on a durable majority, the primary can rely on a qualifying local copy and West's durable copy under that protocol's leadership and log rules. East's network receipt is weaker evidence. A bare count of acknowledgments without terms, membership and durability semantics does not prove consensus.

The application may still distinguish committed from applied. If a caller receives success and immediately reads from East, that follower could return revision 103. Returning a commit token lets the next request require an applied position sufficient for its own preceding write. The follower can wait, forward the read or return a deadline error. This provides a useful session guarantee for related operations, but does not automatically make all reads globally linearizable. Another client could have completed a still later update unknown to East. For a strong current read use the store's authoritative read mechanism and satisfy its apply barrier.

Consider an asynchronous standby in a remote region. A dashboard reports replica lag of two seconds. Ask what clock produced the number. Is it a timestamp on the last received commit, a difference between source and destination positions converted with a sampled rate, or the age of the last heartbeat observed locally? During idle periods these measurements can tell different stories. Measure byte backlog, last applied source position and age of an end-to-end marker. A zero-byte backlog observed before a new write is not proof that an acknowledgment made later has crossed regions. A recovery operator needs the exact watermark of the latest recoverable data, including referenced objects kept elsewhere.

Synchronous, asynchronous and application-level reconstruction

Under synchronous replication, define exactly which remote action sits on the success path. Waiting for a remote flush provides a different read guarantee from waiting for remote application. The success latency depends on the required subset and its network and storage delays. In the three-copy example, losing the fast follower may put the slower one on the critical path. Under asynchronous replication the primary may acknowledge before the standby has received the change. This often protects foreground latency, while the window of acknowledged data loss after source destruction depends on the outstanding changes and promotion policy.

For some AI workloads the state is reconstructible. A serving KV cache can often be recomputed from inputs and model state under an appropriate application contract. Losing its placement might increase latency or recomputation cost without losing the customer's durable conversation. A model registry pointer with acknowledged ownership history has a different role. Reconstructing it by scanning object storage might discover uncommitted uploads and omit intentional deletions. State explicitly what is authoritative and what can be rebuilt. A cost-effective system may replicate the authoritative pointer more strongly than it replicates expensive but recoverable cache entries.

A leaderless store permits a different set of tradeoffs. Multiple replicas may accept writes, and replicas or clients reconcile concurrent versions according to a defined policy. This flexibility can improve write availability, yet a last-writer-wins timestamp policy may discard one of two valid business actions. Counting a write quorum and a read quorum with an intersection is informative only with assumptions about the exact replica set, version comparison, failure handling and read protocol. Be wary of claiming linearizability merely because two integers sum to more than the replication factor. Describe a concurrent execution and show the precise legal answer.

Operate the failure budget

Make the committed, received and applied watermarks observable at each destination. Keep source retention long enough for the expected interruption and catch-up time. A slow follower that falls behind compaction may need a snapshot, so its recovery suddenly competes for disk and network capacity with foreground traffic. Test the transition from log replay to snapshot reinstall. Include client retries during the change. If everything is sized for quiet replicas, the system can look healthy until the very first fault and then exhaust the capacity needed to repair itself.

SD-005 · Distributed Systems Foundations · 03

Key design determines where contention lives

A uniform distribution of rows can coexist with a spectacularly uneven distribution of work. Choose a partition key from the real access pattern, then ask how it behaves during the busiest minute of the busiest tenant.

Worked example 3 · The popular model defeats the hash

One million model IDs are hashed over 128 virtual buckets. Ninety-nine percent of those models are rarely touched. One popular shared model accounts for 30,000 pointer reads per second and 2,000 conflicting pointer updates per second. A perfect hash of distinct IDs still sends every operation for that model to the same bucket. Splitting the bucket into two ranges can move unrelated neighbors away, but the hot logical key remains indivisible as long as every request addresses the same value with the same ordering requirements. Spreading 999,999 other IDs evenly solves a different problem.

Separate the workload into operations that require an authoritative mutation and operations that can be distributed. Immutable model versions can be cached widely by digest. Reads of a mutable active-version pointer may use a cache if its freshness contract admits a bounded delay or version check. Several updates to ephemeral progress might be coalesced when later values subsume earlier ones. Unique allocation grants cannot be silently discarded or reordered that way. If sustained writes genuinely require one total order for one key, choose a tested single-key capacity, reduce work per transition or change the product contract. Salting a key and selecting the latest wall-clock value afterward creates a different service.

A range layout groups consecutive keys in an ordered keyspace. It works well when requests regularly scan nearby records. A poor range design places increasing timestamps first in the key, sending nearly every new insertion into the final range. Splitting yesterday's cold ranges increases the partition count while today's writes still hammer the moving right edge. A time bucket plus a bounded hash prefix can distribute current writes across several partitions. A range query over that period must then gather several ordered streams and merge results. The cost scales with the number of stripes, the requested result size and each stream's ability to stop early.

Suppose you need the newest 50 experiment records in one tenant. With eight write stripes and an index ordered by descending timestamp within each stripe, fetching at most 50 candidates per stripe is sufficient under a consistent snapshot and a deterministic global order. Merging up to 400 candidate records finds the global top 50. If pages are independently read while new events arrive, stable pagination requires a snapshot or an appropriate continuation contract. A tie on timestamps needs a unique secondary ordering key. Record any per-stripe cursors needed to resume safely. This is the kind of hidden read-path cost a partitioning decision imports.

Choosing between hash, range and an explicit directory

Hash partitioning is convenient for equality lookups. Consecutive business identifiers may land far apart, spreading independent work while making range scans expansive. Ordered range partitioning preserves locality and makes splits along meaningful bounds possible. A directory mapping tenant IDs to cells makes special placement and isolation easier at the cost of maintaining a highly reliable directory. Many systems combine them. For example, a tenant directory could pick a home cell while a stable hash of experiment ID picks a logical bucket within that cell. Keep both levels explicit when reasoning about migration or offboarding.

The encoding is part of the contract. If one client includes the tenant namespace in its hash and another hashes only the model ID, they may disagree about the destination while both believe their code is correct. Pin the canonical serialization, hash algorithm, version, case normalization and treatment of missing fields. Define half-open range boundaries so a split key belongs to exactly one child. Persist routing fixtures covering boundary keys, unusual encodings and renamed objects. Avoid process-randomized language hashes for durable placement. The same representative keys should map to the same logical bucket after a process restart in a different language runtime.

Use workload evidence to defend the cut

Count distinct keys, bytes, requests, read and write CPU, index amplification and network egress at the same level of granularity. A cheap point lookup and an expensive vector index update are two requests with very different resource footprints. Evaluate a candidate scheme against real or representative hot intervals, including tenant-specific bursts and recovery traffic. A design that balances bytes today may be entirely suitable for a cold archive and disastrous for a real-time control plane. In an interview, offer one counterexample that defeats your chosen key and say exactly what you would measure before changing it.

SD-005 · Distributed Systems Foundations · 04

Logical buckets decouple routing from machine count

A new server should receive a deliberate share of data. Computing a node number directly from the number of current machines can turn a small capacity increase into a fleet-wide rewrite.

Worked example 4 · Growing four nodes to five

Consider nonnegative integer hash values distributed uniformly over residues zero through nineteen. Under the old rule a key goes to the node given by its hash modulo four. Under the new rule it goes to its hash modulo five. Label the common nodes zero through three and the new node four. The mapping is unchanged for residues zero, one, two and three. For the other sixteen residues, the node changes. Uniform traffic therefore sees about eighty percent of keys remapped even though only twenty percent would need to end up on the new equal-capacity node in an ideally balanced final layout.

The discrepancy comes from combining the logical partition function and physical assignment in one formula. Fix the logical keyspace at, say, 1,024 buckets and keep an authoritative table mapping each bucket to a replica group. A new machine can take a chosen subset of those buckets without changing the hash of any key. If a single bucket is huge or hot, you still have a granularity problem; a directory entry is not an infinitely divisible unit. Choose enough units for flexibility without creating unreasonable amounts of metadata, replication overhead and scheduling work. A million tiny groups with independent leadership have a different cost from a million logical buckets packed into a small set of groups.

A consistent hash ring maps a key to a token position and assigns the interval to a responsible owner under a stated traversal convention. Adding a token changes a bounded neighborhood of the ring instead of recomputing every key's destination. Multiple virtual tokens per physical node can smooth placement and facilitate movement. A deterministic ring on paper does not itself transfer the bytes, exclude old writers or achieve uniform request load. During a membership change, clients with different ring versions may compute different owners. A handoff protocol still has to explain how each request is accepted, redirected or reconciled.

Replica placement is a constrained assignment

Each owned range may have several copies. If successive ring tokens all belong to the same underlying server, placing a replica at each token creates a fiction of redundancy. Select distinct physical nodes and, where the failure model requires it, distinct racks, zones or regions. Also consider capacity headroom, network paths, storage classes and which tenants may share hardware. Some constraints are hard, such as a residency policy. Others are objectives, such as minimizing bytes moved. A planner should report when the hard constraints make a desired assignment impossible instead of quietly producing an apparently balanced but unsafe layout.

Imagine three zones with storage capacities proportional to two, two and one. If every shard must have exactly one full copy in each zone, the smallest zone caps usable logical capacity unless the layout or hardware changes. Averaging total free disk across zones overestimates what the placement rules can actually use. A replica movement intended to relieve a full disk must not temporarily remove the only qualifying copy in a required failure domain. Check the transition and the final placement. A system can be safe before and after an abrupt reconfiguration yet vulnerable during the intermediate copy and deletion sequence.

def retained_residues(old_count, new_count):
    from math import lcm
    period = lcm(old_count, new_count)
    return [h for h in range(period)
            if h % old_count == h % new_count]

assert retained_residues(4, 5) == [0, 1, 2, 3]
assert len(retained_residues(3, 4)) == 3

Keep routing available without making caches authoritative

Routers cache directory revisions to avoid a central lookup on each request. Requests should carry the logical key, expected assignment generation and command identity. The serving group validates its ownership on the authoritative write path and can return a structured redirect or a stale-generation result. A client refreshes its map and retries under bounded backoff. It must not blindly follow an untrusted redirect across tenant boundaries. Keep ownership enforcement independent of cache TTL; a delayed process may hold a stale entry far beyond the configured lifetime. Directory cache accuracy improves performance. It cannot serve as the sole proof of exclusive authority.

SD-005 · Distributed Systems Foundations · 05

Copy a changing partition without losing a write

A byte-for-byte copy of a source that changes while you scan it is not necessarily a consistent snapshot. A usable migration establishes a base image, an ordered delta and a precise cutover boundary.

Worked example 5 · Start at a snapshot, end at a fence

Source group S owns bucket 51 at assignment generation 7. The destination group T can accept private migration writes but must reject ordinary customer mutations for this bucket. S creates a consistent snapshot at log position 500. The migration job records its identity, source lineage, bucket predicate and snapshot position durably. It also ensures the change stream after 500 will remain available until the destination has consumed it. An image from one instant combined with changes starting from an unrelated wall-clock timestamp leaves a gap or overlaps that are difficult to interpret. The snapshot and stream must refer to the same ordered source history.

While the image is copied, client Alice updates model A at 501, client Ben deletes model B at 502 and client Chen creates model C at 503. T stages the snapshot privately and applies or buffers those changes under a defined ordering scheme. An implementation might load the complete image first and then replay changes after 500. A more incremental implementation can mix copying and replay but needs a protocol preventing an old copied row from overwriting a newer applied change. For example, an old snapshot row for B arriving after its deletion could resurrect B. Include deletes, secondary representations and request-outcome records in the migration contract.

When T reports applied through 503, S may already have accepted 504 through 510. Progress is good, yet ordinary writes cannot switch safely merely because monitoring rounded the lag down to zero seconds. Establish a short write barrier at S that serializes with customer mutations and persists the point after the last accepted source write. Say that boundary is position 512. In the example S is now fenced against fresh writes for this bucket. If clients present generation 7 after the barrier, S rejects them or points them to a retry path; S cannot grant a late successful mutation into an abandoned history.

T must demonstrate that its snapshot and change application cover the fenced source position. A single high seen position of 512 is insufficient if 509 is missing; the watermark must mean a complete relevant prefix with sound handling of filtered and committed transactions. Once the state is durably present under T's recovery contract, the authoritative directory may install generation 8 with T as new owner under the designed handoff. Before serving, T confirms its activation state and validates each request generation. There can be a deliberately bounded interval when neither side serves writes. Preserving exclusive authority is easier when the protocol tolerates this explicit interruption.

Size the migration window

Suppose a range contains 120 GiB and the copy sustains 80 MiB per second of useful payload. Ignoring compression and overhead, the minimum copy time is 1,536 seconds. If the source produces 6 MiB of retained relevant changes per second during the copy, about 9,216 MiB, or 9 GiB, accumulates. After the copy, T can apply at 18 MiB per second while new changes continue at six. The net drain is twelve MiB per second and catch-up takes about 768 more seconds under steady rates. The hypothetical total is already 38.4 minutes before validation, barriers and operational delays. The customer-visible pause need not equal the entire transfer time.

If the incoming rate rises to 20 while replay stays at 18, the backlog grows. More patience cannot make this migration converge while rates remain constant. Add bounded replay capacity, reduce the moved scope, defer the transfer, or limit incoming writes under an explicit admission policy. Compression may reduce network bytes but cost CPU that replay needs. Compaction may free space while worsening tail latency. Measure source read pressure, captured stream retention, destination replay and both platforms' service objectives together. A move that drains its backlog by overwhelming production queries is not a successful online migration.

PYTHON · executable model
from math import ceil

def drain_seconds(backlog_mib, apply_rate, incoming_rate):
    # Rates are MiB/s and represent a steady-state approximation.
    if min(backlog_mib, apply_rate, incoming_rate) < 0:
        raise ValueError("negative work or rate")
    if backlog_mib == 0:
        return 0
    if apply_rate <= incoming_rate:
        return None
    return ceil(backlog_mib / (apply_rate - incoming_rate))

assert drain_seconds(9216, 18, 6) == 768
assert drain_seconds(9216, 18, 20) is None

Recover every ambiguous phase

Persist the phase and concrete evidence of completed operations under a stable migration identifier. Retrying the same snapshot upload must not create a second competing ownership transition. If the worker dies after fencing S, a replacement inspects S's durable barrier, T's watermark and the authoritative directory. If the directory still names S and T has never been authorized, the procedure may complete forward or allow a carefully coordinated rollback with a fresh generation. If T has already accepted a write at generation 8, simply reopening S at generation 7 would create divergent histories. The recovery decision depends on the last possible user-visible write, not the last coordinator log message.

During migration keep source and target checksums comparable at the same snapshot or logical revision. Comparing counts on a live source with counts on a target a few commits behind can create false alarms. Equal row counts also miss swaps, wrong values and missing deduplication results. Reconcile representative key ranges by ordered digest of canonical records, check invariants and replay read-only shadow traffic with well-defined comparison rules. Document which data types, defaults, collations and indexes may legitimately have different physical encodings. A checksum validates its defined representation. It cannot prove that every future query will use the right authorization policy or consistent routing metadata.

SD-005 · Distributed Systems Foundations · 06

Balance several scarce resources at once

A database node can have half-empty disks and still be unable to accept another shard. A useful placement planner produces a feasible sequence of moves, not merely an attractive final spreadsheet.

Worked example 6 · The move that looks perfect on disk

Node Alpha has 80 GiB occupied and runs at 88 percent of its safe CPU budget. Node Beta has 55 GiB and runs at 81 percent. Node Gamma has 65 GiB and runs at 35 percent. Your objective is to reduce the maximum CPU pressure without moving two replicas of the same group into the same failure domain. Alpha has a 20 GiB shard responsible for five CPU points and a 6 GiB shard responsible for 24 CPU points. Moving the large shard to Beta makes their byte counts look more even but may leave both near the operational CPU limit. The small hot shard is a better candidate for Gamma provided placement and growth constraints allow it.

Using an illustrative additive estimate, moving that small shard would leave Alpha around 64 and Gamma around 59 CPU points. The arithmetic is only a prediction. Cache cold starts, compaction and differences in hardware change actual cost. A planner should separate normalized capacity units from raw request counts and evaluate confidence in its demand model. If the 24-point estimate came from one minute of unusually high traffic, moving immediately could create churn. Use a sustained breach or forecast threshold, a minimum predicted benefit, a cap on moved bytes and a cooldown before reversing a recent move. Record why the planner acted so an operator can audit the decision after the fact.

Add another complication. Gamma shares a rack with the only up-to-date secondary replica of the same shard. A move may violate anti-affinity unless another copy is placed or relocated first. The right output can be a short dependency-ordered plan or a report that no feasible move exists within the current capacity budget. Treating an infeasible objective as permission to violate a durability constraint silently changes the customer's failure model. Prioritize hard constraints first, then weighted goals such as tail latency, predicted headroom, migration cost and tenant isolation. Make these priorities inspectable and independently testable.

Establish explicit movement budgets

Budget concurrent moves per source, per destination, per availability zone and across bottleneck network links. A fleet-wide limit of ten migrations still permits all ten to read from the same struggling disk. Rate-limit snapshot I/O separately from log replay. Keep enough resources reserved for urgent repair after a hardware fault. Foreground-adaptive throttling can protect latency, but a controller that always backs off on the busiest node may never finish evacuating the node most in need of relief. Distinguish best-effort optimization from urgent decommission and give them different admission and escalation policies.

Observe the queue of planned work as well as completed moves. If the planner proposes 100 moves per hour and the executor completes five, accepted plans rapidly become stale. Recheck capacity and failure-domain constraints before starting each step. Protect the directory with compare-and-set on the expected generation, and make operation IDs stable across executor retries. A split, a replica repair and a tenant evacuation can all target the same logical range. Define compatibility and priority rules so concurrent administrative actions do not unknowingly invalidate each other's assumptions. A plan is a conditional proposal. Only the committed transition changes authority.

Separate urgent repair from load balancing

After losing a disk, the first objective may be to restore the configured number of independent durable copies. The fastest candidate node might temporarily worsen CPU balance while restoring safety. A scheduler that only minimizes CPU variance could defer repair for hours. Conversely, initiating mass repair whenever a server misses two heartbeats can copy terabytes in response to a transient network incident. Evaluate the confidence and duration of the fault, the remaining durability margin and the cost of premature movement. If the node returns, reconcile its generation and history before it is allowed to serve anything from its old ranges.

SD-005 · Distributed Systems Foundations · 07

Design a multi-tenant model release ledger

Build a regional service that tracks model revisions, active deployment pointers and durable publication outcomes for thousands of AI teams. A large tenant must be able to move without corrupting the ordering of releases.

Service contract, access patterns and failure domains

Assume 40,000 tenants and five million models. At peak the system receives 72,000 read requests and 12,000 small mutation requests per second. The two main calls are PublishRevision for a model and GetActiveRevision for a model and deployment environment. Artifact bytes live in independently durable immutable storage. A publication places an immutable revision in the registry, while activating it is a separate conditional update using an expected pointer revision. Some projects make hundreds of independent releases in parallel. One extremely busy model still requires a single ordered sequence of changes to its own production pointer. These are original design assumptions for the exercise.

Provide a strong read for release controllers that must see completed cutovers. Give dashboards a less expensive historical or potentially stale read returning its position and observation time. Store tenant identity, model identity, revision digest, environment pointer, monotonically increasing pointer version and a durable request record binding the caller's key to its payload and result. Store model rows with their environment pointers and request outcomes in one logical bucket. A conditional activation can then check authorization, expected revision and request identity in the same authoritative transaction. The object store needs an independent retention contract so a durable pointer never outlives all copies of its target.

Place 1,024 logical buckets onto an illustrative 32 replicated groups, initially averaging 32 buckets per group. Assign independent group replicas across three distinct zones and require the specified local quorum for durable writes. A strongly consistent placement directory maps each bucket to active group, assignment generation, lifecycle phase and any migration record. Tenant and model IDs form a canonical hash input; the namespace also supplies authorization and reporting scope. For special residency or giant isolated tenants, use a validated tenant-to-cell directory before hashing. Measure the lookup and operational overhead of that extra layer against its isolation benefits.

At uniform mean load each group sees about 375 writes per second and 2,250 reads per second at peak aggregated traffic. These divisions hide skew and say nothing about p99 latency. In a controlled benchmark suppose a group safely handles 900 mutations per second under the target read mix before its latency objective fails. Then 375 leaves nominal headroom for bursts and some movement. A tenant sending 4,000 mutations per second spread evenly across 64 independent models may fit if those models land in enough groups. If all 4,000 changes target one pointer, the design as specified cannot usefully split that ordered write stream. Renegotiate the semantics, reduce write frequency or increase per-key capacity.

Worked example 7 · Activate a model while its bucket moves

Tenant Sun requests activation of digest D at pointer revision 60 for model K. The client generates key R and sends the command to group S using cached assignment generation 13. S validates its current authority, verifies D belongs to the tenant and checks revision 60 in the state transition. If S commits activation before its handoff fence, it advances the pointer to 61 and persists the result for R. Replication to T must include that result. If the response is lost, a retry at T can return the original accepted revision even after another deployment has advanced the current pointer again.

If the command reaches S after its durable handoff barrier, S must reject the old generation. The client refreshes the directory, retaining R and the original request body. T may now commit the command if the precondition still holds, return the durable outcome for an already accepted R or report a version conflict. Returning success merely because the desired model is current would erase the distinction between a request that succeeded earlier and a different caller who happened to choose the same digest. Decide whether the business contract requires exact request outcomes and design retention accordingly. Restoring just the current pointer may be insufficient.

An artifact uploader can die after uploading all bytes but before PublishRevision. This leaves an orphaned object that need not be visible in the registry. Garbage collection must protect active uploads, retained versions and snapshots or replicas that might still reference the object. Conversely a release pointer cannot be safely activated solely because a manifest digest has the right shape. The system needs evidence that the immutable bytes are available under the promised recovery model. A metadata migration that passes checksum tests but points at objects unavailable in the recovery region will still fail a real deployment drill.

Isolation, observability and evolution

Authenticate the human or automation principal, derive tenant scope server-side and validate it inside the group as well as at ingress. A migration worker requires narrowly scoped access to the requested tenant or bucket, the selected source and destination, and the operation generation. Use authenticated transfer channels and least privilege for snapshot material, which may contain several tenants. When an isolation policy changes, track which historical backups, temporary copies and change streams contain affected data. Moving the live row does not by itself satisfy a physical residency or deletion obligation. Define those obligations before allowing cross-boundary placement.

Track p50 and p99 by operation, tenant and group, applied and durable replication lag, oldest migration phase, remaining bytes, replay drain rate, map-refresh frequency and stale-generation retries. Protect metric systems from unbounded per-model label cardinality through sampled traces or bounded heavy-hitter tracking. An operator should be able to answer whether a spike follows an individual key, a group leader, a zone or synchronized client retries. Rehearse cutover while one node in the target group is unavailable. Inspect both the new group's ability to accept writes and its remaining repair margin before proceeding.

The evolution path starts small: one group can own many buckets well before extra groups are needed. This permits stable APIs and migration tooling without immediate operational complexity across hundreds of groups. Add groups when a measured limit or isolation requirement demands them. If new workloads introduce global search, build a separate asynchronously maintained, access-controlled search index with its own freshness marker. Do not route every search through all primary groups by default. The backfill, replay position, tenant deletion and read-after-write semantics of the new index deserve an explicit design review.

SD-005 · Distributed Systems Foundations · 08

Survive a bad cutover and a regional disaster

A fault-tolerant design must answer two questions under pressure. Which history should become authoritative, and what evidence is sufficient to discard the others?

Worked example 8 · Roll back after the first new write

The target finished applying the source through position 800, and the directory switched bucket B to target generation 12. A new request now successfully records a deployment at target revision 801 in this illustrative continuation of the history. A load-test dashboard turns red and an operator points the directory back to the old source. The source still has only the state through 800. A client that already received success can now observe a missing deployment. More seriously, a retry may recreate the same operation with a different business outcome. Treating rollback as a configuration flip discarded an acknowledged decision.

A sound rollback first determines whether the new owner accepted post-cutover writes. If the answer might be yes, stop or fence new mutations, obtain a durable final target position and transfer all accepted changes and outcomes to the intended owner. A continuously maintained reverse replication stream can shorten this work when the chosen product, schema and topology support it. Verify its health and coverage before relying on it. A projection that dropped a column, collapsed values or changed primary keys may not be reversible. In that case the safer recovery can be a forward fix on the target while preserving the source for investigation.

You also need a fresh generation for the reverse handoff. Reusing generation 11 because the old source is once again the owner can admit delayed requests from the very first tenure. Review stale routes and in-flight worker sessions, revalidate the receiving group and reject requests carrying retired assignments. A management UI should name the source, target, operation identity, current authority and last safe recovery actions. A button labeled undo can imply that all physical and logical effects run backward when only a routing entry changes. Describe the actual compensating workflow and its prerequisites.

Restore metadata and data as a consistent recovery set

Suppose a region is destroyed while five migrations are in different phases. A directory backup may refer to target groups whose state is behind its activation decision. Restoring each independently to its latest surviving snapshot can produce a map that routes customers into empty or stale ranges. Take recovery records that associate active assignment generations with validated data positions, migration phases and source lineages. Retain sufficient data, logs and keys to construct a coherent recovery point. The recoverable frontier may differ among independent shards, but a cross-shard transaction or shared invariant can constrain which combination of frontiers is valid.

For a disaster recovery discussion, separate the recovery point objective from the recovery time objective. The first concerns tolerated loss of acknowledged business changes. The second concerns time to restore the specified service. Serving cached historical model metadata might happen quickly while authoritative releases remain frozen. Recovering all data bytes and recalculating every secondary index might take much longer. State which client operations are restored and what they guarantee in each phase. Measurements of the time for orchestration to issue a command are not measurements of the time for customers to deploy from a verified model.

Test using observable histories

Record concurrent publications, timeouts, map changes, group crashes and client reads with stable identities and invocation intervals. Check that each successful request has one durable legal outcome, a client observes no impossible transition under its selected read contract, and there is no accepted old-generation write after the corresponding fence. Random load tests can miss a short boundary between a source commit and migration-worker persistence. Provide deterministic barriers just before source fence, after target catch-up, after directory switch and before client acknowledgment. Crash the coordinator at each point and allow a new one with no process memory to recover solely from durable evidence.

Run a second drill that forces rate imbalance during catch-up. Prove that the controller alerts or changes plan when the backlog grows, then allow recovery and verify the final result. A successful migration on a tiny idle database only demonstrates the easiest branch. An operationally useful test quantifies pause time, p99 regressions, replay retention headroom, abort behavior and any change in redundancy. Ask an engineer outside the migration team to interpret the audit trail. If two operators cannot independently identify the authoritative owner after a crash, improve the state model before automating more moves.

Rehearse the failure paths an interviewer can change

The questions below are original practice. They assess whether you can adapt a placement or migration decision to changed assumptions without losing the original service guarantee.

Twelve Staff+ design questions

How would you tell whether this service needs replicas or shards?

Evaluates bottleneck diagnosis. I separate read execution, write ordering, apply work, disk capacity and network egress. Read replicas may absorb independent stale-tolerant queries. If one primary saturates applying globally ordered writes, more followers repeat that work. I would first reduce expensive writes, then partition on independent business invariants if the measured limit remains. The decision also depends on query locality and availability targets.

Follow-up. Would a follower help a strong read? It needs an appropriate authority and apply barrier or another documented protocol.

Common mistake and tradeoff. A high aggregate CPU chart can hide a saturated primary and idle followers.

How does a stable bucket map reduce data movement?

Evaluates placement indirection. The hash-to-bucket function stays fixed when hardware changes. A separate directory moves selected buckets between groups and changes their assignment generations. Keys outside those buckets keep the same logical and physical destination. This reduces unnecessary remapping but still requires safe transfer, stale-router handling and a placement strategy that balances actual load. Overly coarse buckets leave the planner few feasible moves.

Follow-up. Could we increase the bucket count later? Yes, using a versioned split or remapping migration with explicit ownership boundaries.

Common mistake and tradeoff. Directory flexibility costs metadata, recovery logic and a source of authoritative placement.

Can equal bytes per shard imply equal latency?

Evaluates multi-resource reasoning. No single resource measure captures queueing and service time. A six-gigabyte shard with a heavily updated secondary index can consume more CPU and write I/O than a much larger archive. Measure request mix, CPU, disk service time, working set, egress and leader placement. Predict the benefit of moving a candidate and check the receiving group's degraded-state capacity before accepting the plan.

Follow-up. What if the demand sample is noisy? Require sustained evidence and monitor the result after a bounded move.

Common mistake and tradeoff. A balancing policy that chases instantaneous utilization can oscillate and consume the capacity it was meant to free.

What makes a migration watermark safe for cutover?

Evaluates completeness of evidence. It must correspond to the correct source lineage and snapshot and certify a complete applied prefix through the last write allowed by the source fence. A maximum observed offset can hide gaps. The destination also needs durable state under its own failure model, including deletes, indexes needed to serve and request outcomes promised to clients. Only then can routing switch under the designed authority protocol.

Follow-up. What about unrelated records in a shared log? Filtering must still establish progress through all relevant committed changes.

Common mistake and tradeoff. A lag chart rounded to zero is an observation taken at one instant, not a barrier against concurrent source writes.

A hot tenant accounts for half of all traffic. What should move?

Evaluates access-pattern decomposition. First identify whether demand comes from many independent keys, one mutable key, immutable reads, expensive scans or one shared invariant. Moving independent models into separate groups can help. A tenant-wide quota might remain a serial bottleneck. One popular immutable digest can often be replicated and cached instead. I would retain tenant-level admission and isolation even when the data is physically split.

Follow-up. What happens to tenant-wide scans? Use bounded scatter and merge or a purpose-built projection with explicit freshness.

Common mistake and tradeoff. A hash distributes distinct keys; it cannot divide the work of one indivisible ordered update.

How could a snapshot plus change stream resurrect a deleted row?

Evaluates ordering across bulk and delta paths. Suppose the snapshot contains row B and the subsequent stream deletes it. If replay applies the delete before the backfill writes the older row, the copy can bring B back. Stage and finish the base before ordered replay, or implement a carefully defined per-range interleaving protocol with version guards. Compare state at the same logical frontier and test deletes and key changes, not just inserts.

Follow-up. What if the change stream replays an operation twice? Persist replay progress atomically with effects or make application idempotent.

Common mistake and tradeoff. Checksums of live views taken at different positions cannot classify this failure reliably.

What if a stale client writes directly to the former owner?

Evaluates enforcement beyond cache invalidation. The former owner's authoritative mutation path must reject obsolete authority once its barrier takes effect. A TTL or directory notification only makes routing more accurate. Paused clients, delayed messages and stale sessions can outlive any intended cache interval. Include the expected generation in the request, validate tenant scope, and return a refreshable stale-route result. Preserve request identity and original precondition on retry.

Follow-up. What about a packet already accepted before the fence? Its committed effect must be in the source final prefix transferred to the target.

Common mistake and tradeoff. Redirecting at ingress alone leaves bypasses, internal tasks and in-flight operations uncovered.

Why is reverse traffic more than a DNS change?

Evaluates rollback correctness. After target writes become possible, the source may lack acknowledged state. An operator needs a new handoff: fence the current writer, identify and transfer its complete accepted history, verify the receiving copy, then publish a fresh ownership generation. Reverse replication can shorten the data transfer if the transformation is reversible and the reverse stream is healthy. Use a forward fix if rollback cannot reconstruct the old schema safely.

Follow-up. When could you abort cheaply? Before the target has any authority to accept business writes, under a verified source state.

Common mistake and tradeoff. Reducing recovery time by discarding acknowledged results silently changes the recovery-point contract.

Which failure domains should constrain placement?

Evaluates fault model and feasibility. Translate the stated promise into independent surviving copies and a viable write quorum after the named failure. Distinct processes on a single host are insufficient for host loss. Three zones sharing an inaccessible key-management service may still share an availability dependency. Examine every intermediate migration step and ensure the smallest zone can support the required replica policy. Mark infeasible placements explicitly.

Follow-up. Can all repair traffic share one link? Only if its degraded-state bandwidth also supports the recovery objective and foreground demand.

Common mistake and tradeoff. Uniform node counts say little about correlated failures or time to restore redundancy.

How do you page a cross-shard top-fifty query?

Evaluates distributed query semantics. Use a stable total ordering, including a tie breaker, and a common snapshot if stable pagination is promised. Each participating shard returns bounded ordered candidates. Merge them with a cursor strategy that preserves the remaining entries from every contributing stream. An index or projection may be preferable when scatter latency or the cost of many shard queries dominates. Decide whether a slower shard yields a partial result or an error.

Follow-up. What if rows migrate between pages? Pin a compatible snapshot and routing view or define how the cursor survives a move.

Common mistake and tradeoff. A global offset applied independently to each shard can skip or duplicate results.

What if replay falls further behind while your copy succeeds?

Evaluates rate and capacity analysis. Estimate sustained relevant source change rate and sustained destination apply capacity under actual foreground load. Their difference determines whether the backlog can drain. If the difference is negative, completion needs a different plan. Reduce the moved scope, provision replay capacity, admit fewer writes during a negotiated window or restart from a suitable newer base. Verify source retention and destination space before waiting longer.

Follow-up. Can more copy threads help? Only when the bottleneck is base transfer; they can actually starve replay or production reads.

Common mistake and tradeoff. A declining number of uncopied rows says nothing about a growing mutation backlog.

How would you demonstrate the recovered fleet is usable after regional loss?

Evaluates end-to-end recovery evidence. Recover directory generations and compatible shard frontiers, verify pending migrations, then exercise actual business reads and conditional releases through an independent client. Verify the availability of referenced model artifacts and request outcomes, including a retry of a pre-disaster request. Report an explicit recovery point and time to restored customer operations. If recovery excluded recent acknowledged changes, reconcile their external effects before permitting conflicting actions.

Follow-up. Which drill reveals a hidden dependency? Recover while the original region, including its key service and object endpoints, is unavailable.

Common mistake and tradeoff. A healthy metadata process or a completed restore command is weak evidence that deployment can serve customers.

Whiteboard a counterexample

Draw one source, one target, a route cache and a directory. Let a colleague choose the last message to delay. If it is a source write, identify the point where the source rejects it or the exact prefix in which it appears. If it is a route refresh, explain why a stale routing hint cannot authorize a mutation. If it is a client success reply, show where the original request record is recovered. Move one more component into another region and repeat the argument. You will discover which parts of your explanation depended on local latency and which depended on durable evidence.

Explain a design in thirty seconds, two minutes and five minutes

A concise answer starts with workload shape and ends with the promise to the caller. A deeper answer earns its length by showing what happens while data moves and machines fail.

Thirty seconds · The three decisions

Replication gives me several copies of a logical partition. Sharding lets independent partitions carry separate data and write streams. Rebalancing changes placement as demand and hardware change. I choose boundaries from the operations that must agree, place replicas across the specified failure domains, and move a shard by copying a consistent base plus ordered changes. Before switching writes I need a durable source fence and evidence that the destination contains every change through that fence.

Two minutes · Move one hot bucket

Suppose one registry group is saturated while spare capacity exists elsewhere. I would inspect key-level demand first. A bucket containing many independently active models may be worth splitting or moving. A bucket dominated by one hot pointer requires a different solution for that pointer. After checking placement and budget, I would create a private copy at the destination from a snapshot tied to source position five hundred. I retain and replay the committed changes after that point, including deletes and the retry outcomes that clients may still need.

During replay I measure the net catch-up rate. If the incoming changes exceed the destination's ability to apply them, a green base-copy metric will not make the move finish. Once the destination is close, I briefly fence the source against further writes for this bucket. That produces an exact final position. I wait for durable destination coverage through that position and activate it through an authoritative assignment generation. Old clients get a structured retry response, and their original request identities survive the move.

I would prove the result with a lost-response test across cutover, a conditional update against the expected revision and a restore from the target group's durable state. I would also measure the actual write interruption, tail latency and remaining redundancy. If the target later accepts a write, returning traffic to the old source requires a new safe handoff that accounts for that write.

Five minutes · Defend a production deployment

I would begin by asking which customer-visible operation must scale. Model artifact uploads, publishes of small metadata records and activations of a mutable deployment pointer have different costs and failure modes. I would keep bulk model bytes in immutable object storage and group each model's authoritative metadata with its conditional pointer and request outcomes. That gives me one local transaction for the commands that conflict. For cross-tenant search I would consider a separate projection whose delay we can measure and explain.

Next I would size the independent units. With twelve thousand peak writes per second and thirty-two groups, the mean is three hundred seventy-five writes per second per group. I must evaluate a production mix and leave enough headroom for one zone loss, a large tenant and ongoing repairs. I would hash canonical tenant and model identities to stable logical buckets and map those buckets to groups. This indirection lets me add groups without changing the location of every logical key. If an unusually hot tenant requires isolation, I can assign it a separate home cell or migrate suitable buckets under policy.

For durability I would state exactly what a success response certifies. A regional release cannot imply global recoverability if its bytes or latest pointer have yet to reach another region. I would record durable and applied watermarks separately and test a client performing a strong read after a completed activation. Dashboards with weaker requirements can read from followers under an explicit freshness contract. This gives a business reason for read replication instead of attaching replicas to a diagram by habit.

When I migrate a bucket, I stage a consistent snapshot, keep its ordered change stream, measure drain rate and validate contents at a common frontier. The exclusive ownership transition comes after the data is nearly ready. I fence the source, wait for target durability through the final boundary and publish the next assignment generation. If the coordinator crashes immediately after the switch, its replacement reads the durable operation state and cannot decide ownership from a stale local plan. A retry at the new group should recover the same command result the old group might already have acknowledged.

Finally I would test failure and recovery with the caller's contract in view. Delay a source reply across cutover, restore a stale routing cache and destroy the coordinator in the middle of a phase transition. Then lose the original region and try to perform a real model deployment using only the advertised recovery region. The strongest defense of this design is that I can identify a durable record for each claim, identify the operations deliberately unavailable during uncertainty and measure when real customer service resumes.

Final interview cheat sheet

  • Replicate. Specify the durable and read guarantees of each copy.
  • Partition. Align boundaries with the smallest units requiring shared order.
  • Route. Separate logical key mapping from physical ownership.
  • Locality. Price the scans, indexes and transactions that cross boundaries.
  • Skew. Measure concentration in work as well as bytes.
  • Placement. Satisfy durability and residency constraints throughout transitions.
  • Snapshot. Bind the base image to a retained ordered source frontier.
  • Catch-up. A positive net drain rate is necessary to eliminate backlog.
  • Fence. Establish a final source write boundary before activating a new writer.
  • Retry. Transfer command identities and durable outcomes.
  • Rollback. Account for every accepted target write before returning authority.
  • Recover. Restore a compatible directory, shard histories and referenced artifacts.
