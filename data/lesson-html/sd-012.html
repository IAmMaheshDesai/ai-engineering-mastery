sd-012 · Multi-region architecture

Separate where requests run from who may write

Active-active is a workload statement until you define its data and authority semantics.

The misleading two-region diagram

A team draws two identical regions behind a global load balancer and labels the result active-active. Both regions accept inference requests, yet all conversation writes still go to one database primary. During a partition, one region continues generating tokens but cannot append the final answer. Another application accepts writes locally in both regions, then merges records later. The pictures look similar, but the correctness and failure behavior are fundamentally different. Your first architectural responsibility is to unpack the label.

Active-passive usually means one site serves a specified production workload while another is prepared to take over. Passive can mean cold infrastructure, warm processes, or fully provisioned hot replicas. Active-active means multiple sites concurrently serve some specified workload. It does not inherently mean every site independently writes every record, nor that a failed site can be removed without data loss. State whether the label describes ingress, stateless compute, reads, writes, tenant ownership, or business effects.

A useful classification has four axes. Request placement determines which region receives the client. Data placement determines which copies contain the required state. Write authority determines which process or quorum can authorize a mutation. Effect authority determines which executor may perform an external action. These axes may deliberately differ. An inference request can enter near the customer, read a replicated model manifest, forward a durable conversation append to the tenant's home region, and call an external tool only through a single owner.

This distinction extends your OCI Full Stack Disaster Recovery experience. Switching a stack changes more than a route. It changes resource roles, data lineage, and permissions to perform effects. In an AI platform, model artifacts can be globally replicated while workflow execution remains home-region owned. The hypothetical architectures here are original teaching designs; they do not describe proprietary OCI or target-company internals, and they do not attribute unprovided accomplishments to you.

Make the contract visible

Ask what must remain available during a regional partition, which acknowledged writes must survive region loss, and what users may observe after moving between regions. Ask whether tenant data can cross borders, whether external effects are reversible, and whether standby capacity exists for the promised workload. “Globally available” is not a complete answer. A European tenant may require European processing, and a financial action may require rejecting a request rather than accepting an ambiguous duplicate.

Use an operation matrix rather than one consistency label for the whole platform. Model downloads can tolerate immutable replication delay if publication is gated. A quota decrement may need serialization or preallocated rights. User preference updates might allow deterministic merge. A destructive recovery action needs exclusive authority. Each operation should state its write location, read guarantees, partition behavior, and recovery procedure. The matrix is an executable design input for routing and admission, not merely documentation.

How I would explain this in an interview: “I separate active ingress from active write authority. My design can serve compute in several regions while preserving one owner per tenant or record. If we need independent writes to the same data during a partition, I must define merge semantics or negotiate which invariant we relax.” Pause and describe one system where active-active compute and active-passive metadata are a sensible combination.

Chapter summary

Topology names do not establish guarantees. Define operation placement, authoritative state, external effects, and partition behavior before choosing an active-active or active-passive design.

02 · Requirements and network physics

Quantify locality, coordination, and failover capacity

Global architecture is constrained by propagation delay, workload shape, and reserved headroom.

Latency budgets must name the critical path

A nearby frontend does not make a request local if it synchronously calls a distant authority. Decompose end-to-end latency into client transport, authentication, request queuing, authoritative reads or writes, compute, and response delivery. Some stages overlap, so do not add every network exchange blindly. Identify which acknowledgment depends on a wide-area round trip. A global write protocol may pay that cost even when all application code runs close to the client.

Propagation imposes a floor, but observed latency also includes routing, serialization, congestion, encryption, queuing, and persistence. Use measurements between the actual candidate locations. A geographical distance calculation is useful for rejecting impossible proposals, not predicting production p99. Similarly, a benchmark with tiny prompts does not represent an AI workload dominated by large-context prefill or long streaming responses. Capacity and latency should be measured under the same request distribution and admission policy.

Distinguish a latency objective from a consistency objective. A stale local read can be faster than a remote authoritative read, but that is a different operation contract. A user who updates a setting and immediately sees its old value may judge the product broken even if the read returned quickly. Session routing or a minimum-version token can preserve a narrower guarantee without forcing every read globally. The later chapters derive those mechanisms and their failure cases.

Worked example 1: active-active capacity after one region fails

Initial state: three regions each serve 20,000 requests per second, for a total of 60,000. Each has measured capacity of 40,000 requests per second at the required latency under the declared workload. The objective is to retain full demand after losing any one region. If traffic redistributes evenly, each survivor receives 30,000 requests per second. That is 75 percent of its measured ceiling. The normal state uses 50 percent of each ceiling, which leaves enough arithmetic headroom for this one-failure scenario.

The routing operation removes the failed region, checks that both survivors have the correct models and policies, then increases traffic with admission gates. Intermediate state matters: one survivor may receive traffic faster because resolvers and clients converge at different times. A 40,000 and 20,000 split still fits the stated ceilings, but a 45,000 and 15,000 split overloads one region even though total surviving capacity is sufficient. Regional admission and spillover must therefore handle transient skew, not only the final balanced state.

Failure variation: a new model lowers each region's tested ceiling to 28,000. Surviving aggregate capacity becomes 56,000, below demand. No routing algorithm can create the missing 4,000 requests per second. Choose explicit shedding, a permitted cheaper model, reserved extra capacity, or a lower emergency contract. If a burst increases demand by twenty percent, even the original 40,000 ceilings need reanalysis: 72,000 split across two is 36,000 each, leaving much less margin for skew.

The final outcome is full recovery only while the workload and capacity assumptions remain valid. The correctness argument combines resource readiness, admission, and the authoritative-state contract; raw request counts alone do not prove it. Production implication: recalculate failure headroom whenever models, token lengths, tenants, or regional routing policies change. Interview takeaway: active-active can use reserve capacity during normal operation, but utilization must still be bounded by the failure scenario you promise to survive.

Chapter summary

Local ingress does not eliminate remote coordination. Capacity planning must include surviving regions, realistic workload distributions, transient routing skew, and the latency target that defines usable capacity.

03 · Active-passive mechanics

Build a passive region that can safely become authoritative

Replication, promotion, routing, and failback are separate protocols.

Normal operation and planned transition

In a single-writer topology, one region orders changes for a data partition. Other regions may serve reads from replicas. For a planned switchover, stop or redirect new writes, drain in-flight work, establish the destination's complete replication frontier, transfer authority, validate the new writer, and update routing. The exact ordering depends on the datastore's supported promotion mechanism. A product-specific procedure is authoritative; a generic controller should not synthesize unsupported database states.

Warmth is multidimensional. A standby can have current data but no available GPUs, or running compute but missing encryption access. Readiness must cover state, authority, network, identities, application versions, and capacity. The destination should regularly demonstrate that it can serve a business canary without changing production ownership. This is stronger than checking that a replica process is alive, but still weaker than a full regional failure exercise.

PostgreSQL's versioned documentation describes asynchronous standby behavior and a possible loss window. OpenAI's January 2026 engineering publication provides a concrete public example of a single PostgreSQL primary with geographically distributed read replicas. These references establish that geographically active reads need not imply multiple writers. They do not establish a universal recommendation or a private regional recovery contract. The protocols and numbers in this lesson remain original analysis unless specifically attributed.

Worked example 2: an unplanned promotion with a missing suffix

Initial state: A owns tenant T at ownership epoch 17. Its authoritative event log contains committed sequence numbers through 10,500, while B has a verified complete prefix through 10,460. The link fails and A becomes unreachable from the recovery authority. The objective is to restore service without allowing both owners to mutate the tenant. First, the authority records the recovery decision and establishes a supported fencing boundary preventing A's old writer from committing protected effects.

B cannot infer that missing events 10,461 through 10,500 never existed. If A's acknowledgment ledger is known and trustworthy, those forty events are exposed. If the exact primary frontier is unknown, report uncertainty rather than an invented exact loss count. The recovery policy chooses B's complete prefix, records the selected frontier, and issues epoch 18. The new writer starts from that prefix only after safety and loss-acceptance gates are satisfied.

Intermediate state: old clients still reach A because routing has not converged. A rejects or forwards writes under the supported exclusion policy; it does not continue accepting simply because clients can connect. B accepts requests with stable identities and authoritative epoch 18. Final outcome is one writable history based on the explicitly selected prefix. Previously acknowledged missing effects may need reconciliation with external systems, even if the database itself opens cleanly.

Failure variation: A returns with a divergent suffix after B has appended new events. Never splice both logs by sequence number alone. Sequence 10,461 in A's old lineage and the same number in B's new lineage are different histories. Preserve incarnation or epoch metadata, investigate missing business effects, and reseed or reconcile using application rules. Production implication: failback is a controlled data-lineage transition, not a DNS reversal. Interview takeaway: a standby can reduce operational complexity while still requiring precise authority and loss semantics.

When active-passive is the better design

Choose active-passive when write locality is acceptable, conflicts are hard to merge, the service already depends on a single ordered history, or operational simplicity is valuable. You can still use global stateless compute and local immutable caches. Reject the claim that a passive site is necessarily wasted: it can serve safe reads, drills, or approved lower-priority work, provided reclamation and failure capacity are tested. Every additional standby workload creates a recovery dependency that must be budgeted.

Chapter summary

Safe promotion establishes one authoritative lineage and explicit loss handling before routing new writes. Planned switchovers and unplanned failovers have different evidence and operational prerequisites.

04 · Partitioned active-active

Distribute ownership without permitting conflicting writers

Many global systems are active-active across shards and single-owner within each shard.

Home regions and ownership directories

Partitioned ownership assigns each tenant, key range, or business entity to a home region. A and B both accept writes, but to disjoint ownership sets. Requests arriving in the wrong region are forwarded or redirected using an ownership directory. The directory should include a revision or epoch so stale routes can be detected. A cached directory entry is an optimization, not authority to violate the current owner.

This design reduces same-key conflict complexity and can place writes close to their usual clients. It introduces hot tenants, cross-home transactions, movement, and directory availability. Shard selection is a semantic decision. Putting all resources of a protection group together makes recovery-plan updates easier to transact, but a very large tenant can dominate one partition. Splitting the tenant improves scale while creating coordination across its resources. Explain that tradeoff before choosing a hash function.

Meta's historical TAO article describes one primary region per shard and replication to secondary regions. That is public evidence for separating global serving from per-shard write authority. It is not proof that all Meta systems use that model today. The lesson's tenant directory, migration state machine, and control-plane APIs are hypothetical designs used to explore the general pattern.

Worked example 3: move a tenant without dual ownership

Initial state: tenant T is owned by A at directory revision 91 and epoch 7. B holds a replicated copy through event 800. The objective is to move T to B while preserving a single ordered mutation history. First, create migration M with expected directory revision 91. Prepare B and copy state while A continues writing. Then enter a draining phase that stops new conflicting mutations for T while reconciling already-dispatched effects.

A produces a final transfer frontier, say event 840. B verifies all required state through that frontier, including referenced object manifests. The authority atomically changes the ownership record from A, epoch 7, to B, epoch 8, under the supported transaction or compare-and-set boundary. Resource enforcement rejects A's stale epoch. B then becomes writable. The directory update is small, but it is safe only because data readiness and exclusion already have reliable predicates.

Intermediate state: a frontend caches revision 91 and sends a request to A. A returns a structured moved or stale-ownership result carrying the current directory revision, or safely forwards without executing locally. The frontend refreshes and retries the same request identity at B. If A executed the request before the transfer barrier but its response was lost, B must find the recorded result rather than execute it again. Scope request deduplication to tenant and logical operation, not just to one regional process.

Final outcome: T is writable at B under epoch 8, and all acknowledged pre-barrier operations are represented in the transferred lineage. Failure variation: the authority update succeeds but the coordinator crashes before notifying B. A successor reads the authoritative record and completes activation; it does not roll back ownership based on the missing notification. If state transfer is incomplete before the update, the protocol must refuse to advance. Production implication: define migration transitions as durable states with recoverable postconditions. Interview takeaway: routing changes are consequences of ownership changes, not substitutes for them.

Cross-home operations need a separate contract

A transfer touching two tenants cannot be made atomic by independently updating each home region. Choose a distributed transaction when its coordination cost is justified, or a business workflow with reservations and compensation when partial progress is acceptable. If both resources need frequent atomic updates, consider colocating them under one owner. A global architecture should make these exceptional operations visible in API design rather than conceal them behind a generic database client.

How I would explain this in an interview: “Active-active across tenants gives us useful locality without arbitrary same-record merge. The hard part becomes ownership movement and cross-owner work. I use a revisioned directory and resource-side exclusion, then treat multi-owner transactions as a separate correctness problem.”

Chapter summary

Partitioned active-active distributes authority while preserving a single owner per partition. Safe movement requires a transfer frontier, an authoritative ownership change, stale-route handling, and durable request identity.

05 · Independent writes and merge

Convergence is useful only when it preserves the business meaning

A deterministic winner is not automatically a correct resolution.

Concurrent updates need explicit semantics

If disconnected regions both accept writes to the same logical object, recovery must reconcile histories. A last-writer-wins register chooses an update using an ordered timestamp and tie-breaker. It converges when replicas apply the same ordering rule, but it can discard a valid business action. Physical-clock skew can select an update that occurred earlier in real time. Even a perfect clock cannot infer whether two concurrent edits should be combined, rejected, or escalated.

A vector of per-writer counters can describe causal ancestry. If one version's vector dominates another component by component, the former includes the latter's causal history. If neither dominates, the versions are concurrent. This detects a relationship; it does not decide the business merge. The Dynamo paper provides a historical example of object versioning and application-assisted reconciliation. Its techniques should not be confused with a universal guarantee of linearizability or a current specification for every product named Dynamo.

Some data types admit merge functions with useful algebraic properties. A state-based replicated grow-only counter stores one monotonic component per stable writer. Merge takes the componentwise maximum, and the visible total is the sum. Maximum is commutative, associative, and idempotent, so reorderings, batching, and duplicate state deliveries do not change the converged result once all updates are delivered. These algebraic properties are grounded in CRDT research; they do not remove the need to define writer identity, durability, membership, and business invariants.

Worked example 4: merge a usage counter, then test a quota

Initial state: two regions have the counter vector A = 100, B = 60, representing 160 recorded usage units. During a partition, A records seven units by increasing its own component to 107. Independently, B records five by increasing its component to 65. Each owns its monotonic component. On reconnection, merging [107,60] and [100,65] yields [107,65], or 172 total. Applying either state repeatedly produces the same result.

The objective is accurate eventual aggregation, not an immediately enforced global quota. If the maximum allowed usage is 170, both local sides can still approve operations based on incomplete remote information and collectively exceed the limit. The counter converges correctly to 172 while the quota invariant has been violated. This is the distinction between convergent data and coordinated admission. A correct merge is not a reservation protocol.

To enforce a hard quota during partitions, preallocate exclusive spending rights. With ten units remaining, give A six and B four. A can accept at most six new units while disconnected and B at most four. Transferring rights requires a protocol that does not allow both sender and recipient to spend the same rights. The intermediate state can reduce availability when one region exhausts its share while another has unused rights. That is a deliberate coordination tradeoff, not an implementation defect.

Failure variation: A loses its durable counter and restarts under the same writer identity at zero. Taking maximum can mask new increments until A exceeds its previous component; reusing an identity incorrectly breaks the model. Persist components and membership, or issue a new unique writer incarnation with a safe retirement policy. Final outcome under the valid model is 172 recorded units with no duplicate increment from repeated state merge. Production implication: counter semantics must be paired with ingestion deduplication if business events themselves may arrive twice. Interview takeaway: prove both algebraic convergence and the separate application invariant.

Deletes and arbitrary effects resist naive merge

A set union can merge additions but cannot express deletion safely without more metadata. A removed element can reappear when an old replica sends its state unless the type records removal semantics and relevant causal context. Tombstone collection therefore requires evidence that old versions cannot return, or a protocol supporting their safe interpretation. Similarly, sending an email or deleting a volume is not an algebraic state merge. Assign effect ownership and reconcile outcomes rather than claiming that a CRDT makes external actions exactly once.

Chapter summary

Choose merge semantics by business operation. Convergence, causality, quota enforcement, and external-effect safety are separate properties that require separate arguments.

06 · Coordinated global writes

Place quorums according to the failure you must survive

A global endpoint does not make coordination local or quorum placement irrelevant.

Replication groups and transaction boundaries

A strongly coordinated replicated group establishes one ordered history through a consensus protocol. A leader can serialize requests while obtaining the required durable quorum before acknowledging. The leader's location affects write latency, and voter placement affects which failures preserve progress. Read-only replicas may improve locality without participating in write quorum. Distinguish these roles before counting nodes on a deployment diagram.

A majority intersects another majority, which helps consensus protocols preserve chosen state when their other rules are followed. Merely setting read and write counts so they intersect does not by itself establish linearizability. Version ordering, leader rules, concurrent writes, configuration changes, and recovery behavior matter. State the actual datastore contract rather than deriving a stronger property from a quorum equation alone.

Google's Spanner paper documents a sharded globally distributed system using Paxos replication and additional mechanisms for externally consistent transactions. It is useful evidence that per-group consensus and cross-group transaction semantics are different layers. Do not collapse the entire design into “Paxos plus a global clock.” The placement calculations below are original teaching examples, not measurements of a target company's deployment.

Worked example 5: five voters across three regions

Initial state: a five-voter group places two voters in A, two in B, and one in C. A majority requires three. The objective is continued progress after any one whole region fails, assuming the surviving regions communicate. Lose A: B plus C provides three. Lose B: A plus C provides three. Lose C: A plus B provides four. This placement satisfies the stated arithmetic requirement, unlike a three-voter group with two voters in A and one in B, which cannot progress after losing A.

Now inspect latency. If the leader is in A, its own durable copy and the second A voter provide only two votes. At least one remote voter must participate in each majority acknowledgment. Suppose the measured inter-region round trips are A–B 70 milliseconds, A–C 100, and B–C 40. With all voters healthy and no other bottleneck, A's acknowledgment path must wait for some remote evidence, potentially from B. After losing A, a leader in B can use its two local voters and C. The network component of the required remote acknowledgment can therefore change.

Do not equate these round trips with total commit latency. Durable storage, queuing, batching, protocol implementation, and client-to-leader transport add or overlap work. If the application forwards from C to an A leader, its end-to-end path differs from a client already in A. The intermediate state after failure includes election and catch-up, not just a new steady-state round trip. Final outcome is quorum availability under the specific one-region fault model, not guaranteed uninterrupted writes.

Failure variation: C remains alive but the A–B path partitions and C can reach only B. B plus C can form three; A alone has two and cannot independently create a conflicting majority under the protocol. If C cannot communicate with either side, neither two-voter region has a majority. Production implication: a small witness location can be critical to progress even if it holds little compute. Interview takeaway: test failure sets and communication graphs, not merely total replica count.

Global transactions add another cost surface

If a business operation updates two separately replicated partitions, ordering inside each partition does not automatically make the operation atomic across both. A transaction coordinator, locking or validation scheme, and recovery protocol may add wide-area messages and contention. Colocating related data can reduce this cost, while increasing hot spots and limiting independent scaling. For AI infrastructure, the distinction appears when a placement claims GPUs across two ownership groups or a tenant migration updates both quota and deployment metadata. Name the atomicity scope in the API.

Chapter summary

Count durable voters, locate the required remote acknowledgment, and enumerate regional failure sets. Per-group consensus, end-to-end latency, and multi-group transactions remain distinct design layers.

07 · Read semantics and routing

Preserve the session when a client changes regions

Replica locality requires an explicit answer to “Which version may this user read?”

Read-your-writes is a contract, not a routing accident

A user creates a conversation in A, then their mobile network reconnects through B. B's asynchronous replica has not applied the create event. Returning not found may violate a read-your-writes expectation even though eventual consistency permits it. Sticky routing can reduce the frequency, but it is not a correctness mechanism if the home region becomes unavailable or the client loses its affinity token.

One design returns a minimum-version token with the write acknowledgment. A later read supplies that token. A replica may serve only when its applied frontier includes that version, otherwise it waits within a bounded deadline, forwards to an authority that can satisfy the token, or returns an explicit consistency-unavailable result. The token must identify the partition and lineage, not merely a globally meaningless integer. It also must be validated so an attacker cannot force arbitrary waits by inventing impossible frontiers.

Define whether tokens are opaque signed values, server-stored session state, or validated references. They must not expose another tenant's state or bypass authorization. Version satisfaction says the replica is current enough; it does not authorize the reader. If the service supports reads spanning multiple partitions, a single scalar may be insufficient to represent the required dependency set. Either use an appropriate snapshot or dependency contract, or narrow the guarantee to one partition.

Worked example 6: region change after an acknowledged write

Initial state: tenant T's partition P in lineage L has acknowledged event 901 in A. B has applied through 896. The client carries a token identifying T, P, L, and minimum event 901. The objective is to prevent B from showing a state older than the client's acknowledged write. B validates the token and identity, compares its applied frontier, and finds a gap of five events. It waits for up to the configured consistency deadline while replication advances.

At intermediate frontier 899, B still cannot satisfy the request. At 901, it can serve the read under the declared partition-local guarantee. If the token's event corresponds to a conversation append, the query must read from a snapshot including that frontier, not check one replica and read another stale cache. Cache entries need a compatible version predicate or must be bypassed. Final outcome is a response that includes the required write without forcing all users to read from A.

Failure variation: A is permanently lost before B receives event 901, and a permitted lossy failover establishes a new lineage from event 898. Waiting forever cannot restore missing history. The service must report the consistency token as unsatisfied under recovery policy, reconcile with durable acknowledgment evidence if available, and communicate the loss. Reinterpreting event 901 from the new lineage as if it were the old write would be incorrect.

Another variation is concurrent updates from another client after 901. Read-your-writes does not imply the returned value must equal the exact old value forever; a legitimate later update may replace it. The guarantee concerns inclusion of causal history under the chosen data model. Production implication: session consistency needs version-aware caches, routing, and loss semantics. Interview takeaway: define the precise observation a user receives when locality and recovery conflict.

DNS and anycast do not transfer data authority

DNS changes influence future resolution but do not forcibly move established connections or guarantee immediate client compliance with an intended transition time. Anycast or global proxies can move ingress, but application state still needs the correct owner and version. A long-lived inference stream may need to fail and restart using a stable request identity and explicit partial-output policy. Avoid automatic replay of effectful requests unless the business idempotency contract covers it.

Health checks should test the capability relevant to a route. A region can be healthy for immutable model downloads while unable to commit agent effects. Use operation-aware routing and explicit readiness gates. Hysteresis can prevent flapping; it does not establish single ownership. Keep route selection, ownership validation, and admission separate so a mistaken routing decision cannot create a second writer.

Chapter summary

Session guarantees require version evidence through the full read path. Routing makes requests reachable; it does not establish freshness, authorization, lineage, or safe replay.

08 · AI workload placement

Global compute can use several different state topologies

Choose regional placement separately for inference, agents, retrieval, and training.

Inference and retrieval publication

Stateless inference is a natural candidate for multiple active regions when model artifacts, runtime compatibility, tenant policy, and accelerator capacity are ready. However, the request may still depend on stateful admission, quota, retrieval, or conversation storage. A global gateway should know which optional capabilities can be disabled and which are required for correctness. A lower latency response using an unapproved model or unauthorized retrieval corpus is not successful availability.

Publish model and index versions through immutable manifests. Upload objects, verify hashes and regional presence, then publish a regional readiness record for the complete version. A global rollout can allow A to serve version 7 while B remains on version 6 only if the product's version contract permits that difference. If all requests for a tenant must use version 7, route only to ready regions or retain an explicit wait state. Do not update a global alias before every promised destination is actually capable of serving it.

For retrieval, freshness includes both documents and access policy. A document may be removed or its permissions revoked after an index snapshot. Decide whether query-time authorization filters provide the necessary guarantee and what happens when the policy authority is unavailable. Eventual indexing is often acceptable for discoverability, while eventual authorization revocation may be unacceptable. Separate those clocks rather than assigning one freshness SLO to the entire RAG stack.

Agents and disaster recovery plans

A durable agent's planning model can run near available compute, while its authoritative execution state and external-effect ownership stay in one tenant home. Persist model outputs when reproducible continuation requires them, and do not assume rerunning a prompt produces the same plan. The execution authority should validate the plan revision and current approval before dispatching tools. Moving an agent across regions must preserve pending approvals, stable tool identities, and uncertainty about already-dispatched actions.

Anthropic's public multi-agent research account discusses coordination and production reliability. It provides workload context, not a documented internal multi-region storage protocol. Our proposed home-region execution design is original. Similarly, NVIDIA's public inference-server materials establish deployable serving infrastructure and scaling integration, not NVIDIA's private regional topology. Treat framework capabilities and your own placement policy as separate layers.

Imagine an OCI-style disaster recovery plan that switches a tenant's application stack. Global read-only plan inspection can use replicas. Editing the plan requires its authoritative revision. Executing the plan requires exclusive ownership, an approved immutable plan version, and reconciled provider actions. A standby region can prepare resources while the primary owns execution, but it must not independently dispatch conflicting volume attachments. This is the same distinction between active compute and authoritative effects applied to a familiar operational domain.

Training and accelerator economics

A synchronous training job usually needs a tightly coupled communication topology. Calling a global fleet active-active does not imply that one job should span distant regions. Wide-area communication, failure correlation, checkpoint movement, and accelerator availability can dominate useful progress. Separate the global scheduler from job-local execution. The scheduler may distribute independent jobs across regions while keeping a particular job within one suitable fabric.

Regional evacuation requires compatible checkpoints, sufficient contiguous accelerator capacity, network topology, and dataset access. A thousand spare GPUs scattered across unsuitable islands may not replace one thousand-GPU gang. Describe reserve capacity by placement shape and hardware class, not only a fleet-wide count. A cost model should include idle reserve, inter-region artifact transfer, checkpoint bandwidth, duplicated index storage, and the operator burden of additional write topologies.

How I would explain this in an interview: “The global AI platform is a composition of placement contracts. Inference replicas may be active everywhere; tenant effects remain owned; retrieval publication is versioned; and large training jobs stay within appropriate communication domains. The architecture is global without forcing every subsystem into multi-master semantics.”

Chapter summary

Use regional compute where it helps, but choose state and effect semantics independently. AI readiness includes artifact compatibility, authorization, capacity shape, and reproducible execution state.

09 · Production system design

Design a global tenant execution platform

Combine local inference, owned effects, verified artifacts, and controlled tenant movement.

Requirements, APIs, and persistent records

Design a hypothetical service for fifty thousand enterprise tenants across three workload regions. Assume 60,000 inference requests per second at peak, uneven tenant sizes, an agreed emergency throughput of full demand after one region loss, and region restrictions per tenant. Conversation writes require read-your-writes within a tenant partition. Destructive tools require exclusive execution authority. Usage analytics may converge asynchronously; hard prepaid limits require coordinated admission or explicit regional rights. These assumptions distinguish operations rather than forcing one global consistency policy.

The global gateway validates identity, operation class, tenant residency, required model version, and any consistency token. It obtains a cached routing record with a revision, chooses an eligible region, and checks regional admission. A regional inference frontend can serve approved stateless requests locally. A tenant command service forwards stateful mutations to the tenant owner. A replicated directory tracks owner, epoch, allowed regions, migration status, and current plan or deployment revision. Regional artifact controllers verify immutable model and retrieval manifests.

Use a request API containing tenant-scoped idempotency identity, requested model or alias, input references, consistency requirements, and operation class. An effectful execution API references an approved immutable workflow revision and returns a durable execution ID, not a promise that all tools completed. A migration API contains expected directory revision, destination, and transfer policy. Reject conflicting migrations with a precondition failure. Return structured stale-route responses so clients can refresh safely without treating every exception as retryable.

Store request results or their durable references according to the replay contract, tenant event lineage and sequence, ownership epochs, migration checkpoints, artifact readiness, and effect outcomes. Maintain audit evidence for ownership changes. The directory's compare-and-set must serialize conflicting transfers of one tenant. A tenant mutation transaction must validate authority within its supported effect boundary. A directory record and an unrelated database write cannot be assumed atomic just because both are durable.

Execution and failure behavior

During normal operation, inference can execute in any eligible ready region. The owner commits conversation events and returns a minimum-version token. A later local read waits or forwards if its replica lacks that frontier. Effectful tools execute through the current owner with stable action identities. Read-only analysis can be retried elsewhere according to the product's partial-output contract; irreversible tools cannot be replayed merely because the client disconnected.

If one region fails, the gateway removes it for affected operation classes and redistributes admitted inference. Owned tenants require a separate recovery workflow: establish exclusion, select a complete frontier, apply the approved loss policy, update ownership, reconcile actions, then activate. A single route flip must not implicitly authorize all those state transitions. If only the directory is unavailable, cached read-only serving can continue within valid policy bounds, while ownership movement stops. Define expiry and revocation behavior rather than granting indefinite authority to cached configuration.

At the assumed 60,000 requests per second, the earlier three-region capacity model requires each survivor to handle 30,000 at target latency. Stateful demand may be much lower but skewed: one tenant can generate a large fraction of writes. Protect the owner with per-tenant concurrency, bounded queues, and separate budgets for migration and normal traffic. Do not move hot tenants during a crisis without accounting for copy bandwidth and recovery contention. A balanced request gateway does not guarantee balanced database ownership.

Security, observability, rollout, and alternatives

Every forwarding hop preserves authenticated tenant context without trusting arbitrary client headers. Service-to-service identities are scoped to allowed operations and regions. Migration validates destination residency, key availability, retention rules, and audit access before copying data. Encrypting data does not make an otherwise prohibited regional transfer acceptable. Admission rights, consistency tokens, and ownership epochs are different credentials; none should accidentally become an authorization bypass.

Measure per-operation availability, regional admission rejection, stale-route retries, token wait time, replica frontier age, owner forwarding latency, migration duration, and stale-authority rejections. Track business completion separately from accepted execution. A runbook includes disabling one operation class, freezing migration, preserving unknown-effect evidence, shedding demand, and choosing a recovery frontier. Test returning regions with old routing records and paused workers, not only clean process restarts.

Roll out by adding read-only replicas and version-aware reads before distributing write ownership. Move a small set of tenants, verify invariants, and retain an explicit stop condition. Schema changes need compatibility across old and new owners; data migration cannot rely on a binary rollback if the schema transformation is irreversible. Compare a simpler single-writer service, partitioned active-active, a global transactional datastore, and independently mergeable data. Choose based on operation semantics, measured latency, failure objectives, and operational staffing, then document what workload change would invalidate the decision.

Chapter summary

A global service can combine local compute with owned effects and version-aware reads. The architecture is defensible when every route, state transition, and failure response follows an explicit operation contract.

10 · Executable models and operational proof

Test convergence and failure capacity separately

Small executable models expose assumptions; integrated drills test the complete service.

Merge algebra and regional headroom

The executable Python model below implements a grow-only counter merge and a one-region-loss capacity check. These are deliberately separate functions. One proves a useful data algebra on sample states; the other checks a simplified capacity envelope. Neither function models authorization, replication durability, real routing convergence, or external effects. A strong engineer states these exclusions before applying a toy model to an architecture decision.

The merge function takes the union of writer identities and the maximum observed value for each writer. Its inputs must be nonnegative integer components maintained monotonically by stable writers. The assertions test commutativity, duplicate-delivery idempotence, and one associativity example. They are illustrative tests, not a mathematical proof over arbitrary inputs. The proof follows from maximum having those properties independently for every component. Summing the merged components gives 172 for the worked counter example.

The capacity function uses total demand, number of regions, and each region's measured usable ceiling. Under uniform redistribution after one loss, each survivor receives total demand divided by the surviving region count. It returns both that load and a boolean feasibility result. Real systems need skew, priority classes, placement constraints, and correlated failures; the model is a lower-complexity sanity check. A feasible aggregate number does not prove every tenant or GPU placement can be served.

PYTHON · executable standard-library model
def merge(left, right):
    if any(type(v) is not int or v < 0 for v in [*left.values(), *right.values()]):
        raise ValueError('counter components must be nonnegative integers')
    return {key: max(left.get(key, 0), right.get(key, 0))
            for key in left.keys() | right.keys()}

def after_region_loss(total_demand, regions, usable_per_region):
    if total_demand < 0 or regions < 2 or usable_per_region <= 0:
        raise ValueError('invalid capacity model')
    load = total_demand / (regions - 1)
    return load, load <= usable_per_region

x, y, z = {'A': 107, 'B': 60}, {'A': 100, 'B': 65}, {'C': 3}
assert merge(x, y) == merge(y, x)
assert merge(x, x) == x
assert merge(merge(x, y), z) == merge(x, merge(y, z))
assert sum(merge(x, y).values()) == 172
load, feasible = after_region_loss(60_000, 3, 40_000)
assert load == 30_000 and feasible
assert after_region_loss(60_000, 3, 28_000)[1] is False
assert all(5 - failed >= 3 for failed in [2, 2, 1])
print('merged usage:', sum(merge(x, y).values()))
print('failure-state utilization:', load / 40_000)

The code uses only the Python standard library and prints the converged total and 75 percent failure-state utilization for the original example. Merging two maps requires time proportional to the distinct writer identities in them and space proportional to the output identities. With a stable bounded region set, this is small; with unbounded per-process identities, metadata grows. Membership retirement must preserve correctness before components can be discarded. This is a concrete example of an algorithmic property creating an operational lifecycle requirement.

Failure drills, consistency checks, and cost

Build a test matrix that separates a region crash, an asymmetric partition, stale directory caches, clock skew, delayed replication, and simultaneous schema versions. A clean shutdown exercises the easiest case. Suspend an old writer, promote a new owner, then resume the old process and demonstrate that its protected mutations are rejected. Duplicate migration notifications and provider responses. Keep evidence of each accepted operation so the test can detect loss or duplication rather than only inspect aggregate counters.

For reads, test a client that writes in one region and reconnects to another with a version token. Inject a lagging cache as well as a lagging database. For mergeable state, replay messages in different orders and repeat them. For quotas, verify that converged usage can exceed a limit unless admission rights or coordination enforce it. For residency, make the nearest region disallowed and prove the gateway does not silently select it during overload.

Compare the cost of idle reserve, duplicated storage and indexes, inter-region writes, replication bandwidth, request forwarding, and operator complexity. A three-region active-active compute fleet can improve normal utilization while still requiring reserve for a region loss. Multi-master conflict handling can consume more engineering effort than the compute it saves. Include migration, testing, and incident response in the ownership model. A useful architecture decision record names the business contract, evidence, rejected alternatives, and the threshold for changing the design.

Chapter summary

Validate algebra, state authority, read observations, failure capacity, and residency as separate properties. An architecture becomes credible when integrated tests cover their interactions rather than only their isolated happy paths.

11 · Original interview practice

Defend the topology when the requirements change

These questions are original preparation, not claims about any company's interviews.

Twelve Senior Staff questions

1. Two regions both serve traffic. Is the system active-active?

Evaluation: semantic precision. It is active-active for the specified serving workload, but that does not establish write authority. Identify whether reads, stateless inference, tenant partitions, or the same mutable record are active in both places. Trace one request through ingress, state, and effect owners. Follow-up: all writes still go to A. Explain the partition behavior. Common mistake: inferring multi-master from two load-balancer backends. Tradeoff: global compute with one writer may be simpler but retains write locality and failover constraints.

2. Can we accept conflicting writes in both isolated regions and preserve a global hard quota?

Evaluation: invariant reasoning. Not with unconstrained local approvals based on incomplete state. A convergent counter may accurately reveal an overspend afterward. Use coordinated admission, exclusive ownership, or preallocated spending rights whose total never exceeds the quota. Follow-up: one region exhausts its rights while another is idle. State the temporary availability cost. Common mistake: equating merge correctness with quota enforcement. Tradeoff: rights improve partition-time autonomy but require careful transfer and can strand capacity.

3. Why not resolve every conflict with the latest timestamp?

Evaluation: business semantics. A total ordering can converge while discarding a legitimate concurrent action, and physical clocks may not reflect real-time order. Define whether the operation is replace, append, increment, remove, or an irreversible effect. Choose an appropriate merge or owner. Follow-up: two regions revoke different permissions. Explain why arbitrary replacement may restore access incorrectly. Common mistake: treating deterministic resolution as semantic correctness. Tradeoff: richer merge preserves meaning but adds metadata and product complexity.

4. How do you move a tenant without creating two writers?

Evaluation: transition design. Prepare the destination, capture a complete transfer frontier, drain or reconcile effects, atomically change authoritative ownership, and enforce stale-owner exclusion. Handle old route caches with versioned responses and stable retries. Follow-up: the coordinator dies after ownership changes. Recover from the authority rather than undoing based on a missing notification. Common mistake: updating DNS before data and exclusion are ready. Tradeoff: a brief per-tenant write pause simplifies the transition; avoiding it requires a stronger forwarding protocol.

5. A user reads stale state after changing regions. What guarantee do you offer?

Evaluation: observable consistency. Return a partition-and-lineage-aware minimum-version token with the write. Serve only from a path that includes that frontier, otherwise wait, forward, or return a defined consistency-unavailable result. Include caches in the predicate. Follow-up: a lossy failover removed the required write. Explain the unsatisfied token rather than waiting forever. Common mistake: relying exclusively on affinity cookies. Tradeoff: token-aware local reads reduce remote load but add waiting and protocol complexity.

6. Does five voters in three regions guarantee regional availability?

Evaluation: placement and communication reasoning. Count the surviving connected voters for each failure set. A 2–2–1 placement retains a majority after any single region loss if survivors communicate. A partition can still prevent progress. Follow-up: remove the single-voter region and partition the other two. Each has only two. Common mistake: counting replicas without locating them. Tradeoff: more regions improve failure coverage but add remote acknowledgment costs and operational dependencies.

7. Can a route flip complete failover?

Evaluation: separation of concerns. Routing directs requests; ownership and state recovery establish whether the destination may safely process them. Check complete data, authority, policy, capacity, and unknown effects before enabling writes. Existing connections may continue reaching the old region. Follow-up: how are those old requests rejected or redirected? Show the boundary. Common mistake: using DNS TTL as an exclusive-owner mechanism. Tradeoff: explicit readiness can delay traffic but prevents unsafe partial recovery.

8. The platform has enough total GPUs after a region fails. Are we safe?

Evaluation: capacity shape. Determine model compatibility, memory, topology, tenancy, request distribution, and latency at each surviving region. A training gang needs a suitable connected placement; scattered GPUs may be unusable. Inference routing can be temporarily skewed. Follow-up: a new model lowers usable throughput. Recompute the emergency envelope. Common mistake: equating fleet count with usable capacity. Tradeoff: shape-aware reserves cost more but support the actual failure contract.

9. Why keep agent effects in a home region if model inference is global?

Evaluation: state/effect boundaries. Model compute can be rerouted while a durable owner serializes execution state, approvals, and tool identities. This avoids arbitrary same-action concurrency across regions. Moving ownership preserves pending and unknown effects. Follow-up: the tool completed before the owner crashed. Query or replay under the provider contract. Common mistake: assuming regenerating a plan reconstructs external outcomes. Tradeoff: owned effects simplify correctness while adding forwarding latency and migration work.

10. What changes when residency forbids the nearest healthy region?

Evaluation: policy under failure. Eligible destinations are the intersection of health, artifact readiness, capacity, and authorized residency. Reject or queue under the declared policy if that set is empty. A global outage is not permission to copy data anywhere. Follow-up: can an encrypted prompt cross the boundary? Consult the actual policy; encryption alone does not authorize transfer. Common mistake: treating compliance as a steady-state-only concern. Tradeoff: regional constraints can reduce availability and require dedicated reserve.

11. Is a cross-shard transfer atomic because both shards use consensus?

Evaluation: transaction scope. Each group orders its own state. A transfer requires additional coordination, reservations with explicit partial states, or colocation under one atomic boundary. Explain coordinator failure and recovery. Follow-up: a debit committed but credit is uncertain. Reconcile using a stable transfer identity. Common mistake: extending a group guarantee to the whole database without evidence. Tradeoff: global transactions simplify application invariants but may add latency, contention, and reduced availability.

12. Leadership insists on active-active. How do you choose the actual design?

Evaluation: architectural leadership. Translate the label into operations, latency, loss, partition behavior, locality, and budget. Offer several topologies with concrete failure traces. Use public designs as evidence for principles, not endorsements of one universal answer. Follow-up: only user preferences need independent partition-time writes. Keep stronger ownership for destructive effects. Common mistake: turning a topology preference into a blanket consistency policy. Tradeoff: mixed semantics require a clear API but avoid unnecessary global coordination.

Architecture defense: local writes everywhere, no lost effects

The interviewer asks for instant local writes in every region, arbitrary partitions, no lost updates, no duplicate destructive actions, and zero coordination latency. Clarify which operations are mergeable and which require a single business outcome. A strong response partitions the requirement: accept local analytics and suitable CRDT updates, route owned effects to their authority or spend exclusive preallocated rights, and reject unsafe operations when proof is unavailable. Show a counterexample where two regions independently approve the final unit of a quota. Then negotiate latency or availability for that invariant. The model solution is a defensible contract, not a fictional protocol that removes uncertainty.

Chapter summary

Defend a topology by tracing operations under failure. Strong answers distinguish convergence, single ownership, global coordination, read observations, and usable capacity.

12 · Speaking and recall

Explain a global design without hiding its tradeoffs

Build a precise spoken answer at three levels of detail.

Thirty-second explanation

Active-active describes where a workload runs, not automatically who can write its data. I separate ingress, compute, state, and effect ownership. Global reads can use replicas; tenant writes can keep one owner; suitable operations can merge; and strong global writes require coordination. I choose per operation, then test partitions, stale routes, capacity loss, and recovery.

Two-minute explanation

I would first ask which operations need local latency, what must remain available during a partition, and which invariants cannot be relaxed. An inference request, a conversation append, a usage counter, and a destructive tool action need different semantics. A two-region diagram is not enough to answer those questions.

My default candidate is globally active compute with tenant-owned writes. Requests can enter locally, but the tenant owner orders mutations and effects. A revisioned directory and supported resource-side exclusion govern ownership changes. Version-aware reads preserve the client's required frontier when it moves regions. Immutable model and retrieval manifests establish regional readiness.

If the business requires independent writes to the same data, I choose merge semantics explicitly. A convergent usage counter does not enforce a hard quota, so admission needs coordination or exclusive rights. If we instead use globally coordinated writes, I locate the voters and calculate which regional failures preserve a connected quorum. Then I measure the remote acknowledgment path.

Finally, I size surviving regions under real workload distributions, enforce residency during failover, and test returning stale owners. I would recommend the simplest mix of topologies that meets the operation contracts, with a decision record showing the evidence and what changes would force a new design.

Five-minute explanation

Suppose we need an enterprise AI platform serving tenants across three regions. I would begin by separating read-only inference, conversation state, retrieval publication, usage accounting, and effectful agent execution. Then I would ask about latency, acknowledged loss, residency, emergency capacity, and what happens during a partition. These requirements determine authority; the load balancer does not.

For inference, several regions can be active if they have compatible model, tokenizer, runtime, policy, and capacity. I would publish immutable artifacts and record readiness per region before routing a tenant's pinned version there. Retrieval indexes also need versioned publication, with authorization checked under a separate revocation contract. A fresh index is not necessarily a safe index if policy is stale.

For stateful execution, I would initially use one owner per tenant partition. Both regions can own different tenants, giving active-active service without conflicting writers for one tenant. A revisioned directory directs requests. A migration prepares the destination, establishes a complete transfer frontier, drains or reconciles effects, transfers authoritative ownership, and enforces exclusion of the old owner. Stale frontends refresh their route and retry the same logical request identity.

Reads need their own contract. After a write, the server can return a partition-and-lineage-aware minimum-version token. A local replica serves only if its full read path, including caches, includes that frontier. Otherwise it waits, forwards, or returns an explicit consistency-unavailable result. A lossy recovery cannot satisfy a token for a missing old-lineage write merely by reaching the same sequence number in a new history.

If some operations must accept local writes in both isolated regions, I would choose their merge semantics carefully. A grow-only counter can merge per-writer maxima and converge despite duplicate state delivery. That helps analytics, but it does not prevent overspending a global quota. For a hard bound, I would coordinate admission or allocate exclusive rights whose total respects the limit. Irreversible tools still need an effect owner and outcome reconciliation.

For a global transactional datastore, I would inspect its actual guarantees rather than infer them from replica counts. With five voters placed two, two, and one, any single region loss leaves a majority if survivors communicate. The leader still needs remote evidence, and cross-partition transactions add another layer. Network round trips, storage persistence, queuing, and client forwarding all contribute to the measured path.

I would also prove capacity and operations. Three regions serving sixty thousand requests per second need surviving capacity for thirty thousand each under uniform failover, plus tolerance for skew. Model changes can invalidate that envelope. Residency can make an otherwise healthy region ineligible. I would test asymmetric partitions, paused old writers, stale directory entries, lagging caches, and incompatible deployment versions. The result is a global architecture built from precise contracts, rather than one active-active label that hides contradictory promises.

Important concepts and final cheat sheet

  • Ingress: where a request arrives.
  • Write authority: who may order a mutation.
  • Effect ownership: who may dispatch a business action.
  • Home region: a partition's designated owner.
  • Ownership epoch: the generation used to exclude stale owners.
  • Transfer frontier: complete state required before movement.
  • Lineage: the history that gives a version meaning.
  • Session token: evidence of a minimum required frontier.
  • Convergence: replicas eventually agree under the type's assumptions.
  • Invariant: a business property every allowed state must preserve.
  • Admission rights: exclusive capacity to approve bounded work.
  • Quorum placement: replicas arranged for named failure sets.
  • Regional readiness: state, artifacts, policy, and capacity are usable.
  • Failure headroom: capacity reserved for the surviving workload.

Avoid saying “eventual consistency is fine” without naming the operation and user observation. Avoid promising zero downtime from DNS, exactly-once effects from a replicated log, or strong consistency from quorum arithmetic alone. Replace each shortcut with a failure trace and a supported boundary.

Whiteboard and speaking practice

In thirty seconds, distinguish active ingress from active write ownership. In two minutes, show why a converged usage counter can still exceed a quota. In five minutes, defend the tenant platform while the interviewer removes one region and forbids cross-border data movement. On a whiteboard, draw request routing, data replication, ownership, and external effects with different boundaries. Inject one stale directory record and one resumed old writer.
