SD-006 · Distributed Systems Foundations · 01

Begin with a promise that two regions cannot both verify

A model-serving gateway in Dublin is still answering requests. Its control plane in Phoenix has stopped responding. A deployment operator asks whether the gateway can report the current model version. What exactly would a successful answer certify?

Worked example 1 · Two histories behind one timeout

At nine o'clock both sites agree that the current revision of the translation model is seventeen. The gateway caches revision seventeen and its immutable artifact. At nine oh one, messages between Dublin and Phoenix stop arriving in either direction. Clients can still reach both sites. In the first history, the deployment operator stays home and no write occurs. In the second history, the operator asks Phoenix to move the model pointer to revision eighteen. Phoenix replies that the change succeeded. After that reply, a different client in Dublin asks for the current pointer. No Dublin process has received a single bit distinguishing these two histories.

If Dublin must answer successfully using its local state, it has to take the same action in both histories. Answering seventeen is correct in the first and violates the completed write in the second. Guessing eighteen fails in the first and would fail just as badly if the operator had published nineteen instead. Waiting for Phoenix preserves the possibility of a correct answer but cannot guarantee eventual completion when the partition endures forever. Returning an explicit cannot establish current revision is honest and can be a useful product behavior. It relinquishes successful availability of the specified read.

Moving the decision to Phoenix does not evade the reasoning. If Phoenix waits for Dublin before acknowledging the write, the first half of the second history never completes while the partition persists. That policy can preserve the register specification by withholding the write success. It still gives up the promise that every request at a live site eventually succeeds. A retry routed to a third region helps only when the actual connectivity and client routing let every affected operation reach sufficient authority. A proof can choose a partition that cuts the necessary path.

The counterexample uses one value, one write and one later read. There are no simultaneous writers to merge. The real-time relationship is essential: Phoenix completed its response before Dublin's read began. Had the operations overlapped, either ordering could be consistent with the abstract register. In a test harness one client can wait for the write response and then signal a second client to invoke the read through an independent channel. The channel controls test invocations; it must not secretly transmit the new value into the replica whose knowledge the proof analyzes.

Translate the theorem into an API contract

The consistency property in this example is linearizability for a read/write register. Each completed operation must appear to take effect at a single instant between invocation and response, respecting the real-time order of nonoverlapping operations. The availability property is eventual successful completion at nonfailed participants under the modeled failure. It is a liveness property with no promise that a response arrives within a particular number of milliseconds. Partition tolerance means the system's claim must address executions in which messages between groups can be lost indefinitely. It is a statement about the executions under consideration, not an optional checkbox that restores connectivity.

A useful response begins with the object and the verb. GetCurrentRevision asks a stronger question than GetArtifactByDigest. A site that already has immutable bytes can answer the second from local storage, checking the requested digest and access authorization. The same site can truthfully expose LastAppliedRevision with the observed revision and evidence of local application. Neither endpoint purports to answer what an isolated authority may have changed since then. Defining a weaker but useful operation can preserve product functionality while the strongest operation waits. The client must be able to see that choice in the endpoint or response contract.

For a read-aloud interview answer, I would draw one completed write on the left and two indistinguishable worlds on the right. Then I would name the exact request that can still succeed. In this case the customer may continue translating with an already pinned model under a separately specified policy. The customer cannot both require the newest published pointer and insist that an isolated replica always answer. That distinction converts a theorem about a register into an operational decision about a serving product.

Specify which failures count as partitions

A service has five replicas, all running, yet an operator on one side cannot complete a conditional update. Healthy processes and reachable authority measure different things. A topology drawing only helps when its arrows represent the actual message paths an operation requires.

Worked example 2 · A majority exists beyond the client

Place three voting replicas in site X and two in site Y. The five form one fixed consensus group. When the sites lose mutual connectivity, X can potentially commit a current-term command using its local three, assuming a valid leader, durable storage and functioning links inside X. The two voters in Y cannot form a majority. A client that can reach only Y receives a retryable error or waits for recovery. The group can remain operational for some clients while failing the formal guarantee at other live participants. A workload monitor located exclusively in X can report perfect availability throughout the event.

Now put the client in X but leave its authentication service in Y. The database still has a majority, yet the request may fail before reaching it. Alternatively, credentials may be cached under an explicit expiration policy, allowing reads but withholding credential-sensitive mutations. The object-level CAP analysis remains intact. The service-level availability calculation now depends on authentication, admission control, discovery and data readiness as well. Draw paths from the user to the stated outcome. Counting database voters alone can substantially overestimate what the user can actually accomplish.

Reverse one network edge. X can send heartbeat requests to Y, but replies to X get dropped. A packet counter at Y suggests connectivity, while a request waiting for acknowledgments at X cannot complete a round trip. Add a third site Z that can communicate with both. Some protocols can use Z to reach a legal quorum; some clients have no route through Z, and some designs do not forward messages along that path at all. Annotate each arrow with direction, protocol, authorization and whether the implementation forwards traffic. A region-level diagram with a green line connecting each pair hides these differences.

A prolonged delay is operationally indistinguishable from a partition when it exceeds the request's deadline. The mathematical model for the impossibility proof allows indefinite loss. A finite outage followed by repair has a different liveness argument if requests are allowed to wait through it. Product budgets make that distinction concrete: an order that succeeds after thirty minutes may satisfy an unbounded eventual completion statement but violate a two-second checkout target. Tell the interviewer both the fault model used in the proof and the deadlines used for the product.

Trace independent failure domains

Suppose a witness deployed in a third availability zone stores the durable information an implementation requires to participate in decisions. Its usefulness depends on both sites' ability to reach it, on its own data and voting semantics and on whether it has correlated dependencies. A process that merely casts whichever vote a caller asks for can create two incompatible majorities. An arbitrator that safely chooses one side must persist its obligations through restarts and enforce the protocol when asked by the other side. Purchasing an extra small virtual machine is not an independent correctness argument.

Independence matters on the data path too. A strongly replicated pointer can identify an artifact stored only in a disconnected object store. The control plane may truthfully report the committed current model, while the local server cannot load it. If the customer promise is that a successfully published model can immediately be served in each region, the acknowledgment also needs evidence about artifact distribution and readiness. Capture that requirement in a publication protocol, or provide separate statuses for committed, staged and locally ready. Each status has its own failure paths and its own valid success criteria.

What to say during a topology review

I would ask which participants can send which messages, which replies they must receive and where each client enters. I would also ask what remains durable when a voter or storage service restarts. A fault may disconnect only an acknowledgment path or only the role that authorizes writes. When I claim a partitioned system remains usable, I identify the successful operation, the eligible callers and any stricter operations that must wait. I would test from both sides because a single successful probe proves little about the isolated user's experience.

SD-006 · Distributed Systems Foundations · 03

Put latency on the healthy path with PACELC

A system that rarely partitions can spend almost every healthy minute paying for remote coordination. PACELC asks about that ordinary cost as well as the exceptional behavior when communication breaks.

Worked example 3 · Price a conditional publication

Consider a regional control service with leader A and followers B and C. It commits a pointer update after persisting locally and obtaining a durable acknowledgment from at least one follower for a valid current-term entry. B is nearby; C is on the other side of an ocean. In a particular trace local persistence takes four milliseconds, B's acknowledgment arrives at eight, and C's at seventy. The leader dispatches concurrently with local persistence. Its first possible commit is the larger of four and the smaller of eight and seventy, or eight milliseconds. Add three milliseconds of client transit and two of deterministic apply work. The client sees thirteen milliseconds.

Remove B while retaining the path to C. There are still two voters and the same abstract write can succeed. Now the first eligible follower acknowledgment arrives at seventy milliseconds. The client sees roughly seventy-five milliseconds in the otherwise identical trace. Move the client near C while the leader remains at A and the costs change again because ingress may add an additional long round trip. If the leader fsyncs before dispatch rather than in parallel, use a sum for that dependency instead of a maximum. A latency estimate is only as meaningful as its account of execution order.

Consider a cheaper acknowledgment in which A returns after recording its own local update and ships changes asynchronously. A client at C may still read the old pointer after this success. If A is destroyed before replication survives elsewhere, the completed change may disappear under failover. These are two different weakened properties: remote freshness and survival of an acknowledged write under a specified loss. An architecture can weaken one without necessarily weakening the other. For example, a write may be synchronously durable on multiple nodes and still be read stale from a lagging nonvoter. Ask which cost the cheaper acknowledgment actually removes.

Abadi's PACELC framing asks what happens if communication is partitioned and what latency-versus-consistency choice matters otherwise. It is a design lens. It does not prove that every request for strong consistency always takes a cross-region round trip. If the only writer is local and properly holds a valid authority lease, some strong reads can be local under stated timing assumptions. If the application asks for a historical snapshot at an already safe timestamp, the serving replica can sometimes prove the requested prefix is available locally. Details of placement, session, workload and read type change the achievable tradeoff.

Separate the latency distributions

Suppose 99.5 percent of reads are served from a local pinned version in four milliseconds and the rest request the current revision through a remote leader at eighty milliseconds. An aggregate p99 can remain near four even when every current-revision read becomes intolerably slow. Conversely, an incident that shifts the share of strong reads from half a percent to two percent can cause a sharp jump in aggregate p99 while each individual path's performance remains unchanged. Report latency and success by requested semantics and region. Include the path selected after any fallback, otherwise a dashboard may reward silent degradation.

Averages also hide queueing caused by a slow remote peer. Picture a fixed worker pool holding open requests until a quorum responds. Replacing an eight-millisecond dependency with a seventy-millisecond dependency increases concurrency needed for a fixed arrival rate. At a thousand requests per second, Little's law gives about eight outstanding requests during an eight-millisecond mean wait and seventy during a seventy-millisecond mean wait. That comparison assumes steady state and isolates this waiting stage. It does not license using p99 in place of the mean for an exact concurrency estimate. An implementation needs headroom for variance and separate admission capacity for urgent control actions.

PYTHON · executable model
def first_commit_ms(local_flush, follower_durable_times, followers_needed):
    # One trace with parallel dispatch, fixed membership and durable matches.
    if followers_needed < 0 or local_flush < 0:
        raise ValueError("invalid timing or quorum")
    times = sorted(follower_durable_times)
    if len(times) < followers_needed:
        return None
    kth = times[followers_needed - 1] if followers_needed else 0
    return max(local_flush, kth)

assert first_commit_ms(4, [8, 70], 1) == 8
assert first_commit_ms(4, [70], 1) == 70
assert first_commit_ms(4, [], 1) is None

Speaking through a healthy-day decision

My normal-path design starts with a concrete response contract. A pinned model can be fetched near the customer, a conditional change of the deployment pointer needs serialized authority, and a security revocation needs an enforcement deadline I can verify. I calculate each critical path under normal placement and under the loss of the cheapest quorum member. Then I ask whether the expensive operation happens on every generated token, on every new session or only on a deployment. Moving coordination to the narrowest boundary that preserves the promise can change cost by orders of magnitude.

SD-006 · Distributed Systems Foundations · 04

Decide what disconnected regions may safely change

Two regions accepting writes can converge to identical state after repair and still have broken their business promise during the outage. Analyze which updates can be merged and which rights must be allocated before separation.

Worked example 4 · Spend a bounded GPU quota locally

A customer owns a quota of one hundred concurrent GPU reservations. Both East and West initially see eighty in use. During a partition, East accepts fifteen new reservations and West independently accepts fifteen. Each local view remains at ninety-five. After merging, the distinct active reservations total one hundred ten. A last-writer-wins counter might display ninety-five and conceal the ten excess allocations. A set of reservation IDs would show the full total correctly but cannot retroactively keep the system under quota. Correct representation and preservation of a global bound are separate problems.

An alternative allocates the remaining twenty rights before the partition. Suppose East owns fourteen spendable rights and West owns six. Each region can issue new reservations only by durably consuming its own rights. East can now accept fourteen and reject or queue its fifteenth; West can accept six and queue the other nine. Combined admissions cannot exceed twenty so long as rights are neither duplicated nor consumed twice. The cost is uneven utilization: East may be full even if West has unused rights that East cannot safely borrow. A local rejection can coexist with spare global capacity.

Track operations rather than reconstructing them from a number. Each right or bounded allotment belongs to one authority at a time. A transfer of four rights from East to West must subtract them from East before West can make them spendable and ensure retries cannot credit West twice. A lost transfer acknowledgment may strand four temporarily. The transfer protocol can use a stable identity and an authoritative state transition or durable outbox/inbox mechanism with precisely specified debit and credit semantics. If it cannot prove the outcome during a partition, leave the rights unavailable until reconciliation. Making both regions optimistically count them would abandon the bound the design was introduced to preserve.

Release raises its own question. A reservation marked complete by a stale scheduler might still occupy physical hardware. Decide whether the quota bounds admitted reservations, active provider instances or simultaneously running processes. Releasing a right when a termination request is issued can exceed the physical bound if the provider delays termination. If the requirement concerns actual execution, observe or enforce termination at the device boundary before returning capacity. An interview answer that solves the arithmetic but omits the resource's state machine has solved only the accounting layer.

Merge a different operation

A fleet incident tracker lets each region append immutable diagnostic observations with unique IDs. Concurrent observations can often merge by set union. Reapplying the same observation changes nothing. The resulting aggregate is independent of arrival order if IDs really identify immutable observations and all accepted records eventually reach the replicas under repair. This is a good candidate for accepting locally during a partition. A decision to close the incident because all regions are healthy is a different operation: each side may lack current evidence from the other. The write type and invariant determine which path needs coordination.

Deletes complicate even simple collections. If an observation can be removed, a recovering replica carrying an old copy may reintroduce it unless removal semantics and retention are defined. A tombstone marks deletion but deserves a lifetime tied to the maximum permitted replay or an explicit full resynchronization procedure. A merge function alone does not grant infinite retention at zero cost. Decide what a node must do after it has been disconnected longer than the repair window. Rebuilding from an authoritative snapshot can be cheaper and safer than merging a month-old image under assumptions intended for short outages.

PYTHON · executable model
def spend(rights, requested):
    # A local state transition; durable, atomic application is a separate requirement.
    if min(rights, requested) < 0:
        raise ValueError("negative capacity")
    accepted = min(rights, requested)
    return rights - accepted, accepted

east_left, east_used = spend(14, 15)
west_left, west_used = spend(6, 15)
assert 80 + east_used + west_used == 100

Frame the decision as a proof obligation

For any operation you want to admit locally, start with two valid states sharing a common ancestor. Apply independent locally legal operations on each side. Merge them and ask whether the invariant still holds and whether each earlier returned success was truthful. If you find a counterexample, change the representation, restrict available rights, change the promise, or coordinate. The quota example fails with plain local counters and can preserve its bound with nonduplicated rights. Reconciliation repairs what can be repaired; it cannot make a once-violated real-world exclusivity promise continuously true.

SD-006 · Distributed Systems Foundations · 05

Design a multi-region model release service

A model platform serves inference near customers and deploys new artifacts a few times each day. Product wants low-latency inference during a WAN outage, no conflicting rollout decisions, and immediate emergency withdrawal of an unsafe version everywhere.

Negotiate the incompatible parts before drawing boxes

Give the platform a deployment register per tenant and model. A release is a conditional command proposing a new immutable manifest digest against an expected revision. The register records the accepted revision and operation identity. A regional distributor stages the immutable bytes and verifies their integrity. A regional serving gate admits new sessions for a chosen digest according to its locally installed policy. Existing streams pin the selected version for their documented lifetime. These components have separate responsibilities because a single replicated metadata commit cannot instantaneously load a model on every GPU or stop a stream already emitting tokens.

Define PublishDesired to mean the authority accepted the new desired version. GetDeployment reports that desired revision along with per-region stage and readiness evidence. BeginSession carries a policy specifying whether a pinned locally ready revision is acceptable or whether the client requires the current authority-confirmed revision. Report the chosen revision, region and admission policy in the session metadata. Do not use the same unlabeled success response for both. A user debugging a regression needs to know which weights actually served the request, not which pointer the deployment dashboard had most recently observed.

Now focus on emergency withdrawal. If a disconnected region can indefinitely admit new sessions for a previously permitted model, it cannot also guarantee that a remote withdrawal immediately stops those admissions. The local region sees the same inputs in two executions: no withdrawal during the partition and a withdrawal acknowledged elsewhere. To ensure no new admission after a global success response, one option waits for every required admission gate to install and durably confirm the withdrawal before acknowledging completion. A missing region delays commitment of that product-level success even if the desired revocation is already durable at the control authority.

A different policy grants short-lived permissions to continue serving within a bounded offline window. The permission must be scoped to region, tenant, model and allowed revisions. If clocks and suspend behavior meet explicit bounds, the local gate stops new admissions before its conservative validity expires. The authority must account for every outstanding grant when claiming universal enforcement. A revocation request can be accepted immediately, then become globally effective after all acknowledgments or after a defensible upper bound on outstanding grants. If the requirement demands zero delay from the operator's click under an arbitrary partition, bounded windows still do not meet it. Document a smaller availability promise or renegotiate the withdrawal deadline.

Worked example 5 · Publish, withdraw and recover

Three regions serve revision twenty. The administrator publishes revision twenty-one using key K with expected revision twenty. The authority commits revision twenty-one. Regions East and South have verified the digest and marked it ready. West is cut off with only revision twenty loaded and a valid offline permit for that revision. A strong BeginSession at West must establish the current permitted revision and the ability to serve it, so it fails or waits. A request explicitly accepting the earlier permitted local version may use twenty until its permit expires. Pin the stream to twenty and record when its authorization must be rechecked or the stream terminated.

The incident commander discovers an issue in revision twenty and submits Withdraw with request W. The authority now forbids new permits for twenty. East and South install the denial. West cannot receive it. Return an accurate intermediate state indicating withdrawal accepted, two regions confirmed and one outstanding permit. If an emergency procedure can independently cut traffic to West, determine which clients can bypass that route and whether already-open connections keep producing output. A traffic manager change may change future DNS answers without touching clients using cached addresses. A successful control-plane operation is not evidence that all admission paths have closed.

When West reconnects it has telemetry about sessions accepted while isolated, a cached pointer at twenty and possibly queued requests for newer versions. First synchronize the current policy and membership generation through an authoritative path. Install revocations before admitting or replaying old work. Discard queued admissions whose client deadlines or permissions have expired. Reconcile actual loaded digests with desired state and report observed rollout status. Never compare unsynchronized host timestamps to decide that West's older cached policy should overwrite a committed withdrawal. Test rejoin with messages delivered in reverse order, including a delayed allow for twenty arriving after deny for twenty.

Data model and interfaces

Use immutable manifest IDs and monotonic deployment revisions within one lineage. The authority's deployment record includes tenant, model, generation, desired digest, policy revision, expected-revision comparison result and durable outcomes for retried administrative requests. A separate table ties permits to their resource scope, issuance and expiration evidence, and possibly a revocation watermark. Regional state records installed policy generation, loaded digest inventory, readiness, and last successfully synchronized control revision. A local admission journal stores enough to investigate serving decisions without synchronously sending per-token data over the WAN. Protect that journal according to the sensitivity of tenant metadata and minimize the information collected.

The publication path validates authorization and immutable references, commits intent, distributes it and waits only for the readiness level declared by the caller. A strict path may require all selected regions. A canary path may require a named subset. Do not silently substitute whichever regions replied first when the deployment policy named particular regions for compliance or workload diversity. Authenticate leader and distributor identities, protect per-tenant namespaces, reject commands from obsolete lineages and validate digests before activation. A stale permissive policy can look authentic if keys remain valid, so freshness and provenance are independent checks.

At 200,000 inference requests per second, placing one remote read on each request adds 200,000 authority queries per second before retries. Suppose there are 800 regional model gates renewing every ten seconds. Their average is eighty renewals per second under a stable schedule. These two loads have different failure semantics. Batching permission changes can greatly reduce healthy-day traffic, but a shorter permission lifetime tightens the margin for renewal during jitter or regional overload. A reconnect storm can synchronize renewals. Use staggered renewal times, reserved control capacity, and caps on artifact reload concurrency to avoid turning a transient partition into a prolonged outage after healing.

Defend the architecture

I would start with local pinned inference, a strongly ordered deployment register, and an explicit effective-withdrawal API that exposes its actual scope. I would ask product to choose between longer disconnected serving and faster universal withdrawal for each model risk tier. For the most sensitive tier I can require recent authority evidence at admission and fail closed when it expires. A public demonstration model might tolerate a longer offline window. Each policy needs a path for existing streams, cached routing and process restarts. The resulting contract describes what a customer experiences and what an operator can prove, even when regions disagree about the present.

Plan failover without confusing freshness with durability

During an OCI-style regional recovery exercise, a replica is healthy and the database team can promote it. A customer asks whether promotion loses any acknowledged transactions. The answer depends on the commit acknowledgment, the replication boundary and the history available after the failure.

Worked example 6 · Choose a recovery point from incomplete evidence

Suppose Portland acknowledged commits through sequence 12,443. Its asynchronous destination in Chicago has durably applied through 12,430 and has received but not yet applied through 12,438. A monitoring dashboard last sampled the source at 12,441, then lost connectivity. Do not infer from the dashboard that three or thirteen writes were definitely lost. In the hypothetical full history we know the source acknowledged through 12,443. An operator during the event may know only a lower bound from the last sample and a destination receive watermark whose durability and replayability must be verified.

If 12,438 is durably present at the recovery site, intact and replayable as a contiguous prefix, recovery may be able to apply up to it before promotion. If those records were merely buffered in memory, only the applied durable prefix may be available after a simultaneous receiver crash. Check the database's actual contracts for receipt, flush and apply. For a clean test where every sequence corresponds to one transaction and acknowledged history is known, promotion at 12,438 omits five source transactions. That count is an operational fact about this execution. It is not the recovery point objective, which is a stated target about tolerable data loss, often expressed as time.

Now assume the source might still be serving clients isolated from the recovery team. Promotion to a new writable primary can create two live histories even if Chicago has most source writes. Before authorizing conflicting writes, establish how the prior writer is excluded from taking effect at the shared resource, or use a design whose quorum rules enforce single authority. Traffic redirection alone does not fence old clients with cached endpoints. A business owner may authorize restoration from a known older point after confirmed regional destruction, accepting documented loss. That decision is different from an automatic switchover that claimed continuous zero loss through an unconfirmed partition.

Recovery also crosses systems. The database could restore an order to pending while a payment provider still records the charge completed after the restored prefix. Reconcile using stable operation identities and authoritative external observations. Replaying the unseen tail as if every absent transaction never happened can repeat side effects. Similarly, an AI control plane may roll back its record of allocated GPUs while physical jobs remain active. A recovery point describes the data recovered at one boundary. Each external action needs an independent policy for observation, deduplication and compensation.

Make the availability contract visible to the operator

A recovery console should distinguish planning, accepted recovery decision, old writer isolated, destination replay complete, application verification and traffic cutover. A progress bar showing fifty percent says little about what a new operation can safely do. Present revisions, known ranges and uncertainty explicitly. If source connectivity returns during approval, recompute the proposal against current evidence and require the stable administrative request to refer to a particular recovery plan. An approval for recovery point 12,438 must not silently authorize an unrelated point selected later by a retrying worker.

The runbook can offer a read-only recovery mode where a time-labeled data snapshot supports inspection while promotion awaits fencing. Some applications can tolerate that mode for customer history but cannot authorize a new invoice or capacity grant from it. Make the degraded verb explicit and control it at the API boundary. If the product routes a strong balance check to a historical snapshot and reports the answer as current, a seemingly useful recovery feature breaks the promise that justified failover. A cheaper, faster recovery can be offered as a different service only when the customer understands its semantics.

Connect the recovery argument to PACELC

Synchronous durability in a second region may increase normal commit latency but reduce the set of acknowledged operations that can be missing there. Choosing a local durability acknowledgment can reduce ordinary latency and leave a tail at risk on destructive failure. Read freshness at the remote replica has separate costs: even durably replicated bytes may await application, and a safe current read may require additional evidence of authority. In an interview I would separate three questions: which commits survive the site loss, which prefix a specific replica can currently serve, and which side has authority to accept the next conflicting write.

SD-006 · Distributed Systems Foundations · 07

Measure semantic availability and the cost of recovery

A status dashboard says 99.99 percent of requests returned HTTP 200. Several tenants report that their required model revision never appeared in one region. A status code counts responses; it does not certify the requested meaning.

Worked example 7 · Recompute an availability report

Over an hour, clients issue one million BeginSession calls. Nine hundred thousand explicitly permit a pinned local version. Of these, 899,100 succeed within the deadline. The other one hundred thousand require current revision. An incident causes 12,000 strong requests to receive an older locally valid digest under an unlabeled fallback. Another 1,000 time out. The remaining 87,000 succeed with the promised current digest within their deadline. Under the stated contract, the strong class achieved 87 percent. Calling the stale 12,000 successes would raise the apparent figure dramatically while concealing the very failure the customer bought the strong option to prevent.

The local class succeeded at 99.9 percent. Across both classes the contract-correct total is 986,100 of one million, or 98.61 percent. The weighted average is still a poor substitute for reporting each class and its geographic distribution. A tenant sending entirely strong requests in the isolated region might have had almost no usable service. Track request identity so automatic retries do not inflate the denominator or hide long client-visible waits behind short server-side attempts. Count a request as successful only once and only for the contract selected at invocation or renegotiated explicitly with the client.

Track revocation separately from successful inference. Compute the maximum interval during which a disallowed model remained admissible under each policy, and attach the evidence source. If a region is disconnected, the latest report from that region is stale precisely when enforcement is most important. Record known installed revisions, time since verified contact, maximum remaining permission lifetime under the clock model and any independently confirmed isolation. Unknown should remain an allowed state in the dashboard. Treating missing data as zero violations will make the graph look clean during the worst incidents.

Tail recovery load

When the WAN returns, regions may simultaneously request missing manifests, refresh permits, upload admission logs and retry old deployment commands. Suppose each of 600 gates needs a 16 GiB model image. A naive reload produces 9,600 GiB of transfer. With a shared bottleneck sustaining 20 GiB per second, the ideal lower bound is 480 seconds before overhead, fairness and ongoing serving load. If gates already have the same immutable artifact, validate their local copy and distribute only missing material. Regional caches and staged rollout can turn a bandwidth emergency into a small policy refresh. Availability after repair depends on work accumulated during the partition, not just the time a router reports healthy.

Set separate queues and priorities for safety-critical policy refresh, ordinary publication, bulk artifacts and telemetry replay. Prevent a large snapshot transfer from starving the very messages that prove a region can resume safely. Use per-tenant fairness, bounded queues, retry budgets and circuit breakers whose state transitions are observable. A disconnected region should not keep thousands of expired client requests to replay unconditionally after healing. Expired requests are evidence for metrics; fresh authorization and current business preconditions govern new work.

Run an experiment that can reveal an error

A test should generate strong and local reads from both sides, issue writes with unique values and explicitly control the happens-before relationship between clients. Record invocation, response, chosen revision, deadline, admission policy and whether a fallback was requested. Inject a one-way blackhole while leaving local clients, DNS and authentication reachable. Then isolate the leader from a quorum but keep it reachable from old clients. Follow with a disk pause that looks like packet loss to the coordinator. Examine each history for impossible strong results and measure the successful weaker operations independently.

Finally restore connectivity with queued messages in reverse order. Verify that an obsolete allow cannot override a newer deny and that a retry with the same request identity cannot create a second deployment. Repeat after restoring a region from a snapshot older than the revocation. A test suite that stops as soon as network probes turn green checks outage handling but misses the recovery phase where stale state is most likely to re-enter service. Checking a finite set of histories cannot prove an implementation correct under all schedules. It can find concrete counterexamples and demonstrate whether the operational evidence you need actually exists.

SD-006 · Distributed Systems Foundations · 08

Reason about bounded staleness without trusting a quiet replica

A catalog owner proposes serving from any replica whose last heartbeat was received less than five seconds ago. A freshness requirement expressed in seconds needs stronger evidence than a recent sign of life.

Worked example 8 · A recent heartbeat can protect an old value

At local time ten, a follower sends a heartbeat containing its current applied revision, fifty. The receiver gets it at time eleven. The primary had already committed revisions fifty-one through sixty but the follower has been unable to apply them for thirty seconds because a local compaction stalls progress. The heartbeat is recent. The observed prefix is old. Choose another execution in which the primary never advanced past fifty. From the follower's heartbeat alone these executions look identical. If the request requires data no more than five seconds behind the primary, accepting it in both cases can violate the first history's contract.

One approach uses a source-provided safe timestamp up to which a replica knows it has applied a complete prefix. Its exact construction depends on the replication protocol, clock assumptions, handling of in-flight transactions and how timestamps relate to committed order. A client requesting a snapshot at that time can receive a consistent historical view if the implementation meets those conditions. If instead it requests data current as of the present, the replica needs evidence of how its safe time relates to the client's freshness bound. The timestamp embedded in a business row may describe when an event happened, and says nothing about writes the replica has not yet seen.

Another approach lets the client send a minimum revision it already observed. The receiver can prove it has reached that revision or wait until it does, subject to the operation's order and lineage. This supports useful guarantees such as reading one's own successful publication. It does not guarantee the globally latest value: another writer may have already committed a newer revision unknown to that client. In the model-serving example a newly configured client can ask for at least its deployment revision. Existing clients with no such token cannot infer that revision from the absence of local change.

Define fallback behavior before the deadline expires

Suppose a client requests minimum revision sixty with a 200 millisecond deadline. A lagging replica at fifty-nine can wait a bounded interval, route to a suitable authority, or report the unsatisfied precondition with retry information. If the client has explicitly authorized a historical fallback, the service can return it under a different result type with the served revision. If the client has not authorized a weaker contract, guessing that any answer is better than an error invites downstream correctness failures. A stale answer for a ranking experiment may be acceptable. A stale answer authorizing a withdrawn model can violate a different promise entirely.

Ask whether stale reads include access control decisions. Retrieving an immutable artifact by digest removes uncertainty about the artifact's identity; it does not remove uncertainty about whether this tenant is still authorized to retrieve it. A useful design can separate immutable payload distribution from short-lived signed access grants. Bounds on grant expiry and the response to unknown policy still matter. Identify the exact claim each bit of evidence proves, then check whether composing those claims is sufficient to answer the requested operation.

Answer the questions that change the design

Each prompt below is original practice. Give an answer using an explicit object, failure schedule and success response. Then state which operational measurement would reveal that your answer is wrong.

Twelve Senior Staff interview questions

Can I disprove a CAP argument by adding ten replicas?

Evaluates quantifiers and topology. Start with the precise failure model. Additional replicas create more opportunities for quorum connectivity under likely failures. The general theorem still admits a partition that isolates a live participant from evidence of a completed remote write. If that participant must implement the same latest-value register and always succeed, the indistinguishability argument still applies. I would use the extra replicas to improve measured availability under an explicit placement and routing model.

Follow-up. What if clients can always reach the leader? That is a stronger reachability assumption and excludes executions relevant to the original claim.

Common mistake and tradeoff. Availability for a subset of clients is valuable. It needs its own denominator and failure assumptions.

Does returning a fast error meet availability?

Evaluates semantics of completion. An implementation that always returns an error is responsive but fails to implement a useful read/write register. The specification determines which replies are legal successful results. A conditional update can legitimately report a conflict if its actual precondition failed. An isolated replica cannot invent such a conflict simply to finish the call. I would expose a retryable inability to establish current authority and count it as unavailable for the requested operation.

Follow-up. Could we return a previous value marked stale? Only if the client requested or explicitly accepted that different operation.

Common mistake and tradeoff. An HTTP success envelope cannot make an inadmissible value a successful strong read.

Must every strong read pay a WAN round trip?

Evaluates assumptions behind latency claims. No single latency formula applies across all placements and protocols. A valid local leader lease can support certain local strong reads with timing assumptions and a correct application boundary. A replica serving a requested historical snapshot may also have sufficient local evidence. Conversely, a peer reachable in one millisecond may still require a slow durable operation. I would draw the exact read protocol and identify what evidence it needs after the request begins or from a still-valid grant.

Follow-up. What changes when a lease expires? A renewed proof of authority or a different documented safe read path is required.

Common mistake and tradeoff. Treating local cache freshness and a proven authority lease as interchangeable hides the safety argument.

Why can merging two valid quota states violate a bound?

Evaluates invariant preservation. Each isolated side can legally spend the same apparent remaining capacity. The union of distinct accepted reservations can then exceed the global bound. Later choosing one history loses legitimate promises; adding both preserves the records but exposes the overspend. Split the spendable rights in advance and let each side consume only its own durable share. Transfers of rights require a protocol preventing double credit even if a reply is lost.

Follow-up. What if capacity exists in the other region? During a partition those rights can be stranded there, reducing useful local availability.

Common mistake and tradeoff. A correct merge result is a statement about eventual representation. The customer also cares about what was allowed at every earlier moment.

Could a recent heartbeat support a five-second freshness SLA?

Evaluates evidence and clocks. A heartbeat proves a peer recently sent something under a specified observation model. It need not prove the peer has applied recent committed updates. I would require evidence tying a contiguous applied prefix to source commit progress and to the freshness time reference, with clock uncertainty included. A weaker session requirement can use a minimum revision supplied by the client. Define whether a slow or uncertain replica waits, reroutes or returns an explicit failure.

Follow-up. What if there have been no updates? The replica needs evidence that no newer committed update is missing.

Common mistake and tradeoff. Silence between writes is not a globally certified safe timestamp.

How would you detect a stale minority leader serving successful reads?

Evaluates adversarial test histories. Keep the old leader reachable from a client while cutting its links to the voting majority. Have the majority elect a successor and successfully update a uniquely identifiable value. After that success, invoke a strong read against the old endpoint. If it returns the old value, the recorded nonoverlap rules out a legal linearization. Track attempted retries and actual endpoints so a fallback cannot mask the bug.

Follow-up. Could the old value be legal if the calls overlap? Yes, which is why the harness must establish the real-time ordering.

Common mistake and tradeoff. Single-site green probes usually exercise the healthy majority and miss this history entirely.

Can a strong control plane guarantee global model withdrawal?

Evaluates cross-component reasoning. A strongly ordered withdrawal records one authoritative decision. Every serving path still has to enforce it. If a disconnected admission gate can keep using a valid cached permit, there is an interval where it may accept new sessions. I would separate acceptance of the withdrawal from effective completion and record evidence for each required gate or conservative expiry. Specify whether running streams must terminate or only new admissions must stop.

Follow-up. Could routing changes fence the region? Only if all paths are controlled and the required behavior covers existing connections.

Common mistake and tradeoff. Global enforcement requires facts at the data plane that a single metadata commit cannot provide.

What does a region's recovery watermark tell you about acknowledged data loss?

Evaluates rpo and uncertainty. It identifies progress according to the receiver's documented semantics. An applied durable watermark can support a restore prefix; a received watermark might refer to volatile buffers or unapplied logs. To calculate actual lost acknowledged transactions you also need evidence about the source's acknowledged history and any independently durable tail. If the source is unreachable, report what is known and which interval remains uncertain.

Follow-up. Why not equate replication lag with RPO? One is an observation at a point in time, while the other is a target under a specified failure.

Common mistake and tradeoff. A healthy replica may be promotable yet still omit acknowledged writes.

Can several replicas and read/write quorum overlap alone establish linearizability?

Evaluates protocol versus counting. Quorum overlap gives an opportunity for readers to encounter prior state. The protocol must still define version order, handle incomplete writes, establish valid reads and preserve obligations across leader changes. As an example, a partially propagated value seen by one reader may disappear from a later reader's quorum unless a safe protocol prevents that reversal. I would ask for the complete register algorithm and a history argument before claiming the strong contract.

Follow-up. What about sloppy quorums? Changing eligible participants can eliminate the intersection assumed by the simple arithmetic.

Common mistake and tradeoff. A numerical threshold cannot describe what the intersecting replica must remember or communicate.

How would you measure partial availability during an outage?

Evaluates sli design. Count logical operations by original requested semantics, location and deadline. A strong lookup that falls back to an old entry without the caller's agreement fails its strong contract even if the server returns 200. Include synthetic traffic from the partitioned side and customer traces where available. Report time to first usable fenced capacity or correct revision if a successful response alone does not satisfy the customer outcome.

Follow-up. Could a fallback count as success? Yes for an explicitly defined flexible request whose returned semantics are visible.

Common mistake and tradeoff. A global average can improve when dissatisfied clients stop sending traffic.

Why does the system stay slow after the WAN recovers?

Evaluates recovery capacity and admission. Repair drains accumulated work through finite queues while new traffic continues to arrive. Compare available transfer or apply capacity with both the backlog and incoming load. Prioritize control updates that make work safe, deduplicate immutable bytes, bound fan-out and reject stale client attempts. Validate rejoined nodes before returning them to active capacity. A transport-level fix restores a path but does not prove every replica can safely serve.

Follow-up. What if repair bandwidth equals incoming work? The backlog cannot shrink without extra capacity or temporary load reduction.

Common mistake and tradeoff. Unbounded retries create new load exactly when the system needs spare capacity for repair.

What should a Staff+ candidate challenge in a request for global 10 ms writes?

Evaluates budget negotiation. Ask where clients and durable failure domains are located, what the success response certifies and what prior staging is allowed. If the ordered decision requires a fresh remote acknowledgment over an eighty-millisecond path, a ten-millisecond budget cannot hold for that execution. Pre-stage artifacts, group independent decisions locally or expose a separate geographically protected watermark if the product can use it. Present the stronger slower option alongside the actual semantics of the faster one.

Follow-up. Would a faster database solve it? It can reduce processing cost but cannot remove an indispensable propagation delay.

Common mistake and tradeoff. Quantify both the common case and the failover path before promising a percentile.

Defend an unexpected answer on the whiteboard

Ask a partner to play the interviewer and choose a customer promise you initially considered unimportant. For example, shift from publishing a desired model pointer to guaranteeing a model is stopped in all regions. Preserve the same boxes on the whiteboard and mark which arrows must now carry acknowledgments before the API can return success. Then hold one arrow indefinitely and say what a local client can still do. The best exercise changes the architecture only where a changed promise forces it. Distinguish needing a new service from needing a clearer contract at an existing boundary.

Rehearse a partition argument at three depths

Practice the same design under a thirty-second opening, a two-minute explanation and a five-minute architecture defense. Adjust your depth in response to the interviewer's interest in impossibility, latency or production recovery.

Thirty seconds · Show the missing information

If two live regions cannot communicate, a reader in one region cannot tell whether a write already completed in the other. Answering its old value may violate a latest-value promise. Waiting or refusing the request can preserve correctness while losing availability for that operation. I would decide separately what each API can promise under that partition and what coordination latency it pays when the network is healthy.

Two minutes · Explain the decision to a product owner

Take a deployment changing a model from revision seventeen to eighteen. Both regions initially know seventeen. We lose the WAN link, the deployment succeeds on one side and a user on the other side asks what version is current. Their local server has no evidence the change happened. It sees exactly the same state it would see if no one had deployed today. We can serve the old model by its pinned digest under a local-version policy, but we cannot present that answer as proof of the latest revision. If the user requires current authority we must wait, route them to it when possible or tell them the service cannot currently establish the answer.

I would add a separate emergency withdrawal contract. Suppose the old model has a serious defect and the operator asks for immediate global withdrawal. A cached permit allows continued isolated service only within the window we agreed to. We can acknowledge that the withdrawal was recorded and show which regions have enforced it. Global completion requires evidence from every required path or a trustworthy bound on the expiration of outstanding permission. An unreachable region cannot certify its own shutdown merely by disappearing from monitoring.

On an ordinary day we can keep the large model bytes and most inference requests near users. We pay a remote coordination cost when changing the shared pointer or satisfying an explicitly strong read. Monitoring should show strong and local operations separately. That gives product a legible choice about latency, disconnected behavior and the safety of its most important operations.

Five minutes · Defend a production architecture

I would begin by writing the customer-visible verbs across the top of the board: publish a desired version, admit an inference session, inspect the current deployment and withdraw a version. Next to each I write the evidence needed to return success. For publication that is a committed conditional update with a durable request identity. For admission it is a ready local artifact and a policy that allows the requested version. For inspection I ask whether the caller needs the current authority or a historical revision. For withdrawal I distinguish recording the decision from enforcing it across all required admission gates.

Now I draw a partition through that system. Two regions initially serve the same model. An operator changes the desired version on one side. A client isolated on the other asks for a strong read after the operator receives success. I can explain the impossible combination without discussing any database brand. The isolated client cannot distinguish a completed write from no write at all. If it insists on an answer equivalent to a single current register, ordinary local success is unsafe. If a customer chose pinned local execution, it is perfectly possible for exactly those immutable bytes to remain usable. Authorization is a separate question, so I include a scoped, expiring permission or a fresh authority check as required by policy.

I would then defend the normal path with numbers. In one trace the leader's local flush takes four milliseconds and durable follower replies arrive after eight and seventy. A three-voter leader needs one follower. With parallel local persistence the commit stage takes eight milliseconds while the nearby follower is healthy and seventy when it is unavailable. I would add actual client transport and application time and avoid claiming a percentile from these samples. The important question is how often this path must be used. A handful of model releases a day can justify remote agreement much more easily than hundreds of thousands of token requests a second.

During a long outage the local region stops using expiring permissions when it can no longer establish their validity. It may still serve workloads that were explicitly designed for a longer offline window. An incident commander's view exposes desired and installed revisions, last trusted contact, active permits, pinned streams and known uncertainty. When the network heals, I prioritize policy synchronization before bulk artifact downloads or delayed requests. I reconcile the loaded digests with authoritative state and discard requests whose original deadlines expired. Reconnection is an opportunity to verify state, not permission to accept every message still in a queue.

Finally I would ask the interviewer to challenge one assumption. If a region can be physically destroyed, synchronous replication of a pointer without the artifact is insufficient for restore-ready publication. If a client can reach old endpoints directly, withdrawing a DNS record will not stop its traffic. If one tenant's operations require instant revocation, its offline-serving policy must reflect that. Each change tells us exactly which component, acknowledgment or measurement has to move, and why.

Final interview cheat sheet

  • Object. Name the register and verb before assigning an availability policy.
  • Order. A read invoked after a completed write must respect that write in a linearizable history.
  • Two worlds. Hold the local observations fixed and vary the remote write.
  • Liveness. Finite but unbounded waiting and a two-second customer deadline have different meanings.
  • Scope. A surviving majority can still be unreachable to a live client.
  • Normal path. Compute the actual critical path under ordinary placement and degraded placement.
  • Rights. Preallocated nonduplicated rights preserve a bound while leaving some capacity stranded.
  • Pinned artifacts. An immutable digest answers identity; authorization needs its own evidence.
  • Withdrawal. A durable decision and global enforcement are different milestones.
  • Recovery. Receipt, durable replay and application define different watermarks.
  • SLI. Count successes under the requested contract at the client boundary.
  • Rejoin. Revalidate policy and lineage before replaying delayed work.
