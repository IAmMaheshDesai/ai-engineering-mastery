SD-003 · Distributed Systems Foundations · 01

Start at the operation that must exclude competitors

A recovery coordinator is about to attach a storage volume to a replacement host. The retry worker is about to do the same. Before choosing a lock service, find the one operation that would make these two reasonable decisions incompatible.

Worked example 1 · The same observation leads to two successful promises

At revision 40 the volume named V is recorded as unattached. Worker A reads that record and chooses host Alpha. Worker B reads the same record and chooses host Beta. Each worker asks its own process-local mutex for exclusive access. Each succeeds. A sends an attach to Alpha, B sends an attach to Beta, and the database finally shows Beta because B wrote its status last. Depending on the device contract, one host might still have a valid write path even after the visible metadata says otherwise. The failure is already real before any monitoring system discovers the disagreement.

To specify the requirement, give every successful attach a precise meaning. A successful reservation might mean that only one host is authorized to attempt the physical attach. A successful attachment might instead certify that the device actually enforces single-writer access, the expected host can read it, and the previous writer can no longer modify it. Those are different state transitions with different evidence. A single status column named attached invites operators to infer more than the service established. Separate reserved, attaching, verified and uncertain states. A lock on metadata is useful only to the extent that it helps implement one of those transitions.

If the whole invariant lives in one transactional row, the shortest solution is often a conditional update. Ask the store to change unattached at revision 40 to reserved by A if that revision and state still match. When B's command is processed, the store either sees that reservation or proves its own command preceded it. The loser retrieves the existing reservation and can decide whether its request duplicates the winner's intent. This design does not require every client to remember a separate lock around a read and a write. It places the rule where all legitimate mutations already serialize.

Change the exercise to refreshing a read-only embedding cache. Two workers independently computing the same immutable result might waste expensive GPU time. If they publish under a content-derived key and the computation contract tolerates duplication, the customer may see no correctness error. A best-effort lock that occasionally admits two workers could be cost-effective here. Quantify the cost of an occasional duplicate against the cost of blocking useful work during a coordination outage. Now return to the volume exercise and try the same reasoning. Two writers corrupting customer data is not an acceptable optimization trade, even if its probability appears small in a week of testing.

Establish the lock domain

A lock domain names the participants and the state whose access must be coordinated. Suppose one API uses locks named by display name, another uses volume UUIDs and a maintenance job truncates a long display name to build its key. Two callers can then acquire different records for one physical device. Alternatively two tenants can unexpectedly block each other. Use canonical identifiers defined by the resource owner, explicit tenant scope and a documented hierarchy when one operation covers both a collection and its members. Scrutinize rename, restore and deletion paths. Reusing a human-readable name must not accidentally grant an old client a right over a newly created object.

Define acquisition, release and cancellation as observable operations. Which pending request owns a place in line? Can a timed-out acquire later succeed? Can a holder renew after its grant is already gone? Which response proves the caller may enter the protected section? These questions distinguish a usable API contract from an attractive diagram of three boxes marked lock service. They also define the events your tests must record. In the volume example I would log the canonical key, acquisition attempt ID, exact grant identity, protected revision and provider operation identity. Each answers a different question in incident recovery.

How I would explain this in an interview

I begin with the smallest state transition that could violate the customer contract. If it is a single datastore update, I use the datastore's conditional mutation or transaction. If participants must coordinate across time or services, I define the lock's namespace and lifetime, how acquisition survives a lost reply and where a stale holder is rejected. I also ask what running twice would cost. Duplicate computation and conflicting device ownership call for different failure policies.

SD-003 · Distributed Systems Foundations · 02

Design a recoverable acquisition protocol

A timed-out lock acquisition can leave behind exactly the record that prevents the client from acquiring again. Discovering that record is part of acquisition, not a cleanup detail.

Worked example 2 · The grant you cannot see

Assume a queue of ephemeral sequential nodes under a ZooKeeper lock path. The client creates a node that includes an acquisition-specific GUID in its name. ZooKeeper assigns a sequential suffix, which orders contenders by their service-assigned positions. Initially R holds position 17. Client A creates position 18, but the connection drops before A receives its generated path. Client B creates position 19. Without the GUID, A might create position 20 on reconnect and wait behind its own unknown position 18. From outside, the lock looks healthy: one session really does own 18, and 20 really does have a predecessor.

The recovery step is to inspect the children for A's acquisition GUID under a valid session and recover the generated path if present, following the service's recipe for uncertain creation. Use a new identity for a genuinely new acquisition and a stable identity across retries of one outstanding creation. Do not let two independent callers within a process share the same GUID merely because their process ID is the same. Once A has recovered its place, it orders the children according to the sequential part of their names. A GUID prefix is not a queue position. Sorting full names beginning with random GUIDs can silently destroy the intended order.

At this point R is still the minimum and A cannot enter. A sets a watch on R's existence. B independently observes A as its immediate predecessor and watches A. R eventually releases by deleting its own node. A receives an event, rereads the queue and discovers that its own live node is now the minimum. Only that recheck justifies acting as the holder under the recipe. In particular, a watch event is not a transferable capability. It conveys that an observation might have changed; the queue record and protocol determine what action can follow.

Now lose A's entire session before its response arrives. A fresh session is a new participant. It cannot treat the old ephemeral node as its valid place merely because it can see the old GUID during cleanup. Distinguish temporary disconnection, uncertainty about session state, and confirmed expiry. The service owns removal of ephemeral records when sessions expire. The client needs a clear policy for pausing protected work when it cannot establish eligibility. A worker operating an external provider also needs enforcement at that provider or another reliable mutation boundary. Releasing the queue head cannot reach into arbitrary in-flight packets and revoke them.

The cancellation race

Suppose A's caller aborts while A is learning it has reached the front. The cancellation should name A's exact attempt or generated queue node. Deleting whichever node currently has the smallest suffix risks releasing somebody else's grant. If A receives both success and cancellation through independent callbacks, its local state machine must pick one externally visible result and settle the associated queue record. Closing a session to abandon one waiter also releases every ephemeral resource bound to that session. An API that pools sessions behind the scenes needs to document the blast radius of that choice.

One robust interface returns an acquire attempt handle before the caller waits for the final outcome. GetAttempt can report pending, granted, canceled or expired. Cancel compares the attempt identity and records or verifies its terminal state. A race can legitimately produce already granted; that result must trigger an explicit handoff or release path rather than leaving an orphaned grant. A simpler blocking library can hide this machinery, but its tests still need to cover the same interleavings. APIs often become unreliable precisely where they hide ambiguity from their callers without resolving it internally.

What you pay for ordering

The sequential-node recipe orders admitted requests at the coordination service. It cannot promise that the request issued earliest according to a laptop clock will acquire first. A client with poor connectivity may arrive later even when its human operator clicked first. A minimum queue position may also belong to a process whose application thread is paused. Fairness for admitted contenders and low time to the next useful action can pull in opposite directions. Expose queue wait and hold time separately, and ask whether the service should allow cancellation, retry elsewhere or optimistic work outside the protected section.

SD-003 · Distributed Systems Foundations · 03

Wait without losing a wake-up

When 300 workers wait for one model artifact, waking all of them to award the next turn can turn a small coordination task into a read storm. Watching one predecessor changes the work caused by each ordinary release.

Worked example 3 · Delete between listing and watching

The queue in service order reads P at 41, Q at 42 and R at 43. R lists the children and decides to wait for Q. Before R registers its existence watch, Q cancels and its node disappears. A naive implementation asks to be notified on a future deletion of Q and sleeps forever. There may be no future deletion of that node. The ZooKeeper recipe uses an existence check with watch registration. If the predecessor is already absent, the client loops and computes its current predecessor again. The observation governing the decision to sleep must account for the race with watch setup.

R now discovers P and installs its watch while P still exists. P releases. R gets a notification, rereads the children and verifies that its own node exists and precedes the others. A delayed callback from the prior watch on Q could arrive during this process. It should merely cause another re-evaluation. Store the acquisition attempt identity with callbacks so an obsolete event cannot accidentally activate the next request made by the same worker. A notification handler that calls startWork directly is hard to reason about under reconnection or callback retry.

Compare wake-up work under two idealized policies. Start with one holder and 100 waiters, assume nobody arrives or cancels, and drain the entire queue. A watch on the common lock record that wakes every remaining waiter can cause 100 plus 99 and so on down to one wake-up. The total is 5,050 notifications that trigger a competing read or retry. One-predecessor watches can reduce ordinary deletion wake-ups to approximately 100 over this drain. That comparison concerns wake-ups, not all bytes transferred. If each awakened participant still lists a hundred child names, there is real listing and parsing work left. Connection recovery and session loss can produce additional bursts under either policy.

Shared readers and a waiting writer

A reader-writer lock has different compatibility rules. Readers may coexist. A writer needs exclusive access. Imagine reader R1 at position 10, writer W at 11, and readers R2 and R3 at 12 and 13. A policy that allows every new reader to pass as long as there is no active writer can starve W during a continuous stream of arrivals. A fairer recipe blocks later readers behind the earlier writer even though they could have run alongside R1. W waits until all earlier conflicting holders are gone. Once W leaves, a group of waiting readers may become eligible simultaneously. That fan-out now corresponds to useful parallel work, unlike a hundred exclusive waiters contending for one turn.

An upgrade from shared to exclusive introduces a second kind of wait. If two readers hold compatible grants and both wait to upgrade without releasing, each may need the other to leave before it can proceed. Decide whether upgrades are disallowed, whether one upgrader has a distinct reservation, or whether clients release the read grant and revalidate upon acquiring the write grant. In the last design the protected value can change while the client has neither grant. Record the observed version and recheck the domain precondition. An upgrade API that sounds atomic but implements an unprotected gap will lead users to write incorrect read-modify-write code.

PYTHON · executable model
def predecessor(sequence, live_positions):
    # Snapshot of one queue; actual watches require service-side registration.
    ordered = sorted(set(live_positions))
    if sequence not in ordered:
        raise ValueError("acquisition no longer live")
    index = ordered.index(sequence)
    return ordered[index - 1] if index else None

assert predecessor(43, [43, 41]) == 41
assert predecessor(43, [43]) is None

How to choose a fairness policy

For an artifact cache that may serve stale data, an impatient foreground user could bypass a refresh queue and read the previous artifact while background work continues. For a maintenance operation that must eventually drain all readers, unbounded bypass is much more dangerous. Use a writer-wait-age alert and make the policy explicit. If business priorities permit high-priority bypass, specify limits and measure the age of the oldest low-priority waiter. Average wait time can improve while one class of customer makes no progress at all.

SD-003 · Distributed Systems Foundations · 04

Decide which service enforces the critical section

A correct queue can choose exactly one eligible holder while an obsolete holder still changes an external resource. Follow the operation across the gap between the coordination record and the protected effect.

Worked example 4 · A lock that works and a restore that fails

A owns the recovery-group lock and sends a request to publish backup manifest M1. A leaves the request in a network queue and pauses. The coordination service eventually expires its session. B takes over and successfully publishes manifest M2. The delayed M1 request arrives at a plain object-store pointer that accepts unconditional overwrite. Every grant in the lock service history was legitimate. The pointer now refers to M1. The service believed it provided last-authorized publication, while its actual implementation provided last-arriving write.

One possible fix uses immutable manifest objects and one authoritative pointer inside the same transaction domain as the lock. Store an ownership record and change the pointer only in a transaction that verifies the exact still-live grant. An older client's transaction fails after its grant is gone. Readers retrieve the committed pointer and fetch the immutable object it names. This design shifts the publication boundary from an arbitrary object overwrite to a protected metadata transition. It still requires that objects be durable, completely validated and retained while referenced. Holding a lock does not make a partially uploaded manifest suitable for recovery.

When the external storage service instead offers a version precondition, use it precisely. B reads current pointer version 87 and replaces it with M2 if it still has version 87. After that write succeeds, A's earlier request conditioned on 87 fails. If A is permitted to reread version 88 after it loses the lock and try again, version checks alone no longer enforce ownership. A receiver that can validate a scoped grant or an integration that binds the allowed transition to the correct authority gives a stronger design. Explain which failure the version comparison excludes and which permission check still belongs elsewhere.

A third service might have no conditional update primitive, no usable operation lookup and no ordered downstream command channel. You can serialize new requests in your dispatcher and still fail if a timed-out request already left it. A safe policy might block the successor's conflicting action until an external observation proves the earlier operation completed or was rendered impossible. This costs availability and needs an incident procedure. A weak policy that declares old work canceled when the caller disconnects is much cheaper until an old request arrives after the new one. Discipline about these boundaries is part of a Senior Staff answer.

The release path is a mutation too

Consider a simple single-record lease in a store that supports atomic comparisons. The value contains a fresh acquisition token. At time zero A acquires token p; later p expires and B acquires q. A's cleanup runs after B is already active. An unconditional delete removes B's record. A separate get followed by delete is also racy: the record can change between those operations. Release must compare the exact acquisition token and delete in one atomic step. Bind the token to a session or grant and authenticate the caller where the service requires it. A reusable worker name alone cannot distinguish an old cleanup from a valid current release by the same restarted worker.

If the protected state and lock live in PostgreSQL, distinguish the resource you actually hold. A transaction-level advisory lock is released at transaction end. A session-level advisory lock can remain held across a transaction rollback and through an application request boundary on a pooled connection. Returning a still-locked connection to a pool can let an unrelated task appear to own the lock or block other sessions. Recover by choosing a lifetime that matches the business operation and by testing cancellation and connection reuse. A database transaction left open during a ten-minute provider operation has different costs again, including retained connections, blocked transactions and recovery complexity.

PYTHON · executable model
def release(grants, key, expected):
    # Pure transition modeling an atomic compare-and-delete.
    if key not in grants or grants[key] != expected:
        return grants, False
    next_grants = dict(grants)
    del next_grants[key]
    return next_grants, True

A spoken design review

For a lock to protect this operation, I need both agreement about ownership and a way to enforce that ownership where the irreversible change happens. When they share a transactional store, I combine the checks and update. Otherwise I trace the slowest old request through every downstream component. I ask what happens if it arrives after the new holder has already acted. Finally I audit every legitimate bypass path, including repair tools, scripts and manual administration.

Use a wait-for graph to reason about multiple resources

A scheduler must reserve a GPU pool and a compatible network slice. An independent repair worker needs both objects in the opposite order. Each single-resource lock implementation may be flawless while the combined operation never completes.

Worked example 5 · Two honest holders form a cycle

Planner A acquires pool G and asks for network slice N. Repair worker B has already acquired N and now asks for G. A wait-for graph has one vertex per waiting participant and an edge from a waiter to the holder it needs. A points to B via N. B points to A via G. Neither can voluntarily finish its normal path. Increasing lease duration delays the moment a crash might release the cycle. Renewing both leases successfully can preserve the deadlock indefinitely. Both processes can appear healthy to a monitor observing only lease renewals.

One remedy imposes a global order on resource acquisition, for example by comparing a tuple of type, tenant and canonical resource ID. Require every operation, including administrative repair, to acquire its entire set in that order. A waiting participant can then only wait for a resource later than those it already holds. A cycle would imply a strictly increasing sequence that eventually returns to its starting point, which is impossible under one consistent order. The proof assumes all participants obey the rule and have a compatible order for every relevant lock. A special-case bypass path can invalidate it.

Sometimes the full resource set is unknown until a partial read discovers a dependency. If you already hold N and discover you need earlier G, abandon or safely roll back the tentative work, release what you hold, then attempt the complete ordered set. Revalidate the discovery because state can change during the gap. Another possibility is a single allocation transaction over the necessary inventory. It may create a shared hotspot, but it can eliminate an intricate distributed protocol. Compare both under actual contention and failure conditions. Two uncontended locks on a whiteboard say little about the tail when one is continuously held.

Deadlock detection works differently. Record wait edges and look for cycles. Choose a victim, abort its waiting acquisition, release its actual held locks and retry its higher-level operation if safe. This can support dynamic acquisition patterns but detection in a distributed system may observe an inconsistent snapshot. An apparent cycle can already have disappeared by the time the cancellation arrives. Scope cancellation to a particular attempt, and decide how external work performed before abort will be reconciled. Killing a thread that owns an incomplete external reservation is not equivalent to rolling back an uncommitted database transaction.

Distinguish starvation, livelock and a convoy

Starvation means some participant is repeatedly bypassed although others progress. Livelock can occur when A and B both release their first lock on conflict, both retry in synchrony and repeatedly collide. Randomized exponential backoff with a deadline can reduce synchronized collision. It provides a probabilistic improvement, not a hard bound on acquisition time. A convoy occurs when many participants queue behind a slow holder. They may all be progressing according to the protocol while customer latency becomes unacceptable. Each condition needs different evidence and a different intervention.

For a convoy, inspect critical-section contents. If a planner downloads a 20 GiB artifact while holding a lock needed only to publish its final reference, move independent work before acquisition and revalidate readiness before publication. Some speculative preparation will be discarded when the resource changes. Compare that cost with the reduction in serialized hold time. Delay nonessential logging, notification and reporting until after the durable decision, using a recoverable outbox if those follow-up actions matter. A short critical section is valuable only if moving work outside it preserves the invariant you originally wrote down.

Whiteboard exercise

Give a colleague three resources named quota, rack and job. Ask for a deadlock-free policy after adding an admission path that discovers its rack from the job record. A sound answer either includes a restart and revalidation when the discovered set violates acquisition order, or changes the state representation so one transition covers the relevant reservations. A policy saying always acquire alphabetically while implicitly fetching a new earlier resource halfway through the operation has left the hard part unresolved.

SD-003 · Distributed Systems Foundations · 06

Build an artifact materialization coordinator

A model-serving fleet repeatedly needs the same verified model artifact in each zone. Thousands of compatible requests can arrive near deployment time. Design a coordinator that prevents a cache stampede, preserves a recoverable publication pointer and gives operators a useful response during a partition.

Requirements, state and APIs

Assume 200 models, six zones, and immutable model bundles averaging 4 GiB. The unit of deduplication is tenant, model digest, format and target zone. Two different configurations that happen to use the same display name can require different bytes. Treat the source model version and conversion parameters as part of the immutable input, and choose an explicit isolation scope before sharing cached outputs. The fleet may tolerate occasional duplicate downloads, but a successful ready response must point to a verified bundle for the requested version that workers can read in that zone.

Separate the hot lookup from the miss path. GetArtifact reads the publication record and, for a verified usable entry, returns its immutable reference and digest. EnsureArtifact accepts a stable request key and either returns an existing result or identifies a pending materialization operation. A worker competes for the right to materialize a missing entry. The coordination store holds a scoped attempt record with the operation ID, current claim, epoch or comparable ownership evidence, staging references and terminal outcome. Bulk bytes travel directly between artifact storage and the zone cache. Clients waiting for completion subscribe to the operation record or poll with bounded backoff.

The publication API compares a live claim or generation and expected pointer revision in a single transaction where possible. The candidate bundle and its shard inventory must be immutable and verified before publication. The worker may stage bytes while holding a renewable claim if avoiding duplicate work matters, but the short publication transaction alone governs validity of the shared pointer. A waiting client that times out gets a resumable operation ID. A payload change under the same client key is rejected. A completed response records the exact digest and ready revision so the system can explain what it previously promised even if a later version is already active.

Worked example 6 · Recover a nearly complete download

Consider model K in zone two. Revision 31 has no published bundle. Worker A wins attempt 15 and stores verified chunks one through nine of ten, each under an immutable content digest. Before it publishes, its session expires. Worker B wins attempt 16, checks the verified inventory and reuses safe chunks under the retention and tenant policies. B verifies the final chunk, builds a manifest of all ten chunk digests and atomically publishes at revision 32 with its active grant. When A resumes, its stale attempt cannot publish a conflicting result. Extra staged chunks may remain, consuming storage until garbage collection.

If A had published just before expiry but lost the reply, B could discover an already complete pointer at revision 32. It should validate that the pointer satisfies its requested artifact identity and return the existing result. It does not need to download another 4 GiB merely because its own acquisition succeeded. This is the double-check after acquisition that prevents serial redundant work. The first miss observation occurred before A finished, while B's recheck occurs after acquiring a right to act. Correctness requires that B also account for invalidation or retention if those concepts can make an existing pointer unusable.

Now consider a malicious or buggy requester repeatedly asking for different invalid digests. Protect the coordinator and the storage fleet with authenticated tenant-scoped admission, validation of source references, fair concurrency limits and bounded retries. A failure result such as digest unavailable should have a documented cache lifetime so every request does not trigger a fresh transfer. Keep a distinction between permanent input errors and transient storage timeouts. The resulting service is useful operationally because an on-call engineer can inspect where a request is stuck: waiting for ownership, waiting for bytes, verifying shards or waiting for a safe publication.

Capacity and service-level objectives

A single deployment of one 4 GiB model to six zones requires about 24 GiB of source traffic if exactly one successful transfer is sufficient per zone and the source is shared. If 100 starting workers in every zone independently fetch on a cold miss, that same rollout can pull about 2,400 GiB before retries. Shared immutable caching can reduce bulk traffic by two orders of magnitude in this simplified workload. Coordination is justified by what it saves. A lock acquisition per inference token would instead add serialization to a path where no competing materialization decision is taking place.

For one hot key, a critical section held for 50 milliseconds can complete at most about 20 serialized holders per second, ignoring handoff overhead. If each of 600 waiting servers must acquire and release just to observe success, draining them takes roughly 30 seconds even after the bytes are ready. Publish one completion event and let readers retrieve the immutable result in parallel. Fairness among materializing writers need not create a serialized line for successful readers. This design change addresses throughput without enlarging the coordination cluster or weakening the validity of publication.

Suppose the target SLO is 99 percent of valid cold requests ready within 90 seconds, measured per zone from accepted request to a verifiable reference. Under ideal sustained transfer at 100 MiB per second, 4 GiB alone takes about 41 seconds. Include queue waiting, source authorization, checksum verification, staging, publication and retry overhead before promising the remaining margin. Identify a separate SLO for already published hits. An outage of the lock authority may allow continued reads of retained immutable artifacts while preventing a new strong publication. Availability is a property of each API path and its contract.

Architecture defense and evolution

Product now asks for zero duplicate transfer under arbitrary process failures and immediate replacement whenever a worker is unreachable. If A has already requested a transfer and B cannot determine whether it is still running, starting B immediately can duplicate bytes. Refusing to start B can delay recovery. I would ask whether the real success criterion is zero wasted cost, a bound on duplication, or a single verified published result. The last is much easier to guarantee through conditional publication and immutable object identity. We can cap per-tenant duplication through admission budgets and deduplicated chunks without pretending every TCP transfer occurs only once.

Start with one claim per artifact-zone identity. If very large bundles cause long tail downloads, introduce chunk-level parallelism with an immutable manifest and a final publication barrier. That change increases metadata volume and complicates garbage collection of partially referenced chunks. A safe collector must consider active staging attempts and published references, with a grace interval or stronger reference tracking suited to the store. If aggregate writes saturate one coordination group, shard by the materialization key. Preserve one authority per publication key during migration and give each outstanding request a way to recover its operation across a shard move.

Read the wait graph during a production incident

A model rollout has stalled in one zone. The lock service shows fewer writes than normal and the on-call engineer proposes deleting every outstanding lock. Work out which actions would preserve evidence and which might create a second incident.

Worked example 7 · A live session with a dead worker

For artifact K the oldest pending waiter has waited 95 seconds. The holder's session renews every four seconds and the grant service reports no election or storage errors. Staging progress has not changed for 82 seconds. The application thread running the transfer is waiting for a storage callback; its session heartbeat runs on another thread. This is consistent with a healthy lock service, a healthy network path for heartbeats and a stuck business operation. Expiring every session would move the bottleneck to hundreds of new workers that might all encounter the same storage fault.

First compare grant age, last useful progress and elapsed time in the specific transfer stage against distributions for the same model size and storage class. A long hold on a tiny pointer update suggests a different cause from a long hold while verifying a large artifact on a slow node. Query the provider for the known transfer ID. If it reports a terminal success, recover the staged work and publish under a valid claim. If it reports a definitive failure, terminate the attempt and admit the next contender within its retry budget. If the outcome is unknown, choose whether duplicate transfer is acceptable under the service's business policy.

Now suppose the holder is waiting on a second lock for the quota bucket. Reconstruct the wait graph using attempt identities, since a reusable hostname can label several sessions. Inspect whether a quota manager holds that bucket and waits on the artifact lock. A cycle suggests a lock-order bug. An acyclic graph ending in a slow storage operation suggests a convoy. In the first case, adding transfer bandwidth will not break the cycle. In the second, aborting one waiter in the middle of the graph may not change the blocked critical path. Each diagnosis should predict which observation would change after the proposed intervention.

Failure injection before rollout

Add an explicit barrier in a test transport between sequential creation and client receipt. Drop the response, reconnect while keeping the session valid, and verify that searching for the acquisition GUID results in one live queue position for the intended operation. Repeat after expiring the session. The expected outcome changes because a fresh session cannot just inherit the previous grant. Introduce a predecessor deletion between list and watch and verify that the waiter loops rather than sleeping forever. These tests expose protocol bugs far more directly than running hundreds of identical uncontended acquisitions overnight.

Another test pauses a holder after validating authority and before sending the protected mutation. Grant the successor, publish a different pointer and then resume the old request. Check the pointer contents, revision and durable audit record. A test that checks only whether both workers were simultaneously inside a Python block measures local behavior and cannot establish the external guarantee. For a queue protocol also record whether each waiter eventually acquires under a specified healthy period, bounded operation duration and eventual notification delivery. A safety test can pass a service that never grants any lock. A liveness test must state the conditions under which progress is actually promised.

Operate with bounded evidence

Log every ownership-changing administrative override with actor, key, previous grant, replacement grant and a reason. Redact bearer credentials while retaining correlation identifiers. Measure grant wait, protected hold time, stale mutation rejection, uncertain acquisition count, queue depth and wait age. Prefer distributions by workload class over one fleet-wide mean. The rate of abandoned waiters tells you when callers are paying queueing cost for results they no longer need. A page should describe the customer operation impaired and the evidence needed to decide whether takeover is safe.

SD-003 · Distributed Systems Foundations · 08

Staff-level interview round

These questions are original practice. Answer each with a concrete execution and defend the boundary where your solution enforces its most important promise.

Twelve questions with follow-ups

Do both writers have to participate in a lock for it to protect a database row?

Evaluates enforcement boundary. An advisory lock excludes cooperating participants using the same key. A maintenance writer that updates the row directly can bypass it. If all writers must respect the invariant, enforce it through a constraint, transactional conditional update or a single controlled mutation path. Inventory repair and administration alongside the normal API. Then demonstrate a race involving the least conventional writer. A clean application-layer lock trace says little about that bypass.

Follow-up. Could a database transaction check the lock? Yes if the lock evidence and state mutation share an appropriate serialization boundary.

Common mistake and tradeoff. Hiding the advisory lock in an SDK improves adoption but is not a database invariant.

How would you recover a timed-out sequential-node create?

Evaluates ambiguous acquisition. Give each acquisition an attempt-specific identifier included in its sequential node name. After reconnecting under a valid session, follow the recipe to find its existing generated path and recover its queue position. Confirm session status, order by sequence number and recheck whether the node is eligible. If the session expired, treat the old grant as lost. A retry is an operation recovery decision, not merely another transport call.

Follow-up. What if you used the worker hostname? Simultaneous or restarted acquisitions can share that label.

Common mistake and tradeoff. A stable attempt identity costs metadata but prevents self-blocking behind an unknown queue entry.

Why watch the predecessor instead of the lock root?

Evaluates contention and race handling. For an exclusive queue, one normal release enables one successor. Waking every contender causes unnecessary list and watch traffic. Watch the nearest preceding live node and rerun the eligibility test when it disappears. Handle the race where it is gone before watch registration. On cancellation or session loss several contenders may have to recompute predecessors; the one-notification intuition applies to ordinary handoff, not every outage pattern.

Follow-up. What if 100 readers can all run after a writer? Multiple wake-ups may correspond to real useful concurrency.

Common mistake and tradeoff. Counting notification volume alone misses the cost of listing long queues.

Can a client start work when its watch fires?

Evaluates notification semantics. The event signals a change, but eligibility depends on the current queue, session state, request identity and lock mode. Re-read the relevant children and verify its own live entry is eligible. A stale callback may belong to an acquisition the caller already canceled. Use the attempt identity when processing asynchronous completions and ensure any local start transition occurs only once. An external resource still requires its own safe publication rule.

Follow-up. What if a predecessor cancels rather than releases? Recompute in exactly the same manner.

Common mistake and tradeoff. Binding business execution directly to a callback makes delayed and duplicate observations hazardous.

A stale release deletes the current lease. How do you prevent it?

Evaluates aba and atomic comparisons. Assign a fresh grant token for each acquisition in the correct resource namespace. Compare and delete the matching token atomically at the authority. An unconditional delete, or a read followed by a separate delete, can remove a replacement. Treat an already-gone token as having no remaining authority and do not clean up by worker name. Test a late release after the same process identity has reacquired the resource.

Follow-up. Should a rejected release trigger an urgent page? Usually classify it by rate and cause; a known stale cleanup can be expected.

Common mistake and tradeoff. A comparable token for release protects the lock row but does not independently fence an external write.

Should a highly contended key be spread over ten independent lock shards?

Evaluates partitioning and exclusion scope. Splitting independent keys across groups can distribute load. Giving the same mutually exclusive operation ten authorities allows incompatible grants. Instead shrink the protected decision or make work parallel and reduce the final critical section to a conditional publication. Measure how many waiters need a writer grant at all. Immutable readers can normally consume a published result in parallel without entering the materializer queue.

Follow-up. When could subkeys help? When a documented invariant decomposes into independent components or uses a genuine aggregation protocol.

Common mistake and tradeoff. Hash distribution improves throughput only when it respects the independence of the protected state.

Two acquisitions deadlock despite using leases. Why?

Evaluates wait graph and progress. A's lease on G and B's lease on N can both renew forever while each waits for the other's resource. Their health and ability to renew do not make the critical sections progress. Build the wait-for graph at acquisition-attempt granularity. Use a consistent order, an atomic reservation or a recoverable victim-abort policy. When aborting, account for effects already acknowledged outside the transaction.

Follow-up. How does random backoff help? It can reduce synchronized collisions after voluntary release but does not repair a still-held cycle.

Common mistake and tradeoff. A timeout may select a victim without explaining which external work remains valid.

When would a reader-writer lock be worse than optimistic reads?

Evaluates isolation and fairness. Long-lived readers can delay maintenance writers, and writer preference can inflate tail latency for an arriving read cohort. If reads can consume immutable snapshots, publish a version and let readers pin a retained snapshot instead. Pay for retention, garbage collection and an explicit freshness contract. If a read causes an irreversible decision, verify the relevant preconditions at the write point. Long snapshot lifetime can create storage pressure even without blocking writers.

Follow-up. Would an atomic pointer solve multi-object consistency? Only if it references a complete immutable snapshot or equivalent version boundary.

Common mistake and tradeoff. Replacing locks with snapshots moves costs to retention and publication semantics.

Why is session-level locking risky with a database connection pool?

Evaluates resource lifetime mismatch. A pooled connection survives an application request. Session-scoped advisory locks can survive transaction rollback, so the next borrower may inherit unexpected held state. Map the lock lifetime to the database session or use a transaction-level primitive when the actual protected work fits one transaction. Exercise exception, timeout, rollback and return-to-pool paths. If a remote call can outlive the transaction, independently handle its outcome.

Follow-up. Would closing the entire pool fix it? It can disrupt unrelated requests and leave external operations unresolved.

Common mistake and tradeoff. Scope mismatch is often invisible under happy-path acquisition and release tests.

What exactly would you measure when a queue stops draining?

Evaluates operational diagnosis. Inspect age of the oldest waiter, current holder, progress stage, hold distribution and wait dependencies. Distinguish a dead holder, a healthy session with stalled application work, a cyclic wait and a slow but progressing transfer. Query a stable external operation identity where possible. Every proposed recovery action should predict which signal changes and whether it can create a second conflicting operation.

Follow-up. What if the average queue time is low? Segment by hot key and workload class; one tenant can be starved in a low fleet average.

Common mistake and tradeoff. Force release improves a queue graph even if it creates an unsafe stale publisher.

Can you promise zero duplicate transfers and instant recovery?

Evaluates failure ambiguity and product requirements. If the old process is unreachable and its provider request is in flight, a successor may be unable to distinguish an active transfer from a lost one. Immediate retry may duplicate cost, while waiting can delay readiness. Decide whether the contract concerns bytes transferred, published identity or billed work. Use immutable verified chunks and a durable publication rule to preserve the customer-facing invariant even when a bounded amount of transfer repeats.

Follow-up. What if the storage API offers a durable operation key? Reuse it within its documented scope and retention window.

Common mistake and tradeoff. The word exactly must be tied to one observable effect and failure horizon.

What makes a lock test meaningful for a cloud recovery operation?

Evaluates end-to-end verification. Drive the old and new clients through an adverse schedule and inspect the actual protected resource. Pause after the old check, transfer the grant, perform the new publication and deliver the held request. Assert both the post-handoff pointer and the response to the stale operation. Repeat around persistence boundaries and session expiration. For liveness, observe eventual success under stated stable conditions with bounded work; a never-granting system can pass trivial exclusion checks.

Follow-up. What if production cannot expose mutation lineage? Improve observability or state exactly which property the test cannot verify.

Common mistake and tradeoff. Separate evidence from coordinator logs and evidence at the point of effect.

Whiteboard challenge

Draw the lock service history and the external resource history in separate columns. Place a lost acquisition response in the first and a delayed publication in the second. Have your partner change just one assumption: the session can be resumed, the object store supports a version precondition, or the transfer is allowed to execute twice. Show exactly which steps of your recovery algorithm change. A mature design makes these dependencies visible instead of attributing every guarantee to the word lock.

SD-003 · Distributed Systems Foundations · 09

Speaking practice and final review

Use a cache stampede and a disaster recovery promotion as contrasting customer problems. Move from a short explanation of exclusion to a five-minute design defense with a worked failure trace.

Thirty seconds · What is a distributed lock?

A distributed lock coordinates participants that cannot share a process mutex. I define the resource, how a caller acquires a specific grant, and how the system recovers if that caller disappears. Then I identify the mutation that really matters. If an old holder can still issue a valid external write after a replacement acquires the lock, the lock protects the queue but leaves the customer operation exposed.

Two minutes · Explain a reliable waiting protocol

Suppose ten workers all want the same model artifact. I would first check whether any work needs to be exclusive. Multiple verified immutable chunks may safely exist, but there must be one authoritative publication record for the requested digest. To reduce expensive duplicate transfers I can coordinate materializers through an ordered queue. Each creates a session-bound sequential record containing a durable attempt identifier. A lost reply means it must recover the original record if its session remains valid. Creating another queue entry every time the connection drops could leave it waiting behind itself.

A participant that is not at the head watches its immediate predecessor. It handles the race where that predecessor disappears between listing and setting the watch. When notified, it reevaluates the queue and its own grant. It checks the publication record again after acquiring because the previous holder may already have produced the result. This gives fairness among materializers without forcing successful readers to queue one by one. I would make release and cancellation specific to the exact grant or attempt.

The last step is publishing the result under a valid authority check or conditional transaction. If the worker pauses before that transition, a newer holder may finish first. The old worker must not replace the published result after handoff. That example distinguishes the costs saved by coordination from the actual correctness guarantee customers depend on.

Five minutes · Defend the production architecture

I would open by writing the materialization identity on the board. It includes model digest, format and destination zone, plus tenant scope wherever sharing must be restricted. Clients requiring the same bytes can share a result. Clients with different transformation parameters may need different artifacts even if they use the same display name. The invariant is that a ready record always references complete, verified, accessible bytes of the requested identity. My cost objective is to limit duplicate source transfers. These objectives justify different behavior during failure.

For the fast path, workers look up an immutable published reference and fetch from the local cache. On a miss, EnsureArtifact returns a stable materialization operation. A worker acquires a claim for the key, checks readiness again and stages content-addressed chunks. A separate short publication transition compares the valid grant and expected revision, then records the verified manifest and operation outcome together. With a six-zone cold rollout of one four-gibibyte artifact, one copy per zone needs roughly twenty-four gibibytes of source traffic. One hundred independent downloads per zone could require roughly twenty-four hundred. The control plane orders small publications while the data plane moves large objects.

Next I would draw three events for the failure trace. A's last chunk reached storage, the authority expired its session, and B began a new attempt. B verifies reusable chunks and checks whether A already published. If the pointer exists and meets the requested identity, B returns it. Otherwise it can finish under its own grant. A delayed publication from A cannot advance the protected pointer once B has installed the required authority. I would tell the interviewer exactly where that exclusion happens and which contract lets a successor inspect a timed-out operation. Unverified chunks remain staging data until the integrity checks succeed.

I would handle waiters separately from workers. A predecessor watch can avoid waking hundreds of exclusive contenders for one grant. Once a valid result exists, many readers should consume it concurrently. Requiring every reader to acquire the lock would turn a successful publication into another queue. With fifty milliseconds of serialized work per holder, six hundred readers would spend about thirty seconds draining the line after the bytes were ready. That delay would be a property of my design, not a physical limitation of the storage system.

Finally I would test the parts most likely to fail silently. Drop a successful create reply, delete a predecessor just before watch installation, expire a holder during verification and delay an old publication until after its successor succeeds. Measure cold readiness and hot-read availability separately. If the lock service becomes unreachable, already verified immutable artifacts can still serve many readers. I may allow bounded duplicate staging under a cost budget, but I would keep uncertain publications out of the authoritative read path. That conclusion states what customers can still do and what evidence will let the coordinator recover the rest.

Final interview cheat sheet

  • Lock domain. Canonical identity and participating writers define the protection scope.
  • Acquisition identity. A stable attempt ID resolves a lost creation reply.
  • Session. Disconnection and confirmed expiry have different implications.
  • Queue position. Order admitted contenders by the service sequence.
  • Predecessor watch. Recheck eligibility after an event or an absent predecessor.
  • Release. Compare the exact grant and delete atomically.
  • Fencing. Enforce the current authority where mutation takes effect.
  • Critical section. Move independent expensive work outside and revalidate.
  • Lock ordering. All paths must use a consistent resource order to eliminate circular wait.
  • Starvation. A low mean wait can hide a permanently bypassed caller.
  • Convoy. One slow holder can dominate tail latency for many callers.
  • Readiness. Publish verified immutable references through a recoverable transition.
