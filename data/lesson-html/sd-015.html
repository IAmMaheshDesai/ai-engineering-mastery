sd-015 · Distributed caching

A cache is a second representation with a contract

Optimize avoided work without confusing cached state with authority.

The database survives ordinary traffic but not cache failure

An enterprise AI service reads tenant configuration, model routing, and document metadata millions of times a minute. Most reads hit a distributed cache, so the database looks lightly loaded. A deployment flushes the cache, every application instance refills at once, database latency rises, and clients retry. The architecture's apparent spare capacity was conditional on a healthy cache. The problem is not simply choosing a better eviction algorithm; it is defining correctness and overload behavior when the optimization disappears.

A cache stores a derived or reusable representation to avoid expensive work. The authority may be a database, immutable object, model computation, or remote service. Identify what the representation means, how long it can be used, and what validates its identity. A cached tenant policy, a model-weight file, a negative lookup, and a transformer prefix have very different validity conditions. Calling all four key-value entries does not make their safety contracts interchangeable.

Separate freshness, availability, and authorization. A product may tolerate a slightly old display name but not an old permission grant. A stale model-routing entry may be acceptable only if both model versions are approved. Serving a cached recovery-plan status can improve a read-only console during an outage, while authorizing a destructive step from stale ownership is unsafe. Your OCI/FSDR experience provides the right intuition: desired state, observed state, and authoritative permission are different things.

The design examples in this lesson are hypothetical. They connect cloud control-plane reasoning to AI serving and retrieval without describing private OCI implementation details or attributing unprovided accomplishments to you. Published company evidence grounds the engineering context; the proposed protocols and numerical values are original educational designs.

Start with the cached object's identity

A key must represent every input that changes the validity of the result. For a document projection, include document version and projection schema. For an embedding, include the exact model and preprocessing identity, not merely the source text. For a query result, account for authorization scope or apply authorization separately at read time. Missing one input can turn a high-hit-rate cache into a consistent producer of wrong or unauthorized answers.

Define an entry as value, source version or content hash, production time when relevant, expiry or policy deadline, and representation version. Metadata costs memory but supports validation and diagnosis. A timestamp alone may not order source changes if clocks differ. An authoritative revision is often better for rejecting older data. Distinguish an entry's insertion time from the age of the source snapshot used to create it.

How I would explain this in an interview: “I first identify the source of truth and the stale behavior the product permits. Then I design a key that includes all validity inputs and a protocol for filling, invalidating, and failing over. Hit rate is useful only if cached results are correct and the source survives the miss path.” Pause and classify a recovery-plan summary, a permission check, and a model prefix by their acceptable stale behavior.

Chapter summary

A cache changes load and latency while creating a second representation. Correct identity, freshness policy, authorization, and miss-path capacity determine whether that representation is safe.

02 · Quantifying the benefit and exposure

Model source load before celebrating hit rate

A small change in a high hit ratio can multiply backend demand.

Hits, misses, and the critical path

Let request rate be λ and hit probability h under a defined workload. In a simple one-lookup cache-aside model, source request rate is approximately λ times one minus h, before coalescing, retries, writes, and refresh traffic. This equation is a first-order model, not a universal service measurement. A single customer request may perform many cache lookups or trigger several database queries on a miss. Count avoided source work, not just cache operations.

Average latency can be approximated by h times hit latency plus one minus h times miss latency when those paths and probabilities are measured consistently. A miss may include the failed cache lookup, source read, serialization, and cache fill. The formula does not determine p99. If misses occupy more than one percent of requests, they can heavily influence the tail, but actual quantiles depend on the full distributions and correlations. Averages can conceal correlated cache loss that overloads the source.

Track request hit ratio, byte hit ratio, and work-weighted benefit separately. Caching tiny cheap objects can raise request hit rate while expensive misses still dominate database CPU. A large object can dominate byte traffic but be rarely reused. A useful cache policy considers frequency, object size, recomputation cost, and validity. It also considers fairness: a tenant scanning unique keys should not evict every other tenant's hot working set.

Worked example 1: a five-point hit-rate drop

Initial state: the application receives 100,000 reads per second. Each read makes one lookup, with 95 percent hits. The source receives about 5,000 reads per second under the simplified model. Hit latency averages two milliseconds and complete miss-path latency averages thirty milliseconds. The objective is to understand how a rollout lowering hit rate to ninety percent affects source load and average latency before declaring the cache healthy.

At 95 percent, expected average latency is 0.95 times 2 plus 0.05 times 30, or 3.4 milliseconds. At ninety percent, source demand doubles to 10,000 reads per second, while the simple average becomes 0.9 times 2 plus 0.1 times 30, or 4.8 milliseconds. A modest average-latency increase can therefore accompany a dangerous doubling of source traffic. If the source's sustainable budget is 8,000 reads per second, the new workload is already beyond its tested envelope.

Intermediate state: source queuing increases miss latency, so thirty milliseconds no longer remains a constant. Timeouts and retries raise offered load further. The original average formula becomes an optimistic lower-complexity estimate rather than a reliable prediction. Admission, coalescing, and source concurrency limits must intervene before the source enters a retry spiral. A cache metric dashboard showing ninety percent hits can look good while the service is unstable.

Failure variation: the cache becomes completely unavailable. Blind fail-open behavior sends 100,000 reads per second to a source tested for 8,000. Choose an explicit degraded response, bounded stale data where permitted, prioritized source access, or rejection. Final outcome is a capacity-aware miss contract rather than an assumption of unlimited bypass. Interview takeaway: design for the miss-rate multiplier and the correlated failure path, not only steady-state savings.

What availability should the cache add?

A cache can make some reads available when the source is down, but only for objects already present and still valid under policy. It can also become a required dependency if every request blocks on a slow lookup before fallback. Set separate lookup timeouts and circuit behavior, then test the source budget during bypass. A circuit breaker that sends all traffic to the database is not a complete availability mechanism; it can move the outage to the authority.

Chapter summary

High hit ratios make the source sensitive to small regressions. Quantify miss amplification, workload cost, tail behavior, and cache-loss admission before optimizing memory or lookup speed.

03 · Fill and invalidation protocols

A delayed fill can undo a correct invalidation

Trace concurrent readers and writers rather than memorizing cache-aside steps.

Cache-aside, write-through, and write-behind

In cache-aside, the application reads the cache, reads the source on a miss, and fills the cache. Writers usually update the source and invalidate or refresh the derived entry. In write-through, a layer coordinates writes to the authority and cache under a defined acknowledgment rule. In write-behind, an acknowledged update may wait in an intermediate system before reaching the ultimate source. These names do not prove atomicity. Ask what survives a crash and which component is authoritative for an acknowledged write.

Deleting before updating the source permits a concurrent reader to refill the old value before the write commits. Updating first and deleting afterward avoids that particular ordering, but a reader that began earlier can still publish an old snapshot after the deletion. Delayed duplicate deletion can reduce some race windows operationally, but without additional assumptions it is not a proof that no stale value can return. Version-aware fills, invalidation ordering, leases, or a bounded-staleness contract address different parts of the problem.

An invalidation event should identify the key and a meaningful source revision where the design supports it. Delivery may be duplicated, delayed, or reordered. The source update and durable publication intent can share an outbox transaction, avoiding a lost notification after database commit. The consumer still needs a repeat-safe invalidation protocol and a recovery method after disconnection. Reliable event transport does not itself prevent a stale in-flight fill.

Worked example 2: stale fill after deletion

Initial state: source key K has value A at revision 10 and is absent from the cache. Reader R starts a source read and obtains that snapshot, then pauses before filling. Writer W commits value B at revision 11 and invalidates K. The objective is to prevent R's delayed reply from restoring A as if it were current. Under naive cache-aside, R resumes, sets A, and later readers observe stale revision 10 despite a correct source write and invalidation.

A proposed version-gated fill keeps a known minimum acceptable revision per key. W's invalidation advances the floor to 11. R's attempted fill carries revision 10 and is rejected. A new reader obtains revision 11 and can fill B. Intermediate state may be a miss, which costs work but preserves the chosen version invariant. Final outcome is that an older fill cannot overwrite evidence of a newer committed update while the revision floor remains valid.

Failure variation: the floor is stored only inside the value entry and disappears on eviction. After B is evicted, R's old revision 10 can arrive to an apparently empty key and be accepted. The protocol must retain version evidence long enough, use a generation tied to the fill, consult the authority, or define another supported barrier. A bare compare-by-version on resident values is insufficient when absence also deletes the proof.

Production implication: separate fill eligibility from ordinary data residence, and bound how long old reads or fill tokens can remain valid. If you cannot maintain that evidence economically, choose a weaker explicit freshness contract rather than claim strong consistency. Interview takeaway: the adversarial sequence is read old, write new, invalidate, then fill old. Any proposed invalidation design should explain that exact trace, including eviction and delayed messages.

When TTL is the contract

A TTL can bound residence after insertion, but it does not necessarily bound source staleness from the instant of a write. A very old source read inserted just now can live for the full TTL unless age or version is checked. State whether TTL begins at source snapshot, fill creation, or cache insertion. Use a maximum source-age predicate or version requirement when needed, and include clock uncertainty if wall time drives correctness. Expiration is a useful policy, not a universal consistency proof.

Chapter summary

Invalidation races involve in-flight reads as well as write order. Version evidence, fill generations, durable notification, and explicit TTL semantics must be tested through eviction and delayed delivery.

04 · Leases and generation barriers

Protect publication, not just cache occupancy

A fill token is useful only when the cache enforces its current authority.

Coalescing ownership and freshness ownership differ

A fill lease can choose one loader for a missing key and reduce duplicate source reads. It can also carry a generation that invalidation advances. The cache accepts a fill only when the token matches the current generation under an atomic operation. Distinguish a local single-flight promise within one process from a distributed lease across many clients. Local coalescing alone can still create one source request per application instance.

Lease expiration must not accidentally validate an old loader. A new lease should have a distinct generation or nonce, and release must compare identity so an old owner cannot delete a newer owner's lease. A paused loader may continue after expiry, so resource ownership and fill publication cannot rely on its voluntary behavior. The cache or publication authority must reject the stale token. A lease is not useful merely because a client received one.

Retaining metadata forever is expensive. A safe reclamation policy needs evidence that no old fill can be accepted later, such as bounded token validity checked at publication, a new namespace generation after recovery, or a reliable connection/session protocol with stated failure behavior. If the cache loses all generation metadata on restart, it should not treat an arbitrary pre-restart token as current. Restart identity is part of the protocol.

Worked example 3: eviction removes the newer value

Initial state: loader L1 holds generation 7 and has read source revision 40. A source write commits revision 41. The invalidation path advances key K to generation 8 and installs or records revision floor 41. A new loader L2 fills revision 41 under generation 8. Memory pressure then evicts the value. The objective is to prevent L1's delayed generation-7 response from becoming valid merely because the value is gone.

The design retains the generation barrier independently of the evicted payload for the required token window. L1's fill request compares generation 7 against 8 and fails. L2 or a later loader can refill current data after obtaining a current token. Intermediate state is empty payload with retained authority metadata, not a reset to “no history.” Final outcome preserves the freshness barrier across ordinary eviction.

Failure variation: the entire cache process restarts and loses payload and generation state. It creates a new cache incarnation C2, and all fill tokens from C1 become invalid under the publication rule. Clients refresh tracking state or reconnect before filling. If the system instead accepts old tokens against a default generation zero, it has not established the invariant. Define how invalidation resumes and how the authority handles writes during the restart gap.

Another variation is an invalidation stream that falls behind while clients keep serving. Mark affected partitions or tracked keys untrusted, flush or bypass under source budgets, and reestablish a verified frontier before resuming the stronger contract. Production implication: generation metadata, source revisions, stream progress, and cache incarnation form a correctness lifecycle, not decorative fields. Interview takeaway: absence of a value is not evidence that no newer write occurred.

Measure inconsistency directly

A high hit rate cannot establish freshness. Sample or systematically check whether served versions violate the declared contract, using authoritative evidence without overwhelming the source. Delayed checks can distinguish temporary propagation delay from persistent inconsistency when the measurement is designed carefully. Meta's public cache-consistency article grounds the importance of version-aware races and consistency measurement. The generation protocol above is an original design exercise, not a claim to reproduce Meta's implementation or reported metrics.

Chapter summary

Eviction and restart can erase evidence needed to reject stale fills. Retain or renew publication authority explicitly, and observe correctness rather than inferring it from hit rate.

05 · Stampedes and source protection

A miss is a workload, not a free fallback

Coalesce duplicate loads and bound total source work independently.

One missing key can trigger thousands of reads

When a popular entry expires, many clients can observe the same miss before the first refill completes. This thundering herd can overwhelm the source. A single-flight mechanism lets followers wait for one in-flight load rather than each issuing a duplicate. A distributed lease can extend coalescing across processes. Both need deadlines and failure behavior: if the loader dies, followers must not wait forever, and a new loader must not accept an expired predecessor's fill.

TTL jitter spreads expirations across time for different keys. It does not solve a single extremely hot key expiring, and it does not protect against a whole cache restart. Probabilistic early refresh or soft-expiry refresh can smooth demand when stale serving is permitted. Define a soft freshness deadline for background refresh and a hard deadline after which the value cannot be used. If authorization requires immediate revocation, a stale-while-refresh policy may be inappropriate.

Per-key coalescing and global source admission solve different problems. A scan of a million unique missing keys has no duplicates to collapse. Bound source concurrency, rate, queue age, and bytes under a tested budget. Reserve capacity for authoritative writes and recovery operations so cache refill traffic cannot starve correctness-critical work. A fallback path should know which requests may be rejected or served from bounded stale state.

Worked example 4: a 200-millisecond fill window

Initial state: one key receives 20,000 requests per second, and a source read plus fill takes 200 milliseconds under normal load. The key expires at time zero. The objective is to prevent duplicate loads during the refill window. Without coalescing, roughly 4,000 requests arrive during those 0.2 seconds and may all issue source reads. The estimate assumes steady arrivals and ignores any latency growth caused by the herd, so it can be optimistic.

With one effective distributed fill owner, one load starts and followers await or receive a permitted stale value. With only local single-flight across one hundred application processes, there can still be about one hundred simultaneous source loads, depending on arrival distribution. That is much better than 4,000 but may exceed a fragile source budget. Intermediate state includes waiting requests and one or more authorized loaders; memory and deadlines for followers must remain bounded.

Failure variation: the loader crashes after obtaining data but before publication. Its lease expires, a new generation becomes eligible, and another loader proceeds. The old process later resumes but cannot publish under its stale token. If all followers immediately become loaders when a timeout occurs, the recovery path recreates the herd. Use jitter and a controlled ownership handoff rather than an unbounded retry race.

Final outcome is a small bounded set of source operations and explicit follower behavior. Production implication: measure coalescing effectiveness, loader timeout, follower wait time, abandoned waits, and source rejection. Do not report a cache hit for stale serving without separately tracking its age and policy. Interview takeaway: collapse duplicate work locally where useful, coordinate distributed hot misses when justified, and protect the source against aggregate distinct misses regardless.

Negative results and errors

Negative caching can protect the source from repeated valid not-found lookups, but scope keys correctly and use an appropriate lifetime. A newly created object should not remain invisible behind a long negative entry if the product expects immediate visibility. Distinguish authoritative not found from timeout or permission failure. Caching an infrastructure error as absence can hide existing data, while sharing an authorization-dependent negative result across users can leak or distort access behavior. Define invalidation for creates as carefully as updates.

Chapter summary

Coalescing reduces same-key duplication; jitter spreads multi-key expiry; source admission bounds all miss traffic. Errors, negative values, and stale serving need explicit semantic policies.

06 · Hot keys and distributed placement

Distribute read heat without losing invalidation control

More shards do not automatically help the one key everyone wants.

Hash placement and its limits

Hashing keys across cache nodes distributes many independent keys, but one hot key still maps to one owner in a simple design. Consistent hashing or rendezvous hashing can reduce reassignment during membership changes, yet neither inherently divides one key's request rate. Virtual partitions improve balance over many keys; they do not turn a hot entity into independent state. Distinguish hot read traffic from hot update traffic before choosing replication.

Read replicas, client-local L1 caches, or deliberate replication of a hot immutable object can spread demand. Mutable copies multiply invalidation paths and memory. A short-lived L1 can reduce network traffic but create more stale-serving sites after a write. If the item is authorization sensitive, every copy must obey the same validity contract. An architecture that adds replicas to fix latency may create a correctness problem larger than the original capacity issue.

Client-side load balancing should account for failures and congestion rather than retry every alternate node immediately. A node outage remaps keys and produces misses, potentially overloading surviving cache nodes and the source simultaneously. Plan failure-state memory and network headroom, admission, and staged warming. The cache cluster's redundancy objective should include the cost of rebuilding its working set, not merely the ability to reconnect.

Worked example 5: a hot immutable routing manifest

Initial state: one immutable model manifest version receives 120,000 reads per second. A cache node sustains 40,000 such reads per second at the required payload size and latency. The objective is to serve the hot version with headroom while preserving exact content identity. Three perfectly balanced copies provide only the nominal 120,000 ceiling, leaving no failure or skew margin. Four copies divide demand to 30,000 each under uniform routing, or 75 percent of the tested per-node ceiling.

If one copy fails, the remaining three receive 40,000 each in the ideal steady state, reaching the tested limit. That may still be too aggressive once transient skew and retries are included. Five copies would leave four after one failure, preserving the 30,000 ideal load. This arithmetic makes the reserve decision visible; it does not prove a real load balancer can redistribute instantly. Add per-replica admission and test the failure transition.

The manifest is keyed by content hash and version, so an existing copy never changes in place. A separate mutable alias selects the approved version. That alias has its own consistency and rollout contract; replicating immutable content does not make alias updates safe automatically. Intermediate state may intentionally serve two approved versions during rollout if the product permits it. Otherwise route only to copies ready for the required version.

Failure variation: the same replication approach is applied to a mutable tenant permission map without reliable invalidation. Read capacity improves while revoked access persists on an overlooked copy. Final outcome is safe read scaling for immutable content, with a separate controlled authority for mutable selection. Production implication: use replication selectively based on update rate, object size, semantics, and failure headroom. Interview takeaway: immutable hot data is easy to duplicate; mutable authority needs a different argument.

Hot writes and key decomposition

A frequently updated aggregate can invalidate so often that caching has little benefit. Consider caching immutable components, maintaining incremental projections, batching compatible reads, or changing the API's consistency scope. Splitting a counter into shards can scale writes only if merge and read semantics support it. Do not salt a key randomly and call the resulting independent values correct without explaining how updates and reads combine. Some hot state needs a serialized authority more than it needs a cache.

Chapter summary

Hashing balances many keys; hot-key replication balances one key's reads at the cost of more copies and validity paths. Immutable content and mutable authority should usually be treated separately.

07 · Memory, eviction, and economics

Cache the most valuable reusable work

A memory budget includes keys, metadata, allocator overhead, replicas, and failure reserve.

Eviction is not invalidation

Invalidation removes eligibility because the representation is no longer valid under policy. Eviction removes resident data to reclaim space. An evicted value may still be correct and refillable; an invalid value should not be served merely because memory is available. Expiration is another rule, often based on time. Conflating these operations makes it difficult to reason about version barriers and to diagnose misses.

LRU approximates reuse by recency, LFU by frequency, and admission policies can reject one-time scans before they displace a useful working set. Implementations may approximate these policies to reduce metadata and lock overhead. Redis documents several eviction modes; check the actual selected mode and workload rather than assuming an exact textbook algorithm. Some modes consider only entries with expirations, and a no-eviction policy shifts pressure to write failure instead of automatic removal.

Object size and recomputation cost matter. A large cheap object can displace many small expensive ones. A cost-aware policy might estimate avoided work per resident byte, but dynamic estimates can be noisy and expensive. Tenant partitions or quotas can prevent one scan from polluting shared space. Reserve memory for operational buffers and non-evictable metadata, especially if version or lease evidence must outlive payloads. A configured maximum is not always equal to process resident memory.

Worked example 6: size and replicate a working set

Initial state: ten million entries have average value size 500 bytes, key size 80 bytes, and measured per-entry metadata plus allocator overhead of 120 bytes under the chosen implementation. The objective is a first-order resident-memory estimate for two complete copies at seventy percent planned occupancy. Each entry costs 700 bytes, so one logical copy requires 7,000,000,000 bytes, or 7 GB decimal. Two copies require 14 GB before additional process buffers and reserve.

At a target occupancy of 0.7, the memory capacity for those entries is approximately 14 divided by 0.7, or 20 GB decimal across the replicated placement. That is not a hardware recommendation: replication placement, uneven shards, failover, transient warming, connection buffers, and implementation overhead can require more. If one node fails, survivors must handle both request load and the intended post-failure memory policy. A two-copy design does not mean every failure can be repaired without temporary eviction.

Intermediate state during warming can include old and new representations at once, especially after a schema or key-version change. A rollout that doubles resident versions can exceed the steady-state estimate and trigger eviction storms. Rate-limit warming, remove old versions under a safe lifecycle, and measure peak memory. If metadata overhead rises after enabling per-key barriers, repeat the sizing rather than pretending correctness fields are free.

Failure variation: a new tenant scans one hundred million unique objects with little reuse. LRU alone may cycle the hot working set out. Admission based on observed reuse, dedicated scan paths, or tenant budgets can protect valuable entries, but policy must be measured with representative traffic. Final outcome is a capacity and policy choice tied to avoided work, not an arbitrary cache size. Interview takeaway: quantify complete resident cost and test workload changes, including the migration peak.

Choose the economic unit

Compare saved source CPU, avoided latency, network bytes, GPU prefill, and failure exposure against cache memory and operational cost. A cache that saves expensive GPU work can be valuable at a lower request hit rate than one avoiding cheap metadata reads. Conversely, a cache with excellent hits but severe invalidation complexity may cost more engineering effort than it saves. Record the workload assumptions and the metric that would justify resizing or removing it.

Chapter summary

Separate invalidity from memory pressure. Size full resident cost and peak transitions, choose admission and eviction for the actual workload, and optimize saved work rather than one headline hit ratio.

08 · AI cache semantics

Prefix reuse, response reuse, and retrieval reuse are different

Correct cache identity must include every model and policy dependency that changes meaning.

Transformer prefix reuse

Autoregressive transformer inference builds intermediate attention state for prior tokens. Reusing a compatible exact prefix can avoid repeated prefill work. It does not automatically avoid the work of generating new output tokens, and it is not the same as returning a previously generated answer. The reusable state depends on the token sequence and model computation context. A textually similar prompt may tokenize differently or include different hidden templates, making a naive text key insufficient.

Anthropic's prompt-caching documentation establishes a public prefix-reuse capability with product-specific identity and lifetime rules. NVIDIA TensorRT-LLM and vLLM documentation provide serving-system context for KV/prefix reuse. These references are not evidence that every implementation shares the same eviction policy, cache isolation, or internal key. Check the chosen runtime's version, model adaptation behavior, and tenant isolation before deploying shared reuse.

A hypothetical prefix-cache key may include exact model weights, tokenizer identity, token IDs, prompt template version, adapter identity, relevant positional configuration, and a permitted sharing scope. Not every runtime exposes this exact tuple; it is an analysis checklist. If an adapter or embedding configuration changes computation, reusing state from the old computation can be wrong even when the visible text matches. Use a verified runtime contract rather than inventing a universal key.

Response and semantic caches

A response cache returns a previously accepted output. Its validity includes model/version policy, requested output format, tool results, retrieval corpus version, authorization, and any nondeterministic or time-sensitive inputs the product promises to reflect. Similarity-based semantic caching changes the contract further: two prompts judged nearby are not necessarily interchangeable. Treat it as an approximate product decision with evaluation and safety constraints, not as an ordinary exact lookup optimization.

A financial or recovery instruction should not be answered from another user's semantically similar context without checking the actual resources, policy, and current state. A cache can store a read-only plan explanation while effectful execution revalidates authority. For a hypothetical OCI recovery assistant, cache stable documentation by version, retrieve live plan status under its freshness contract, and never cache permission to execute a destructive action as an indefinitely reusable answer.

Retrieval caches also require careful scoping. Query text and embedding model may identify candidate search work, but document access can change after the cached candidate set was created. Apply current authorization where required, version the corpus and ranking pipeline, and measure whether caching hurts retrieval quality or freshness. A fast unauthorized answer is a correctness failure even if its semantic similarity score is high.

Security and observability

Cross-tenant reuse can expose data directly through a bad key or indirectly through timing and resource behavior. Define whether sharing is permitted, separate sensitive namespaces, and avoid logging raw prompts in cache diagnostics. Encrypting entries does not repair an incorrect sharing scope. A deletion or policy change may require invalidating multiple representations, including responses, embeddings, retrieval candidates, and prefix state under the runtime's supported controls.

Observe prefill work avoided, cache-resident bytes, eviction churn, token or byte reuse, response correctness, freshness, and isolation violations separately. A prefix hit that saves prefill may leave decode latency largely unchanged for a long generation. A response hit may save nearly all compute but carry much stronger validity obligations. How I would explain this in an interview: “I classify the reused object first. Prefix state, an answer, and retrieval candidates each have different identity and security dependencies, so I evaluate benefit and correctness separately.”

Chapter summary

AI caching is not one mechanism. Exact computation reuse, output reuse, and approximate semantic reuse need distinct keys, evaluation, isolation, and freshness contracts.

09 · Production cache architecture

Design a cache layer that degrades safely

A complete hypothetical design for tenant metadata and immutable AI artifacts.

Requirements, authority, and APIs

Design a service receiving 100,000 metadata reads per second and 2,000 writes per second, with skewed tenants and a source read budget of 8,000 per second under the tested workload. Assume display metadata permits bounded staleness, immutable model manifests are content addressed, and authorization or destructive-operation ownership requires a stronger authoritative path. These are proposed contracts, not a universal consistency level. The system should preserve source availability during cache loss and report when it cannot satisfy freshness.

The application SDK performs key construction, local single-flight, validity checks, and policy-aware fallback. A distributed cache stores payloads and publication metadata. A fill coordinator or supported cache protocol issues generation-bound tokens for selected mutable keys. The source commits updates with durable invalidation intent. An invalidation consumer advances version or generation evidence, while a reconciler detects gaps and reestablishes trusted state after disconnection. A separate admission layer bounds source reads and refresh work.

Expose get with namespace, tenant, key, required source revision or freshness class when applicable, and deadline. Return value, representation version, source revision, and whether stale serving was used under policy. A fill request includes value, source revision, cache incarnation, generation token, and token validity. Invalidate includes the authoritative revision and logical event identity. These are conceptual API contracts; implement only through mechanisms the selected cache and store can enforce atomically.

Keep authoritative database records separate from cached payload and barrier metadata. The source's revision must order relevant writes within the object's scope. A transaction records the write and outbox event before acknowledgment. Cache-side publication compares token/incarnation and version floor atomically. A cache restart changes incarnation, invalidating pre-restart tokens. Barrier reclamation follows a proven bounded-token or revalidation policy rather than ordinary payload LRU.

Normal read, update, and failure flows

A read first validates namespace and authorization policy, then checks any allowed L1 entry and distributed payload. A hit is usable only if its representation and required source condition match. On miss, local coalescing reduces duplicate requests within the process. A distributed fill owner may be elected for hot mutable keys, and the source admission layer permits only bounded reads. The loader reads a source snapshot, checks age/version, and publishes under current fill authority. Followers wait within a bound, receive permitted stale data, or get a clear unavailable result.

A write commits the source revision and invalidation intent. The invalidation path advances the cache barrier so older in-flight fills cannot become current. If a client requires read-your-writes, its subsequent request carries the required revision and rejects or bypasses a cache entry below that boundary. This is not free strong consistency for every request: it is a specific version contract that must be carried through L1, distributed cache, and source fallback.

On invalidation-stream loss, affected cache state becomes untrusted for the stronger contract. The system can flush or rotate namespaces, reconcile a verified frontier, and temporarily use bounded source access. It cannot silently keep advertising the same freshness guarantee while missing writes. On cache node loss, remapped keys and refill traffic are admitted gradually. On source loss, only existing entries valid under their policy can be served; misses and security-sensitive operations may fail closed.

Capacity, security, operations, and alternatives

The source budget implies that at 100,000 one-lookup reads per second, a simple uncached miss fraction above eight percent exceeds its tested read envelope before refresh and retries. Reserve some budget for writes and recovery, so the operational threshold may be stricter. Enforce source concurrency and tenant fairness independently of cache status. Batch compatible lookups where supported, but do not let one tenant's unbounded multi-get monopolize memory or source work.

Keys and diagnostics must not expose raw secrets or sensitive prompts. Tenant scope is part of the key or access boundary where sharing is prohibited. Authenticate invalidation and fill operations so a malicious client cannot invalidate all tenants or publish forged high revisions. Limit object size and validate schema. A fabricated revision can poison future fills if the cache trusts arbitrary callers, so source version evidence needs an authorized origin.

Measure work-weighted hit benefit, source load, coalescing, stale age, invalidation delay, rejected stale fills, barrier memory, hot-key skew, eviction churn, and cache-incarnation transitions. Sample correctness checks under a source-safe budget. Runbooks cover disabling a bad namespace, freezing warming, isolating a hot tenant, draining cache nodes, restoring invalidation progress, and preserving safety during bypass. Alerts should distinguish normal capacity misses from an invariant violation.

Compare TTL-only cache-aside for tolerant data, version-gated or lease-based filling for stricter objects, immutable content addressing, and direct authoritative reads for high-risk low-volume operations. Managed services such as Google's Memorystore establish public product context, not a substitute for application validity design. Start with the least complex contract that meets the requirement. Evolve when measured miss pressure, stale incidents, or hot keys justify added coordination, and document the memory and operational cost of that evolution.

Chapter summary

A safe production cache joins source authority, publication evidence, bounded miss work, tenant isolation, and explicit degradation. The design must remain coherent when payloads, nodes, and invalidation connections disappear.

10 · Executable race model and validation

Test the stale loader after eviction and restart

A serial model makes the intended publication predicates visible.

What the code proves and what it does not

The executable Python example models one key with a cache incarnation, fill generation, minimum source revision, and optional payload. It issues a token, advances invalidation evidence, rejects the old loader, accepts a current fill, evicts only the value, and rejects a pre-restart token after the cache incarnation changes. This is a small educational state machine, not a networked cache implementation. Its predicates must be enforced atomically in a real system.

The distinction between evict and restart is deliberate. Eviction clears payload while retaining the barrier. Restart changes incarnation and reinitializes state under the example's assumption that new fills read an appropriate current source and invalidation trust is reestablished separately. The model does not implement that reestablishment, clocks, token expiry, distributed leases, durable outbox delivery, authorization, or source concurrency. It cannot be copied into production and advertised as a complete consistency protocol.

PYTHON · executable standard-library model
class CacheKey:
    # Serial single-key teaching model; production checks must be atomic.
    def __init__(self):
        self.incarnation = 1
        self.generation = 0
        self.floor = 0
        self.value = None

    def token(self):
        return self.incarnation, self.generation

    def invalidate(self, revision):
        self.floor = max(self.floor, revision)
        self.generation += 1
        self.value = None

    def fill(self, token, revision, value):
        if token != self.token() or revision < self.floor:
            return False
        self.value = (revision, value)
        return True

    def evict(self):
        self.value = None  # Keep publication evidence.

    def restart(self):
        self.incarnation += 1
        self.generation = 0
        self.floor = 0
        self.value = None
        # Reestablish source/invalidation trust outside this toy model.

Each operation accesses one fixed-size record, so the model's per-operation complexity is constant. A real cache with per-key barriers needs memory proportional to retained metadata and a safe garbage-collection strategy. That lifecycle cost is part of the architecture, not an implementation detail you can ignore.

Extend the model by adding token expiry checked at publication, duplicate invalidations, and a source revision requirement on reads. Then describe the atomic transaction needed if several keys share an invariant. A per-key generation cannot automatically coordinate a cross-key query result. Failure tests and rollout discipline

Inject read-old/write-new/invalidate/fill-old, then repeat after eviction, cache restart, invalidation reconnect, and loader pause. Duplicate and reorder invalidation events. Crash between source commit and event publication. Force token release after another owner has acquired a new token. Validate observed source revisions, not just final values, because equal values can hide a wrong history. Include deletes and creates so negative entries and tombstones follow the same rigor.

Load tests should include a cache flush, hot single-key expiry, unique-key scans, large objects, source slowdown, and partial cache-node failure. Measure source concurrency and rejection as well as hit ratio. Confirm that bounded stale serving never crosses the hard deadline or applies to forbidden classes. For AI reuse, test model and adapter changes, tokenizer differences, retrieval revocation, cross-tenant key collisions, and deletion requirements.

Roll out key or representation changes through explicit namespaces. Warm under a budget and measure peak memory while old and new versions coexist. Retain a path to disable a bad optimization without overwhelming the authority. A rollback may restore an older SDK but leave newer cache entries resident, so version validation must be compatible or entries must be invalidated safely. Record the workload, failure model, and actual validation evidence rather than claiming a benchmark proves all consistency properties.

Test publication predicates through the transitions that erase evidence. Validate both correctness and source protection, then roll out namespace and policy changes with memory and fallback budgets.

11 · Original interview practice

Defend the cache when its assumptions fail

Original Senior Staff questions, not verified interview reports from any company.

Twelve caching challenges

1. Is a ninety-percent hit rate healthy?

Evaluation: workload and source budget. At 100,000 one-lookup requests per second, it implies roughly 10,000 source reads before refresh and retries. That exceeds the example's 8,000 budget. Measure work-weighted benefit, tail latency, and correctness, not one ratio. Follow-up: misses are expensive joins. Recalculate avoided work. Common mistake: calling any high percentage good. Tradeoff: admission or more cache can protect the source but changes cost or availability.

2. Does updating the database before deleting the cache solve invalidation?

Evaluation: race tracing. A reader can obtain the old snapshot before the write, pause, then fill after deletion. Explain a version or generation barrier, or state a weaker freshness contract. Follow-up: evict the newer value before the old fill arrives. Preserve evidence independently. Common mistake: memorizing one write order as a proof. Tradeoff: stronger publication control adds metadata and coordination.

3. Why is compare-by-version on resident entries insufficient?

Evaluation: evidence lifecycle. Eviction can remove the newest version, allowing an old fill into an apparently empty key. Retain a revision floor, invalidate old fill generations, or revalidate through another supported boundary. Follow-up: restart the cache. Include incarnation and reconnect semantics. Common mistake: treating absence as absence of history. Tradeoff: metadata retention costs memory and needs safe reclamation.

4. Can TTL guarantee that no value is older than thirty seconds?

Evaluation: time semantics. A thirty-second insertion TTL only bounds residence after insertion. A delayed old source read may already be stale before fill. Specify snapshot age, fill validity, clock assumptions, and write-relative expectations. Follow-up: the source replica itself lags. Check its frontier too. Common mistake: equating TTL with strong consistency. Tradeoff: strict freshness can require source work or rejection when evidence is unavailable.

5. How do you stop a hot-key stampede?

Evaluation: duplicate versus aggregate work. Coalesce locally, use a supported distributed fill-owner protocol where useful, bound follower waits, and retain global source admission. Jitter helps many-key expiry but not one hot key by itself. Follow-up: the loader dies. Use controlled new generation rather than every follower loading. Common mistake: assuming a process-local lock coordinates the fleet. Tradeoff: distributed coordination adds latency and failure cases.

6. Should cache failure fail open to the database?

Evaluation: failure-state capacity. Only within a tested source budget and permitted semantics. A complete bypass can multiply load twentyfold in the 95-percent-hit example. Use prioritized source admission, bounded stale data where allowed, or explicit rejection. Follow-up: authorization data is unavailable. Do not inherit display-data stale policy. Common mistake: moving the outage to the authority. Tradeoff: controlled degradation protects overall recovery at the expense of some requests.

7. Will more shards fix the one key receiving 120,000 reads per second?

Evaluation: hot-key shape. Simple hash placement still sends the key to one owner. Replicate appropriate read data, use L1 reuse, or change the representation. Mutable copies require invalidation and isolation. Follow-up: one replica fails. Recompute per-survivor load and skew. Common mistake: using fleet capacity for one serial key. Tradeoff: copies save read latency while consuming memory and validity paths.

8. Why can an LRU cache fail under a scan?

Evaluation: admission versus eviction. One-time objects can displace a hot reusable set. Consider reuse-aware admission, tenant budgets, scan bypass, or cost-aware policies, then measure the workload. Follow-up: objects vary a hundredfold in size. Include bytes and saved work. Common mistake: assuming recency equals value. Tradeoff: richer policies use metadata and can mispredict future reuse.

9. Are ten million 500-byte values a five-gigabyte cache?

Evaluation: complete sizing. Include keys, metadata, allocator overhead, replicas, buffers, and failure reserve. The worked example has 700 bytes per entry, 7 GB per copy, and about 20 GB capacity for two copies at seventy-percent occupancy before other costs. Follow-up: two schema versions coexist during warming. Budget the peak. Common mistake: sizing payload bytes only. Tradeoff: lower occupancy costs memory but reduces eviction and transition risk.

10. Does prefix caching return a previously generated answer?

Evaluation: AI mechanism distinction. Prefix reuse avoids compatible prior computation, often prefill; response caching reuses output. They have different keys, benefits, and correctness requirements. Include exact model/token context and permitted sharing scope under the runtime contract. Follow-up: an adapter changed. Revalidate computation identity. Common mistake: claiming all generation latency disappears. Tradeoff: saved prefill competes with resident cache memory.

11. Can semantic similarity justify cross-tenant response reuse?

Evaluation: authorization and product semantics. Similar prompts may refer to different resources, policies, or time-sensitive state. Sharing needs explicit permission and an evaluation contract; it cannot bypass tenant isolation. Follow-up: a retrieved document was revoked. Apply current policy where required. Common mistake: treating approximate matching as exact validity. Tradeoff: approximate reuse may save more compute but introduces quality and security risk.

12. How do you prove the invalidation system is working?

Evaluation: evidence and operations. Measure served versions against the declared source condition using controlled checks, track invalidation delay and rejected stale fills, and test disconnect/restart races. Hit ratio and event-delivery success are insufficient. Follow-up: consistency checks overload the database. Budget and sample them without hiding uncertainty. Common mistake: inferring correctness from performance. Tradeoff: stronger observability consumes source capacity but catches silent errors.

Architecture defense: cache restart during permission revocation

The interviewer restarts the cache while a popular tenant permission is revoked and the source is near capacity. Clarify which reads require current authorization, what cached capabilities remain valid, and how invalidation trust is reestablished. A strong answer rejects old-incarnation fills, bounds source access, and fails closed for operations lacking required permission evidence. It may serve unrelated tolerant metadata from valid stale entries. It does not silently extend every TTL or route all traffic to the database. Defend the reduced availability as a scoped safety decision and propose evidence-based recovery steps.

Chapter summary

A strong caching answer names the source, validity inputs, stale behavior, publication barrier, and miss budget. Performance and correctness are separate claims requiring separate evidence.

12 · Speaking and recall

Explain the cache as a validity and load protocol

Connect saved work to source safety and observable freshness.

Thirty-second explanation

A cache reuses a representation to avoid expensive work. I define its authority, key, freshness, and authorization contract first. Then I protect fills against stale publication, coalesce duplicate misses, and bound source load. Eviction and restart must not erase needed correctness evidence. For AI, prefix state, responses, and retrieval results require different validity inputs.

Two-minute explanation

I would begin by classifying cached objects. Display metadata may tolerate bounded staleness; permission or ownership decisions may require current authority; immutable model artifacts can use content identity. The cache key must represent every input that changes meaning, including tenant scope and representation version.

Next I would quantify the source dependency. At one hundred thousand reads per second, a hit-rate drop from ninety-five to ninety percent doubles simple miss traffic from five thousand to ten thousand. A cache outage can therefore overwhelm the source unless bypass is admitted under a tested budget. Single-flight and fill leases reduce duplicate misses, but distinct-key scans still need global controls.

For correctness, I would trace a reader that gets an old snapshot, pauses, and fills after a newer write and invalidation. A supported version or generation barrier must reject that fill, including after payload eviction. Cache restart needs a new incarnation or equivalent invalidation of old publication authority. TTL alone does not prove source-relative freshness.

Finally, I would test hot keys, restart, invalidation gaps, warming peaks, and source slowdown. I would measure stale-version violations and work avoided separately from hit rate. The design is successful when it saves valuable work without weakening the promised business or security behavior.

Five-minute explanation

Suppose we are adding a cache to an enterprise AI control plane. I would first identify the authoritative data and classify operations. A model manifest is immutable and content-addressable. A tenant display record might allow a short stale interval. A permission or destructive recovery ownership check may require a stronger source contract. One generic TTL policy would conceal those differences.

I would define the key and entry metadata before choosing a cache product. The key needs tenant scope and every version that changes representation meaning. The entry can carry source revision, representation version, and policy deadlines. For AI computation reuse, exact model and token context matter. A prefix hit saves prior computation; it is not automatically an answer cache, and a semantically similar prompt is not automatically interchangeable.

Then I would model load. With high hit ratios, small regressions can multiply database traffic. A source tested for eight thousand reads per second cannot absorb one hundred thousand bypasses during a cache outage. I would bound source concurrency and rate, prioritize critical operations, coalesce duplicate loads, and use permitted stale data or explicit rejection. A circuit breaker is incomplete if its fallback simply destroys the authority.

The key correctness trace is a delayed old fill. A reader obtains revision ten, a writer commits revision eleven and invalidates, then the reader sets revision ten. Updating before deletion alone does not prevent it. I would use a supported publication rule with source-version evidence or a generation-bound fill token. The cache must enforce the check atomically. If eviction removes the newer value, the proof cannot disappear with it. If the cache restarts, old tokens cannot become current by accident.

That stronger protocol has a lifecycle cost. Barrier metadata needs a safe retention and reclamation rule, invalidation disconnection needs a trust-recovery procedure, and source update plus notification intent should not have a silent crash gap. If the product does not need that complexity, I would select a weaker explicit bounded-stale contract rather than advertise strong behavior from TTLs. High-risk low-volume actions may bypass the cache entirely.

For performance, I would separate hot-key reads from general sharding. One popular immutable object can be replicated and locally reused; mutable replicas multiply invalidation paths. I would size full memory, including keys, metadata, allocator overhead, replicas, and warming peaks. Admission and eviction should protect valuable reusable work from scans and tenant interference. Failure-state headroom includes both memory and request redistribution.

Finally, I would measure correctness directly with controlled source-safe checks, alongside hit benefit, stale age, coalescing, source rejection, and eviction churn. I would inject old fills after invalidation, eviction, and restart; pause loaders; duplicate notifications; and test permission revocation under cache loss. The architecture is defensible when its saved work, validity evidence, and degraded behavior all refer to the same explicit business contract.

Important concepts and final cheat sheet

  • Authority: the source defining valid state.
  • Validity key: all inputs needed for safe reuse.
  • Source revision: ordered evidence within an object scope.
  • Invalidation: removing eligibility, not merely payload.
  • Eviction: reclaiming resident memory.
  • Fill generation: authority checked at publication.
  • Cache incarnation: identity separating restart histories.
  • Single-flight: coalescing one in-flight load per scope.
  • Stampede: duplicate work after a shared miss.
  • Miss budget: source capacity available for refill.
  • Hot key: one key dominating a placement path.
  • Admission: choosing which objects or loads enter.
  • Prefix reuse: compatible computation reuse.
  • Response reuse: output reuse under a broader validity contract.

Common mistakes are treating a high hit ratio as health, TTL as universal freshness, delete-after-write as a complete proof, and prefix caching as answer reuse. Replace each shortcut with a concurrent trace and an explicit predicate. Useful interview language includes “this metadata must outlive payload eviction,” “the source budget bounds fallback,” and “the cached representation is valid only under these inputs.”

Whiteboard and speaking practice

In thirty seconds, distinguish invalidation from eviction. In two minutes, trace read-old, write-new, invalidate, evict, and fill-old. In five minutes, defend the production cache while the source slows and a permission is revoked. On a whiteboard, draw authority, payload residence, publication metadata, invalidation transport, and source admission separately. Pause one loader and restart one cache node. State which token remains valid, which value can be served, and how the source avoids overload.
