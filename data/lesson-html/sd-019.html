SD-019 · Chapter 1 of 12

Separate bytes, names, and publication authority

Storage is more than durable capacity

A storage service answers several different questions. Where are the bytes? What logical object do they represent? Who may read them? Which version is current? Has a dataset or checkpoint become complete enough to publish? An object store can hold every uploaded byte while the application still lacks a correct answer to the last question. Begin the design by separating byte durability from namespace authority and application publication.

An object typically has a key and a value accessed through a service API. A distributed file system exposes a file-oriented namespace and a particular set of operations, which might include paths, directories, ranges, append, rename, and permissions. The exact contract varies. A file-system-shaped adapter over an object store does not automatically provide every POSIX behavior expected by an application. Verify the operations actually used, especially concurrent mutation, rename, locking, and visibility after failure.

Metadata maps logical identity to the information needed to interpret or locate bytes. It can include object version, length, digest, owner, schema, chunk placement, and publication state. Some metadata is stored alongside the object; other metadata belongs in a separate transactional catalog. Keeping everything called metadata in one box hides different consistency and scaling requirements. A display label and a checkpoint commit pointer have very different authority.

Define the user-visible consistency unit

Ask whether the product reads one object, a directory, a dataset manifest, or a mutable collection. A store can provide strong consistency for individual object operations without offering a transaction over all objects in a dataset. Reading two keys at different moments can still combine versions that never belonged to one committed application snapshot. Strong single-object semantics are useful, but their scope must match the invariant.

For an AI platform, training examples, tokenizer files, model weights, optimizer shards, retrieval indexes, and evaluation reports each have different update patterns. Immutable bulk data works well with object APIs and content-addressed references. A mutable catalog selects a particular immutable version. A fine-grained shared writable file workload may require a richer file service or a changed application access pattern. Choose semantics from the workload rather than from a generic ranking of storage technologies.

This lesson builds an original hypothetical artifact and checkpoint platform. Its source discussions are public context, not a claim about a company's private storage. Every capacity number is an explicit exercise assumption. Our correctness objective is that readers either obtain a complete authorized published version or a clear failure, never a silently mixed checkpoint assembled from unrelated attempts.

Chapter summary and first design questions

Write down object size distribution, object count, request rate, read ranges, update frequency, concurrency, durability needs, retention, and failure domains. Add the restore objective, not just the write objective. A checkpoint that writes quickly but takes too long to restore may fail the training recovery requirement.

Then name the authority that publishes a version. A successful upload is an object event; a successful publication is an application event. This distinction will guide conditional commits, manifests, garbage collection, and recovery throughout the lesson.

SD-019 · Chapter 2 of 12

Publish immutable data through a small authoritative pointer

The manifest pattern

A manifest is a complete description of one application version. It lists immutable object identities, expected lengths and digests, schema information, and the logical relationships needed by readers. Writers upload data first, verify the required objects, write an immutable manifest, and then conditionally change a small authoritative pointer. Readers resolve the pointer once and follow that manifest rather than discovering membership through an uncontrolled listing.

The pointer update is the publication boundary. Its store must provide the conditional operation required by the design, such as compare-and-swap on a generation. If no such primitive exists in the chosen object API, use a suitable metadata service or revise the protocol. An ordinary overwrite after a read is not a conditional update: two writers can both read the same old pointer and overwrite each other.

Readers should pin manifest identity for the duration of an operation. If they fetch a mutable latest pointer before every shard, an update can mix generations. The manifest is also a portability boundary: object placement can change behind immutable identity if the catalog and verification protocol support it. Do not expose a temporary upload path as the durable logical identity.

Worked example 1: a four-shard checkpoint

The initial state has checkpoint C40 published at pointer generation seven. A new attempt A writes four shards for C41. The objective is to publish C41 only after all required shards from that attempt are complete. A uploads shards zero, one, and two, then crashes before shard three. Readers continue resolving C40 because no complete C41 manifest has been committed.

A replacement attempt B must not combine A's partial optimizer state with B's later training state merely because filenames match. It either resumes the exact consistent snapshot under a supported protocol or writes its own complete attempt-scoped objects. B uploads all four shards, checks their lengths and digests, and writes manifest M41 referencing only B's consistent state. The catalog then conditionally replaces generation seven with eight and points to M41.

Suppose another publisher C already advanced the pointer to generation eight while B was working. B's compare-and-swap expecting seven fails. B re-reads current state and decides whether its version is still eligible. It does not blindly overwrite the pointer and hide a newer checkpoint. Application policy can allow historical publication in a separate index without making it latest.

The final visible result is either C40, C's valid published version, or B's complete C41 after a successful conditional commit. Readers never infer completeness from the existence of three or four similarly named keys. Correctness rests on immutable references, complete validation, and one authoritative conditional publication step. The production implication is that orphaned uploads are normal and need later collection; they are preferable to publishing a partial checkpoint.

In an interview, emphasize that strong object reads do not create a multi-object checkpoint transaction. The manifest protocol supplies the application consistency unit. If a required object disappears or cannot be decrypted after publication, the read fails visibly and triggers recovery; a reader must not silently substitute a shard from another checkpoint.

Retries and publication evidence

A timeout on the conditional pointer update is an unknown outcome. Re-read the authoritative pointer and compare change identity or manifest identity. If the intended commit is visible, return that result. If another valid commit won, report the conflict. Stable change identity prevents a client from confusing repeated attempts with unrelated publications.

Keep publication receipts and audit evidence according to the recovery contract. A local log line saying upload finished is weaker than the authoritative pointer state. Distinguish uploaded, verified, committed, retained, and restorable. Each word corresponds to a different failure boundary.

SD-019 · Chapter 3 of 12

Scale the namespace and protect metadata hot spots

Object count can dominate byte count

A billion tiny objects can be harder to manage than a much larger byte volume in a modest number of large objects. Each object requires naming, authorization, indexing, request handling, lifecycle decisions, and perhaps per-object billing. A metadata cache can accelerate reads but does not eliminate the authoritative work of creating, deleting, or changing ownership.

Namespace partitioning can follow tenant, hash, range, or directory boundaries. Hashing spreads uniformly distributed keys but makes ordered scans less natural. Range partitioning supports locality but can create a hot newest range. Directory partitioning matches file semantics but can concentrate a popular directory. Choose the partition key from measured access patterns and provide a migration strategy for hot partitions.

A single mutable latest pointer is intentionally small and potentially hot. Cache immutable manifests aggressively, but treat pointer freshness according to the product contract. High read traffic can often use a short-lived pointer cache with explicit version pinning. Conflicting publishers still require authoritative conditional serialization. Read scaling and write authority are different problems.

Worked example 2: small-file metadata budget

Assume a dataset contains one hundred million samples, each four kilobytes decimal. Raw payload is four hundred gigabytes. If each sample is a separate object and our hypothetical metadata representation consumes five hundred bytes per object, metadata alone is fifty gigabytes before indexes, replication, allocator overhead, and operational reserve. This estimate is a model, not a claim about any vendor's metadata layout.

Packing one thousand samples into each shard reduces object count to one hundred thousand. The average shard payload becomes four megabytes. At the same assumed per-object metadata size, object metadata is fifty megabytes. The application also needs an index mapping sample identity to shard and offset, so the saved object metadata does not mean all indexing disappears.

If a training batch reads one hundred randomly scattered samples and each access downloads a whole four-megabyte shard, the naive payload can reach four hundred megabytes for four hundred kilobytes of useful samples: one thousand times amplification when no shard reuse occurs. Range reads, batch-aware packing, caching, and locality can reduce this. A compressed shard format may prevent efficient arbitrary ranges, so the file format is part of the design.

The failure variation is a corrupted shard. Packing increases the number of samples affected by one damaged or unavailable object and changes retry granularity. Checksums, immutable identities, and reconstruction remain necessary. The final design chooses shard size using request overhead, locality, recovery granularity, and index cost together.

Correctness requires the sample-to-offset index to match the exact shard version. A mutable index pointing into replaced bytes can silently return the wrong sample even when every read succeeds. The interview takeaway is to quantify both metadata reduction and read amplification rather than declaring large objects universally better.

Metadata authority and caching

Cache entries should carry the version they describe. Negative caching needs a bound, because a cached absence can conceal a newly committed object or permission change. Tenant authorization cannot be reduced to a globally shared key name. A cache hit that bypasses the required access check is a security defect, not a performance optimization.

Measure per-partition operation rate, queue age, conditional-write conflicts, namespace scan cost, cache freshness, and tenant distribution. Average metadata latency hides hot directories and a single tenant's pathological workload. Use admission limits and fair queues so lifecycle scans or bulk import do not starve checkpoint publication.

SD-019 · Chapter 4 of 12

Choose durability layouts and repair budgets explicitly

Replication and erasure coding solve different cost problems

Replication stores complete copies. It can provide simple reads and repair from a healthy copy, with storage overhead proportional to replica count. Erasure coding divides data into fragments and adds redundancy so a sufficient subset can reconstruct the original. It can reduce storage overhead while increasing coordination, reconstruction work, and sensitivity to fragment placement and degraded reads.

For a k-plus-m coding scheme, k data-equivalent fragments and m parity fragments represent the object under the code's assumptions. Storage expansion is approximately (k+m)/k before other overhead. The ability to tolerate missing fragments depends on the code, available independent fragments, and placement. Do not turn this count into a probability of data loss without a failure model, repair behavior, and correlated failure assumptions.

Durability is not only a layout choice. Detect corruption through checksums and scrubbing, maintain inventory, repair under bounded resource budgets, and preserve enough free capacity to place replacements. An object with redundant bytes on disks can still be lost through a bad lifecycle rule, compromised credentials, or missing decryption keys. Backups and versioning address different failure causes from disk redundancy.

Worked example 3: storage expansion and repair exposure

Start with one petabyte decimal of logical immutable artifacts. Three full replicas require three petabytes of payload storage. An ideal eight-plus-three erasure code requires eleven eighths, or 1.375 petabytes. The payload difference is 1.625 petabytes. This excludes metadata, small-object padding, temporary staging, rebuild reserve, compression, and any cross-region copies.

Now place fragments without considering racks. If four fragments of one stripe share a rack and that rack fails, an eight-plus-three code has only seven remaining fragments, below the required eight. The nominal three-fragment tolerance did not protect this placement. Distribute fragments across declared failure domains so the failure being promised does not remove too many fragments together.

Assume a repair needs to read eight one-gigabyte fragments to reconstruct one missing one-gigabyte fragment in a simplified decode path. That is eight gigabytes of source reads plus one gigabyte of output, ignoring protocol overhead and algorithm-specific optimizations. A hundred simultaneous repairs can compete with customer reads and increase degraded exposure if repair is throttled too aggressively.

The failure variation is another fragment loss before repair completes. Whether data remains reconstructable depends on which stripe and failure domain are affected, not merely the fleet's average healthy-disk percentage. Prioritize repair based on risk and available fragments while reserving enough serving capacity. Excessively aggressive repair can itself cause timeouts and cascading load.

The final recommendation depends on artifact temperature, object size, restore latency, and operational skill. Correctness includes detecting corrupt fragments rather than counting them as usable. The interview takeaway is to connect capacity savings to placement and repair cost, then admit that no durability probability follows from the overhead ratio alone.

Placement, rebalancing, and cost

Algorithmic placement can let clients compute candidate storage locations from a versioned map, reducing a centralized lookup path. Ceph's public CRUSH documentation is one concrete example of failure-domain-aware placement. Our coding arithmetic is original and not a claim about Ceph's exact repair implementation or default policy.

When the placement map changes, old and new locations may coexist during migration. Readers and repair workers need a valid map version and a safe transition protocol. Moving bytes is not enough: update ownership evidence and retain old copies until the new placement is verified. Capacity planning includes migration and repair reserve, not just the steady-state expansion factor.

SD-019 · Chapter 5 of 12

Make reads efficient without weakening identity

Read paths and bottlenecks

A read can involve pointer resolution, manifest retrieval, authorization, key access, range selection, storage transfer, decompression, and deserialization. The slowest stage changes by workload. Large sequential checkpoint restore can be bandwidth-bound. Tiny feature reads can be request-latency-bound. A high cache hit ratio can coexist with poor tail latency if misses synchronize on a hot object.

Use immutable content identities to make caching safe. Cache data only within an authorized scope or enforce access on every retrieval as required. A digest confirms byte identity, while a signed manifest binds the expected digest to the application and tenant. Neither replaces confidentiality. Encryption keys, their recovery, and their revocation behavior belong on the read dependency graph.

Range reads reduce transferred bytes only when the format supports independent interpretation of the requested range. A compressed stream may require reading preceding data; a columnar or indexed format may expose useful blocks. Measure useful bytes divided by transferred bytes and decompression work. Optimize end-to-end restore time rather than a storage benchmark detached from the runtime.

Worked example 4: checkpoint restore bottleneck

A hypothetical job restores a 1.2-terabyte decimal checkpoint across one hundred twenty workers. Equal partitioning gives ten gigabytes per worker. Each worker can receive five hundred megabytes per second, suggesting a twenty-second per-worker transfer floor. But the shared store allocation is only thirty gigabytes per second, giving a forty-second aggregate floor. The larger constraint wins before any other work is included.

Suppose deserialization takes another fifteen seconds after transfer and cannot overlap in this implementation. The simplified restore floor becomes fifty-five seconds. If it can fully overlap with independent chunks, the pipeline bound changes; it is not correct to keep adding all stage times automatically. State the dependency and overlap assumptions before presenting the estimate.

A metadata service limits manifest lookups to two thousand per second. If each worker performs one hundred sequential metadata requests, twelve thousand requests exist in total and a six-second service-capacity floor appears. Individual round trips can impose a larger serial bound. A complete manifest fetched once per worker can reduce request count, but its size and authorization still matter.

The failure variation is one worker restoring much more data because the checkpoint partitioning does not match the new training topology. Average bytes per worker no longer predicts the straggler. A portable checkpoint format and explicit remapping can help, while remapping itself costs CPU, network, and memory. NVIDIA's documented distributed-checkpoint facilities provide public context for topology-aware loading, not a guarantee for this invented workload.

The final result is a bottleneck model with aggregate bandwidth, per-worker bandwidth, metadata request capacity, deserialization, and skew. Correctness means every worker reconstructs its assigned consistent state. The interview takeaway is to reason from the critical path and shared budgets rather than multiplying a device's advertised throughput by the worker count.

Cache stampedes and prefetch policy

When a model version becomes popular, many workers may miss the same artifact simultaneously. Coalesce downloads, stage through regional caches, and use bounded prefetch. A cache can reduce origin load while still overloading a rack uplink or local disk. Observe both origin and downstream traffic.

Prefetch competes with active work and can fetch a version never used. Give it a separate budget and cancel obsolete requests without deleting data still referenced by readers. A reader's pinned manifest is evidence that the corresponding objects remain needed even after the latest pointer advances. This connects read performance directly to retention and garbage collection.

SD-019 · Chapter 6 of 12

Delete safely while writers and readers remain concurrent

Garbage collection is a reachability protocol

Immutable objects accumulate from failed uploads, superseded versions, and completed experiments. A collector distinguishes objects reachable from retained manifests from objects eligible for deletion. Its root set includes current versions, rollback versions, legal retention, active reader pins, and any recovery checkpoints required by policy. Listing all keys and subtracting a stale catalog snapshot is insufficient when publication is concurrent.

A safe design can use upload intents, versioned roots, retention windows, reader leases, or epoch-based collection. The particular mechanism depends on the store and workload. The invariant is that an object eligible for a valid future or active publication cannot be deleted by a collector using an incompatible view. Time-based grace periods help only under stated bounds; they are not a proof when a paused writer can return arbitrarily late.

Deletion also has semantic layers. Removing the latest pointer, creating a tombstone, deleting an object version, expiring a backup, and destroying a key have different effects. A privacy deletion request may need to propagate through replicas, derived indexes, caches, and retained backups under a documented policy. Do not promise instantaneous physical erasure merely because an API returns success.

Worked example 5: a collector races publication

Initially manifest M10 is current. Writer W has uploaded object X for a future M11 but has not committed M11. Collector G snapshots only published roots, sees that X is unreferenced, and plans to delete it. W then publishes M11 referencing X. If G deletes X afterward without a protocol check, a successfully published version becomes unreadable.

Introduce an upload intent I that reserves X under writer identity and a bounded lifecycle. Publication requires the intent to remain valid, verifies the objects, and atomically records the manifest as retained in the authoritative catalog. Collection must respect both retained manifests and active intents under a compatible catalog view. After intent expiry, a returning writer must revalidate and reacquire publication eligibility; it cannot publish from an obsolete assumption.

Walk the race again. G sees active I and skips X. W commits M11 and releases I only after the retained reference is durable. If W crashes, I eventually becomes eligible for cleanup under the specified protocol. If G has already claimed an expired intent for collection, W's conditional publication fails and it must verify or rewrite its objects. The state transition is serialized where collection eligibility and publication meet.

A second failure variation concerns readers pinned to M10 after the latest pointer moves to M11. Keeping only the current root would allow premature deletion of M10's objects. Retain reader pins, a documented bounded read duration plus grace period, or explicit version retention. State what happens to an expired reader rather than silently allowing it to read arbitrary deleted state.

The final result prevents valid publication and collection from both claiming incompatible rights to the same object. Correctness is a concurrency property, not a periodic housekeeping task. The interview takeaway is to ask what stops a paused writer or old reader from returning after the collector's view was taken.

Operational deletion and recovery

Run collection in phases with auditable candidates, bounded batches, and a reversible quarantine when policy allows. Recheck eligibility at the commit boundary. Protect the root catalog more strongly than disposable staging data. A corrupted root set can make a perfectly functioning collector delete the wrong objects at enormous speed.

Test restore from retained versions and backups, including key access. A backup containing bytes but no compatible manifest, schema, or decryptable keys may not restore the application. Report deletion backlog, pinned-byte age, intent age, failed object deletes, and unexpected missing references. These measures reveal whether safety is preserved at an unsustainable cost.

SD-019 · Chapter 7 of 12

Handle concurrent namespace changes and cross-region recovery

File operations need their own invariants

File systems often support operations such as rename and directory traversal that applications treat as atomic. Whether a rename is atomic, whether it spans directories or volumes, and how open readers behave depends on the system contract. Copying an object and deleting the old key is not automatically an atomic rename. A reader can see both, neither, or an intermediate state unless a higher-level namespace protocol prevents it.

A metadata service can implement an atomic logical rename by changing namespace references transactionally while leaving immutable bytes in place. This works only if every relevant reader uses that authority. Clients bypassing the namespace and interpreting raw object listings do not receive the same guarantee. The abstraction boundary must include tooling, backup jobs, and data-science scripts, not only the main application.

Concurrent writes require a conflict policy. Options include exclusive ownership, conditional versions, append-specific coordination, immutable new versions, or application merges. Last-writer-wins can be acceptable for a disposable label but dangerous for a checkpoint pointer or access-control update. Choose based on the lost-update consequence rather than assuming one policy fits every metadata field.

Worked example 6: recovering a catalog and its objects

Region A publishes manifests through catalog generation one hundred. Region B has copied objects through checkpoint ninety-nine and has catalog backup generation ninety-eight. A fails. The objective is to restore a consistent published set, not to choose the numerically highest generation from any available source.

Restore catalog ninety-eight and verify that every object referenced by its retained manifests is readable, correctly identified, and decryptable in B. If all references are complete, ninety-eight is a candidate recovery point. Objects from ninety-nine may also exist, but without a trusted complete manifest and publication evidence they are not automatically eligible to become current. Recover those records from a verified log or treat the bytes as unpublished until reconciled.

Suppose the catalog backup contains a pointer to generation one hundred but B lacks one required shard. The metadata is newer but the application snapshot is incomplete. Recovery must fall back to the latest verified complete retained version or restore the missing shard from another protected source. Never substitute a shard from ninety-nine just to make the directory look complete.

Now add failback: A returns with a stale publisher still active. Establish new recovery authority before accepting writes, and fence or otherwise exclude the old publisher where catalog commits occur. Reconcile diverging unpublished uploads separately. Reusing the same mutable latest key without authority coordination can lose the newly recovered state.

The final recovery result names a verified checkpoint and the lost-work boundary. Correctness includes bytes, metadata, keys, schema, and write authority. The production implication is that replication lag needs to be measured by complete restorable versions, not only transferred bytes. In an interview, explain why independent backups of catalog and objects require a consistency and reconciliation plan.

Chapter summary

Durability, regional replication, backup, and application recovery overlap but are not synonyms. A replicated deletion can remove every live copy; a retained backup can protect it if keys and catalog survive. An asynchronous copy can be durable while still lagging behind the published application state. State the recovery point in terms the workload understands.

Connect public storage research to AI workloads

What the published systems establish

Google's GFS paper is a historical primary source for a distributed file system built around its stated workload and assumptions. Meta's Tectonic publication discusses consolidating storage and scaling metadata and tenant performance. These sources demonstrate that storage architecture follows workload and operational requirements. They do not establish that every modern application should copy either design or that their historical properties describe current private systems.

OpenAI's public Kubernetes scaling account provides context for large AI compute fleets. It does not disclose a complete private object-store architecture. Anthropic's public multi-agent research account provides workflow context, including persistent artifacts and coordination concerns. It does not specify a private metadata consistency protocol. Our manifest platform and publication algorithm are independent teaching proposals.

NVIDIA's NeMo distributed-checkpoint documentation describes sharded state and loading concerns for its documented software version. That grounds the distinction between a pile of tensor files and a restorable training state. Verify compatibility against the actual runtime and checkpoint version before depending on specific behavior. Do not infer that a generic object store can remap arbitrary training topology by itself.

AI-specific correctness and security

Training checkpoints can require model parameters, optimizer state, scheduler state, random-number state, dataset position, and parallelism metadata. What is necessary depends on the recovery contract. A weights-only artifact may be enough for inference but insufficient for reproducible training continuation. Name the intended use rather than calling every saved directory a complete checkpoint.

Retrieval datasets add index compatibility. A vector index, document store, embedding model, and access-control snapshot must describe a compatible published version. Replacing only embeddings can produce a semantically inconsistent retrieval path even when the file checksums are valid. Access filters must remain correct while old and new indexes coexist. Tenant-specific data must not leak through a shared cache or a reused content key.

Agent artifacts can include untrusted documents, tool results, and executable files. Storage durability does not make them trustworthy. Preserve provenance, limit preview and execution privileges, and enforce download authorization. A content hash can detect changed bytes but cannot establish that the original bytes are safe. Avoid raw secrets and unnecessary prompt retention in metadata searchable by broad operator roles.

OCI-oriented design transfer

For a cloud interview, map logical responsibilities to candidate object storage, metadata database, key management, identity, network, and cache services. Then verify the exact region, storage class, API, and failure contract. Do not assume that a familiar service name provides cross-object transactions, automatic key recovery, or an application-consistent regional replica.

The portable lesson is to specify the publication unit, byte identity, namespace authority, access scope, restore path, and collection protocol before choosing products. That vocabulary lets you compare managed object storage, a distributed file system, and a dedicated artifact service using the same workload requirements.

Defend a complete artifact and checkpoint platform

Requirements and component diagram

Design a hypothetical multi-tenant platform serving immutable model artifacts, dataset shards, and training checkpoints. Assume one hundred million sample records, occasional terabyte-scale checkpoints, concurrent publishers, regional reads, and a requirement to restore only complete authorized versions. Confirm object size distributions, restore-time objectives, retention, regional recovery point, and compliance requirements before sizing the system.

The metadata API owns tenant namespace, publication generations, upload intents, retained manifests, reader pins, and audit identity. A transactional catalog serializes publication and collection eligibility within the selected scope. Bulk immutable bytes live in object storage. A validation worker verifies expected object identities and schema. Regional caches serve authorized immutable content. A collector reclaims only objects eligible under the catalog protocol.

Clients obtain an upload intent and attempt-scoped object names. They upload, verify, and propose a complete immutable manifest. The metadata API conditionally advances the published pointer. Readers resolve and pin one manifest, acquire scoped access, then fetch ranges or shards directly from the data path. This keeps bulk transfer away from the metadata API while retaining a clear publication authority.

Normal operations and failure transitions

On a successful checkpoint, every required shard belongs to one consistent save attempt. The catalog records the manifest and generation once. On a client timeout, the client resolves the stable publication identity before retrying. On conflicting publishers, one conditional update wins and the other re-evaluates policy. On partial upload, readers remain on the previous published version and the collector eventually handles orphaned data.

On a missing or corrupt object, the read returns a visible integrity failure and invokes reconstruction or fallback to another complete retained version. It must not silently assemble a mixed checkpoint. On a cache authorization failure, the cache denies access even if it holds the bytes. On key-service unavailability, the platform reports the affected capability rather than claiming byte durability implies readable service.

On region loss, restore a catalog and object set with verified complete references and usable keys. Establish recovery write authority before accepting new publications. Reconcile old publishers and copied unpublished objects when the original region returns. Measure the recovery point as a complete restorable application version, with an explicit lost-work boundary.

SLOs, costs, alternatives, and evolution

Measure publication success and latency, conditional conflicts, incomplete attempts, manifest validation failures, useful restore throughput, metadata tail latency, cache miss amplification, repair exposure, missing references, and collector backlog. Separate storage-service availability from application restore success. A successful GET for every requested key is not enough if the application requested the wrong generation.

Cost includes capacity expansion, metadata indexes, API requests, egress, cache storage, repair traffic, retained rollback versions, and abandoned uploads. Large shards reduce request and per-object metadata overhead but can increase amplification and recovery granularity. Erasure coding reduces payload expansion but adds degraded-read and repair considerations. Regional replication supports availability and recovery while increasing cost and publication-lag complexity.

A plain object store with a manifest may be sufficient for immutable batch artifacts. A distributed file system can be better when applications require documented shared-file operations and low-latency namespace behavior. A metadata database holding every byte may simplify small-record transactions but be inappropriate for huge checkpoints. Explain the invariant each option supports rather than choosing the technology with the longest feature list.

Begin with a simple manifest catalog and managed bulk storage if they meet the contract. Add packing, regional caches, specialized metadata partitions, and coding tiers only after measurements show the relevant bottleneck. Preserve immutable logical identity during migration. A versioned manifest boundary makes evolution possible without forcing every reader to understand physical placement.

Execute a publication and collection model

Model assumptions and code

PYTHON · executable standard-library model
from hashlib import sha256

class Catalog:
    def __init__(self):
        self.objects = {}
        self.intents = {}
        self.manifests = {}
        self.generation = 0
        self.current = None
        self.pins = set()

    def upload(self, intent, payload):
        key = sha256(payload).hexdigest()
        self.objects[key] = payload
        self.intents.setdefault(intent, set()).add(key)
        return key

    def publish(self, intent, expected, name, required):
        if expected != self.generation:
            return False
        if not required or not all(k in self.objects for k in required):
            return False
        if not set(required) <= self.intents.get(intent, set()):
            return False
        if name in self.manifests:  # immutable manifest identity
            return False
        self.manifests[name] = tuple(required)
        self.current = name
        self.generation += 1
        del self.intents[intent]
        return True

    def collect(self):
        roots = self.pins | ({self.current} if self.current else set())
        keep = {k for name in roots for k in self.manifests[name]}
        keep |= {k for keys in self.intents.values() for k in keys}
        self.objects = {k: v for k, v in self.objects.items() if k in keep}

def main():
    c = Catalog()
    a = c.upload('A', b'shard-0')
    assert not c.publish('A', 0, 'partial', [a, 'missing'])
    b = c.upload('A', b'shard-1')
    assert c.publish('A', 0, 'M1', [a, b])
    c.pins.add('M1')
    newer = c.upload('B', b'new-consistent-state')
    assert not c.publish('B', 0, 'stale', [newer])
    assert c.publish('B', 1, 'M2', [newer])
    c.collect()
    assert a in c.objects and b in c.objects
    c.pins.remove('M1')
    c.collect()
    assert a not in c.objects and newer in c.objects
    assert 100_000_000 * 4_000 == 400_000_000_000
    assert (8 + 3) / 8 == 1.375

The Python model below stores immutable bytes by digest and commits a manifest through a generation comparison. It rejects incomplete proposals and stale publication attempts. Upload intents protect staged objects in the model, and a reader pin protects an old committed manifest during collection. Assertions demonstrate the race boundaries from the lesson with deterministic state.

The model is intentionally local and synchronous. Its atomic method calls stand in for transactions that a real catalog must provide. It does not implement distributed consensus, cryptographic authentication, durable replication, concurrent clock behavior, or a production object-store API. It is useful because the state transitions are visible, not because it reproduces every deployment detail.

The digest verifies byte identity in this exercise. Tenant scope, signer trust, schema compatibility, and decryption are separate production checks. A successful hash comparison never authorizes a tenant to read another tenant's artifact. Keep these conditions separate when extending the code.

Run experiments and interpret failures

Run the code with standard Python. The first proposal lacks a required shard and fails without changing the current pointer. The complete proposal commits. A second proposal using the old generation fails. An active pin prevents old content from being collected after the latest version changes. Releasing the pin allows collection under the model's retained-root rules.

Remove the completeness check and observe that a manifest can reference missing bytes. Remove the generation condition and observe a lost publication update. Remove reader roots from collection and observe that an active old reader loses its data. Each experiment changes an invariant. Passing assertions after deleting the relevant assertion would not count as fixing the design.

A useful extension adds explicit intent expiry and a collector claim state. Publication and collection must conditionally serialize eligibility, including a writer resuming after expiry. Another extension separates replicated catalog durability from object durability and simulates a region with an incomplete copy. Require recovery to choose a verified complete version rather than the largest generation number.

The code exercises correctness at a small scale. Production validation also needs load tests with realistic object sizes, namespace skew, key-service behavior, concurrent writers, large restores, and repair activity. Compare useful application throughput with total transferred bytes, not just a fast isolated storage request.

Speaking scripts and whiteboard rehearsal

Thirty-second explanation

I separate durable bytes from namespace and publication authority. Writers upload immutable objects, verify a complete manifest, and conditionally publish one pointer. Readers pin that manifest. This avoids mixed checkpoints even when uploads fail or publishers race. I size metadata and restore paths separately, choose replication or coding with placement and repair budgets, and make collection respect writers and readers. Recovery requires compatible metadata, bytes, keys, and write authority.

Two-minute explanation

The first question is the application's consistency unit. An object store can provide strong operations for one key while a checkpoint still spans hundreds of shards. I make that checkpoint an immutable manifest and publish it through one authoritative conditional transition. A partial upload remains unpublished. A lost response is reconciled using publication identity. Readers resolve once and pin a complete version.

Next I quantify workload shape. A hundred million tiny objects can create large metadata and request overhead. Packing samples reduces object count but can increase random-read amplification and corruption granularity. I evaluate both effects with the format's range-read behavior. For large restores, shared bandwidth, per-worker bandwidth, metadata calls, deserialization, and skew determine the critical path.

Durability combines layout, failure-domain placement, integrity checks, and repair capacity. Eight-plus-three coding has different expansion from three replicas, but the ratio alone says nothing about correlated-loss probability. Deletion and backups address different failure causes. A collector must not race a paused writer or an old reader; intents and retained roots need a compatible authority protocol.

For regional recovery, I verify complete manifest references and keys before selecting a recovery point. I also establish write authority before old publishers can return. The design is successful when it restores a complete authorized application version, not merely when it can list a large number of durable objects.

Five-minute architecture explanation

I will design a multi-tenant artifact and checkpoint service. I first confirm whether clients need immutable versioned objects or shared mutable file semantics. That determines whether a manifest service over bulk object storage is sufficient or a documented distributed file-system contract is required. I also ask about object count, size distribution, read locality, update concurrency, retention, restore-time objectives, and regional recovery point.

The metadata API owns tenant namespace, upload intents, publication generations, retained manifests, and reader pins. A transactional catalog serializes the transitions that must agree. Bulk immutable objects live outside this API so huge transfers do not bottleneck on a metadata process. Validation checks byte identity, completeness, schema, tenant scope, and compatibility. Regional caches accelerate authorized immutable reads.

A writer obtains an attempt identity and intent, uploads every required object, writes an immutable manifest, and conditionally advances the publication generation. If it crashes after three of four shards, readers remain on the old checkpoint. If another publisher wins, the stale conditional update fails. If the response is lost, the client resolves the stable publication identity rather than blindly publishing again. Old and failed uploads become collection candidates under a separate protocol.

A reader resolves and pins one manifest. It does not ask latest before every shard. The manifest identifies exact object versions and the structure needed to interpret them. A missing or corrupt shard produces an integrity failure or fallback to another complete retained version. It never becomes permission to borrow a shard from another training attempt. Training continuation may need optimizer, random state, dataset position, and topology metadata beyond inference weights.

Capacity planning separates payload, metadata, API work, caches, repair, and retention. One hundred million four-kilobyte samples are four hundred gigabytes of payload. Packing a thousand samples per shard reduces object count dramatically, but random reads can amplify transferred bytes unless format and locality are designed together. A 1.2-terabyte restore over a thirty-gigabyte-per-second shared allocation has at least a forty-second transfer floor before non-overlapped processing. I would test skew and topology changes rather than trust average worker bytes.

For storage layout, I compare three replicas with a declared erasure code and include failure-domain placement. Eight-plus-three expansion is 1.375 before overhead, but placing four fragments in one rack breaks a one-rack tolerance claim. Repair competes with serving and needs reserve capacity. Checksums and scrubbing discover corruption. Versioning, backup, and protected keys address logical loss that redundancy alone cannot prevent.

Collection respects current and retained manifests, active intents, and readers. A stale listing cannot safely subtract a current root snapshot while writers publish concurrently. The catalog protocol must serialize collection eligibility and publication, including expired writers that later resume. Quarantine and bounded batches reduce operational damage where policy permits. Privacy deletion may override old reader access according to an explicit contract.

Regional recovery verifies complete references, schema, and decryption keys before choosing a recovery point. A newer catalog with missing shards is not better than an older complete checkpoint. Establish new write authority, then reconcile returning old publishers. Measure recoverable application versions and lost work, not only replication bytes.

I would begin with the simplest architecture meeting these requirements. Add specialized metadata partitions, packing, coding tiers, or cache hierarchy when measurements justify them. The stable boundary is immutable logical identity plus authoritative publication. It keeps correctness reviewable while the physical storage layout evolves.
