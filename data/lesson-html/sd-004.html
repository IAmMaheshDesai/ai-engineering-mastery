SD-004 · Distributed Systems Foundations · 01

What is the reader entitled to believe?

At 10:00 a deployment engineer publishes model revision 72. At 10:01 another engineer opens the console and sees revision 71. Before declaring a consistency incident, find out exactly what the first response acknowledged and which question the second engineer asked.

Start with an observable contract

A storage system can preserve every acknowledged byte and still return an old value. A cache can return the newest value on a million sampled reads and still make no promise about the next one. Consistency names the observations an implementation permits when operations interact. The important part of the contract is the set of histories that must be ruled out. An architect should be able to give an example that would conclusively violate the proposed model, then explain which components could allow that example to occur. If the only criterion is that results usually look reasonable, the system has an operational aspiration but no testable specification.

For the deployment console, name the objects. A release artifact is immutable content addressed by a digest. The desired revision is a mutable pointer for a tenant and deployment. The observed revision at one inference worker describes what that worker actually loaded. A summary in a regional dashboard is a projection built from reports. If publish means the desired pointer moved, a worker that still serves 71 one minute later may be fulfilling a gradual rollout policy exactly. If a fresh read of the authoritative desired pointer returns 71 after a successful publish of 72, and no rollback occurred, a linearizable pointer contract has been violated. The same displayed number has two entirely different explanations depending on the object.

Write the operation before choosing a database. GetDesired asks for the value of one pointer. SetDesired takes an expected revision, a target digest and a request identity. It either atomically advances the pointer or returns a conflict. GetObserved asks for one worker's last report and includes the report time, worker session and generation. ListFleet returns a materialized summary and a watermark that states how far the view has been processed. A successful list response can be perfectly consistent with its documented snapshot and still disagree with a current point read. A user interface that labels all four results as current makes an implicit guarantee its underlying APIs do not support.

Worked example 1 · Two operations with the same timestamps on a dashboard

Start with desired revision 71 everywhere. Operator N calls Publish at local second 10 and receives success at second 14. Operator S calls GetDesired at second 15 and receives 71. To make the order independent of wall-clock synchronization, have N send S a message after receiving success, and have S invoke its read only after receiving that message. The message establishes that the publish completed before this read began. Assume the current object is one register, the initial value and all writers are known, and nobody rolled back. Any specification requiring a read to see a completed write or a subsequent one forbids returning 71 here. The fact that two requests traversed different regions changes implementation costs, not the contract.

Now let S begin the read at second 12 while the publish is in flight. Even if S receives 71 after N sees success, the read overlapped the write. There is a point during the read when 71 was a legal value. A linearizable implementation can return it if the read is placed before the write in a legal sequential explanation. It may return 72 instead if the read is placed after the write. Measuring freshness from response timestamps alone would incorrectly classify the first outcome as an anomaly. Keep both invocation and completion events in a history.

When explaining this case aloud, separate the observation from its interpretation. Say that an operator received a successful pointer update, then another client invoked a current pointer read and observed the previous value. Ask whether the endpoint promised a historical, session-scoped or current read. That single question often resolves a false alarm. If the endpoint promised a current read, follow the request path all the way to the representation that served it. A strongly consistent source does not make an asynchronously populated cache a strongly consistent read endpoint.

SD-004 · Distributed Systems Foundations · 02

Linearizability as a search for one legal history

The word instantaneous describes the illusion offered by a completed operation. A real write may execute dozens of steps. What matters is whether all observed operations fit one legal order that respects real-time precedence.

Build the specification before searching for an order

For a read-write register, the sequential rules are compact. A write replaces the current value and reports success. A read returns the current value without changing it. For compare-and-set, a command changes the value only when its expected value matches, and its result must reflect that comparison. Now record complete operation intervals. If operation A completed before B began, place A before B. If they overlap, either order is initially possible, but the chosen order has to make every response legal simultaneously. Finding a plausible order separately for each client can miss contradictions visible only when those explanations are combined.

Consider a single write changing zero to one that remains in flight for ten seconds. During that interval reader P observes one and returns. After P returns, reader Q observes zero and returns, all before the writer's response. Looking at the overlaps one reader at a time suggests that each read is defensible. For P to observe one, the write must precede P in the candidate order. Real time requires P before Q. Q must therefore see one since there is no intervening write of zero. There is no legal placement for Q's zero. Even a slow, incomplete-looking write cannot be moved to two different places to justify two incompatible reads.

Worked example 2 · The last free GPU slot

An admission service has one remaining slot represented by an empty owner field. Request A and request B each issue CompareAndSet(empty, job) to reserve it. Their calls overlap. Both receive success. Try ordering A first. The slot contains A by the time B applies, so B must fail. Try B first, and A must fail. No legal ordering yields two successes. Assigning unique timestamps to both replies cannot repair the result. The service needs a mutation that joins the check and update at the authority responsible for that slot. A read followed by a blind write breaks this specification even if each individual read and write is linearizable.

Now suppose A times out and B receives a conflict naming A. Timeout means A's response is missing from the history. The implementation might have applied A. The conflict is consistent with an execution in which A reserved the slot despite its client observing no success. A history checker must account for incomplete invocations under its formal model. Removing all timed-out operations as if they never ran could report a false violation. Conversely, treating a timeout as permission to retry under a new identity can leave the client with two reservations in a richer service where capacity exceeds one. Stable operation identity binds uncertain transport outcomes to one logical intent.

In a practical diagnostic, record the precondition, result, object identity and client invocation interval. Use unique values such as request-specific owner identities. If many writes store the same string, it becomes difficult to determine which write a read observed. For a small history, enumerate topological orders of the real-time constraints and replay them against a tiny reference register. For larger traces, partition by independent objects only when the operation specification permits it. A transfer between two pools cannot be validated by checking each pool independently if the advertised operation moves capacity atomically across both.

PYTHON · executable model
from itertools import permutations

def legal_orders(history, initial=0):
    # Each completed call is (name, kind, value, start, end).
    results = []
    for order in permutations(history):
        pos = {call[0]: i for i, call in enumerate(order)}
        if any(a[4] < b[3] and pos[a[0]] > pos[b[0]]
               for a in history for b in history):
            continue
        value = initial
        for name, kind, observed, start, end in order:
            if kind == "write":
                value = observed
            elif value != observed:
                break
        else:
            results.append(tuple(call[0] for call in order))
    return results

write = ("W", "write", 1, 0, 10)
early = ("P", "read", 1, 2, 3)
late = ("Q", "read", 0, 5, 7)
assert legal_orders([write, early]) == [("W", "P")]
assert not legal_orders([write, early, late])

Sequential consistency and the missing real-time edge

Sequential consistency requires some common total order consistent with each participating process's program order. It does not impose every cross-process real-time edge required by linearizability. Suppose process A completes Write(1) before an unrelated process B begins Read(), which returns zero. With no other modeled communication or program-order constraint linking them, a sequential explanation can place B's read before A's write. A linearizable register cannot. When modeling an application that communicates out of band, specify whether that communication imposes a dependency in the model. An informal claim that all clients agree on an order becomes misleading if users actually rely on real-time precedence between completed calls.

Use the phrase strong consistency carefully in a design review. Some vendors use it for linearizable point reads, others define transaction semantics, and some teams mean only that the system normally serves a preferred primary. Ask for the precise unit, the failure conditions and the ordering rule. Is this a guarantee for one key, a collection scan, or an atomic multi-key transaction? A crisp answer saves the interviewer from guessing which proof you think the word strong conveys.

SD-004 · Distributed Systems Foundations · 03

Session guarantees when a caller changes region

A disaster-recovery drill moves the console from the primary region to the standby. Its first page contains yesterday's plan, even though the same operator already approved today's version. A session guarantee can prevent this experience without forcing every observer to see the newest plan.

Worked example 3 · Carry a minimum acceptable revision

Plan P was updated from revision 205 to 206. The write response includes an authenticated or otherwise validated progress token for the relevant replication stream. The client sends that token with its next read. The standby's applied revision is 203. A read from its local materialized state cannot honor a minimum of 206. It can wait for catch-up, route to a replica already at or beyond 206, or return an explicit failure after exhausting the deadline. Returning 203 with an ordinary success violates read-your-writes for this session. The token gives the server a concrete condition to test instead of asking the load balancer to guess where the last write went.

At revision 207 a different operator rolls back the contents to the older plan text. A read returning that text at revision 207 can satisfy the minimum revision even though it looks identical to revision 205. Progress is a property of the history included, not of whether the visible value pleases a particular caller. The converse is also important. Two replicas could display coincidentally identical text even though one has not yet incorporated the client's write. A comparison of text values alone cannot prove session progress. The token must refer to a durable ordering domain and the reader must know that the corresponding prefix was actually applied.

A single numeric revision works when the operation concerns one stream with a well-defined prefix. If P and its approval policy live in different shards, comparing P's 206 with the policy shard's 1500 is meaningless. Carry per-shard positions or a snapshot identifier that the service can interpret across shards. Include a topology or lineage identifier when a restore or shard migration can reuse numeric positions. Tokens that clients can invent without validation may cause unbounded waiting for nonexistent future revisions. Enforce deadlines, reject impossible or obsolete tokens and decide what recovery is offered if compaction removes old routing metadata.

Four different session promises

Read-your-writes means subsequent reads in the same session reflect its completed writes or later state consistent with them. Monotonic reads mean that once the session has observed a version or prefix, a later read does not move it backward according to the defined order. A new observer might first see 207 from a nearby replica and then see 205 after load balancing. That violates monotonic reads even if this observer never wrote anything. Neither property alone says that the session sees a write completed yesterday by an unrelated user if it has no corresponding dependency.

Monotonic writes order successive writes by the same session. A user submits an initial plan and then an amendment. If the second data center applies the amendment before the initial plan, preserving each write eventually may still yield an invalid state or confusing intermediate view. Writes-follow-reads captures another edge. A reviewer reads plan 206 and writes approval of that version. The approval depends on the plan it was based on. Propagating the approval ahead of the plan can expose an approval without its subject. Documenting all four guarantees separately forces the designer to say which information follows a client across failover.

When a session changes identity

What happens when the operator closes a laptop and resumes on a phone? If the product defines a session as a single browser context, the phone has no inherited watermark unless the service persists it against the user or the client transfers a token. Pinning a browser to one replica can approximate several session guarantees during ordinary operation, but the pin disappears during a region evacuation. A durable per-user watermark carries cost in storage, authentication and privacy. A signed response token avoids a global write for every read but may grow with the number of shards touched and can become invalid after topology changes.

In an interview, state which fallback protects the contract when the preferred replica is too far behind. Waiting increases tail latency and ties up capacity. Redirecting makes a strong replica's capacity part of the failure budget. Returning an explicit error is sometimes the right answer for an administrative operation that must see the user's latest approval. A stale dashboard can instead offer a separate historical path displaying the revision, but switching a mandatory session read to that path without telling its caller silently changes the promise.

SD-004 · Distributed Systems Foundations · 04

Causal order follows what one action depends on

A review system stores a model evaluation and a release decision in different regions. An engineer can tolerate delayed publication. They cannot make sense of an approval referring to an evaluation that is still invisible.

Construct the dependency graph

Three kinds of edges give causal histories their structure. Actions within one process have program order. A read that returns a write's value can create a reads-from edge. Dependencies propagate transitively: if a reviewer read an evaluation and then wrote an approval, and another reviewer read that approval before issuing a recommendation, the recommendation depends on the original evaluation even if its author never fetched the evaluation directly. Different operations that have no dependency path are concurrent in this sense. Their wall-clock timestamps may differ by hours. Concurrency here means the model has no causal ordering edge between them.

Causal consistency constrains observations of causally related writes. It does not force all observers to order independent writes identically at every instant. A concrete implementation also needs a policy for resolving concurrent updates and for eventual convergence if the product requires it. The COPS paper describes causal consistency with convergent conflict handling and tracks dependencies explicitly across keys and clusters. The following trace is a simplified design exercise. Its dependency representation illustrates the mechanism rather than reproducing that system's metadata format or optimization strategy.

Worked example 4 · Release approval arrives before its evidence

West accepts evaluation E5 and makes it visible to a reviewer. The reviewer writes approval A9 for E5, carrying a dependency on the evaluation revision. East receives A9 before E5. If East exposes that approval immediately while its corresponding evaluation history is missing, an East reader can observe the dependent write before its cause. In the exercise East stages A9 in a pending queue, asks about the evaluation version and makes A9 visible only after its dependency is installed. The observed approval now has a coherent explanation in East's available history even though other newly written evaluations might still be absent.

A second reviewer independently writes a note about cost in another region. That note has no dependency on A9. East can make it visible immediately under the chosen causal contract. Requiring every remote update to wait behind the missing E5 would introduce head-of-line blocking for unrelated work. Such blocking can be acceptable for a simple single-stream scheme, but it is not required by the causal relationship itself. Per-key dependency tracking can expose greater concurrency while consuming additional metadata and complicating recovery. A dependency frontier compressed by origin can simplify storage if origin positions describe contiguous, causally safe prefixes.

Consider a network partition that isolates a mobile reviewer who has already observed E5. A replica missing E5 cannot promise that session a causally complete latest local experience merely because it remains online. It may retrieve dependencies, wait, redirect or reject the dependency-bearing operation. Describing a model as available without specifying session mobility, data placement and whether the client carries unseen dependencies conceals this case. A stateless server cannot honor an edge it never learned about. Pass causal context through the application path, including queues and background jobs that turn a read into a later write.

PYTHON · executable model
def relationship(a, b):
    # Fixed tuple coordinates identify the same origins in both inputs.
    if len(a) != len(b):
        raise ValueError("incomparable origin layouts")
    if a == b:
        return "equal"
    if all(x <= y for x, y in zip(a, b)):
        return "before"
    if all(x >= y for x, y in zip(a, b)):
        return "after"
    return "concurrent"

assert relationship((1, 0), (0, 1)) == "concurrent"
assert relationship((1, 0), (1, 2)) == "before"
assert relationship((1, 2), (1, 2)) == "equal"

A small vector clock by hand

Use two origins named W and E. Starting from zero at each origin, W creates the evaluation with vector (1,0). E independently creates a cost note with vector (0,1). Neither vector dominates the other: each is larger in one coordinate. After E observes W's evaluation, its context includes both writes. A subsequent E approval has vector (1,2), which componentwise dominates both earlier vectors. If W receives that approval before the cost note, its current E prefix is still zero and it cannot safely pretend to have installed both E events. In a prefix-based protocol W must recover or otherwise account for the missing predecessor before advancing its applied frontier.

Componentwise comparison answers a question about dependencies summarized by this representation. It does not tell the product which concurrent model setting a customer wanted. A vector with two large components is not inherently more valuable, and adding components to pick the larger sum erases concurrency information. Bound the number of tracked origins, define how origin identity changes after a crash and ensure that removal of a retired origin preserves valid comparisons for delayed messages. For a small number of regions this can be manageable. A vector with one entry per short-lived worker can be much more expensive than the values it protects.

How I would explain this in an interview

I would draw an arrow from the evaluation the reviewer read to the approval that reviewer wrote. A region may lag behind both changes. Once it exposes the approval, its visible history should include what that approval depends on. Independent updates may still be visible in different orders. I would carry context across service boundaries, measure age and cardinality of blocked dependencies, and choose a separate conflict-resolution rule for concurrent edits. Where every read must respect unrelated completed writes in real time, causal order alone does not meet that requirement.

SD-004 · Distributed Systems Foundations · 05

Eventual convergence and the cost of forgetting

A stale cache entry persists for a day after a model alias has been updated. Every update event has been delivered. Which condition is still missing for the replicas to agree?

Worked example 5 · A stale fill races a fresh invalidation

At revision eight an alias points to a small preview model. A cache miss launches a database read that returns revision eight, but its fill is delayed. The deployment controller changes the alias to a larger approved model at revision nine. The cache processes an invalidation for nine, finds no current cached value and drops the invalidation. The old fill then arrives and installs revision eight. If nothing happens next, the cache can serve eight for much longer than the nominal event propagation delay. Both the old read and the invalidation were individually legitimate. Causal ordering among operations in the authoritative store did not automatically serialize a slow fill in a separate cache.

A possible remedy stores a version floor even when no value is cached. When the invalidation for nine arrives, record that an older fill may not install. When the delayed fill of eight arrives, reject it. This helps only while the floor is retained or recoverable. Evicting the floor while an old fill remains in flight can recreate the race. A bounded time-to-live on values provides an eventual correction mechanism under recovery assumptions, but it does not by itself define the maximum age of an authoritative state change a client can miss. The database serving the refill may itself be a lagging replica.

Under eventual consistency the convergence claim is conditional. Common formulations say that if updates cease and communication and repair continue as required, replicas eventually agree. The word eventually supplies no numerical deadline. Convergence also needs a rule that maps concurrent updates and duplicates to compatible final states. Two independent servers applying noncommutative assignments in local arrival order may diverge even after they receive exactly the same messages. Event delivery and deterministic agreement over a common set of updates are distinct engineering obligations. Specify both before claiming a replicated design is eventually consistent.

Merge information in the right domain

Take a replicated set of immutable evaluation IDs that only grows. Each replica stores its observed IDs and merges by set union. Receiving the same remote set twice changes nothing after the first merge. Merging smaller pieces in a different order yields the same set. Grouping the merges differently also yields the same result. These are the idempotent, commutative and associative properties that make union convenient. If users must retract evaluations, a grow-only set is insufficient. Erasing an ID locally without communicating removal information lets an old replica reintroduce it on the next union.

A last-writer-wins register chooses a deterministic winner by a timestamp and a tie breaker. Under assumptions ensuring every replica eventually considers the same candidate versions, this can converge while silently discarding a concurrent edit. A machine with a clock far in the future can dominate ordinary later updates for an extended period. A logical ordering scheme avoids some wall-clock problems but still embeds a conflict policy. Ask the product owner whether dropping one concurrent change is acceptable. For independent user tags, merge their set. For incompatible deployment decisions, require an explicit compare-and-set and surface a conflict. An operation's mathematical merge behavior must match the meaning people assign to it.

Prove what repair will repair

Track the authoritative revision and the cache's observed revision. A periodic auditor can sample disagreements and retry after a delay to separate ordinary transient lag from persistent disagreement. Distinguish an absent cache entry from an incorrect cached value, and distinguish a value that legitimately changed again during comparison. In a rapidly updated key, comparing two non-atomic observations can create a false positive. Include version evidence and instrument the read, fill, invalidation and eviction paths. Data about a stale fill that was rejected successfully is a sign of a race being contained rather than a user-visible failure.

For a disaster-recovery dashboard, state which fields may converge asynchronously and what a mismatch means. A list of recovery plans can tolerate delayed descriptive labels. A control action that promotes an external writer must revalidate its generation with the authority at the mutation boundary. Putting a prominent refresh button on an eventually convergent dashboard does not create a strong control path. The safe division of labor is that the dashboard helps the operator choose an action, while the command's preconditions determine whether acting on that view is still legal.

SD-004 · Distributed Systems Foundations · 06

Quorums, safe snapshots and a semantic trap

The overlap of a read set and a write set is an information path. It is not a complete algorithm for deciding which value a reader may return.

Worked example 6 · A later read goes backward despite intersecting quorums

Start three replicas A, B and C at value zero. In a deliberately incomplete register algorithm, a writer sends a uniquely tagged update assigning one to A, B and C in parallel. Only A receives it before the writer stalls. A reader queries A and B, takes the largest tag in their replies and returns one. After that read completes, another reader queries B and C and returns zero. Both reads used two replicas. Any two-replica read set intersects every completed two-replica write set. Yet the writer in this trace had reached just one replica and the first reader exposed its value. Once that happened, the later read could not return zero in any linearizable single-register history with no subsequent write of zero.

A family of atomic register algorithms repairs this by making the chosen value sufficiently durable and visible before the read returns. In a simplified single-writer majority-register setting, a read queries a majority, chooses the highest tagged value, writes that value back to a majority using monotonic tag handling and only then returns. Any later majority query intersects that completed propagation. More complete algorithms specify how tags are allocated, how concurrent writers are handled, what failures are allowed and when operations can finish. Treat the exercise as a counterexample to the simplistic quorum slogan and an intuition for read repair with acknowledgment, not a production implementation of an arbitrary replicated store.

Increasing the read quorum from two to three would mask this particular read regression in a healthy three-node cluster, provided highest-tag handling and the rest of the model are respected. It would also make all reads unavailable after the loss of one replica. Other errors, such as tags that regress after restart or reconfigurations with incompatible membership, could still break the design. Strong semantics depend on the entire protocol. Counting responses in an architecture diagram answers neither what state those responses describe nor what a concurrent operation may already have exposed to clients.

Time travel is a different service

A multi-version store may serve a perfectly valid snapshot from a minute ago. Its contract is to return the database as of an agreed snapshot, subject to retention and visibility rules. That is useful for reporting over many shards and for reproducible evaluation. It is different from a latest strong read. Define the timestamp domain and what evidence tells each shard it can serve a snapshot at that point. A wall clock that reads noon does not prove all writes assigned timestamps before noon have arrived and been applied locally. The store needs a safe read timestamp or equivalent protocol watermark.

Suppose one shard can serve a safe snapshot through revision time 105 and another through 101, expressed in the same supported global timestamp domain. A request reading both can choose 101 if versions remain available and both shards satisfy the snapshot contract at that time. Choosing independently latest values from 105 and 101 may produce a fractured view. If the customer specifically asks for 104, the slower shard must catch up, route the read elsewhere or report that it cannot yet serve that snapshot. If the shards have independent, incomparable local revision numbers, taking the numeric minimum is meaningless. The architecture must first establish a common timestamp or consistent-cut mechanism.

Transaction isolation is another axis

Two registers can each be linearizable while a client reads an inconsistent pair. Start with deployment X at generation eight and policy Y at version four. A client reads X, then a writer updates X and Y through separate calls, then the client reads Y. Each individual read can be legal while the pair never existed together at a single instant. Even a database with atomic multi-key writes requires the reader to use its supported snapshot or transaction to get an atomic multi-key read. A collection of correct point calls cannot confer an unrequested transaction boundary.

Serializability asks whether committed transactions can be explained in some serial order. Strict serializability also respects real-time precedence of nonoverlapping transactions. Snapshot isolation commonly supplies a stable snapshot for reads and detects certain write conflicts, yet transactions updating different rows can jointly violate a cross-row invariant through write skew. Imagine two on-call control-plane regions must never both disable promotion authority. Each transaction sees both regions enabled, disables its own row and commits. Different write targets may avoid a write-write conflict. Choose serializable enforcement, a shared guard object or a redesigned invariant, then verify the actual database's semantics rather than assuming that a stable snapshot solved coordination.

SD-004 · Distributed Systems Foundations · 07

Design the model-release registry by reading need

A release platform serves three audiences. Operators change the desired model. Workers need a compatible set of immutable artifacts. A fleet dashboard shows how rollout is progressing. Giving every endpoint the same freshness contract makes the critical ones hard to defend and the cheap ones unnecessarily expensive.

Authority, observation and the API boundary

Start with an ownership boundary of one tenant and deployment. A replicated authority stores desired generation, immutable manifest digest, rollout policy revision and prior request outcomes for the supported retry horizon. Publish accepts a request ID, expected desired generation and sealed manifest digest. It verifies authorization, checks the expected generation and advances that generation as one transaction. A failed comparison returns the observed conflict under the API's disclosure policy. Retrying an already accepted request returns its recorded historical outcome, even if a newer publication has since moved the pointer. A repeated ID with a changed body is rejected.

The manifest names exact immutable versions of weights, tokenizer, serving code, feature configuration and any policy bundle required to interpret inputs. A verifier seals the complete manifest only after checking that the referenced content exists and meets retention and compatibility rules. A release pointer that changes atomically is still unusable if the manifest points to mutable file paths or if old artifacts disappear while in-flight sessions depend on them. Separate immutability, durability and consistency in the design. They answer related but different questions about what bytes are available and which version a caller is entitled to observe.

GetDesiredCurrent uses an authoritative linearizable read of one pointer. GetDesiredAtLeast accepts a scoped revision returned by Publish and may be served by a replica whose applied position covers that revision. These endpoints can return the same value most of the time. Their difference becomes visible during failover, load shedding or network delay. PinSession fixes a request stream to a validated manifest digest unless policy explicitly forbids continuation. GetFleetSnapshot returns rollout estimates at a watermark and records the fraction of expected workers whose reports are missing or older than the reporting horizon. Treat missing workers as unknown rather than counting silence as evidence of readiness.

Worked example 7 · Publish, fail over, then read in another region

Generation 40 for deployment D points to digest M40. A release engineer publishes M41 with expected generation 40 and request key K41. The authority commits generation 41, records K41 and returns its revision token. Regional replica East has applied only generation 39. The engineer switches to East and asks for at least 41. East cannot meet the floor locally. It waits briefly within the caller's deadline, then forwards to an authoritative read if the fallback capacity budget permits. Meanwhile fleet watchers deliver separate readiness reports. A dashboard showing 60 percent ready at generation 41 cannot serve as proof that all workers enforce 41.

Suppose the engineer lost the publish reply. A retry with K41 recovers the same publication outcome and its token. If M42 has already been published by someone else, a current read can legally return 42. The recovery API must still be able to say whether K41 succeeded because a current value alone cannot distinguish a superseded success from a command that never ran. If the pointer replica is recovering from a snapshot that predates the acknowledged revision, pinning to it just because it is local defeats the session contract. A verified token can detect the gap, but restoring the acknowledged history or establishing the declared recovery policy is what resolves it.

During an emergency rollback, publish a new generation 43 referencing older immutable M40. Observers must compare publication generations rather than numerically comparing model labels. Workers may load M40 concurrently and report readiness independently. For a hard policy requirement such as immediate cessation of a disallowed model, define the actual enforcement point for new requests and the treatment of already-running streams. An asynchronously consumed pointer offers no universal instantaneous revocation promise. A separate admission gate, draining protocol, bounded authorization lease with explicit timing assumptions, or verified regional barrier may be required. Choose the mechanism only after identifying what external behavior the customer requires to stop.

Capacity and deployment evolution

Assume 50,000 workers poll once every two seconds. That yields 25,000 potential pointer reads per second before retries, plus synchronized bursts when a region returns. Suppose only 100 release writes occur per minute across the fleet, about 1.67 per second. A write rate a tiny fraction of the read rate argues for immutable bundles, resumable notifications and local validated caches. It does not prove latest reads are free. If one in a hundred worker polls suddenly falls back to the authority, it adds 250 strong reads per second; if every replica is behind after a correlated restart, the fallback demand can approach the entire poll rate.

Set independent admission limits for fresh-read fallback and for publishing, maintain per-tenant fairness and collapse duplicate fetches for the same immutable digest. A watch stream should resume from a durable position when supported; if history has been compacted, take a fresh consistent listing and resume from its boundary. Measure control traffic and data bytes separately. At four GiB per worker, a simultaneous cold reload across 50,000 workers implies 200,000 GiB of artifact traffic before caching, so stagger the rollout and exploit regional distribution. The consistency contract determines what workers may serve while loading. It does not deliver the weights over the network.

As the service evolves, isolate hot tenants and regions by sharding deployment ownership, provided each pointer's invariant stays within one authoritative group. A simultaneous release of a shared tokenizer and five deployments may require a single immutable composite release or a transaction spanning records. A sharded plan that promises multi-deployment atomic cutover implicitly created a new cross-shard coordination service. Put audit identity, grant checks and resource quotas on the publication path. Authenticate revision tokens or validate their issuer and scope, and reject cross-tenant reuse. Record a decision log sufficient to explain which generation a particular request was authorized to serve.

Architecture defense under conflicting objectives

Product asks for local reads everywhere, a five-millisecond deadline, permanent availability during inter-region partitions and immediate visibility everywhere after a global publish. To clarify, name one write completed in the west and a subsequent current read in a disconnected east. East receives the same local inputs whether the west published a new generation or remained idle. Returning the latest value in both executions is impossible without some additional communication or prior restrictions on the writer. A timestamp printed on the client cannot contain the unseen manifest. I would give product a choice of behavior for each endpoint and explicitly preserve the safety-critical promise at admission.

For dashboards, serve local snapshots with an age and coverage indicator. For operator confirmation, carry the publish token and route or wait when a local replica is behind. For new session admission requiring immediate enforcement, deny or reroute during uncertainty according to the verified barrier policy. Existing sessions can continue on a pinned immutable bundle only if the policy explicitly allows it. This keeps the important guarantees measurable. A useful launch review demonstrates an actual region partition, lost publish response and cold model load, then shows the exact user-visible behavior for every endpoint.

Measure the promise the request actually needed

During a recovery drill, replicas report zero replication lag for ten seconds and an operator still sees an old model. The metric may be entirely accurate for the wrong stage of the read path.

Worked example 8 · The source is caught up and the caller is stale

Trace one GetDesired request across gateway, request cache, regional replica and application projection. A publish of generation 150 completes at the authority. The replication receiver durably obtains log entry 150, so its receive lag is zero. The local state machine is still applying 148. A downstream cache holds 147 and a projection emits a snapshot at 145. Four dashboards could show four reasonable numbers labeled revision. Attach distinct names: delivered, durably replicated, applied, served and projected. Carry the response revision to the client so that a successful read can be compared to the condition it promised to satisfy.

Inject a pause after durable receipt and before application. An at-least-150 read must wait or choose a suitable fallback; returning 148 exposes an implementation bug even though the receive monitor stays green. Then resume application but hold an older cache fill in flight and release it after invalidation. Repeat the same read through a warm cache and a cold cache. This separates two causes that would look identical from the client's perspective. Include an explicit revision reset or lineage change in a recovery rehearsal. A follower applying a new history at numeric position 160 might not contain the old acknowledged operation at 150.

Histories, freshness and operational judgment

For a canary object, write unique values under an isolated test tenant. Chain a second client's read after receipt of a successful write to establish precedence without assuming perfect clock synchronization. Record invocation, completion, operation identity, client session, endpoint, expected minimum revision and returned revision. A history checker can explore legal orders against the chosen state machine. Crashes and lost responses produce incomplete operations that must be modeled correctly. Passing thousands of finite histories increases confidence in tested behaviors. One demonstrably impossible complete history is enough to refute the claimed model for that execution.

Define latency and correctness observations separately. A service returning an explicit freshness-unavailable error within five milliseconds can correctly enforce its safety condition while delivering poor availability. A service returning 200 instantly with stale data may score well on success counts and fail its consistency contract. Track eligible reads, successful reads satisfying the requested constraint, time spent waiting, authority fallback rate, end-to-end latency and load shed at each tier. Stratify by region and degraded versus healthy state. If an SLO promises age under two seconds for 99.9 percent of eligible dashboard responses, explain how age is computed and what happens to the remaining responses. A percentile objective is not a bound on every observation.

Design a drill with a real decision at its end. Can the release owner safely proceed with a regional rollout while read fallbacks are saturated? Inspect current authority health, rollout admission mode, missing report coverage and retention of the prior model. If only the dashboard is behind, the supported operation may continue with an explicitly uncertain observation. If required revocation barriers cannot be established, pause new admission in affected regions. The best alert points to the failed evidence and identifies the action that remains safe.

Design review under cross-examination

These are original Senior Staff practice questions. For each one, sketch a legal history first, then try to produce a counterexample by delaying one message or moving one reader to another region.

Twelve interview questions

Can a read that finishes after a successful write return the old value?

Evaluates real-time precedence. Yes, if the read overlapped the write and there is a legal sequential order consistent with every other response that places the read first. If the read began after write completion, absent a subsequent change back to the old value, it cannot return that value under a linearizable register contract. I need both invocation and completion events.

Follow-up. What if another read saw the new value first? If it completed before this read began, it may constrain the order enough to forbid the old value.

Common mistake and tradeoff. Sorting only responses overlooks overlaps and can both excuse violations and report false alarms.

A system offers a total order of writes. Does that make its reads linearizable?

Evaluates missing read-side evidence. A replica may apply a prefix of a perfectly ordered write log and still serve stale state. I would ask how a read establishes a sufficiently recent boundary and how the read server proves its state machine has applied it. Ordering writes solves agreement over their sequence. Observations also need to be tied to an admissible point in that sequence.

Follow-up. Can a follower serve strong reads? Yes, if the implementation supplies the required authority and application evidence or an equivalent valid protocol.

Common mistake and tradeoff. A read from a designated leader can also be stale after failover if the node only assumes it is still leader.

Why might a sequentially consistent history fail linearizability?

Evaluates comparing ordering constraints. A sequential history must preserve each process's operation order but can place an unrelated client's read before another process's write even when real time shows the write completed first. Linearizability imposes that additional edge. I would draw a single initial-zero register, one completed write to one, and a later unrelated read that returns zero. Then I would add the cross-process precedence arrow.

Follow-up. What if clients exchanged a message? Identify whether it is a modeled operation or a carried dependency and specify the program constraints it adds.

Common mistake and tradeoff. Using the word latest without identifying the ordering domain makes the claim untestable.

A mobile client visits a replica missing its last write. What should it receive?

Evaluates session guarantees under failover. The client should provide a verifiable minimum revision with the replication lineage and object scope. The server can wait within a deadline, route to a qualifying replica or explicitly fail the requested read. It can optionally offer a separate historical response with a clearly different contract. A blind local success silently violates the client's session promise.

Follow-up. Does a larger numeric timestamp suffice? Only when it denotes a comparable applied prefix that includes the write.

Common mistake and tradeoff. Fallback traffic can overload the authority during evacuation. Reserve capacity and limit amplification.

Can an approval be exposed before an evaluation if the client never queries the evaluation?

Evaluates causal visibility and api scope. If the API promises a causally consistent view across both objects, observation of the dependent approval must be consistent with visibility of its prerequisite. The implementation may stage updates, use a consistent snapshot or fetch dependencies, depending on the contract. Packaging the exact evaluation digest as immutable evidence can simplify the application invariant. A reference alone does not guarantee the referenced data can be retrieved.

Follow-up. What if a reviewer learned about the evaluation by phone? The storage service needs explicit context to enforce that external dependency.

Common mistake and tradeoff. A causality graph describes modeled edges. Hidden workflow knowledge must cross the API boundary.

Why can two independent edits disappear after successful eventual convergence?

Evaluates conflict semantics. A deterministic winner can cause every replica to agree while discarding a concurrent edit. I would ask whether the object represents a setting, a set of independent attributes or an action requiring rejection on conflict. A union merge suits grow-only tags. A model-release decision may instead need an expected revision and a conflict result. The same converged bytes can represent either a correct outcome or lost business intent.

Follow-up. Does a vector clock choose a winner? It can identify incomparable versions under its construction; the domain rule determines resolution.

Common mistake and tradeoff. Treating convergence as correctness ignores what the merged value means.

Does an intersecting read quorum always see the latest acknowledged state?

Evaluates protocol assumptions. Intersection guarantees a common participant under the documented membership. The reader still needs the correct version-selection rule, durable state, suitable treatment of concurrent or incomplete writes and a protocol ensuring reads cannot go backward. A partially disseminated newer value can be exposed by one majority read and missed by the next. A well-defined register algorithm may write back the selected value before returning.

Follow-up. Can sloppy placement break the arithmetic? Yes if read and write sets are drawn from different effective member universes.

Common mistake and tradeoff. Quorum size alone cannot certify a complete consistency model.

How would you read a coherent snapshot of two shards with different lag?

Evaluates time domain and safe frontier. If the store provides a common timestamp domain and safe times, select a retained timestamp both shards can serve or wait for the requested one. If they have independent revision numbers, a numeric minimum does not describe one cut. Use the store's distributed snapshot or transaction protocol or publish a manifest referencing compatible immutable versions.

Follow-up. What if one shard compacted the selected version? Route to retained history, choose another admissible timestamp or explicitly fail.

Common mistake and tradeoff. Choosing the freshest value independently at each shard can produce a pair that never coexisted.

Does a linearizable pointer guarantee safe rollback across the inference fleet?

Evaluates data-plane enforcement. It guarantees an order of pointer operations. It does not instantly stop workers, invalidate cached admissions or cancel existing streams. Define whether rollback means new desired state, cessation of new admissions on the old version, or termination of every in-flight request. Each needs different evidence. I would version manifests, use a new generation for rollback and verify admission barriers where stronger cutoff semantics are required.

Follow-up. Can a region keep serving through a partition? Only under a previously specified policy compatible with the required cutoff.

Common mistake and tradeoff. A fast control-plane commit can coexist with slow worker convergence.

What breaks if we use stale dashboards to authorize disaster recovery?

Evaluates moving from observations to actions. A historical dashboard can legitimately show the former primary as down after it has recovered. Treat the display as input to a proposal. On the mutation path, compare expected generation, verify prerequisites and enforce fencing at the protected resource. Even a current overview can become obsolete before an operator clicks. The critical checks must serialize with the action they govern.

Follow-up. Should the dashboard block all interaction when stale? It can still support investigation and submission of conditioned commands.

Common mistake and tradeoff. Making every dashboard read strong does not make a later external action atomic.

How would you distinguish a real consistency violation from a clock artifact?

Evaluates executable evidence. Chain the test read through a message sent after the writer receives acknowledgment. Use unique values, store invoke and return events, and replay the history against a small reference model. Include failed and indeterminate outcomes with their documented semantics. Record the exact endpoint and consistency class so that a historical read is not tested as a current one.

Follow-up. What does a clean stress run establish? It establishes that the checker found no violation among the sampled histories, under its model.

Common mistake and tradeoff. Wall-clock ordering across machines without bounded uncertainty can fabricate real-time edges.

Which workload deserves a strong cross-key transaction?

Evaluates finding the invariant. If a decision must maintain an invariant across independently mutable objects, point-read linearizability alone is insufficient. For two regions that cannot both relinquish promotion authority, concurrent transactions writing different rows can violate the invariant under snapshot isolation. A shared guard record, a transactional serializable predicate or a redesigned handoff can establish the required constraint. I would compare contention and failure behavior of those alternatives.

Follow-up. Can immutable manifests reduce the transaction scope? Yes. One pointer can atomically select a preconstructed compatible bundle when the business model permits it.

Common mistake and tradeoff. A stable snapshot for readers does not by itself serialize every conflicting business decision.

Whiteboard drill

Draw two clients and two regions. Begin with a completed pointer write, an unrelated local read and an application message carrying an approval dependency. Move the read so that it overlaps the write, then move it after the client's success response. Label what linearizability, read-your-writes and causal consistency require in each drawing. If you cannot decide from the drawing, identify the missing fact: session continuity, reads-from direction, whether an external communication carries context, or whether two events refer to the same object. That habit produces a defensible answer even when an interview question deliberately leaves the requirements incomplete.

Explain the contract out loud

Keep one example throughout the rehearsal. Short answers should make the customer-visible promise unmistakable. Longer answers should tell the listener where the evidence comes from and what will happen when that evidence is unavailable.

Thirty seconds · Speak from the caller's point of view

Consistency describes the histories a reader may observe. A linearizable release pointer behaves like one register whose operations respect completed calls in real time. A session read can instead promise that I will see at least the revision I published. A causal view preserves dependencies such as approval following evaluation. An eventually consistent dashboard can lag and later converge. I would specify each endpoint's promise, then test it under a region failover.

Two minutes · Explain why a stale read can be legitimate

Suppose I just published model generation 72. There are three different things I might mean when I ask whether it is current. I might be confirming that the control plane accepted my write. I might be asking which generation a particular worker has loaded. Or I might be asking what fraction of the fleet can serve it. A strong read of the control pointer cannot establish the second or third fact. Each requires evidence from the workers.

For confirmation I can carry the revision from the write response to my next read. A local replica that has applied at least that revision can serve a read under that contract. If it is behind, I can wait, route elsewhere or return an explicit error. A different user's unrelated successful write could still be unseen by that replica, which is why read-your-writes is a narrower guarantee than a latest linearizable read.

For the fleet, I would show an observation watermark, the count of expected workers and the count reporting at the target generation. Unknown workers should remain visible in the denominator and in the explanation. During rollback I would publish a new generation pointing to an old immutable artifact. The generation moves forward while the artifact changes back. That distinction keeps both client progress tokens and incident timelines meaningful.

Five minutes · Defend the release architecture

I would first write the unit of consistency on the board. The desired release is one pointer per tenant and deployment. The serving bundle is an immutable manifest that names the exact weights, tokenizer, runtime and configuration. The fleet view is an asynchronously updated account of observations. That division follows the decisions the platform has to make. Operators need a reliable answer to what was accepted. Workers need compatible bytes. Release managers need a view of rollout progress that tells them when the evidence is incomplete.

To publish, a client presents an expected generation, a manifest digest and a stable operation key. The authority verifies the sealed manifest and performs the generation check, pointer advance and result recording in the appropriate transactional boundary. If two administrators race, both may submit a well-formed request but only the one whose precondition still holds can win. If the winner loses the reply, it can retrieve the outcome for its original identity. A current read after another release might return a newer generation, so an outcome query and a current pointer read answer distinct questions.

I would then define the read classes. The authoritative current read must respect completed writes even across unrelated clients. A regional read with a minimum token only needs evidence that its local state includes the specified prefix. A pinned inference session repeatedly uses a validated immutable digest. A fleet report carries a processing watermark and reports missing workers explicitly. If a release approval depends on a particular evaluation, I preserve that association in the immutable manifest or propagate a verifiable dependency. A fresh pointer exposing an approval without its evidence would fail an important product requirement even if the register itself were perfect.

Now remove an inter-region link. A region cannot learn about a publication whose messages have not arrived. I choose in advance which reads may return an older labeled snapshot, which must wait and which need to return an error to preserve their guarantees. When immediate revocation is required, I must enforce it where new requests enter and decide how to handle sessions already running. A dashboard update is insufficient evidence that every ingress stopped the old model. When historical continuation is permitted, a pinned session can continue useful work without requesting global agreement on each token.

Finally I would instrument the boundaries. A local receiver can be up to date while application, cache and projection lag. I would trace a controlled publication into an independent client's read, deliberately delay application and force a stale cache fill to arrive late. I would measure safe-read success and latency alongside the rate of authority fallback during recovery. If the new architecture reduces average response time but fails the explicit session floor in one reproducible schedule, I would fix that failure before increasing traffic.

Final interview cheat sheet

  • History. Record both invocation and completion of each logical operation.
  • Real-time precedence. Respect a completed call before a later invocation under linearizability.
  • Overlap. Place concurrent calls in one globally legal sequential explanation.
  • Session floor. Require the local applied position to cover the caller’s comparable token.
  • Causal edge. Carry reads-from and program-order dependencies across services.
  • Concurrency. Incomparable causal versions require a domain-specific merge policy.
  • Convergence. Define the conditions under which replicas eventually agree.
  • Safe timestamp. Prove a shard can serve the requested retained snapshot.
  • Transaction boundary. Point-read guarantees alone do not deliver an atomic multi-object decision.
  • Cutover. Distinguish desired release from actual serving admission.
  • Visibility. Distinguish durable receipt from materialized application.
  • Validation. Judge returned histories against the documented contract and failure model.
