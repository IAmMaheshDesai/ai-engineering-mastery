sd-018 · Plane separation

Keep serving when management cannot make progress

Separate ordinary execution from authority-changing work using explicit dependency contracts.

The management outage that became a serving outage

A model-serving fleet is healthy, loaded, and receiving traffic. Its configuration API fails, and every frontend blocks while fetching the current model route for each request. The system has physically separate services but no meaningful failure separation. The engineering problem is to decide which information execution needs, how it can obtain trustworthy local state, and which changes must stop when management authority is unavailable. Moving an RPC into another process does not remove it from the critical path.

The control plane accepts intent, validates policy, allocates resources, changes desired state, and coordinates lifecycle transitions. The data plane performs the business operation using accepted configuration and authority. The classification is relative to a capability: a storage metadata lookup can be a data-path dependency even though it manages metadata. Do not label every small or administrative-looking request control plane and assume customers can proceed without it.

A useful design states which existing work continues, which new work stops, and how long local state remains valid. Running inference might continue with an approved loaded model, while deployment creation and conflicting placement stop. A recovery dashboard may show cached status while destructive recovery steps require current ownership. These are operation contracts, not a blanket claim that the data plane never needs control information.

Your OCI control-plane and FSDR background provides a direct bridge. Durable desired state, asynchronous workflows, and reconciliation let management recover without restarting every workload. AI adds large model state, accelerator placement, tenant policy, and agent effects. All proposed designs here are hypothetical; they are not assertions about OCI internals or unprovided personal accomplishments.

Authority and availability are separate

A local copy can improve availability only if using it remains safe under the contract. An immutable model manifest can be reused indefinitely while its content remains approved. A credential or policy grant may expire. An ownership token can become stale after a failover. Define validity for each object and enforce the relevant boundary. Cached data is not automatically delegated authority.

Separation also requires resource isolation. If control and serving share an exhausted database pool, network queue, or deployment pipeline, a management storm can still break execution. Identify shared dependencies and failure domains, then decide which require reserve, independent operation, or a documented reduced capability. A diagram with two colored boxes is a hypothesis to test, not evidence of isolation.

How I would explain this in an interview: “I define the serving capability, then remove unnecessary management dependencies from its ordinary path. Existing execution uses verified local state under a bounded validity contract. Authority-changing operations still need a safe control decision. I test both dependency loss and shared-resource overload.” Pause and list what a running inference replica truly needs for one request.

Chapter summary

Plane separation is a failure and authority contract. Existing execution, new mutations, cached state, and shared dependencies must be analyzed independently.

02 · Dependency analysis

Draw the actual request path

A rare management call can still dominate availability if every business request waits for it.

Classify dependencies by operation

For each capability, record dependencies needed to start, dependencies needed continuously, and dependencies needed only to change state. Model loading may require an artifact registry during startup, while already-loaded inference can proceed without it. Token validation may use locally verifiable credentials, while policy revocation may need bounded refresh. A new tenant may need authoritative admission even if existing tenants can continue. This matrix exposes where graceful degradation is possible.

Use a failure-mode table: process loss, metadata authority outage, watch interruption, stale configuration, identity-service failure, network partition, and fleet restart. Static stability means an already provisioned system can withstand a specified impairment without requiring new control actions during the critical interval. AWS's primary material grounds this pattern. It is not a promise that capacity can never change or that security can ignore expiration.

Cold restart is a different scenario from continuing warm service. A fleet can survive a control outage while running yet fail to restart because every replica needs the same registry, policy, or key service. Decide whether the resilience objective includes restart, region evacuation, or only temporary steady-state continuation. Name the interval and failure set so a successful warm test does not become a false disaster-recovery claim.

Worked example 1: serial request dependency cost

Initial state: a serving path requires frontend, model executor, and a configuration lookup, each with success probability 0.999 over compatible request observations. Assume independence only for this teaching calculation. The objective is to see the effect of an avoidable synchronous lookup. Product success is 0.999 cubed, approximately 0.997003, or 99.7003 percent. Removing the live configuration call from the ordinary path under a valid local-state contract leaves 0.999 squared, about 99.8001 percent.

This arithmetic is not a production forecast. Shared failures violate independence, and local-state validity can introduce another failure condition. The design must replace the RPC's required function, not merely delete it. A verified configuration snapshot with appropriate expiry and update behavior can let serving continue, while new routing changes wait for management recovery. Intermediate state is useful service with potentially delayed changes, not unlimited permission to ignore policy.

Failure variation: the model route references an artifact that was never loaded. A local record alone cannot serve it. Readiness publication must ensure the model and runtime actually exist before the route becomes eligible. Another variation is a security-critical policy requiring revocation within sixty seconds; continuing beyond that bound may be forbidden. The availability calculation cannot override that contract.

Final outcome is a request path with fewer unnecessary serial dependencies and explicit replacement semantics. Production implication: measure customer operations during control loss, not only API health. Interview takeaway: quantify dependencies to motivate the design, then test correlated faults, state validity, and readiness before claiming improved availability.

Separate traffic and resource budgets

Control writes, telemetry, watch delivery, model downloads, and inference have different load patterns. A mass restart can trigger all of them at once. Reserve resources for authority and recovery, coalesce observations, and limit fan-out. Do not send high-frequency utilization samples through the same synchronous transaction path as exclusive ownership updates. Resource separation can be logical or physical, but the protected budget must be enforceable during overload.

Chapter summary

Classify warm operation, startup, and change dependencies. Removing a synchronous call requires a valid local alternative, and failure-state capacity matters as much as component count.

03 · Desired and observed state

Reconcile intent instead of scripting assumptions

A controller repeatedly compares authoritative desired state with current evidence.

The reconciliation loop

A declarative control API records a desired configuration or resource specification. Controllers observe relevant actual state, calculate a bounded next action, apply it under authority, and update status with evidence. Repeating this loop allows recovery after crashes and partial progress. Idempotence is a useful goal for actions, but an arbitrary external API may need stable operation identity and reconciliation instead. A controller is not safe merely because it runs periodically.

Separate specification revision from observed revision and operation generation. Desired replicas equal ten does not mean ten are ready. A status record can state that revision 42 has been accepted but only eight replicas are ready under revision 41. Do not overwrite these distinctions with a single successful flag. Conditions should explain waiting, failure, unknown effects, and readiness with a clear owner and timestamp semantics.

Kubernetes component documentation provides a public example of control services and worker components, while Borg and Twine supply historical cluster-management context. These sources motivate declarative lifecycle and execution separation. The simplified controller protocol and numbers here are original teaching designs, not private implementations of those systems.

Worked example 2: controller crash after resource creation

Initial state: deployment D has desired revision 8 and requires three model replicas. Two are ready. Controller C records operation identity K3 for creating the third, sends the provider request, and crashes before recording the response. The objective is to resume without creating an unnecessary fourth replica or forgetting accepted work. A successor reads desired state and the unresolved K3 rather than assuming the request failed.

If the provider supports lookup by K3 or stable resource tags, the successor finds the created replica, verifies its identity and version, and adopts it. If it is not yet ready, status remains progressing. If the provider definitively rejected the action, retry under the documented identity contract. If outcome is unknown and another create could be harmful or expensive, reconcile further instead of silently issuing a new unrelated action.

Intermediate state includes accepted desired revision, two ready replicas, and one uncertain operation. Once the third loads and passes its readiness predicate, observed revision can advance under the defined controller contract. Final outcome is three correct replicas and a durable explanation of their origin. Failure variation: desired revision 9 arrives while K3 is unresolved. The controller must decide whether the old resource can be adopted, updated, or cleaned up under revision 9; it cannot ignore the old effect because intent changed.

Production implication: persist intent before effects, make action identities stable, and compare observed resources against current desired state. Interview takeaway: reconciliation repairs partial execution, but its safety depends on authority, effect contracts, and explicit status—not a loop that blindly repeats commands.

Bound work per pass

A controller can overload itself by reconciling every object after one global change. Use work queues, deduplication, backoff, per-tenant budgets, and incremental resync. Avoid holding global locks while waiting on providers. A permanently invalid specification should expose a stable condition rather than retry at maximum rate. Fairness ensures one failing tenant does not block all progress, while priority can preserve recovery actions under a declared policy.

Chapter summary

Desired state, observed readiness, and unresolved effects are separate records. Reconciliation enables recovery only when repeated actions preserve identity and authority.

04 · Configuration distribution

Deliver a complete version, not an ambiguous stream

Snapshots, watches, validation, and acknowledgments form a publication protocol.

Snapshot plus ordered changes

A worker needs a consistent starting snapshot and a way to learn later changes. A watch stream can efficiently deliver updates, but it can disconnect or fall behind retention. The consumer must track a meaningful revision, detect gaps under the store's actual semantics, and resynchronize from a compatible snapshot. An arbitrary sequence of notifications is not automatically a complete state history. etcd documents specific key-value and watch guarantees; application design must respect their distinction rather than assume every watch read is a fresh linearizable snapshot.

Publish immutable configuration bundles with hashes and a small authoritative reference to the desired bundle. The worker validates schema, signature or authorized origin, compatibility, and required artifacts before activation. Keep last-known-good state when a new bundle is invalid, while reporting that the desired revision was rejected. That is different from falsely acknowledging successful application. The control plane should observe accepted, downloaded, validated, activated, and serving states separately where they matter.

Use version-aware updates to prevent out-of-order delivery from reverting a worker. An activation acknowledgment should identify worker incarnation and config revision. A restarted worker with no local state may need a full snapshot even if it previously acknowledged the latest version. Keep desired and observed identity scoped so an old worker's late acknowledgment cannot mark a new incarnation ready.

Worked example 3: watch interruption and stale rollback

Initial state: worker W serves verified bundle revision 20. The control authority publishes 21, then 22. W receives 22 after a reconnect but later receives a delayed message naming 21. The objective is monotonic activation under the chosen revision contract. W validates and activates 22, records it locally, and rejects the delayed 21 as obsolete. It does not interpret arrival time as authority.

Now suppose W disconnects long enough that required watch history is unavailable. It obtains a new complete snapshot with a verified revision rather than assuming the next received delta fills every missing change. Intermediate state can continue serving bundle 22 only within its validity policy while resync occurs. If bundle 23 requires a new model artifact, readiness waits for that artifact and compatibility validation. Publishing a pointer does not prove every worker can serve it.

Failure variation: revision 23 is syntactically valid but references an unauthorized tenant resource. Worker validation and policy reject it, retain last-known-good permitted state, and emit a clear condition. If current security policy forbids continuing the older state, the affected operation may need to stop. Final outcome is explicit applied-version evidence and no silent rollback or false readiness.

Production implication: test late delivery, snapshot gaps, invalid bundles, and worker restart. Interview takeaway: configuration distribution is a state-transfer protocol with correctness and compatibility rules, not merely a message bus subscription.

Bound propagation and fan-out

A global change can trigger millions of downloads and acknowledgments. Use staged rollout, regional distribution, caching of immutable bundles, and backoff while preserving version evidence. Acknowledgment fan-in can overwhelm the authority even if delivery is cheap. Aggregate status carefully without hiding failed minorities. Rollout policy should define how much evidence is required before expanding and what stops progression.

Chapter summary

Configuration needs complete snapshots, version-aware activation, compatibility checks, and incarnation-scoped acknowledgments. Watch delivery and actual serving readiness are different facts.

SD-018 · Chapter 5 of 12

Bound authority before allowing independence

Serving cached state is a security decision

A worker that has a complete configuration can often continue serving without contacting management. That statement needs a validity boundary. A cached routing table might remain useful for hours. A credential revoked because of compromise might need to stop working within seconds. An approved agent tool invocation might authorize one effect rather than every future action by the same worker. Separate these contracts before calling the design statically stable.

Describe each delegated capability using a subject, resource scope, allowed operations, expiry rule, policy revision, and revocation mechanism. The data plane verifies the capability locally where that is safe. If immediate revocation is mandatory, some fresh authority dependency remains. Calling that dependency a cache does not remove it. The architecture must either accept its availability cost or change the business contract with explicit approval.

Clock assumptions matter when expiry is part of authorization. A process clock moving backward must not silently extend authority. A monotonic clock supports elapsed duration within one process incarnation, but does not establish agreement across machines. Production delegation commonly needs bounded clock uncertainty, conservative expiry, or a server-side authority check. Specify the uncertainty and the rejected boundary instead of treating a timestamp as universal proof.

Worked example 4: the old controller returns

Start with controller A holding epoch seven for tenant T. It sends a request to create a paid resource and then becomes partitioned. The authority service grants controller B epoch eight. A later resumes with its old local state. The objective is to allow safe continuity without allowing two authorities to publish conflicting management effects.

The resource endpoint records the greatest accepted epoch for the protected resource and rejects commands carrying a smaller epoch. B first establishes epoch eight at that endpoint before issuing the new mutation. A's delayed command carrying seven is rejected even if A believes its lease remains valid. The important operation is enforcement where the effect commits, not a warning printed by A. Every participating effect path must honor the same authority boundary.

Suppose A's epoch-seven create already committed before B established eight, but the response was lost. Fencing does not erase that resource. B reconciles it by the stable operation identity before deciding whether a replacement is necessary. The intermediate state is unknown, then discovered committed, then adopted or compensated according to the current desired revision. Retrying a new identifier would risk creating a second paid resource.

Warm workers may continue reading an already valid immutable model bundle while the controller dispute is resolved. That permission does not automatically permit changing quotas, accepting newly privileged tools, or publishing new routes. These are separate capabilities. If the security policy says the bundle's authorization has expired, the worker must stop the protected action even though it still has enough bytes to compute.

The final result is one accepted management authority and a reconciled inventory of effects. Correctness depends on endpoint enforcement, durable epoch state, and stable business identities. In an interview, distinguish fencing from idempotency: fencing excludes stale authority; idempotency relates repeated requests for the same logical action. Neither replaces the other.

Failure boundaries and chapter summary

A lease can reduce coordination frequency, but its safety proof must include pauses, network delay, clock behavior, and the resource endpoint. A process that checks a lease and then pauses before writing can still perform an obsolete effect unless the commit boundary rejects it. Put the check as close as possible to the protected state transition.

Not every external provider supports fencing. In that case, serialize effects through a service that does, use provider-supported conditional updates or stable idempotency keys, or explicitly accept a weaker outcome with reconciliation. Do not promise exactly one arbitrary external effect merely because your internal controller is careful. The boundary of the proof belongs in the design document.

Operationally, expose rejected stale commands, authority changes, unknown effects, and expired delegated capabilities separately. A burst of stale commands may reveal a paused controller returning after failover. Counting every rejection as a new business outage obscures the fact that the safety mechanism worked. The useful incident question is whether valid work continued and obsolete work was prevented.

SD-018 · Chapter 6 of 12

Scale management work without starving execution

Control-plane demand has several dimensions

Management load includes desired-state writes, watch delivery, health reports, artifact preparation, reconciliation, admission checks, and operator queries. These have different scaling laws. A heartbeat rate grows with workers. A rollout can grow with workers times bundle size. A tenant listing query can grow with inventory. A controller retry storm can grow with failures and poorly bounded retries, even when useful customer traffic is flat.

Partition work by stable ownership boundaries such as region and tenant, with explicit exceptions for global policy. Avoid a single queue in which one tenant's invalid configuration repeatedly blocks everyone else's valid updates. Bound reconciliation work per pass, use backoff with jitter, and retain enough state to resume rather than restart expensive scans. Fair scheduling is a correctness aid when urgent revocations share infrastructure with routine changes.

Separate CPU, network, storage, and connection budgets for management and execution. Separate processes on the same host can still compete for memory and packet queues. Conversely, one process can sometimes provide useful isolation through bounded executors and resource limits. State the concrete resource that prevents an overloaded management function from starving requests, rather than relying on a box boundary in the diagram.

Worked example 5: a rollout is a fan-out event

Assume ten thousand workers each send a one-kilobyte heartbeat every ten seconds. Ignore framing and replication for the first estimate. The steady ingress is one thousand heartbeats per second, or roughly one megabyte per second decimal. This is a useful baseline, but it does not describe the rollout distribution path.

A new configuration bundle is two megabytes and every worker needs it. Direct distribution sends twenty gigabytes of payload. If the distributor is limited to two hundred megabytes per second of useful delivery, the ideal transfer floor is one hundred seconds. This excludes TLS overhead, failed transfers, disk writes, validation, activation, and client competition. A claim of a ten-second global rollout contradicts this capacity assumption.

Introduce one hundred regional or rack-local caches and fetch one verified bundle per cache. The origin now serves about two hundred megabytes, while the downstream network still carries twenty gigabytes. This reduces origin load but does not eliminate worker-side bandwidth or synchronized activation risk. Content-addressed caching lets clients reuse verified bytes; it must still enforce tenant scope and artifact authorization.

Now change the failure variation: all workers reconnect after a control-plane outage. Immediate snapshot requests can combine with missed heartbeats, reconciliation scans, and the rollout itself. Apply jittered reconnects, admission limits, bounded snapshot concurrency, and staged activation. Reserve capacity for security-critical changes. Dropping all heartbeats may reduce load but can also destroy the evidence needed to distinguish a dead worker from a delayed report.

The final design budgets steady reports and burst distribution independently. Correctness requires every activated worker to validate the same intended version, not merely to download something. Production readiness also requires measuring time to safe convergence by cohort. The interview takeaway is that a management service can be idle most of the day and still fail at the exact moment a large fleet needs it.

Staleness is a vector, not one dashboard number

Track desired revision, delivered revision, validated revision, active revision, and serving observations. A worker can have downloaded revision thirty while still serving twenty-nine because validation failed. A disconnected worker can appear stale in the controller but continue serving the last valid configuration. A worker that restarted can reuse its name while losing all prior local state.

Attach acknowledgments to worker incarnation and configuration identity. Otherwise an acknowledgment from an old process can make a replacement look ready. Aggregate by cohort, region, tenant, and capability. A global average hides a small critical population that never converged. Do not let a stale management view alone delete healthy serving capacity; use conservative conditions and explicit failure policy.

The summary is to scale the change path for bursts and the execution path for sustained work. Rate limits, fairness, cached artifacts, staged convergence, and independent resource budgets turn conceptual separation into an operational property. Measure the dependency during failure drills, because its true shape often appears only when many workers recover together.

SD-018 · Chapter 7 of 12

Design bootstrap and disaster recovery as first-class paths

Warm survival and cold recovery are different promises

A warm data plane already holds processes, connections, code, configuration, artifacts, credentials, and perhaps local state. A cold region may hold none of them. Surviving a management outage with warm capacity does not prove that a region can restart during that outage. Write separate objectives for continuing valid work, replacing a failed worker, adding capacity, and rebuilding a region.

List bootstrap dependencies in their actual order. A worker might need identity before it can read configuration, configuration before it can find the artifact store, and an artifact before it can start the request server. If the identity service itself needs that request server to start, there is a cycle. Break it using a deliberately small bootstrap mechanism with narrow authority and an independently recoverable trust root.

Bootstrap material needs its own security and rotation story. Keeping long-lived broad credentials in every image simplifies recovery while increasing compromise impact. A smaller signed bootstrap descriptor with scoped access may reduce that risk, but the signing keys and retrieval path become recovery dependencies. Recovery convenience is not a reason to hide these tradeoffs.

Worked example 6: the warm fleet survives, then a zone is lost

A service has three zones with one hundred units of warm capacity each. Peak demand needs one hundred eighty units. The control plane is unavailable, but all warm workers have valid serving bundles. Initially the three hundred units can serve peak load. Losing one zone leaves two hundred units, still above the demand assumption. This is a static-capacity argument, not evidence that new workers can be launched.

Now demand rises to two hundred twenty units. The two surviving zones have a twenty-unit shortfall. No amount of control-plane independence creates missing physical capacity. The design must shed lower-priority work, queue within the user latency contract, reduce optional computation, or restore management and provision more resources. Decide those actions before an incident rather than pretending availability is binary.

Suppose cold recovery requires identity recovery in four minutes, artifact access in six minutes after identity, and worker startup in three minutes after artifact access. The serial path is thirteen minutes. If route publication then takes two minutes, useful added capacity appears after fifteen minutes. An unrelated dashboard restoration that happens in parallel does not shorten this dependency path. Likewise, summing parallel tasks would overstate it.

A failure variation places the identity recovery key only in the failed zone. The arithmetic no longer describes a recoverable path. The missing trust material is a feasibility failure, not a slower step. Restore independently protected key access or change the recovery design. Test with realistic access controls, because a drill using an administrator's personal credentials can conceal this dependency.

The final result states exactly which demand level survives which zone loss and when replacement capacity can become useful. Correctness means no worker serves unauthorized stale state during recovery, and no traffic is routed before its required artifacts and policy are ready. The interview takeaway is to separate survival, reconstruction, and renewed elasticity.

Recovery exercises must remove the real dependency

A meaningful drill blocks the management endpoint, pauses a controller after an external request, removes watch history, replaces a worker incarnation, and denies a bootstrap dependency in separate experiments. Observe what continues, what stalls, what is rejected safely, and what recovers only after authority returns. Keep blast radius bounded and document the exact injected boundary.

Backup validation includes the ability to read desired state, recover its schema, restore signing or decryption access, and identify which effects already exist. Restoring only the configuration database may leave the infrastructure inventory inconsistent with it. Reconciliation after recovery should adopt valid resources before creating replacements. Old controllers must not regain authority simply because their restored database claims they once held it.

A practical recovery runbook names decision makers, evidence, prerequisites, and rollback limits. It also explains when continued operation must stop because delegated authority has expired. The chapter's core lesson is that independence buys time under a defined capability contract; a tested recovery path determines what happens when that time or capacity is exhausted.

SD-018 · Chapter 8 of 12

Apply the separation to AI infrastructure and cloud platforms

Inference has more than a model process

For inference, the execution path includes admission, tokenization, model execution, optional retrieval, tool mediation, and response delivery according to the product. The management path includes selecting models, distributing artifacts, assigning replicas, configuring routes, and adjusting quotas. A route lookup against a remote configuration service on every token can accidentally pull management into the hottest path.

Keep immutable model identity distinct from a mutable product alias. An alias update chooses which verified model bundle new requests should use. A long-lived streaming request may continue on its pinned version while new requests use the next version, if that is the supported contract. The design must also handle safety-policy changes that cannot wait for long streams to finish. Model version, tokenizer, prompt template, retrieval schema, and policy can form a compatibility bundle.

NVIDIA's public Triton documentation describes model-management modes and model loading behavior. Use that as concrete evidence that model lifecycle is explicit, not as proof of any particular company's fleet architecture. A model becoming visible in a repository is not by itself proof of readiness across all workers. Our rollout acknowledgment protocol is an original design exercise layered around this lifecycle distinction.

Training and agents expose different authority boundaries

A running training job may continue taking steps while the scheduler cannot assign new jobs. Checkpoint publication, lease renewal, credential expiry, and input access can still impose fresh dependencies. Losing the scheduling plane might therefore preserve compute briefly but prevent safe restart or durable progress. Measure accepted training work and validated checkpoints rather than only occupied accelerators.

An agent orchestration service may plan work in one component and execute tools in another. A previously approved read-only task might continue under a valid scoped capability, while a new purchase, deployment, or privileged write requires fresh approval. The logical control/data distinction is relative to the operation: a tool gateway executes requests but also enforces authority. A label must never obscure that enforcement role.

Anthropic's public multi-agent research article describes coordination and research workflow concerns. It does not establish a universal control-plane design or authorize assumptions about private approval systems. Here the engineering extension is our own: preserve task identity, delegated scope, durable observations, and unknown effect state across orchestration failures. That extension is clearly a hypothetical design, not a claim about the published system.

Read public systems with precise attribution

Kubernetes documents the control-plane and node components directly. The API server exposes the management interface, controllers reconcile state, and node components run workloads. Its existence does not mean every workload is independent of every control-plane function. A workload's own identity, storage, and discovery choices determine additional dependencies. Test the actual application rather than inheriting an availability claim from the platform name.

Google's Borg paper and Meta's Twine publication provide public examples of large-scale cluster management concerns. They motivate attention to scheduling, allocation, and fleet operations. OpenAI's public Kubernetes scaling article discusses its own published experience. None of these sources justifies inventing private current topology, scheduler algorithms, or interview questions. Our numerical exercises are intentionally original and use declared assumptions.

For an OCI-oriented architecture interview, identify compartments, regional boundaries, identity and key services, network paths, artifact stores, and worker pools as candidate responsibilities. Avoid claiming that a particular managed service guarantees your entire application contract. Ask what survives loss of its management API, what needs a fresh token, and what is required to launch a replacement. The portable skill is dependency analysis, not memorizing vendor names.

SD-018 · Chapter 9 of 12

Defend a complete regional configuration platform

Requirements and component ownership

Design a hypothetical multi-tenant platform managing ten thousand inference workers across three regions. It must continue valid warm inference through a management outage, distribute ordinary configuration within five minutes under normal load, reject stale privileged mutations, and provide a separately specified emergency revocation bound. These are proposed requirements for the exercise, not measured promises from a vendor.

The management API authenticates a tenant administrator, validates schema and policy, assigns a desired revision, and durably records a stable change identity. An authoritative metadata store serializes conflicting updates within the chosen tenant scope. Controllers compute intended resource changes, reconcile unknown provider effects, and publish complete immutable bundles. Regional distributors serve signed manifests and content-addressed artifacts. Workers validate compatibility and activate a local version at a request boundary.

A separate route layer directs traffic only to workers meeting the requested capability and serving contract. The route layer needs enough local information to keep routing safely during a management outage. It does not authorize arbitrary new tenant access. An emergency policy path may carry short-lived deny rules with its own availability and freshness budget. Making this path explicit exposes the residual dependency instead of hiding it in an optimistic cached-state story.

Follow one change and one failure

An administrator changes tenant T from bundle twenty to twenty-two. The API commits revision twenty-two once for the stable change identity. A controller prepares artifacts, verifies digests and tenant scope, then publishes a complete manifest. Each regional distributor obtains the manifest and workers fetch only missing content. Workers stage the bundle, validate schema and runtime compatibility, then atomically switch new request admission to it.

A worker acknowledges with tenant, bundle digest, desired revision, worker identity, incarnation, validation result, and activation timestamp under the defined clock semantics. The controller distinguishes delivered, active, and observed serving counts. A rollout gate uses cohort-level readiness rather than a single global average. Old bundles remain available until the rollback and in-flight request policy permits reclamation.

Now pause the controller after a provider create request. A successor receives a higher authority epoch and reconciles the stable operation identity. It adopts the existing resource if the effect committed and remains valid under current intent. If intent changed, it follows an explicit compensation or retirement plan. A timeout does not become permission to create another resource blindly. Regional workers keep valid warm service while this management reconciliation happens.

If a region disconnects, it keeps its last complete valid bundle. It cannot claim to have applied later security policy. Once its delegated scope or freshness boundary is exceeded, the affected capability stops or degrades according to the contract. On reconnect it detects watch gaps, obtains a fresh snapshot, validates the current version, and converges with jittered bounded work. No observer silently turns missing acknowledgments into proof of worker death.

Security, observability, cost, and evolution

Use tenant-scoped artifact authorization, signed bundle identity, least-privilege controller credentials, and endpoint enforcement of authority. Separate an operator's ability to inspect state from the ability to mutate it. Log privileged change identity and policy revision without retaining raw customer prompts unnecessarily. A valid digest proves byte identity; it does not prove that the signer or tenant assignment was correct.

Measure management write latency, reconciliation backlog age, unknown external effects, fan-out bandwidth, active-version distribution, bootstrap success, stale-authority rejection, and valid warm serving capacity. Service SLOs distinguish ordinary request availability from time to deploy and time to revoke. During an outage the management SLO may fail while the serving SLO remains healthy. This is an intended possibility, not a reason to suppress the management incident.

Cost includes replicated metadata writes, distributor egress, artifact retention, worker staging memory, and idle survival capacity. Start with regional controllers and a simple immutable bundle store if the workload permits. Add hierarchical fan-out when measured bursts justify it. A global strongly ordered configuration stream may simplify reasoning but expand the availability boundary. Per-tenant ordering with explicit cross-tenant exceptions often provides a more useful initial contract.

The defense should reject two tempting alternatives precisely. A synchronous global lookup on every request may simplify freshness while coupling serving availability to management. An unlimited local cache may preserve computation while violating revocation. The selected architecture occupies a declared point between those extremes. Its limits are part of the answer, including provider endpoints that cannot enforce fencing and cold recovery paths that still need management authority.

The model uses integers and in-memory state so the reasoning is visible. A production implementation needs durable authority, authenticated identities, atomic persistence, failure-safe activation, artifact verification, bounded clocks where applicable, and recovery from a crash between staging and activation. Passing this model is evidence about these local rules, not proof of an entire distributed deployment.

Read the order of operations carefully. Validation happens before changing the active revision. A rejected message leaves the last valid state intact. Restart creates a different incarnation even when the human-readable worker name remains the same. The authority endpoint checks the epoch at commit time. These ordering details are the lesson; translating the class into a service without preserving them would change the guarantee.

Code and deterministic experiments

PYTHON · executable standard-library model
from dataclasses import dataclass

@dataclass(frozen=True)
class Bundle:
    tenant: str
    revision: int
    ready: bool = True

class Worker:
    def __init__(self, tenant, incarnation):
        self.tenant = tenant
        self.incarnation = incarnation
        self.active = 0

    def activate(self, bundle):
        if (bundle.tenant != self.tenant or not bundle.ready
                or bundle.revision < self.active):
            return False
        self.active = bundle.revision
        return True

    def acknowledges(self, incarnation, revision):
        return incarnation == self.incarnation and revision == self.active

class Endpoint:
    def __init__(self):
        self.epoch = 0
        self.committed = {}

    def commit(self, epoch, operation, value):
        if epoch < self.epoch:
            return 'stale authority'
        self.epoch = epoch
        if operation in self.committed:
            return self.committed[operation]
        self.committed[operation] = value
        return value

def main():
    worker = Worker('T', 'boot-A')
    assert worker.activate(Bundle('T', 20))
    assert worker.activate(Bundle('T', 22))
    assert not worker.activate(Bundle('T', 21))
    assert not worker.activate(Bundle('T', 23, False))
    assert not worker.activate(Bundle('OTHER', 24))
    assert worker.active == 22
    replacement = Worker('T', 'boot-B')
    assert not replacement.acknowledges('boot-A', 22)
    endpoint = Endpoint()
    assert endpoint.commit(7, 'create-K3', 'resource-K3') == 'resource-K3'
    assert endpoint.commit(8, 'create-K3', 'duplicate') == 'resource-K3'
    assert endpoint.commit(7, 'another', 'obsolete') == 'stale authority'
    assert 10_000 * 2_000_000 / 200_000_000 == 100
    assert 300 - 100 >= 180 and 300 - 100 < 220
    print('Activation, incarnation, authority, identity, and capacity checks passed.')

if __name__ == '__main__':
    main()

Run the copied code with a standard Python interpreter. First observe acceptance of revision twenty-two and rejection of late revision twenty-one. Then restart the worker and confirm that the prior acknowledgment no longer identifies the current process. Finally send an old authority epoch after a newer one has committed. The endpoint rejects the old command independently of the caller's belief.

Change the validation condition so a bundle is accepted before its artifact is ready. The assertion should expose a violation. Next remove the incarnation check and observe that old readiness can falsely cover a replacement. Finally remove the commit-time epoch comparison. A returning old controller can now mutate the resource after ownership changed. Each mutation removes a distinct safety condition rather than merely reducing test coverage.

Interpret results and extend the model

Add an explicit unknown-effect state if you extend this exercise. Represent logical operation identity separately from attempt identity. A lost response should leave the operation unresolved until the endpoint's durable result can be inspected. Fencing decides who may commit now; it does not tell the successor whether an earlier command already committed.

Model liveness separately from safety. A worker that rejects every update never accepts stale configuration, but also never converges. Add a fair delivery assumption and a valid latest snapshot, then require eventual activation under those assumptions. Do not claim convergence during a permanent partition or with an invalid latest bundle. State exactly which environmental condition makes progress possible.

The chapter summary is that local transition models are valuable when their assumptions are explicit. They help uncover stale acknowledgments, incomplete activation, and obsolete authority. Combine them with integration failure tests and operational measurements rather than presenting a small deterministic program as a distributed consensus proof.

Speaking scripts, concept map, and whiteboard rehearsal

Thirty-second explanation

A control plane establishes desired behavior, while a data plane executes it. The separation helps only when execution has complete valid local state, enough capacity, and bounded authority. I trace the request path, distinguish warm survival from cold recovery, and specify how updates converge. For mutations, I enforce authority where effects commit and reconcile unknown outcomes. This lets me say exactly what continues during a partition and what must wait or stop.

Two-minute explanation

I start with capabilities rather than component names. For inference, serving an already admitted request is different from assigning a replica, publishing a route, or authorizing a new privileged tool. I draw every synchronous dependency in the serving path and ask whether it needs fresh state. If a local complete configuration can safely replace a remote lookup, that removes one availability dependency, but it does not remove credential expiry or revocation requirements.

Updates use immutable versioned bundles with explicit validation and activation. Workers acknowledge a lifecycle stage using their incarnation, so a delayed acknowledgment cannot cover a replacement. Watches provide efficient notification, while snapshots recover gaps. Controllers reconcile desired and observed state rather than assuming a timed-out provider call failed.

For authority, a fresh leader is insufficient unless the effect endpoint rejects stale epochs. Idempotency handles repeated logical actions and reconciliation handles unknown outcomes. These are separate mechanisms. For resilience, I budget warm capacity and test bootstrap dependencies independently. A warm fleet may survive a management outage while still being unable to add workers.

Finally, I measure ordinary serving, deployment convergence, revocation freshness, and recovery as separate objectives. That makes the claimed isolation reviewable. The design remains honest about what stops during a partition, where security requires fresh authority, and which infrastructure dependency still sits on the path.

Five-minute architecture explanation

I will design a hypothetical three-region inference configuration platform. The key requirements are continued valid warm serving, normal configuration convergence within five minutes, bounded emergency revocation, and safe management failover. I would confirm demand, tenant isolation, cold-recovery objectives, and provider conditional-write support before choosing exact services.

The management API authenticates the operator and commits a desired revision using a stable change identity. Tenant-scoped ordering is enough unless a named invariant crosses tenants or regions. Controllers reconcile that intent against provider inventory. When an external request times out, the operation remains unknown. A successor discovers whether the resource exists and adopts or compensates it under current intent. It does not create a fresh resource merely because it has become leader.

Controllers publish complete manifests referencing immutable verified artifacts. Regional distributors cache the content. Workers stage, validate, and activate a compatible bundle at a defined admission boundary. Acknowledgments include configuration identity, lifecycle stage, worker identity, and incarnation. Route publication uses capability readiness. Existing streams may remain pinned to their bundle, but an emergency policy can impose a stricter rule.

The serving path uses local valid state where permitted. It retains enough warm capacity to survive the stated zone loss. I would not claim that management independence also provides elasticity. With three hundred units initially, losing one hundred leaves two hundred; demand of one hundred eighty fits, while two hundred twenty does not. That difference determines admission and degradation policy during recovery.

Authority is enforced at the effect endpoint through a durable epoch or equivalent conditional mechanism. Old controllers can return after pauses, so checking leadership only before sending a request is insufficient. Every mutation path needs the same protection. Providers without that feature limit the guarantee and require serialization, idempotency, or explicit compensation. Cached authorization has a separately stated expiry and revocation contract.

Capacity planning separates heartbeat ingress, configuration fan-out, reconciliation scans, and mass reconnects. Ten thousand two-megabyte bundles create twenty gigabytes of downstream payload. Hierarchical caches reduce origin work, not the total downstream bytes. Jitter, fair queues, bounded concurrency, and staged activation prevent a recovery storm from destroying the management layer again.

Recovery begins with identity, keys, artifacts, and configuration. I draw this graph to remove cycles. Survival drills block management; reconstruction drills start with cold workers and realistic access controls. A missing recovery key is a feasibility failure rather than a longer recovery estimate. Restoring desired state also requires reconciling the effects that survived outside the restored database.

The observability plan separates serving availability, change latency, revocation freshness, bootstrap success, unknown effects, and stale-authority rejections. Cost includes idle survival capacity, replicated metadata, distribution bandwidth, and artifact retention. I would begin with the simplest regional design that meets the requirements and add hierarchy after measuring burst bottlenecks. I would defend the design using its declared boundaries rather than an absolute promise that management can never affect serving.

Concept checklist and whiteboard drills

Remember these distinct pairs: desired versus observed state; delivered versus active configuration; worker name versus incarnation; operation versus attempt; leadership versus effect authority; valid cached state versus merely available bytes; survival capacity versus scaling capacity; warm continuation versus cold reconstruction. If two of these share one variable in your design, inspect whether the model has lost a meaningful distinction.

On a whiteboard, draw a worker receiving revisions twenty-two, twenty-one, then twenty-three with a missing artifact. Show the unchanged active state after each rejection. Next draw a watch-history gap and a snapshot recovery. Then pause a controller after an effect, change desired intent, and explain how its successor discovers and reconciles the original result.

For a capacity drill, double worker count and halve useful origin throughput. Recompute direct bundle transfer time before proposing a cache. For a recovery drill, remove the key service and ask which existing capabilities continue and which new ones are impossible. For a security drill, require immediate revocation during a partition and acknowledge the resulting availability cost.

The final rehearsal is a requirement change: the interviewer now needs cross-region ordering for one scarce global resource. Add that authority only to the protected operation and explain its failure boundary. Do not casually turn every local inference request into a global transaction. A Staff-level answer is precise about where coordination is necessary and disciplined about where it is unnecessary.
