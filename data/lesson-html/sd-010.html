SD-010 · Distributed Systems Foundations · 01

When the current row cannot answer the question

A recovery dashboard says that London is the active site. The incident commander asks which checkpoint was approved when that decision was made, whether approval came before the routing change and when the platform first learned that traffic had moved.

Worked example 1 · Three histories hidden in one row

Imagine a record with group G, target London, status active and last updated at 14:12. One possible history has a straightforward promotion from Phoenix after a known primary failure. A second has a failed first promotion, a canceled repair, a later successful retry and a separate verification of the route. A third has a manual database edit that corrected an erroneous target name after the operation finished. All three can leave precisely that current row. If the product must make different decisions based on those histories, keeping only the latest representation has discarded information the service actually needs.

Event sourcing makes the accepted sequence of domain facts authoritative for the state being modeled. In a recovery aggregate we might record RecoveryRequested, CheckpointApproved, PromotionAuthorized, ProviderPromotionObserved and TrafficVerified. Reconstructing the state means reading the ordered facts and applying the transition associated with each. A command such as ApproveCheckpoint asks the system to do something and might fail validation. The past-tense fact CheckpointApproved records a decision that actually succeeded. The distinction becomes operationally important during replay: reconstructing a previously observed promotion must not invoke the provider's promotion API again.

A generic audit log next to a mutable table can be a sensible alternative. Ask which representation wins if the row says active and the log has no authorization event. If the row is authoritative and the log exists for investigation, the system is not event sourced merely because it records history. If both are independently writable, recovering from disagreement becomes an application-specific arbitration problem. In an event-sourced design, mutable projections can be discarded and rebuilt under suitable retention assumptions. Be precise about which data is derivable. A deleted external checkpoint object cannot be reconstructed from a stream that contains only its digest.

Choose a boundary with a reason to keep history

Many systems benefit from storing recovery-plan definitions as ordinary versioned rows while keeping execution decisions as events. Plan editing might require simple lookups, constraints and occasional version history. An individual run, by contrast, can have a long life with retries, human approval and provider observations that need to be reconstructed exactly. Choosing event sourcing for the run does not require converting the tenant directory, invoice history or feature-flag database. A Staff+ design can name the narrow boundary where the additional operational cost buys something concrete.

Think about what tomorrow's investigator needs. A bare field update from status 4 to status 5 conveys little without a copy of the code that interpreted the numbers. A domain fact can include the prior intent identifier, approved checkpoint, authorizing policy version and resulting operation identity. Record only information justified by a use case and avoid embedding giant customer documents or credentials. The lifetime of an event can exceed the lifetime of the application that emitted it. Every value added to the authoritative record creates a retention, compatibility and access-control commitment.

Interview explanation

I would start with the question the current state cannot answer. For a recovery run, knowing the current site is different from knowing which evidence authorized a promotion. I would put those decisions and observations in an ordered run stream, rebuild the run state deterministically and use separate projections for dashboards. I would keep the provider action behind its own idempotency and reconciliation contract. That gives historical explanation without coupling ordinary history reads to live side effects.

SD-010 · Distributed Systems Foundations · 02

An aggregate decides and a state machine evolves

An aggregate is the boundary within which a command's invariants are evaluated together. The state machine defines which transitions are legal. An event stream is one possible durable representation of those transitions.

Worked example 2 · Reject the second activation

Model deployment D starts in Candidate state at revision six. Its artifact was verified against digest H, its evaluation suite passed under policy version P and no rollout has started. An operator issues Activate with expected revision six. The command handler reconstructs D, checks the artifact, policy and rollout preconditions and emits RolloutAuthorized with generation 22 and digest H. The append succeeds only if the stream is still at six. The event store assigns the new position. The transition applying this event sets the desired deployment state to rolling out and records the authorized generation. It does not predict that every serving instance is already healthy.

A second operator concurrently issues WithdrawCandidate based on revision six. If activation appended first, withdrawal sees a revision conflict. It must load the new facts and decide whether withdrawal is now a different operation with a different authorization rule. A blind retry against the latest revision would silently change the meaning of the human's decision. The service might offer RollbackRollout for a deployment already in progress. That command can require a different approval path because some traffic may already use the candidate. Optimistic concurrency turns a simultaneous decision into an explicit question for the domain model.

Two functions help communicate the design. Decide takes a state and command and returns new events or a domain rejection. Evolve takes a state and a recorded event and returns the next state. A rejection of a new command need not be a domain event, although an independent security or audit requirement may record rejected attempts. Evolve must interpret historic accepted facts even if current admission rules would reject the original command today. Re-running today's policy while replaying yesterday's approval can prevent recovery or produce a different historical state. Store enough context to interpret the original fact.

What makes replay deterministic?

A deterministic transition applied to the same starting state and same ordered events gives the same result. Fetching today's model evaluation score, choosing an available host at random or reading the current wall clock inside Evolve breaks that property. If a score drove the original decision, capture the accepted score or an immutable, retained reference and its interpretation. If a scheduler chose host H17, record H17 in the event. Configuration files and locale settings can be hidden sources of nondeterminism too, especially when sequences are sorted using environment-specific collation or times are interpreted in local time zones.

Use a simple test. Build two fresh processes with the same event bytes and deliberately different clocks, network availability and current policy versions. Ask them to reconstruct the aggregate and compare semantic output. A failure tells you which dependency was never captured. Equal hashes alone can conceal differences if the serialization silently drops fields, so compare the state fields that matter to the invariants. Maintain representative old streams from supported software versions, including partial runs, terminal failures and corrective events. An elegant state machine diagram can miss the one historic event variant that a real restore must interpret.

def evolve(state, event):
    kind, generation = event
    phase, current = state
    if kind == "authorized":
        return "rolling", generation
    if kind == "suspended":
        return "suspended", generation
    if kind == "ready" and phase == "rolling" and generation == current:
        return "active", generation
    return state

state = ("candidate", 6)
for event in [("authorized", 7), ("suspended", 8), ("ready", 7)]:
    state = evolve(state, event)
assert state == ("suspended", 8)

Limits of a per-stream invariant

If the rule says at most one rollout runs per deployment, an expected revision on D can enforce it. If the rule says the total GPUs reserved across all deployments must never exceed a tenant limit, a fresh revision check on each deployment independently cannot enforce the sum. Define a quota aggregate, reserve bounded tenant capacity in advance, use a transactional store with a wider serialization boundary or accept explicit temporary imbalance with compensation if the business permits it. Splitting streams enables independent progress and introduces a coordination decision wherever the invariant crosses those boundaries.

SD-010 · Distributed Systems Foundations · 03

Event identity, stream position and time answer different questions

Two facts can share a timestamp and still be distinct. A single fact can be delivered three times. Sorting messages by a UUID or by arrival time does not recover the order the write model authorized.

Worked example 3 · A valid retry after the revision changed

A client sends command C7 to authorize rollout of D from revision six. The handler appends its accepted event E42 at revision seven and records C7's outcome. Its response is lost. A controller then records one healthy instance at revision eight. When the client retries C7 still expecting revision six, the current revision is already eight. A strict check of the revision before consulting the durable command outcome would return a conflict for a command that already succeeded. Depending on the documented API, that can force the client into dangerous guesswork about whether it may retry a different request.

Bind command identity to tenant, aggregate and significant input fields. For a matching previously accepted command return its recorded outcome or the documented equivalent. Detect conflicting reuse of C7 for a different digest. For a new command, evaluate its preconditions and append its events with an atomic expected-revision check. The command result and idempotency evidence must be recoverable along with the append, for example within the same transaction or through a durable binding in the stream that the handler can query consistently. Keeping a result in a process cache loses it at exactly the leadership changes where clients tend to retry.

The event identifier identifies the fact across deliveries. The per-stream revision orders facts within the aggregate. A correlation identifier groups work associated with one business request across services. A causation identifier can link a later message to the event or command that caused it. A consumer checkpoint records how far one particular reader has progressed in a particular subscription. Collapsing all five concepts into one integer will eventually create a puzzle such as why rev 8 of deployment D is being compared with rev 314 of deployment E. Choose identifiers whose comparison domains match the operation being performed.

Work with two clocks in the domain

A historical recovery operation occurred at 14:02 according to the provider, but the platform only received a signed observation at 14:15. The event was appended at stream revision 31 after several other facts. A customer asks what the system knew at 14:10. Applying the late observation at its asserted occurrence time would distort the answer. Distinguish occurrence time, recording time and the order of accepted facts. A separate question might ask what activity was in effect at 14:05 according to everything known today. That is a different temporal query and can require a deliberately bitemporal model.

A stream revision gives a clean answer to what state was reconstructed through a particular prefix. A fleet-wide question across independent partitions requires an explicitly defined cut or watermark. If each partition reports a processed position, a global chart might reflect different physical times across the fleet. Say which partitions and positions the chart includes and what freshness policy applies. An on-call engineer needs more than an updated-at timestamp if one partition stopped moving twenty minutes ago while the other ninety-nine continue normally.

How to reason about corrections

Suppose yesterday's event says approval policy P17 and later investigation establishes that the provider supplied an incorrect label. Silently overwriting yesterday's event destroys the explanation of why the original controller acted. Append a correction identifying the affected fact, the new interpretation, the actor and the evidence. Decide which projections should apply it retrospectively and which should preserve what was known at the time. Corrections to history and remedial actions in the real world are different. Correcting a dashboard's historical label cannot undo requests routed to a model during the incident.

SD-010 · Distributed Systems Foundations · 04

CQRS gives readers a model built for their question

Operators want one dashboard for all model deployments, while an individual activation decision must evaluate a small, strictly ordered stream. A single table shape is rarely optimal for both jobs.

Worked example 4 · The command succeeded but the screen still says pending

At 10:00 the command handler accepts SuspendDeployment and returns deployment D, revision 51. The command stream durably contains the suspension. A dashboard projection has consumed D only through revision 50, so an immediate dashboard query can still display active. This is a normal consequence of asynchronous projection. If the UI turns that stale view into a fresh authorization to route traffic, the separation has crossed an unsafe boundary. Route admission must consult the authority appropriate to its contract. A convenient reporting view cannot become authoritative merely because it refreshes quickly in normal conditions.

One user experience is to return the accepted revision and an authoritative operation status with the command result. The UI can display suspension accepted, projection catching up. A read API might accept a minimum revision. The server waits until the relevant projection covers that revision, redirects to an authoritative path, or returns a clear pending response with the current position when the deadline expires. Do not promise that a fresh per-deployment projection proves every regional traffic router has drained. Model command completion, read-model visibility and data-plane enforcement as different milestones with different observability.

CQRS separates the model used to process commands from the model used to answer queries. It does not require event sourcing, separate databases or asynchronous transport. One transactional database might maintain multiple projections synchronously with state updates. Conversely an event-sourced service can answer modest queries by folding a short stream directly and have no separate read service. Choose asynchronous projections because a particular read workload, latency target or operational isolation benefit justifies accepting their lag and operating their recovery mechanisms.

Projection delivery, gaps and duplicates

Suppose the deployment projector has incorporated revisions through 48. It receives 50 before 49. Overwriting last-seen revision with 50 would cause it to discard 49 later as old, even if 49 carries a critical state transition. For a subscription guaranteed to include every event for D, detect the gap, fetch or wait for the missing revision and only advance the contiguous watermark after application. For a deliberately filtered subscription, missing numeric revisions may simply represent irrelevant event types. The check should match the subscription's ordering contract; use an appropriate delivery cursor or include enough metadata to distinguish filtered gaps from data loss.

A projection that sets the current deployment name to a value may naturally tolerate a duplicate assignment. A projection that increments the total number of failed attempts does not. If a worker updates the count then crashes before saving the cursor, replay can double count. Commit projection changes and their deduplication or checkpoint evidence together in the projection store when possible. When the target store cannot transact with the source checkpoint, design an idempotent or conditional projection keyed by event identity and provide repair. An at-least-once broker plus an exactly-once database transaction at one sink does not give every external subscriber exactly-once business behavior.

Choosing what to return to a reader

Dashboards can usually tolerate bounded visible lag if they expose the relevant watermark. Billing and authorization decisions often require more specific guarantees. An architectural conversation should ask what the caller will do with the answer. Reading active to color a chart and reading active to launch a privileged provider action are not interchangeable uses of the same field. Offer separate APIs or explicit modes when the consequences differ. A high-volume projection can have an impressive availability metric while still being unsuitable for a low-volume decision requiring fresh authority.

Rebuild a projection while writes continue

A customer asks for a dashboard of time spent in each release stage. The command stream already contains the transition facts. You can build that dashboard without changing how releases are authorized, provided you can identify the history you have processed.

Worked example 5 · A shadow projection at revision 900

The current dashboard stores only a release's latest state. The proposed version accumulates duration spent staged, active and suspended. At the start of the rebuild, subscription partition P has high-water mark 900. A builder creates an empty projection under schema version two and records its input stream identity. It folds events from the beginning of the retained history, or from a verified projection-compatible base, through position 900. Ordinary command processing continues. New events at 901 and later must eventually reach the shadow projection. A rebuild that stops when it finishes its initial listing can silently lose every update accepted during that listing.

One safe arrangement is a subscription that permits reading from a precisely specified cursor. After the builder transactionally applies through 900, it resumes from 901. If the store gives an inclusive cursor, it deliberately redelivers 900 and the projector handles that duplicate safely. The important property is continuity at the boundary under the actual API contract. A bootstrap that lists current objects, then subscribes from now, leaves an interval where mutations can disappear. Conversely, starting the live subscription too early without a consistent cut can apply events before their prior state is installed. Document whether the snapshot includes or excludes the cursor event.

At position 850 the worker persists an update but crashes before returning its batch acknowledgment. Its replacement must recover a cursor consistent with the durable materialization. If the destination database supports a transaction spanning the view and cursor, commit them together. If the source broker separately tracks delivery, a duplicate on restart should be harmless because the local projection already records position 850. If the destination is an external search index that cannot transact with a database cursor, use deterministic document identities and conditional version checks where supported. For incrementing aggregates, assigning stable per-event contribution documents may be safer than repeating increments and attempting to undo duplicates later.

Compare old and new views at the same cut

At the moment you compare dashboards, the previous view may have processed through 960 and the new one only through 951. Comparing their current counts can report a discrepancy caused entirely by input position. Pause a test read at a common frontier, recover expected values from a sampled set of authoritative streams and label the comparison with that frontier. Since the new schema adds stage duration, there is no old field to compare directly. Validate invariants instead. Time attributed to contiguous stages should match the modeled observation interval after accounting for transitions, corrections and explicitly unknown periods.

Consider a release still active at the cut. Computing its duration through now during replay mixes the builder's wall time with historical observation. A read model can keep the stage-entry timestamp and accumulated duration of closed stages. A query then computes open-stage duration relative to an explicit as-of time. If an event arrives late with a corrected occurrence time, decide whether the metric reflects recorded order or retrospective effective time. A duration chart that sometimes uses each definition according to event arrival order will be irreproducible. Put the chosen definition and the projection version in the report.

Switch readers using a versioned routing pointer once the new view has caught up to a verified boundary, its live subscription is healthy and queries meet the service objective. Retain the previous view long enough for a controlled rollback and audit. A dual-read phase can expose discrepancy samples without doubling every customer query indefinitely. If the new projector cannot keep up after cutover, the old one must still have a trustworthy cursor before rollback. Throwing away the previous projection as soon as the first dashboard renders saves space but removes the most useful recovery option in the next hour.

PYTHON · executable model
def apply_contribution(state, position, amount):
    # Model one transaction over total and contiguous cursor.
    total, cursor = state
    if position <= cursor:
        return state
    if position != cursor + 1:
        raise ValueError("missing required input")
    return total + amount, position

result = (0, 0)
for position, amount in [(1, 5), (1, 5), (2, 3)]:
    result = apply_contribution(result, position, amount)
assert result == (8, 2)
try:
    apply_contribution(result, 4, 1)
except ValueError:
    pass
else:
    raise AssertionError("gap incorrectly accepted")
SD-010 · Distributed Systems Foundations · 06

Snapshots, historical schemas and correction

A snapshot can shorten recovery dramatically. It introduces a new question: what evidence makes this particular serialized state a valid replacement for replaying the prefix it claims to represent?

Worked example 6 · Restore at revision 400 and apply the tail

Deployment D has 460 events. A snapshot labeled revision 400 stores the result of folding events one through 400 under reducer version V3. A command arrives with expected revision 460. The handler loads the snapshot, verifies stream identity, serialization format, reducer compatibility and integrity, then applies events 401 through 460 in order. Only then can it evaluate the command against the reconstructed state. An expected-revision append still protects against a concurrent event 461 while reconstruction was in progress. Passing the snapshot checksum alone cannot justify committing a decision based on stale state.

Suppose another handler writes a snapshot labeled 401 but serialized the aggregate before applying event 401. Recovery now resumes at 402 and silently drops one transition. The bytes and checksum are internally valid. Bind the serialized state and the actual last applied position in one durable publication operation. A partially uploaded snapshot must not replace the last good snapshot pointer. Periodically reconstruct from an independent trusted base and compare domain state at the same revision. Corrupt or incompatible snapshots should be discardable while the required original history remains available. If history has been intentionally truncated, the retained base becomes a primary recovery dependency with stronger durability requirements.

Choosing a snapshot interval is a capacity decision. Suppose reconstructing one event takes an average of 40 microseconds of CPU and an aggregate normally has 10,000 events. Replaying a whole stream costs roughly 400 milliseconds of CPU before storage reads, parsing overhead or queueing. A valid snapshot every 500 events bounds the ordinary replay tail to fewer than 500 events when snapshots are produced promptly, around 20 milliseconds of CPU under these assumptions. This is not a latency guarantee. If snapshot generation fails repeatedly or a command targets a long-idle hot stream without a compatible snapshot, recovery can still require a much longer replay.

How old events stay understandable

Imagine that version one of ApprovalRecorded stored a boolean and version two records the policy version and a set of approving actors. A reader can transform old event representations into a canonical shape when the missing fields have a documented interpretation. It cannot reconstruct the actual historical list of actors if that information was never recorded. An upcaster that defaults to today's approving committee invents history. Represent unknown values explicitly, preserve the original evidence and decide whether a particular operation requires stronger evidence before proceeding. The production design should test real old payloads alongside new producer versions.

Changes in domain semantics are harder than renaming a field. If suspension once stopped only new sessions and a later rule requires draining all sessions, replaying an old suspension through today's broader interpretation can make a historical report assert an action that never happened. Introduce a new event type or a versioned meaning where needed. A new policy can issue a fresh command to bring current deployments into compliance and record what actually occurred. This preserves both the original story and the subsequent corrective action. The ability to replay history does not license retroactively changing what an authorized operator did.

Retention and access are design constraints

A permanent journal of raw model prompts, customer identifiers and provider payloads enlarges both storage cost and the consequences of broad read access. Prefer small domain facts, scoped pseudonymous identifiers and references to separately governed evidence when the business requirement permits it. Decide which data must be available for deterministic reconstruction and which belongs in shorter-lived diagnostic storage. Deleting a referenced payload can make an old projection impossible to rebuild unless the retained event captures the essential outcome. Document this consequence, test the supported reconstruction horizon and align access boundaries across backups, snapshots and derived views.

Projection deletion does not erase its source. Conversely, retaining the journal does not guarantee an authorized analyst may inspect every older fact. Apply tenant isolation, purpose-specific read access, audited administrative actions and authenticated producers. Design a supported correction or redaction process with the people responsible for data governance. In a design interview, explain the underlying engineering constraint rather than promising a particular legal outcome. A system that copied sensitive data into ten projections and backups needs an inventory of those copies before claiming any retention behavior.

SD-010 · Distributed Systems Foundations · 07

Build a production model-release decision ledger

Design a regional control plane that must explain why a model was enabled or suspended, rebuild fleet reports after a schema change and recover incomplete provider actions after controller failure. All sizing and timing figures in this exercise are hypothetical.

Command boundaries and components

Define the aggregate as one tenant and deployment. Its ordered history records registration of an immutable model manifest, validation evidence, policy authorization, requested activation, observed regional readiness, suspension and retirement. A separate audit stream may track access to the system itself. A deployment command must not insert a new model digest into historical events merely because the manifest catalog changed. Require immutable references and verify that evidence remains accessible for the retention horizon the service promises. Configuration changes that affect decisions must become explicit command inputs or versioned facts.

The authenticated command API validates the tenant and principal, then submits a command ID, expected stream revision and payload. A handler obtains current aggregate state from a compatible snapshot plus journal tail and calls a pure decision function. That function returns a rejection or a set of authorized facts. The event store appends the related events atomically with an expected-revision check and the deduplication evidence required by the API. Choose a store with well-defined durability, failover behavior, stream ordering and batch append semantics. An API that acknowledges an event before its declared failure domain can recover it cannot meet a zero-loss acknowledgment contract.

A subscription exposes committed events to projectors and to an effect dispatcher. The inventory projection answers which versions are deployed in each environment. The time-series projection shows how long each release remained in each stage. A per-tenant audit API permits authorized historical reconstruction. A command-status API returns the specific accepted outcome for its command ID. Partition those workloads independently where useful, and ensure that indexing an enormous audit search cannot block command acceptance. Cross-stream queries must describe the snapshot or watermark at which results were observed.

Worked example 7 · Crash between scheduling a rollout and saving the reply

At stream revision 17 the immutable manifest M passes validation. A release operator sends Activate with command K, the approved policy version and revision 17. The handler appends ActivationRequested at 18 under K. The dispatcher observes 18 and records durable work addressed by the stable identity deployment D and event E18. It asks a regional provider to stage M using an idempotency key derived from that intended action. The provider accepts operation P6, but the dispatcher crashes before saving P6. The control plane knows that activation was requested and the reply is uncertain. It lacks evidence that all workers are ready or that no provider work occurred.

The replacement queries by the original key if supported, or safely retries the same operation under the provider's documented deduplication contract. When it finds P6, it records the provider identity and observes the outcome. If this is a provider without either capability, an indeterminate action requires reconciliation before issuing a conflicting rollout. A projector replaying E18 to rebuild counts must never call the provider. Separation of effect dispatch from pure event application prevents a historical report rebuild from launching a fleet of obsolete rollouts. Replaying facts inside an effect-capable topology needs an explicit mode and isolation barrier.

While the dispatcher was down, a second operator requested suspension at revision 19. A late provider observation for the earlier activation still represents something that happened. Record its original causation identity and evaluate it against the current aggregate state. It might establish that one region briefly staged the old model, prompting cleanup, without making the deployment globally active again. A reducer that unconditionally sets active whenever any readiness event arrives will regress state across these interleavings. Distinguish requested intent, observed evidence and the decision to authorize new admissions. A guarded transition can preserve a late fact without reversing a later policy decision.

Capacity, security and evolution

Assume 20,000 deployments each generate 30 events per day and the average event is two KiB including envelope. That is 600,000 events per day, about 6.94 events per second on average and roughly 1.14 GiB of raw payload per day before indexes, replication and compression. At three durable copies the raw replicated payload is about 3.43 GiB per day. Retaining one year implies roughly 418 GiB of unreplicated payload and 1.22 TiB at three copies, ignoring compaction and metadata. If an incident produces 20 percent of daily volume in five minutes, the temporary input rate is about 400 events per second. Size for bursts, per-stream hotspots, fan-out and recovery traffic, not just the mean.

A projection receiving 400 events per second but processing only 300 accumulates 100 per second. After five minutes the lag is 30,000 events. If input falls to seven per second and processing remains 300, the nominal catch-up time is about 102 seconds. The same queue depth under continued 400-per-second input will never drain at that capacity. Monitor input rate, processing rate, age of the oldest unprocessed event, partition skew and time to a caller's required revision. An event-weighted average lag can hide one low-traffic tenant that has received no updates for hours.

Authentication belongs at the command boundary. A caller permitted to request activation might lack permission to append a fabricated validation result or provider observation. Use writer-specific event contracts, isolate tenant data in subscriptions and projections, and record enough identity to explain privileged transitions. Apply encryption and access control to snapshots and replay environments as well as the live journal. A rebuild worker that can read every tenant and has production provider credentials combines two unnecessarily broad privileges. Provide scoped read access and remove effect capabilities from projection workers.

Architecture defense during a regional failure

The interviewer requires immediate release acceptance in either region during partitions, a unique per-deployment history and zero loss of acknowledged commands after regional failure. For a deployment shared by both regions, independent conflicting commands cannot both receive unconditional success while preserving one expected-revision history. Choose a replicated authority and specify which connected region can commit, or partition ownership by deployment so independent histories continue locally. In either design, returning accepted before sufficient remote durability is incompatible with zero acknowledged-event loss for destruction of the local region. A command can be received locally as pending while its authoritative outcome remains unresolved.

I would first offer strong per-deployment append semantics, explicit pending status during handoff, and asynchronous independently recoverable read views. I would state the recovery point and capacity promised for the journal, the manifests it references and the external effects already issued. When the service grows, shard by deployment identity while preserving each stream's order. Do not move the same stream to an independent writer until the handoff prevents both epochs from appending conflicting revision 52. Measure time to recover correct admission decisions separately from time to rebuild the complete analytics history.

SD-010 · Distributed Systems Foundations · 08

Operate and verify a replayable system

The most revealing readiness test is to start with empty projection storage and a journal containing retries, late observations and an older event schema. Can a new deployment rebuild the same answer without invoking a single external side effect?

Worked example 8 · A poisoned partition

A projector successfully commits subscription position 700 then receives an event at 701 with an unknown schema version. The other partitions are healthy. If it silently skips 701 and marks position 702 as complete, a future version of the projector cannot distinguish an intentionally filtered event from missing data. Stop or quarantine according to the projection contract. Record source identity, position, type, schema version, error class and a safe diagnostic reference. If independent partitions can progress without violating the view's guarantees, keep them moving and mark partial coverage. A service-wide ready flag hides the scope of the failure.

To recover, deploy a compatible reader or a documented transformation, resume from the last trustworthy cursor and compare the updated state at an agreed cut. If an emergency bypass is necessary, represent the resulting coverage hole explicitly and provide a repair plan. A dead-letter queue can preserve a troublesome payload while allowing unrelated work to continue. It does not make a projection containing the hole complete. Distinguish metrics for message delivery, successful application and customer-visible coverage. Counting a dead-letter transfer as successful application is a particularly misleading kind of green dashboard.

Test both the facts and their interpretation

For the aggregate, start from known state, apply a command, assert its emitted events, then fold them back and assert the state. Test delayed facts, conflicting commands at the same expected revision, a lost append response and replay of a matching command identity after the stream advanced. Fold the same stream once from empty state and once from a snapshot plus tail. The states should agree at the same revision. Seed a projector with duplicates and restarts around its transaction boundary. Verify its final totals and cursor against a reference fold, and assert that rebuilding creates no provider calls or emails.

Roll out a schema change by proving that readers in the mixed-version fleet can handle events that writers will produce. A writer introducing an event older consumers cannot parse can stop every projection at once. For a change requiring new mandatory meaning, deploy compatible consumers first or establish a separate versioned path with a catch-up plan. Test a long-retired deployment with sparse old fields as well as a newly created one. The hottest path is usually well exercised. The fragile path is a regional recovery during which a year-old snapshot and a brand-new event must be interpreted by a fresh binary.

Interview explanation

I would put two recovery objectives on the whiteboard. The first is how quickly the authoritative command path can safely resume decisions. The second is how quickly each projection can provide its promised coverage. They can be very different. A customer's deployment may be safely suspended long before the compliance dashboard catches up, while a missing authorization projection could itself prevent safe admission. Classify projections by who uses them and what decision they support. Then test restoration from real retained inputs with side effects isolated and external outcomes reconciled.

Twelve Senior Staff interview questions

What decisive question separates event sourcing from audit logging?

Evaluates authority and recovery. I would ask what happens when the current row and historical log disagree. If the accepted facts define the model and the current row can be rebuilt by folding those facts, the aggregate is event sourced. If the current row is authoritative and the log merely describes some changes, it is an audit design. Either can meet a product's needs. The decision depends on whether reconstructing historical decisions and building new interpretations justifies maintaining an enduring event contract.

Follow-up. Can an audit log still be immutable? Yes. Immutability alone says nothing about which record governs recovery.

Common mistake and tradeoff. A system with two independent sources of truth needs explicit arbitration and reconciliation.

Why should a reducer never rerun today's authorization policy on yesterday's approval?

Evaluates historical determinism. The event records a decision already accepted under its original conditions. A reducer interprets that fact to reconstruct state. Re-running current admission rules might reject an old decision after a policy update or produce a different outcome during disaster recovery. Record the policy revision and enough evidence to interpret the acceptance. New policies can require corrective action through new commands and events. This preserves the historical explanation while permitting present-day enforcement.

Follow-up. What if the old decision was wrong? Append a correction or remediation with its own identity and evidence.

Common mistake and tradeoff. Versioning a schema without versioning the meaning of a transition can still corrupt replay.

How can a timed-out command succeed even though its expected revision is stale on retry?

Evaluates request identity and optimistic concurrency. The original append may already have committed and later events may have advanced the stream. After authentication and validation of request identity and body, recover the previously accepted outcome for the same command. Evaluate expected revision for a genuinely new intent. Keep idempotency evidence recoverable with acceptance, and document retention. A repeated identifier attached to a different command body must not return a misleading historical success.

Follow-up. What if the retention window expired? The API needs a documented reconciliation path or a business identity that remains queryable.

Common mistake and tradeoff. Blindly retrying against the latest revision can authorize a decision the caller never intended.

A dashboard lags after suspension. Is the system unsafe?

Evaluates distinguishing observation from authority. A stale dashboard can be acceptable if it presents labeled historical state and cannot authorize harmful actions on that basis. The system becomes unsafe if a routing service treats the dashboard as proof it may continue admitting traffic despite a suspension contract requiring a current check. Define command acceptance, projection visibility and effective admission cutoff separately. Carry an accepted revision to a minimum-revision query when the user needs confirmation.

Follow-up. Can synchronizing the dashboard solve everything? No. A client may still act after the displayed state changes.

Common mistake and tradeoff. Fix the decision boundary while giving users clear evidence of projection delay.

Can an event subscription guarantee that each email is sent exactly once?

Evaluates boundary of external effects. A broker may redeliver after a worker sends an email but loses its acknowledgment. An atomic cursor update in the worker's database does not include the external provider. I need a stable provider idempotency key with documented scope, a queryable effect identity or a business process that tolerates uncertainty and reconciles before sending again. A replay to rebuild a dashboard must not send email at all.

Follow-up. What if the provider has only a short deduplication window? Bound automatic retries and define handling of ambiguous outcomes beyond it.

Common mistake and tradeoff. Counting one event in the journal cannot establish one real-world effect.

How would you change a projection schema with no read outage?

Evaluates rebuild continuity and rollback. Create a separately named projection, bootstrap it at a known source boundary and consume every subsequent event from an unambiguous cursor. Compare old and new metrics at a common frontier. Test crashes around view and cursor persistence and verify that the shadow consumer cannot dispatch effects. Switch reads only after correctness and catch-up criteria are met. Keep the prior view current long enough to roll back under a defined operational window.

Follow-up. What if the source retention is shorter than the rebuild? Obtain a consistent retained base or extend retention before the rebuild begins.

Common mistake and tradeoff. A zero-downtime schema migration can still produce a silent data gap between listing and subscribing.

What if a new event has information that old events never captured?

Evaluates semantics of evolution. An upcaster can rename fields and transform representations whose old meaning is known. It cannot recover absent historical evidence. Represent unknown information explicitly, retain the old interpretation or limit the historical queries the new view supports. If current safety requires extra verification, issue a present-day command and record the resulting evidence. Do not fabricate an actor or policy version just to make a new schema's required fields validate.

Follow-up. How do you verify compatibility? Replay real old payloads and compare modeled state and decisions at known cuts.

Common mistake and tradeoff. Schema compatibility is weaker than semantic compatibility.

How does a snapshot attach to a safe replay boundary?

Evaluates joined state and offset correctness. The snapshot represents one aggregate or projection state after a precise prefix under a known schema and reducer version. Verify identity, integrity and compatibility, then replay only the subsequent tail. Publish the snapshot pointer after all required bytes are durable. Test the state at the boundary against a full fold. A checksum protects serialized bytes but cannot detect that a formatter labeled revision 400 state as 401.

Follow-up. Can old events be removed afterward? Only when the new base fulfills all supported historical, repair and reconstruction promises.

Common mistake and tradeoff. Compaction can silently convert an optional optimization into an irreplaceable source of truth.

Would you use one global stream for a million deployments?

Evaluates invariants and scaling. I would first ask which decisions actually need common order. Independent deployments can use independent aggregate streams, with a distributed subscription exposing a vector of partition positions for analytics. A global quota shared across deployments needs a separate serialization or reservation design. A single global stream can simplify historical order but creates contention and ties unrelated tenants to the same recovery path. Partitioning improves isolation but introduces cross-stream correlation and snapshot questions.

Follow-up. How would you publish one atomic release across deployments? Consider a shared immutable release manifest with an explicitly enforced cutover boundary.

Common mistake and tradeoff. Partitioning records without partitioning their invariants moves the hardest problem into the application.

What should happen to a delayed readiness event after rollback?

Evaluates late observations and transition guards. Preserve the fact that the provider observed readiness for a specific earlier activation. Bind it to its original action and generation. The reducer should update that action's observation without reactivating the deployment after a later suspension. The controller may enqueue controlled cleanup through its effect pipeline. An aggregate state machine needs to distinguish desired policy, actual observations and pending remedial actions.

Follow-up. What if the event is factually wrong? Record a correction and let projections apply the documented interpretation.

Common mistake and tradeoff. A last-event-wins status field discards essential causation information.

How can a fleet report claim it is current?

Evaluates coverage and watermarks. For a partitioned subscription, report which partitions and consumer positions are included, and how the service determines the freshness of those positions. One freshly consumed hot partition does not imply an idle-looking partition is healthy. A request for one deployment's accepted revision can be fulfilled with a suitable per-stream guarantee, while a fleet-wide snapshot requires a coherent multi-partition definition. Make missing partitions and data gaps visible.

Follow-up. Does a recent refresh timestamp prove freshness? It can record when a query ran even if its source is badly behind.

Common mistake and tradeoff. Measure completeness separately from elapsed rendering time.

When would you explicitly reject event sourcing?

Evaluates architectural judgment. For a modest configuration service with simple CRUD, limited historical requirements and frequent erasure of sensitive fields, a relational representation plus scoped audit history can be easier to operate. I would choose an event-sourced boundary only when historical decision reconstruction, evolving projections or temporal analysis has clear business value. Include migration, old-schema support, snapshots, data retention and replay isolation in the cost estimate. Selectively applying the technique can retain most of its value without making every table a historical protocol.

Follow-up. How do you revisit the choice? Track real requests that current-state storage cannot answer and the cost of adding targeted history.

Common mistake and tradeoff. Using event sourcing as proof of architectural sophistication can create permanent maintenance overhead for little benefit.

Whiteboard practice with a deliberately missing event

Start with a five-event release stream. Remove the provider operation identity from the fourth event while keeping its textual status. Ask a colleague to recover the external operation after a simulated coordinator failure. They may still be able to reconstruct the aggregate's last displayed state, yet have no definitive way to find the real operation. Restore the missing identity or a safe lookup key and try again. This exercise shows why a domain fact's useful content is determined by recovery and queries the service must support, not just by the shape of today's dashboard.

Speak through one production failure

Use the release decision ledger as a single thread across your answers. Explain why the platform accepted a command, what an operator can establish from that response, and how a new worker can reconstruct the outcome after a crash.

Thirty seconds · State the distinction

Event sourcing stores accepted domain facts in order and derives aggregate state by replaying them. CQRS separates the model used to decide commands from the models used to answer questions. A state machine defines how facts change the state. In a model rollout I would order release decisions per deployment, publish a dashboard projection with a watermark and keep provider calls in a separately recoverable effect dispatcher.

Two minutes · Explain why a replay is safe

Suppose a promotion request was authorized yesterday. Its fact identifies the recovery group, approved checkpoint, policy version and operation identity. To rebuild the run today I apply that fact to the run state. I do not ask today's policy whether the historical approval should have succeeded, and I do not call the provider again. The role of replay is to reproduce the decision record and the resulting modeled state. The role of a live dispatcher is to reconcile incomplete real-world actions.

A projector may see that fact twice if it crashes after updating its database but before acknowledging delivery. I either update the projection and its local checkpoint together or use an idempotent target keyed by the event identity. For an external target the same protection might not exist. That is why I distinguish an exactly-once local projection outcome from a claim that a provider executed an operation exactly once.

The customer's immediate question after acceptance is also important. An authoritative command response can identify the accepted revision. A regional dashboard may still be behind and should report its own coverage. If the operator needs confirmation, a minimum-revision read can wait, route to an appropriate source or explicitly indicate that the view has not caught up. Acceptance of a promotion decision and verified traffic cutover remain separate states.

Five minutes · Defend the deployment ledger

I would begin by asking why this platform needs a history. A current row tells me deployment D is suspended. A release owner needs to know which model was running, which evaluation authorized it, who approved activation, which regional operation actually occurred and why the platform later suspended admission. If those questions affect operations and accountability, a per-deployment event stream is a plausible authority. The tenant directory and ordinary configuration tables can retain simpler representations where replay has little value.

The command API verifies tenant scope and principal, accepts the expected stream revision and binds the request identity to significant input. A pure decision function validates the command against current modeled state. The append atomically advances the stream only if the expected revision still matches. A genuine conflict causes a fresh domain decision; a retry of a previously accepted intent returns its recorded result. This protects human intent across simultaneous edits and avoids interpreting a lost reply as a failed action. Each event carries enough retained context to evolve state deterministically even after policies and binaries change.

I would separate the journal from the dispatcher and from the two read models. One projection supports an operator's deployment timeline. The other aggregates fleet readiness across partitions. Each owns its cursor and has its own freshness contract. A rebuild reads the retained facts at an explicit boundary, catches up with live traffic, compares at a common cut and switches queries through a versioned route. It has no provider credentials. A dispatcher instead reconciles action identities and must use the external provider's real deduplication and observation capabilities when recovering from a crash.

Consider the crash immediately after the provider accepts a regional activation. The event stream establishes that the action was requested. It cannot by itself tell me whether the provider accepted it before the crash. I query or retry under the original stable identity. A later regional observation remains attached to that activation even if a new operator already suspended the deployment. The reducer preserves the fact without accidentally re-enabling traffic. If the external API cannot establish the result, I explicitly block conflicting action pending reconciliation.

Finally I would measure the system in terms of user outcomes. Monitor append latency, expected-revision conflicts, ambiguous provider operations, backlog growth, oldest unprocessed event and time until a required projection revision becomes visible. I would test a region failure, a delayed callback and a replay across an old event schema. The design succeeds when the new controller can explain and recover each accepted decision, the dashboard can state exactly what it knows and a projection rebuild cannot send a second production command.

Final interview cheat sheet

  • Fact. Record the meaning of an accepted decision or observation.
  • Command. Validate a requested action before emitting facts.
  • Aggregate. Choose a boundary that can enforce the required invariant.
  • Revision. An expected-revision append detects stale decisions.
  • Replay. Apply recorded facts without rerunning external effects.
  • Identity. Bind command retries and event deliveries to distinct stable identities.
  • Projection. State which input frontier a derived answer covers.
  • Cursor. Advance progress with the durable effect on the view.
  • Snapshot. Bind state to an exact replay boundary and interpretation.
  • Correction. Preserve the original fact and record how its meaning changes.
  • Rebuild. Bootstrap and subscribe without a gap, comparing at a common cut.
  • Governance. Know which sensitive and historical data exists in every derived copy.
