SD-002 · Distributed Systems Foundations · 01

Two controllers can both believe they own recovery

An on-call engineer finds two promotion requests for one database. Both workers show a log entry saying ownership acquired. Before changing a timeout, identify the exact event that should have prevented the second mutation.

Worked example 1 · Pause at the last innocent instruction

Worker Mira acquires the right to orchestrate recovery for group G. Its local log shows a successful lease renewal at second zero. The allocator regards the grant as valid for ten seconds. At second two Mira checks its local deadline, constructs a request to move traffic to site P, and enters a long scheduling pause before sending. The lease authority continues to run. At second eleven it grants the same group to worker Noor, which chooses site Q. At second twenty Mira resumes at the next instruction and sends the previously prepared request. A plain routing API accepts both commands in their arrival order. Users can end up at P after the new owner has already moved them to Q.

The defect is a gap between checking authority and using it. Checking a second time can narrow the window but the scheduler can pause immediately after that second check too. Moving the check into a proxy helps only if the proxy controls the actual mutation and its check remains valid until that mutation takes effect. A proxy that forwards an unchecked request over another delayed channel reproduces the same gap one hop later. End-to-end reasoning follows the delayed command all the way to the component that can change user-visible state.

There are three distinct questions in this incident. Who should coordinate the next steps? When may a replacement begin trying to take over? Which arriving operation may the resource still apply? Election addresses the first. A lease can inform the second. Fencing answers the third when the resource durably rejects previously valid authority. A design might deliberately allow overlapping computation by both workers if it has a reliable final publication boundary. It cannot permit overlapping irreversible writes merely because both participants honestly believed their grants were valid.

Define the customer contract before the timer

For one recovery group, define a takeover point after which commands from any earlier ownership epoch cannot change its routing record. An epoch is an interval of authority identified by a value that changes on each new grant. It can outlive a process restart if the application explicitly provides a safe session identity and recovery protocol. In a conservative design a restarted worker acquires a fresh epoch. Never infer that a repeated hostname, pod name or machine UUID is evidence of uninterrupted authority. Infrastructure routinely reuses those labels after the process that received an earlier grant is gone.

For a strongly ordered ownership service, the grant has a definite place in an authoritative history. A downstream resource with a separate state machine may learn of the grant later. Be precise about the period between those events. If the contract says that old writes stop as soon as the lease authority grants Noor ownership, a comparison against only the largest token previously seen by the resource is insufficient. The old token can still be the largest the resource has seen. Either colocate enforcement with the grant, coordinate a barrier before declaring takeover complete, or specify a weaker and accurately observable takeover point.

I would reconstruct the old worker's last successful authority check, the new grant and the exact order in which the protected resource received the requests. If all I have is two worker log messages, I know something about their beliefs but very little about which mutation was legal. I want a durable resource-side record containing the attempted epoch, the highest installed epoch at that instant and the result. That record lets us explain the customer outcome and design a test that recreates the dangerous interval.

SD-002 · Distributed Systems Foundations · 02

Election selects a coordinator within a scope

A training platform has one elected planner per GPU pool. The platform also runs a replicated metadata database. Its database leader changes twice overnight without changing who owns any GPU pool. Explain why that can be correct.

Authority can exist at several layers

A database term describes a leadership round for one consensus group. A planner epoch describes the right to act on one application object. A provider operation identifier describes one remote action. All three may be integers increasing over time, yet substituting one for another can grant the wrong authority. If the database elects a new leader after a short network interruption, the application ownership rows remain part of the committed state. Invalidating ten thousand planner grants on every database election would create unnecessary recovery work. Conversely, one database leader might serialize hundreds of legitimate application ownership transitions in the same database term.

Choose a namespace for ownership. Suppose pool A epoch 40 and pool B epoch 3 have different owners. If a shared storage service maintains one global maximum, seeing a request for A could fence B forever until its counter passes 40. The receiver needs a comparison key containing tenant, stable resource identity and the appropriate lineage. Separate epochs per pool work only if the protected operation touches one pool or if a stronger coordination protocol handles multi-pool transfers. An efficient way to find this boundary is to ask which two operations would be unsafe if their ownership histories evolved independently.

Worked example 2 · Two candidates read the same grant

At durable version 70 the metadata table says the previous grant for pool A has expired. Mira and Noor each read version 70 and propose a new owner. The store serializes conditional updates against that same version. Mira's update succeeds and creates grant 71. Noor's update then finds a different version and returns a conflict. The authority must return the actual committed grant identity, or provide a safe lookup if the response is lost. If both clients instead performed an unconditional update after their successful reads, both could observe success even though only the later row remains visible.

A watch can notify the losers that leadership may become available again. Its notification is a hint to reread or attempt a conditional change. It is dangerous to treat a watch event itself as ownership. A disconnected watcher might receive an old event after another candidate has already won. A watch stream may require resumption from a revision, and retention may force a fresh snapshot. A correct candidate can tolerate a missed or duplicate notification because the grant primitive enforces the condition. The notification policy changes load and acquisition latency; the conditional grant provides exclusion at the allocator.

On a lost response, give the acquisition operation a stable identity if the authority supports one. Blindly repeating a new acquisition with a fresh identity may increment the epoch again and revoke the grant the first call legitimately created. A new attempt may still be the right recovery choice, but make that an explicit transition whose consequence is understood. If the old attempt and new attempt have identical worker names, binding each grant to a fresh session nonce prevents a stale release from deleting the replacement. Authenticate the principal separately from checking the grant generation.

Choosing who runs versus deciding whose results count

A pool planner may optimistically calculate placements while waiting for its grant. Those calculations can be expensive, so allowing concurrent speculation may reduce failover delay. Enforce freshness where placement becomes a reservation. A speculative result computed against an old capacity view must also satisfy current resource preconditions. Epoch validity alone says who may ask, not whether the requested GPU is free. A strongly designed API therefore combines authority, resource version, request identity and the domain condition in one transition. An interviewer asking whether one leader guarantees correct allocation is asking which of these predicates your architecture actually enforces.

SD-002 · Distributed Systems Foundations · 03

Lease time belongs to an explicit clock model

A lease is a right with a bounded lifetime under specified rules. Its meaning depends on who measures elapsed time, what counts as renewal and how late responses are interpreted.

Worked example 3 · A renewal response arrives too late

At local monotonic time 100 a worker starts a renewal. The lease service accepts it at its own local instant and grants a ten-second extension. The reply reaches the worker at local time 112. If the worker starts its own ten-second timer at receipt, it might continue until 122 even though the authority could already have expired the grant. No synchronized wall clocks are required to see the flaw. The ten seconds during which the message waited on the return path matter. A scheme relying on a conservative client validity window may measure from the start of the call, account for clock-rate error and abandon a response that arrives without sufficient safe time remaining.

Suppose the design bounds the authority's elapsed clock rate at at most 1.01 units per real second and the worker's rate at at least 0.99. With ten authority-clock units of validity, the shortest corresponding real duration is ten divided by 1.01. During that much real time a slow worker measures about 9.80 local units. A client budget smaller than this bound, measured from request start and reduced by an explicit margin, can conservatively model local use if the server did not issue the grant before the request began. These numbers are illustrative. A six-second scheduling pause after a check can still let an outbound mutation arrive outside the budget.

A clock can be monotonic and still have unsuitable suspend semantics. On a platform where the selected clock stops through host suspension, a resumed process may believe almost no time elapsed. Wall-clock synchronization is a different property from bounded elapsed-clock rate. If the protocol depends on either, state how the platform meets the assumptions and what action is taken when they are violated. A resource-side fence reduces how much of the exclusion argument rests on client timing. Timeouts then serve mainly to release blocked progress and select a replacement.

Budget renewal separately from application work

A ten-second lease renewed every three seconds leaves a nominal seven seconds after a scheduled renewal instant. That margin must cover queueing, network variation, storage latency, retry spacing and pauses. Consider three consecutive failed renewal attempts, each with its own deadline and backoff. The time budget is consumed by elapsed wall time across the entire sequence. An unconstrained retry library can keep trying long after the ownership protocol has declared local loss. Cancel outstanding attempts at the conservative deadline and record late replies as evidence for reconciliation. Do not let an old success callback restart a work loop for a session already abandoned.

A dedicated renewal thread reduces contention with application work. It can also mask an important failure. A renewal thread may keep a lease alive while the actual worker deadlocks indefinitely. From the authority's perspective a healthy client is making progress on renewals. From the customer's perspective recovery has stopped. Decide whether automatic transfer should depend on a progress signal in addition to lease renewal. A worker paused while waiting for an inherently slow provider might be healthy. Record the stage, operation identifier and expected progress interval before a watchdog concludes that a transfer is appropriate.

How I would explain a lease in an interview

I use the lease to decide when the coordinator can try replacing a silent worker. I first define whose clock decides expiry and how a client treats a delayed renewal. Then I ask what a paused worker can still do after expiry. For writes to a separate service I require that service to validate authority at the point of effect. Where that service has no fencing primitive, I change the operation or its advertised guarantee. Making a timeout shorter can improve detection and simultaneously increase false transfers. It does not close the check-to-effect gap.

SD-002 · Distributed Systems Foundations · 04

A fence takes effect at the mutation boundary

A resource stores a high-water mark for accepted authority. The comparison, the update to that mark and the protected mutation must form one atomic decision under the resource's failure model.

Worked example 4 · Install epoch 82 before declaring readiness

The route table for group G stores installed epoch 81 and target Phoenix. The allocator grants Noor epoch 82. Mira still has a delayed epoch-81 command to set the target to London. First deliver Mira's command before the route table hears from Noor. If the table simply accepts the highest token it has seen, the command still passes. The allocator's timestamp alone cannot show it was rejected. The new ownership record has not crossed the boundary into enforcement. Label that period acquiring or installing and keep the takeover completion promise pending.

Next deliver InstallFence with the authorized epoch 82. The table verifies the caller's authority, compares the epoch with its stored value and durably records 82 in the same serialization domain as route writes. The installation acknowledgment is the earliest point at which this table can promise to reject subsequent epoch-81 mutations. Now deliver the same stale command again. At the mutation boundary the stored epoch is 82 and the rejection has no effect on the target. Noor may issue an epoch-82 command with its own version and request identity. A stale reinstallation of epoch 81 must also be rejected. A repeated installation of 82 should return the already-established result.

Suppose InstallFence races against a long-running old mutation. A weak implementation checks the old epoch, does slow work, then commits after the installation. To close the race, serialize the final authoritative change with the fence update. Staging an immutable candidate file can occur outside the critical section. Publishing its pointer must atomically compare the required installed epoch and the expected resource version. If the external effect is actuating hardware, the enforcement point may be a device agent that owns the only mutation channel. The proof then depends on that exclusivity and on what an already-accepted device instruction can still do.

Equality throughout one epoch

Rejecting only strictly smaller tokens allows multiple commands in the same epoch. A repeated request with the same epoch can still debit a budget twice. Two concurrent operations within one legitimate grant can arrive out of order. Add a stable request identity for duplicates and an application sequence or expected revision when ordering matters. Enforce uniqueness at a scope that prevents collisions between tenants and jobs. An unexpectedly large token is not automatically trustworthy. Only a genuine, authenticated grant in the correct namespace and lineage may advance the durable fence.

One implementation uses an explicit install operation followed by writes requiring exact equality with the installed epoch. Another advances the high-water mark on the first authenticated write from a newer epoch and performs that write atomically. The first cleanly separates handoff readiness from the business mutation. The second saves a round trip when the first write itself can define takeover. Neither prevents an old write that linearized before the cutover boundary. State which boundary an API response certifies, and expose a query or idempotent replay for the case where the acknowledgment is lost.

PYTHON · executable model
def apply_route(state, epoch, expected_revision, destination):
    # Pure transition; production must apply it atomically.
    floor, revision, target = state
    if epoch != floor:
        return state, "stale or uninstalled"
    if revision != expected_revision:
        return state, "revision conflict"
    return (floor, revision + 1, destination), "applied"

installed = (82, 5, "Phoenix")
assert apply_route(installed, 81, 5, "London")[0] == installed
current, result = apply_route(installed, 82, 5, "Seattle")
assert result == "applied" and current == (82, 6, "Seattle")
assert apply_route(current, 82, 5, "London")[1] == "revision conflict"

Recover after losing the acknowledgment

Noor sends InstallFence and times out. Reading a stale replica that still shows 81 cannot tell Noor whether the primary committed 82. A strongly consistent lookup or safe replay of the same installation can settle that uncertainty. If the receiver now reports epoch 83, Noor itself has become stale and should abandon the attempt. If the receiver restored its database from a snapshot that forgot 82, a stale command might again pass. A production design must treat durability and restoration of the high-water mark as part of the fence. It is possible to restore all user-visible route rows correctly yet reopen a previously closed authorization window.

SD-002 · Distributed Systems Foundations · 05

Handoff across several protected resources

The new controller must update a route, a database role and a storage export. Each resource has its own durable state and failure schedule. A collection of successful fence calls has consequences different from a single atomic promotion.

Worked example 5 · Two barriers install and the third times out

Before handoff, database D, route R and file export F accept epoch 21. A new grant authorizes Noor at 22. Noor installs 22 at D and F. Its install at R times out. An operator looking only at the grant table sees Noor as current. A second operator looking only at F can confirm stale file mutations are rejected there. Neither can conclude that every participating component rejects epoch 21. Model handoff progress as a map keyed by resource identity and record the result of each barrier. A single Boolean named active discards precisely the information recovery needs.

Distinguish an authority barrier from a business transition. Installing 22 on the database should, where possible, reject obsolete administrative commands without immediately promoting a new writable primary. The orchestrator can establish fences first, verify prerequisites and then perform the business actions in a documented order. This does not turn independent services into an atomic transaction. There can be an interval when the new database is ready but routing has yet to switch. Choose a service behavior for that interval. For example, keep external traffic blocked until every safety-critical prerequisite is confirmed and represent the temporary availability cost explicitly.

The intake workflow persists request K before sending InstallFence to R. On recovery it checks R's authoritative state. If R confirms 22, the workflow records the missing acknowledgment. If it confirms only 21 under a contract allowing safe repeated installation, it resends the same operation with the same desired epoch. If R reports 23, Noor cannot finish the promotion and must hand the unresolved state to the successor. Never roll D and F back to epoch 21 just because R is unavailable. Lowering their high-water marks would make delayed requests from the old owner legal again.

A resource without an enforceable fence

Suppose the database vendor accepts a promotion request with an idempotency key but no ownership token. Replaying the same promotion key is safe under its deduplication contract. An obsolete worker using a different legitimate key can still promote a conflicting target. Deduplication solves repetition of one intent. It does not order incompatible intents across controllers. A software adapter can enforce ownership only to the extent that it exclusively controls every path to the underlying action and can account for in-flight asynchronous operations. Hiding the vendor API behind a function that checks a database row before dispatch does not serialize the vendor's eventual effect.

One defensible option is to serialize provider operations per resource through a durable executor and refuse to start a conflicting one until it can determine the prior operation's terminal state. This lowers availability when the provider cannot be queried or its response is ambiguous. Another is to isolate the protected resource through a stronger primitive such as a versioned configuration update or a verified shutdown of the old writer. A third is to narrow the automation contract and escalate ambiguous cases for operator reconciliation. Each option needs a concrete criterion for certainty. A human clicking approve cannot manufacture evidence that a delayed operation will never arrive.

Prove the barrier covers every path

Inventory the command paths, including ordinary workers, administrative repair tools, break-glass procedures and delayed tasks in provider queues. An old credential with direct write access around the gateway can defeat otherwise sound fencing. Separate emergency privileges, audit their use and define how normal operation resumes after an override. A delayed provider task may have been accepted before the barrier but perform work later. The relevant question is whether that later work can still conflict with the promised post-handoff behavior. A gate on new admission cannot retract already-accepted work unless the provider contract explicitly supplies cancellation or ordering guarantees.

SD-002 · Distributed Systems Foundations · 06

Design a regional GPU-pool ownership controller

A heterogeneous fleet has one planner per pool and an independent node agent for each machine. The product wants rapid planner failover without assigning the same physical GPU to two active tenant jobs.

Requirements and interfaces

Assume 4,000 pools with an average of 32 nodes each. Each ordinary ownership transition concerns one pool, but the protected subresource is a physical GPU at a node. A planner admission may reserve a group of GPUs together. State three promises independently. At most one grant is authoritative per pool. A node cannot accept a placement command from an older epoch after the node installs a newer one. A physical GPU cannot be reused while an incompatible workload still controls it. The third property requires local observation and enforcement beyond the epoch comparison. A fence on the control API does not evacuate memory or stop a running GPU kernel.

Use a replicated authority with a pool record containing tenant, pool identity, lineage, current epoch, holder session, expiry rule, change revision and transfer status. Keep a handoff record with the grant identity, required nodes or a versioned membership snapshot, and barrier outcomes. Node agents persist identity, highest installed authorized epoch, allocation version and operation outcomes in local transactional state. Use immutable request identities across workflow crashes. If the node storage is ephemeral, a restarted agent must recover an authoritative epoch and reconstruct actual device ownership before accepting commands. It must start in a fenced or quarantined state rather than initializing its floor to zero.

Acquire names the pool, expected prior revision, fresh session identity and request key. Renew compares holder session and epoch and updates only that grant. Release uses the same comparison so an old holder cannot clear a successor's row. Install authenticates the parent grant and binds it to the target node and lineage. Place requires installed epoch, node allocation version and workload identity. It records intent before attempting a device operation. GetPlacement distinguishes accepted, starting, running, draining and failed. Owners can change while a job continues running. Model the right to administer the job independently of the job's own lifecycle.

Worked example 6 · A node disappears halfway through transfer

Pool twelve changes from epoch 90 to 91 while node N7 is isolated. Thirty-one agents confirm 91. N7 still accepts epoch 90 according to its last local record. If the product requires every node to reject old commands once the pool status is ready, the system cannot declare readiness while N7 remains reachable to the old planner and unenforced. If it requires admission only within a safe subset, exclude N7 from eligible capacity and prove its GPU identities cannot be allocated elsewhere. A disconnected node running an old tenant job still consumes real capacity. Identifying a new instance with the same display name is not proof that N7 stopped.

Suppose an operator removes N7 from the pool membership and adds a replacement machine. Capture a new membership revision and bind the transfer decision to that revision. A returning N7 must not resume receiving ordinary work from a cached assignment. Force it through identity validation, current grant installation and inventory reconciliation. If the cluster uses reusable logical GPU slots, distinguish those slots from the physical devices and enforce a mapping version. Otherwise a stale planner may claim an old logical slot while a successor assigns that same logical identity to a different machine, confusing billing, monitoring and cleanup.

For gang scheduling, a requirement that all 32 workers start together adds another coordination problem. A collection of independent node placements may leave a partly reserved gang. Introduce a durable reservation attempt with expiry, an explicit commit decision and idempotent local transitions, or use an allocator that can atomically reserve the relevant inventory. Keep the semantics of ownership separate from the semantics of all-or-none allocation. A successful epoch handoff tells us whose command may be considered. It does not by itself prove that every requested GPU was available or that every process successfully started.

Load, isolation and the failure budget

With 4,000 pools renewing once every three seconds, the mean is roughly 1,333 renewals per second before retries. Sending a consensus write for every one of 128,000 node heartbeat samples at that same interval would produce about 42,667 writes per second. Decide which observations must survive, which only affect suspicion and which represent durable ownership transitions. A regional network outage can synchronize renewal retries across the fleet. Stagger their phases and limit recovery concurrency with per-tenant fairness. A tail-latency spike in the authority can otherwise cause widespread grant loss, triggering barrier installations that increase its load still further.

At a transfer rate of 50 pools per second and 32 nodes per pool, completing a barrier at every member means 1,600 node installations per second before retransmissions. Dispatching all requests in parallel makes handoff time depend on the slowest required node. Using a fixed concurrency of eight creates at least four waves for 32 nodes. If each wave took 20 milliseconds, the optimistic barrier time would already be 80 milliseconds before queueing, persistence and retries. These are illustrative lower bounds, not service objectives. Decide whether safety permits a smaller ready subset before promising a low tail on an all-node barrier.

Publish distribution metrics for grant latency, renewal lateness, grant churn per pool, age of the oldest pending barrier, stale rejections by resource and time from grant to safe capacity. Add a user-visible measure such as time until sufficient verified GPUs can admit the waiting job. Security needs an authenticated, tenant-scoped issuer and node authorization. A client-supplied counter that may freely jump to a huge value lets a buggy caller deny future work by poisoning a node's floor. Verify scope and provenance before advancing a fence and record both the grant and the effective node revision in the audit trail.

Architecture defense under a hard partition

The interviewer now requires activation in five seconds after any planner crash, continued operation on every reachable node and no stale placements even when nodes can only communicate with the old planner. Ask whose network is meant by reachable. A node reachable by the old planner but isolated from the grant authority may lack any evidence of a new epoch. Under an arbitrary delay it cannot simultaneously learn the new authority and continue accepting unrestricted old commands. Choose an explicit exclusion or bounded lease mechanism whose assumptions fit that node. If those assumptions fail, the safe capacity available within five seconds can be smaller than the entire pool.

My initial choice is a rapidly transferable regional grant and per-node barrier acknowledgments, with the eligible capacity API reporting the exact fenced subset. For workloads needing the entire gang I expose waiting until all required members are safe or replacements have been validated. I would evolve from one authority group to partitioned groups by pool only after measuring saturation. Moving a pool between authority groups requires transferring a lineage and high-water information in a way that cannot issue competing grants. This is a new migration protocol with its own recovery point, not just a change to a hash function.

SD-002 · Distributed Systems Foundations · 07

Restore a lost authority without reopening old permissions

A backup restores the ownership service to a point ten minutes ago. Every node is healthy. Is incrementing the restored counter enough to make the fleet safe?

Worked example 7 · Counter reuse after a restore

At the backup point pool K had reached epoch 50. Over the next ten minutes it advanced to 53, and several agents installed that value. The allocator then loses its data and restarts from the backup. It grants epoch 51 to a fresh worker. Nodes retaining 53 reject it, preventing progress. A newly reimaged node that initializes its floor to zero might accept it immediately. Worse, a delayed command carrying the old epoch 53 could now outrank the recovered grant. Authenticating the original issuer does not solve reuse of its logical history. The old token is genuinely signed and may name the correct pool.

A new cluster lineage can make that discontinuity explicit. A random identifier can distinguish lineages, but comparing two random identifiers lexicographically is no proof of which is authoritative. Define a trusted installation procedure for a new lineage, revoke or isolate old authorities and require every protected node to establish the new trust root before accepting ordinary work. If a node cannot be reached and could continue accepting old authority, it cannot count as ready under a fleet-wide exclusion promise. A recovered platform can instead support a deliberately isolated new fleet under a distinct resource namespace, with a carefully controlled mapping of external traffic.

Try a second recovery strategy: obtain the maximum epoch from protected resources, add one and resume. Observing only the responsive nodes misses a higher grant issued to an unavailable node or a signed grant still in transit. A sound high-water recovery needs an independently durable allocation boundary or a trusted reset that invalidates everything issued before the reset. If the authority documented that allocations come from reserved ranges persisted in a surviving system, it can skip beyond a verified reserved range. A scan of convenient telemetry dashboards cannot substitute for that evidence.

Rollouts, key rotation and operator tools

An upgrade that changes token encoding must permit both versions to coexist safely during the rollout. A signed token should bind issuer, subject or holder, tenant, resource, epoch and lineage according to the threat model. Consider when a node learns of key rotation. An isolated node caching a still-trusted old key may accept old grants until the key or lineage is explicitly revoked or securely expires. Key rotation alone is not an instantaneous distributed fence. Measure propagation and define conservative behavior when trust material is stale. Keep private credentials and full bearer grants out of ordinary logs.

Node images should include a bootstrap mode that cannot accept placements until the local agent proves its identity and installs a current configuration. Disk replacement and restoration should be test cases, alongside the easier case of a process restart with an intact durable floor. One particularly revealing test restores the disk to a snapshot immediately before installation, delays an old command until after recovery, and checks whether the node accepts it. If it does, recovering state machine data and recovering authority have different durability requirements in the present design. Resolve that discrepancy before certifying disaster recovery.

Diagnose two owners from independent records

Collect allocator grant history, node install history and external operation history. The allocator can show that epoch 53 was issued. A node can show when it installed 53 relative to a placement. A provider can show when that placement actually became effective. These timelines use different clocks, so prefer causal evidence such as request identities, predecessor versions and observed revisions over timestamp sorting across machines. Absence of a sampled log message is weak evidence. Audit the mutations that change ownership and inventory with enough durability to support recovery decisions and customer-facing incident explanations.

SD-002 · Distributed Systems Foundations · 08

Prove the handoff with failure injection

A passing test that shuts down one process and observes another becoming leader measures the easiest path. Build an execution that makes an apparently obsolete request arrive at the worst possible moment.

Worked example 8 · Turn a race into a deterministic test

Use a fake transport with queues for grant, install and mutation messages. Begin with resource value blue and installed epoch seven. Allow the old worker to prepare a write of red with epoch seven, then hold it in the transport. Grant epoch eight to the new worker. At this point deliver the held message in one branch of the test and observe the result permitted by the documented cutover boundary. In a second branch first deliver the authenticated installation of eight, then deliver red. The assertion in this branch is precise: the old write must be rejected and the value must be unchanged by that write.

Add crash barriers before durable installation, after durable installation but before reply, and after replying. Recovery from the first barrier can legitimately show seven if the service did not acknowledge a durable install. Recovery from the latter two must honor eight under the stated storage contract. Delay a duplicate install of eight until after a newer epoch nine has installed. It must not lower the fence. Finally send two different requests with epoch nine and the same expected allocation revision. One may win; the other must observe a conflict. This distinguishes ownership exclusion from optimistic concurrency within a valid grant.

A useful history checker takes a sequence of accepted operations at one resource and verifies that every accepted business mutation used the installed authorized epoch at its linearization point. To test an asynchronous device action, record both acceptance and the later external completion. A simple monotonic sequence of logged tokens cannot establish that physical effects respected the same order. If the device offers no such observation, document the limit of the test. A dashboard showing zero stale rejections could mean all workers are well behaved, or it could mean the enforcement point never checks epochs at all.

Deliberate availability experiments

Introduce a pause only on client renewal callbacks while the authority and node agents continue normally. Measure the number of spurious local resignations and the time until a new planner can admit a job. Next delay only one node's install response while permitting its ordinary RPCs to proceed. Observe whether capacity incorrectly includes it. Finally disconnect the authority from a healthy planner while leaving the planner connected to every worker. This last case makes it easy for a stale process to continue doing real work. A test that disconnects all network paths together may never reveal it.

Model clock drift explicitly in unit tests rather than changing wall time on a real shared host. Drive the worker's elapsed time and the authority's elapsed time separately. Include forward jumps or suspend behavior for clock sources the design claims to tolerate. A failure injection that violates the stated model can still be valuable, but classify it as testing containment under an assumption failure. A Staff+ design should explain which component fails closed, how the operator detects the condition and which recovery step restores trust.

}

Tie the evidence to an operational release gate

Choose an acceptance criterion derived from the service promise: zero successful stale mutations after a resource has acknowledged an installed epoch across the tested crash schedules. Pair it with a liveness criterion, such as the distribution of time from old planner loss to safe capacity for a representative job when a healthy quorum and sufficient eligible nodes remain. A system can pass every safety assertion by never accepting a command. It can also meet an attractive failover target by accepting commands without validating ownership. The two measurements answer different questions and should appear side by side in a launch review.

Answer the interviewer from the resource outward

All questions here are original practice. For each answer, name the protected object, the authority that granted the right and the component that actually rejects a stale mutation.

Twelve Senior Staff interview questions

Why can two healthy processes both report leadership?

Evaluates scope of election safety. I would ask which grant and interval each process is reporting. An old process may be alive, paused or isolated while a quorum grants leadership to a successor. Its local log can accurately describe the last grant it observed. A unique decision at the authority does not synchronize the beliefs of all clients. I would find the protected state and identify the last point where an old command could still change it.

Follow-up. Would an extra heartbeat remove the race? A delay immediately after that heartbeat recreates it.

Common mistake and tradeoff. Use process beliefs for diagnosis. Use durable resource decisions for exclusion.

Could a UUID be a fencing token?

Evaluates equality versus ordering. An opaque UUID can work when an authority installs the exact current UUID at the resource and every mutation checks equality atomically. A receiver that accepts any UUID it has never seen cannot tell a fresh transfer from a replay. Monotonic tokens instead allow a resource to reject values below a durable floor. Either approach needs trusted installation, resource scoping and protection against restoring old equality or floor state.

Follow-up. How would you order lineages? Install a new trusted lineage through an explicit transition, independent of random numeric order.

Common mistake and tradeoff. Random uniqueness prevents accidental collisions. It provides no chronology.

Why retain a session nonce when worker IDs are unique?

Evaluates delayed release and worker reincarnation. A unique machine identity may host successive sessions. An old release delayed through a partition can arrive after a restarted process reacquires the same object. A conditional release naming the exact session and epoch only affects its intended grant. If no grant matches, the response conveys that the release has no current effect. A retry then remains safe even if the old worker never learned about the successor.

Follow-up. Could an epoch alone suffice? Yes if it uniquely and durably identifies the grant in the full resource namespace and authentication is enforced.

Common mistake and tradeoff. Unconditional cleanup looks convenient during teardown but can delete healthy ownership.

What does an acknowledged fence actually guarantee?

Evaluates linearization and scope. The guarantee is local to the protected mutation domain and its durability model. After installation linearizes, a subsequent obsolete mutation in that domain must fail. A separate provider already processing earlier work may still act later. A pool containing several nodes may have only partly installed the new epoch. I would document the exact set of resources, the cutover event and whether previously admitted operations are drained or simply allowed to finish.

Follow-up. What evidence proves a pool is ready? A verified barrier set tied to a specific membership revision or a clearly named subset.

Common mistake and tradeoff. A grant record alone cannot prove fleet-wide installation.

Should the platform shorten leases during an incident?

Evaluates availability feedback and load. I would identify the bottleneck first. If slow renewals stem from authority saturation, shorter leases can expire more clients, induce more elections and produce a burst of barrier traffic. Shortening a lease can help if an idle failed holder unnecessarily delays takeover and there is enough headroom for variance. I would measure local renewal margins and actual time to safe capacity, apply bounded jitter and keep fencing independent of optimistic timing.

Follow-up. How would you canary? Use a small independent pool cohort and track both churn and completed safe placements.

Common mistake and tradeoff. A lower configured timeout can increase observed recovery time.

Why check allocation revision in addition to epoch?

Evaluates concurrency within one legitimate grant. The current planner may have multiple threads, retried RPCs or queued decisions based on stale observations of inventory. All carry the same valid epoch. Two commands may both try to reserve the last GPU. A compare on allocation revision and resource availability inside the mutation transaction makes at most one succeed. Idempotent retry records distinguish a repeated attempt from a different conflicting command. The three checks each close a different window.

Follow-up. What if independent allocations can commute? Use narrower resource versions where the invariant permits independent transitions.

Common mistake and tradeoff. Using epoch equality as a substitute for application concurrency control admits same-owner conflicts.

Can a gateway fence an API that accepts no epoch parameter?

Evaluates location of enforcement. A gateway can protect an authoritative local publication it completely controls. For a remote call it must also control alternative writers, outstanding requests and the remote ordering contract. If an unchecked command leaves the gateway, becomes delayed and later takes effect after takeover, the remote state may still violate the promised ordering. One approach serializes conflicting actions and waits for definitive completion before handoff. Uncertain completion then deliberately blocks progress.

Follow-up. Can a provider idempotency key solve it? Only repeated execution of the same intent, subject to provider scope and retention.

Common mistake and tradeoff. Name the exact external behavior before promising both immediate takeover and strong exclusion.

What should happen to a job already running on an unfenced GPU?

Evaluates physical versus logical ownership. Exclude the device from safe allocatable capacity until the agent establishes its current lineage, installed epoch and observed workload. Acquiring authority to plan future placements does not kill processes holding the device. A replacement can choose to adopt or drain the running workload if the tenant isolation and job contracts permit that action. Enforce admission locally at the physical resource and verify deallocation before giving it to another tenant.

Follow-up. What if the device cannot be contacted? Keep its capacity unavailable or prove isolation through an independent trusted mechanism.

Common mistake and tradeoff. Marking capacity free in a metadata row cannot clear device memory.

Can a strongly consistent read of ownership replace a resource fence?

Evaluates check-to-effect races. Take a valid strong read proving Mira is the current owner. Delay the network packet carrying her write. During the delay Noor legitimately acquires the next grant. A receiver that trusts the earlier result may now apply Mira's command. Strong reads make observations linearizable but do not freeze subsequent state changes. I would combine ownership verification and mutation in one linearizable operation, or install an enforceable downstream barrier and define its cutover precisely.

Follow-up. When is a local transaction enough? When both the grant comparison and authoritative mutation share the same transactional serialization domain.

Common mistake and tradeoff. Improving read freshness cannot repair a non-atomic compound operation.

How do you restore an allocator from yesterday's backup?

Evaluates lineage and field recovery. I would establish whether any previously issued grant can still reach a live actuator. Reusing the old counter can produce grants below durable node floors or collide with old grants. A trusted reset can change lineage, isolate prior writers and rebootstrap resources before admitting mutations. Alternatively use independent durable evidence of an upper bound on every issued epoch. Restoring the largest value found in responsive-node logs ignores messages in flight and unavailable nodes.

Follow-up. What can the fleet do during reset? Run existing isolated jobs if policy permits while withholding conflicting new admissions.

Common mistake and tradeoff. An available stale allocator can be more damaging than a temporarily unavailable one.

What service-level objective represents successful takeover?

Evaluates customer outcomes and evidence. Define time from the start of a specified failure to verified capacity sufficient for a representative job. Report acquisition, installation, reconciliation and admission stages separately. Specify the failure model and which participants must remain accessible. Pair that liveness target with an invariant measured in tests and audits: obsolete commands never succeed after the relevant fence is acknowledged. Report blocked or quarantined inventory separately so partial recovery cannot masquerade as total readiness.

Follow-up. What if a job needs the entire pool? The slowest required barrier or replacement may set the tail.

Common mistake and tradeoff. A fast election metric can conceal prolonged inability to run customer work.

How would you move pools between two independent ownership databases?

Evaluates migration design and tradeoffs. Pin each pool to a directory generation. First stop the source authority from issuing new grants for the moving pool, reconcile its acknowledged history and prepare the destination with a verified lineage or a durable high-water boundary. Then switch routing and install the destination's authority at protected nodes under a documented transfer rule. During ambiguity, clients must avoid starting a second independent grant history. I would roll out by pool, measure the handoff and test both a failed switch and a returning old authority.

Follow-up. Could both authorities temporarily issue grants? Only with a protocol establishing one order that every receiver honors.

Common mistake and tradeoff. Hashing a pool to a different shard is simple routing. Moving exclusive authority requires a recoverable protocol.

Draw two timelines: the allocator and the route table. Add the worker sessions between them. Mark Grant, Install, Apply and Reply as four distinct events. Speak through a handoff under pressure

Use the same incident at three levels of detail. The short answer states the rule. The longer answers demonstrate it under a paused worker, a partially installed handoff and a resource that performs an irreversible action.

Thirty seconds · Define fencing

Fencing prevents an obsolete owner from changing a protected resource. When ownership changes, the authority grants a new epoch. The resource durably installs that epoch and checks it atomically when applying commands. A paused worker can still wake up and send a request. Once the fence is installed, the resource rejects that request. A lease helps decide when another worker may take over. The fence determines what can still take effect.

Two minutes · Explain a stale owner to an operator

Imagine that a worker is about to switch traffic during disaster recovery. It checks its lease successfully and then pauses. Another worker takes over because the lease expires, and prepares a different routing change. When the original worker resumes, it does not jump back to the top of its function and consult the new owner. It continues from the instruction where it stopped. Its delayed request can reach the router last. The two successful lease records tell us why both workers thought they should act. They do not tell the router whose command is allowed.

I would issue a distinct epoch for each grant and authenticate it for the particular routing resource. The router stores the installed epoch durably. Its final mutation compares that epoch, checks the expected resource revision and records the request outcome. These checks prevent three different problems: stale ownership, conflicting commands from one owner and duplicate execution after a lost response. I would report takeover complete only after the router confirms the new barrier according to the contract.

If the provider cannot enforce such a fence, I would describe the actual alternatives to the operator. A known idempotent request can be retried under the same identity. A conflicting operation with an uncertain outcome may need reconciliation or isolation before promotion can safely continue. This makes the availability cost visible and tells the operator exactly what evidence would unblock the next action.

Five minutes · Defend the GPU controller

My first question is what successful failover means to a training customer. Is it having a new planner process, having permission to submit work on one node, or being able to start a complete multi-node job? These events can happen several seconds apart under normal conditions and much farther apart during a partition. I would expose the current grant, the size of the safely fenced subset and the amount of verified allocatable inventory as different observations.

A conditional grant operation lives in a replicated authority. It identifies tenant, pool, lineage, holder session and epoch. A failed response is reconciled with a stable request identity. The elected planner cannot simply write an arbitrary larger number to every node. The node verifies grant provenance and scope, then durably installs the authorized epoch. In the local placement transaction it checks the grant, checks the allocation revision and records the command identity. A device operation can be asynchronous, so the accepted state also needs a reconciliation path to observed running or failed state.

For a concrete failure, take a 32-node pool where 31 nodes installed epoch 91 and one isolated machine still has 90. The allocator can ensure that no other new grants conflict with 91. It cannot send information into an isolated machine by declaring the transfer successful. If that machine can still receive old commands, I exclude it from ready capacity. I allow the new planner to admit a job only if it fits in the fenced subset and the inventory checks succeed. A training run requiring all 32 must wait for reconciliation or a verified replacement. This is a product tradeoff about the meaning of pool readiness.

I would next estimate the operating cost. Four thousand pools with three-second renewals produce over thirteen hundred renewals per second at the mean. A network incident can align those renewals and add a surge of handoffs. I would jitter their scheduling, protect the authority from unbounded retries and bound barrier concurrency per tenant. The alert that wakes an engineer should include time to sufficient safe capacity and the age of the oldest blocked handoff. High stale-rejection counts can mean the fence is successfully containing a faulty worker. Zero rejections alone does not prove health.

Finally I would explain disaster recovery for the authority itself. A restored database may have forgotten grants the agents still enforce. Reusing a counter from the backup can lock out a good planner or revive an old one. I need a verified durable upper bound or an explicit new lineage with a trusted installation and isolation procedure. My release drill holds an old command through transfer, crashes the receiver around fence persistence, restores from a snapshot and observes the final device or routing mutation. That is how I connect a formal ownership rule to a customer-visible guarantee.

Final interview cheat sheet

  • Election. Select the next coordinator through a serialized grant.
  • Lease. Specify who measures expiry and how a late renewal is handled.
  • Epoch. Compare generations only within one resource namespace and lineage.
  • Session. A process name can recur across unrelated grants.
  • Installation. The protected resource must durably adopt the new authority.
  • Atomicity. The final state change must serialize with the fence.
  • Provenance. Only a legitimate issuer may advance a floor.
  • Revision. Concurrent requests from one valid worker can still conflict.
  • Retry identity. One command may be sent more than once.
  • Readiness. Define the membership and barrier predicate before claiming handoff.
  • Physical state. A new grant does not release a device used by an existing workload.
  • Restore. Recover high-water evidence or explicitly reset the trust lineage.
