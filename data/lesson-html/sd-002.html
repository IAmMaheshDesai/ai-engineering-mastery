01 · The ownership problem

The ownership problem: why a leader is not enough

A paused scheduler wakes up after its replacement takes over. At which exact moment must the old scheduler’s next write fail?

A production incident to imagine

Picture an AI compute platform with three scheduler replicas, a fleet of GPU nodes, and thousands of pending training jobs. Scheduler A currently assigns jobs. Its control-plane process pauses for forty seconds because the host is overloaded. The monitoring system stops receiving heartbeats and elects scheduler B. B starts assigning work. Then A resumes and still believes it owns the scheduling role. Both schedulers are healthy enough to send network requests. This is the central danger: an old owner can remain capable of acting after the rest of the system has moved on.

An equivalent disaster recovery example is a failover controller that initiates recovery in another region. If a stale controller resumes, it might issue an incompatible recovery step, overwrite a newer status, or try to reverse a promotion. Merely displaying a single leader in a dashboard does not make these side effects safe. We must define where authority is recorded, how authority changes, and how each consequential resource verifies it.

  • Leader selection chooses a candidate; exclusive authority requires an enforceable protocol.
  • A crash, long pause, delayed packet, or partition can all create stale actors.

Separate four concepts that sound similar

Leader election is the mechanism for choosing a coordinator among candidates. A lease is a time-bounded permission, generally requiring carefully defined timing assumptions. An ownership epoch is a logical generation number that changes when authority transfers. A fencing token is an ordered credential presented to a protected resource so that operations from an older generation can be rejected. These mechanisms solve related but different problems; combining them without understanding their boundaries creates false confidence.

For an interview, start by defining the safety invariant in application language: at most one authorized owner can successfully mutate the protected resource for a given ownership generation. The invariant is stronger than “at most one process thinks it is leader.” Processes can have stale beliefs. What matters is whether their operations are accepted. This is why fencing at the resource boundary is so important.

  • Safety concerns accepted effects, not subjective leader beliefs.
  • Election, lease, epoch, and fence are distinct layers.

Failure model and system boundaries

Assume crash-stop and crash-recovery failures, unpredictable message delay, duplicated requests, temporary network partitions, and processes that may pause without losing memory. A process may be alive but disconnected from the coordinator. Another process may be newly elected but unable to reach the GPU host. The system must remain safe through these situations, even if availability temporarily suffers. Arbitrary malicious behavior is outside the basic crash-fault model and requires separate authentication and threat controls.

Write down exactly which resources need protection: scheduler assignments, storage writes, cloud API calls, deployment steps, or region promotions. A token checked only by the control-plane database cannot automatically protect a downstream cloud API that does not understand it. You need a resource-side enforcement point, an intermediary with durable state, or a different application-level reconciliation protocol. This boundary is one of the most valuable observations a Staff+ engineer can make.

  • Define the failure model before choosing an algorithm.
  • Map every external side effect to its authority check.

How I Would Explain This in an Interview

I would begin by saying: a leader election protocol establishes a preferred coordinator, but it does not guarantee that an old coordinator has stopped running. In distributed systems, stale processes can resume after pauses or partitions. I therefore use a durable ownership generation and require protected resources to reject operations from obsolete generations. Leases help with availability and timely handoff, while fencing protects correctness at the point where side effects occur.

Now practice without looking: explain why a paused leader is more dangerous than a cleanly terminated leader. Then describe what you would need to verify before declaring that a new owner may safely issue commands. Your answer should mention durable ownership state, ordering, downstream enforcement, and reconciliation of uncertain operations.

Name the event that makes the promise true

Write two events on the board. At E1 the ownership service commits that B has succeeded A. At E2 the storage service installs B’s generation. A delayed request from A arrives between those two events. Which answer would be correct? Under a resource-floor design, the storage service may still accept it. The design is sound only if it acknowledges this window and B incorporates that result before declaring the resource ready. If your requirement forbids every old write starting exactly at E1, ownership and writes need a shared serialization boundary, or a revocation barrier must complete before you declare the transfer effective.

Say the invariant in a way that an engineer can turn into a test. For each protected resource, after the operation installing generation 18 commits, every later successful mutation must carry verified authority at generation 18 or higher. A request can start earlier and complete later in wall-clock time. The question is where its effect falls in the resource’s serial order. This distinction guides both transaction design and the evidence you collect after an incident.

Chapter summary

Locate the exact write that could make the old owner dangerous.

02 · Leader election

Leader election: choosing an owner safely

Two schedulers read the same expired grant. How does the coordinator make only one of their claims succeed?

Election is a replicated decision

A naive algorithm might declare the lowest-numbered live server to be leader. That rule fails when different servers have different views of who is alive. During a partition, A may see B as failed while B sees A as failed. Both can independently select themselves. The problem is not sorting candidate IDs; it is reaching a coordinated decision despite inconsistent observations.

A consensus-backed coordination service can serialize ownership changes. A candidate asks for leadership through a linearizable transaction, compare-and-swap, or consensus log entry. A majority-backed service decides which candidate wins. The winning candidate receives a generation value. Other candidates either observe the existing owner or retry after the current ownership expires or is explicitly relinquished. A client should never infer exclusive authority from a local heartbeat timer alone.

  • Local failure detectors are suspicions, not proof of death.
  • A linearizable ownership decision gives a common order.
Worked example

Three schedulers

At time zero, the coordinator stores owner=A and generation=17. A heartbeats normally. At time ten seconds, A stops responding to coordinator traffic. The coordination service eventually determines that A has not renewed its session according to its own protocol. Scheduler B and scheduler C race to claim the next generation. The service serializes their transactions; B wins and receives generation 18, while C observes that B is now owner. B can now begin actions carrying generation 18. A may still be alive, but its generation 17 must not be accepted by protected resources once generation 18 is established there.

Notice the critical ordering question. If a GPU worker has never heard of generation 18, it may accept a delayed generation 17 command. A robust design must specify when the worker learns the new floor, how that floor is persisted, and whether the new owner must first establish its generation at the resource. If the operation is destructive or non-reversible, the handoff protocol needs stronger coordination than a best-effort notification.

  • State: A/17 → B/18; C loses its claim.
  • Generation changes must be reflected where commands are enforced.

Election mechanics and split votes

In Raft, a follower that misses heartbeats may become a candidate, increment its term, vote for itself, and request votes. A candidate wins after obtaining a majority under Raft’s voting and log-freshness rules. Randomized election timeouts reduce repeated split votes. Terms order election rounds; they do not automatically fence every external resource. A newly elected leader may need to commit an entry or establish a read barrier before serving some operations safely.

For a five-voter cluster, a majority is three. If two voters become unreachable, the remaining three can elect a leader if they can communicate and meet the protocol rules. A minority partition of two cannot elect a legitimate leader. This preserves election safety but can reduce availability when the network topology prevents any majority. Avoid saying “Raft prevents two processes from thinking they are leaders”; it prevents conflicting legitimate leadership in a term under its rules, while stale beliefs may persist.

  • Raft term and application ownership epoch can be related but need not be identical.
  • Quorum availability depends on connectivity, not just machine count.

Practical interview tradeoffs

For one region with modest metadata traffic, an existing coordination service such as etcd or ZooKeeper is usually preferable to inventing a new election algorithm. A database with sufficiently strong conditional writes may also be appropriate for simple ownership records, provided its consistency and failure semantics meet the requirements. For high-rate per-request ownership changes, a centralized consensus service can become a latency bottleneck; partition ownership by resource key or batch work under longer-lived assignments.

Distinguish election from an ownership transaction

Suppose two clients both read revision 90, see an expired holder, and compute 18 as the next generation. A plain write from each would let both clients report success. Instead each submits a transaction conditioned on revision 90 and on the grant being eligible for takeover. B’s commit advances the record to revision 91. C’s comparison now fails. C rereads the current owner and waits. If B loses its response, it looks up its claim identifier before issuing another acquisition. That avoids burning through generations on retries or confusing a successful claim with a later transfer back to B.

Chapter summary

Elect a coordinator, then prove the new owner can safely act on each target.

03 · Leases

Leases: time-bounded authority and its limits

A client pauses for longer than its lease. What can the grantor reclaim, and what can still arrive at the destination?

What a lease promises

A lease grants authority for a bounded period according to an explicitly defined clock and renewal protocol. It can reduce coordination on the common path because a client may act while it believes its lease remains valid. However, the safety of such behavior depends on timing assumptions: clock drift, pause duration, network delay, and how the server defines expiration. A lease is not simply a database timestamp that all machines interpret identically.

Imagine a lease with a nominal duration of thirty seconds. The holder renews every ten seconds. If renewal stops, the service can eventually reassign ownership. But a client paused for forty seconds might wake with stale local state, and an unsynchronized clock can make two parties disagree about whether a lease has expired. A robust client must stop acting when it cannot establish current authority; a resource-side fence protects against the cases where it fails to stop.

  • Lease expiration is a protocol decision, not proof that the old process is dead.
  • Fencing reduces dependence on perfect clock behavior.
Worked example

A long garbage collection pause

Worker A acquires lease L with generation 41 and begins preparing a model checkpoint. At time five seconds, A experiences a forty-five-second stop-the-world pause. The coordinator no longer receives renewals and eventually allows B to acquire generation 42. B starts checkpoint work. A resumes, reads its in-memory lease object, and attempts to upload an old manifest. If storage blindly accepts the upload, the checkpoint can regress even though the lease service correctly transferred ownership.

Now add a resource-side rule: the checkpoint metadata service stores the highest accepted generation per checkpoint namespace. B first establishes generation 42 through an atomic operation. Any subsequent A/41 manifest write is rejected. The safety property now depends on a durable monotonic comparison at the protected resource. If A writes directly to an object store without this check, the metadata fence may not cover the underlying blob, so use immutable content-addressed blobs and atomically publish only the fenced manifest.

  • Lease handoff and resource fencing must compose.
  • Immutable blobs plus fenced manifest publication simplify recovery.

Clock discipline and conservative renewal

A practical lease client renews well before expiry and stops initiating new operations if renewal becomes uncertain. A monotonic local clock is preferable for measuring elapsed time because wall clocks can jump due to synchronization or administrative changes. Nevertheless, monotonic clocks on different machines are not globally comparable. Design around a server-authoritative expiration policy, bounded assumptions if needed, and explicit acknowledgment of uncertainty.

If a service grants a thirty-second lease, do not assume a client can safely execute a thirty-second uninterruptible external call right up to the deadline. The call may complete after expiration. Either the destination validates an ownership token at commit time, or the operation must be designed to be safely retryable and reconciled. For destructive actions, use approval, fencing, and state-machine preconditions rather than relying on a local timer alone.

  • Use monotonic time for local elapsed intervals.
  • External operations can outlive their initiating lease.

Lease design decisions

Choose lease duration by balancing failure recovery time against renewal overhead and false failovers. Short leases improve potential takeover latency but increase heartbeat traffic and sensitivity to transient pauses. Long leases reduce churn but delay legitimate recovery. The correct duration follows measured tail latency, process pause distributions, network conditions, and the cost of temporary unavailability.

Calculate a conservative local deadline

Suppose a grant lasts ten server-clock seconds. For this calculation alone, assume the server clock can run one percent fast and the client clock one percent slow, both relative to real elapsed time, including suspension. The shortest real grant lasts ten divided by 1.01 seconds. Over that interval the slow client measures about 9.80 seconds. Starting its timer just before sending the request and choosing a local budget of 9.5 seconds leaves additional margin. A reply that arrives after the local deadline conveys no usable client time. Starting the budget on receipt instead would silently add the entire return-path delay.

This arithmetic relies on the stated clock bounds and time source. A clock that freezes while a virtual machine is suspended breaks the premise. Even a perfect local deadline cannot recall a request already in the network. For a manifest update I therefore put the decisive comparison inside the storage commit. For an external actuator with no conditional write I would investigate physical isolation or an authoritative stop acknowledgment before offering exclusive handoff.

Chapter summary

Measure elapsed lease time conservatively and fence delayed requests at commit.

04 · Fencing tokens

Fencing tokens: stopping stale writers

A write passes its permission check just before a new generation arrives. Which transaction boundary closes the race?

The monotonic-token rule

A fencing token is a monotonically increasing value associated with successive ownership grants. A protected resource remembers the highest generation it has accepted and rejects commands with older tokens. The rule is conceptually simple: if incoming generation is less than the recorded floor, reject the command. For same-generation commands, the resource still needs operation-specific idempotency and ordering rules; a fence is not a substitute for them.

The ordering value must come from a durable, correctly serialized authority. Random UUIDs are excellent for identifying operations, but they do not by themselves establish which owner is newer. A local process counter is also insufficient because two candidates could independently generate the same or conflicting values. Use a consensus-backed counter, a linearizable compare-and-swap record, or another authority that can establish an unambiguous total order for the protected namespace.

  • Monotonic means newer grants compare greater than older grants.
  • A UUID identifies an operation but is not an ordered fencing token.
Worked example

Stale file writer

At generation 7, controller A writes the current desired configuration. A loses connectivity and controller B receives generation 8. B writes configuration version B. A later resumes and attempts to write version A using generation 7. A resource with a durable highest-generation value of 8 rejects the stale write. Without that check, the old configuration can overwrite the new one despite perfectly functioning leader election.

What if A’s generation-7 write arrives before B’s first generation-8 write? If the resource has not learned generation 8, it may accept the old command. A strong handoff protocol can require B to establish its generation at the resource before acting, or route all mutations through a gate that atomically checks current ownership. This nuance is often missed. A fencing token is effective only when the protected resource enforces the right ordering at the right time.

  • Reject generation 7 after generation 8 has been established.
  • Handoff ordering and enforcement placement matter.

Correct implementation and concurrency

Implement the check and the protected mutation as one atomic transaction or under an equivalent linearizable serialization boundary. A read-then-write check is unsafe: two requests can both read the same floor and then write conflicting values. In a database, use a conditional update or transaction with appropriate isolation. In a service, serialize per-resource commands and persist the floor before acknowledging. If the floor is lost on restart, stale commands may become valid again, so its durability is part of the correctness argument.

One safe simplified pattern is a conditional operation that verifies generation >= stored_generation, applies the domain-specific precondition, updates the stored generation, and records the operation ID atomically. A second command with the same generation may be allowed only if it is the same idempotent operation or follows the owner’s ordering policy. The greater-than comparison alone does not serialize all commands issued by one owner.

  • Atomic fence check plus mutation is required.
  • Store operation IDs for retry deduplication.
PSEUDOCODE
# Pseudocode. One durable transaction for this resource.
with resource.transaction() as tx:
    tx.verify_grant(caller, resource.id, epoch)
    require(epoch == tx.installed_epoch)
    prior = tx.lookup(request_id)
    if prior is not None:
        require(prior.payload_hash == hash_payload(command))
        return prior.result
    require(command.expected_version == tx.version)
    result = tx.apply_and_increment_version(command)
    tx.remember(request_id, hash_payload(command), result)
    return result

Where fences cannot be applied directly

Some cloud APIs, GPU drivers, and external services do not accept fencing tokens. Do not pretend that adding a token field to your own request magically protects those systems. Introduce a controlled gateway that serializes commands, use conditional version updates where the API supports them, or design reconciliation and compensation around ambiguous effects. For operations such as irreversible notifications, payments, or region promotions, carefully define what can be retried and what requires human review.

Trace a check that races a commit

At revision 70, a handler reads floor 7 and approves A’s write. Before that handler updates the configuration, B commits floor 8 and publishes a new configuration at revision 72. If the first handler now issues an unconditional update, the resource regresses. A transaction with a row lock held through commit, or a conditional mutation against revision 70, closes the gap. With the conditional design the stale mutation affects zero rows. The handler rereads the floor, classifies the operation as stale, and returns that result. Retrying the same write with B’s epoch would improperly manufacture authority.

Chapter summary

Make installation and mutation obey a single durable order at the target.

05 · Ownership epochs

Ownership epochs: versioning authority over time

Shard S17 moves from A to B and back to A. How can a worker distinguish the two grants to A?

Epochs as logical time

An ownership epoch is a logical period during which a particular owner is authorized to coordinate a resource. Each transfer advances the epoch. Epochs allow the system to distinguish commands issued under old authority from those issued under new authority without relying on synchronized wall clocks. An epoch may be represented as an integer, a compound generation and sequence number, or a version stored in a coordination service.

An epoch is not necessarily a Raft term. A single Raft group can elect a new leader while application ownership of a shard remains unchanged, or application ownership can move several times during one Raft term. Likewise, a database row version might advance for ordinary metadata edits that are not ownership transfers. Name each counter according to its semantics so that engineers do not accidentally compare incompatible values.

  • Protocol term, ownership epoch, and record version serve different purposes.
  • Use stable namespaces and document the ordering scope.
Worked example

Shard reassignment

Shard S17 is owned by scheduler A in epoch 105. The coordinator decides to rebalance because A is overloaded. It commits a new record assigning S17 to scheduler B in epoch 106. B retrieves the pending jobs, reconstructs in-flight state, and establishes epoch 106 at the execution agents. An old A command carrying epoch 105 arrives after B starts. The agents reject it as stale. B then resumes dispatching jobs using the new epoch and new per-job operation IDs.

Now suppose B crashes during recovery. The coordinator transfers S17 to C with epoch 107. C must reconstruct the state of jobs whose outcomes are ambiguous. It should not assume that every command sent by B failed. Instead it queries workers, reads durable job states, and uses idempotent command identifiers to decide whether to retry, continue, or compensate. The epoch fences ownership; it does not resolve every ambiguous business effect.

  • Epoch progression: A/105 → B/106 → C/107.
  • Recovery requires durable operation state in addition to ownership state.

ABA and token reuse

The ABA problem appears when a value changes from A to B and back to A, making a naive equality check mistake the final A for the original A. Owner identity alone is therefore insufficient. A may own the shard in epoch 11, lose it in epoch 12, and regain it in epoch 13. An old command from epoch 11 must not become valid just because the owner ID again says A.

Never reset a fencing counter during ordinary failover. If a coordination store is restored from an old snapshot, generation reuse becomes a serious risk. Define a recovery strategy that preserves monotonicity across restoration, possibly using a higher-level incarnation ID and an authoritative durable generation. A compound token may compare lexicographically only if every participant agrees on the ordering and the authority guarantees uniqueness.

  • Owner identity is not a generation.
  • Protect monotonicity across backup restoration and disaster recovery.

How I Would Explain This in an Interview

I would say that an ownership epoch is a logical generation of authority. Every handoff increments the generation, and commands carry that generation to downstream resources. The generation lets us distinguish an old controller from a new controller even if both are alive. We persist it durably and enforce it at the resource boundary. This is particularly useful for long-running workflows because a controller may pause or lose connectivity and later resume with obsolete state.

Handle deletion and recreation of a namespace

A tenant deletes queue blue while a request for its old incarnation is delayed. A day later another queue called blue is created and its local counter starts at one. If the endpoint accepts only a name and an integer, a delayed command from generation fifty may appear newer than every valid writer. Give the recreated queue a fresh immutable resource identity. Bind each grant to that identity and reject tokens from the previous incarnation before comparing generation numbers. A random identifier works well for separating lifetimes because equality is enough there. Within one lifetime, ordered generations still tell the receiver which handoff is newer.

Chapter summary

Bind a generation to its resource identity and incarnation.

06 · Designing a safe ownership handoff protocol

Designing a safe ownership handoff protocol

A provider accepts a database promotion, but its operation handle disappears with the worker. Trace the handoff from intent to reconciliation.

The handoff state machine

Define explicit states such as UNASSIGNED, ACTIVE, DRAINING, TRANSFERRING, and RECOVERING. A controller may initiate a graceful handoff by marking the shard DRAINING, stopping new work, waiting for in-flight commands, and then committing a new owner and epoch. A forced failover cannot wait for an unreachable old owner. It must establish a new generation at protected resources and recover outstanding operations by reading durable state.

A durable coordinator record should include resource ID, owner ID, generation, lease or session metadata, desired state, and last transition ID. Each transition is conditional on the expected prior version. A new owner should not issue destructive commands until it has established the appropriate fencing floor at the resource and reconstructed the last known durable workflow state. For multi-resource workflows, a single atomic fence across all destinations may not exist; model the sequence explicitly.

  • Use explicit handoff states and compare-and-swap transitions.
  • Different resources may require separate fencing and recovery.
Worked example

Region failover controller

In a hypothetical OCI-style recovery plan, controller A owns epoch 220 and records its client-generated key K1 with the intended database promotion before submitting it. The provider accepts the call and returns handle O1, but A crashes before saving O1. Controller B claims epoch 221, fences new submissions from A at the orchestration gateway, and reloads K1. Under a provider contract that atomically deduplicates by tenant and key and returns the original handle on replay, B resubmits the identical request with K1. It recovers O1, waits for confirmed completion, and advances the plan using a conditional update. A retry carrying a fresh key could launch a second operation.

Crucially, the external database service may not understand epoch 221. The orchestration gateway must prevent new stale submissions, but a previously accepted operation may still finish. B cannot simply roll it back. The workflow needs preconditions, a durable operation journal, state reconciliation, and compensation only where safe. This is an example of end-to-end reasoning that distinguishes a senior architect from someone who merely deploys a lock service.

  • Persist operation ID before making the external call.
  • A fence cannot cancel work already accepted by an external service.

Handoff pseudocode

The coordinator can use a linearizable conditional transaction to assign the next generation. The worker must establish that generation at each protected resource and recover ambiguous operations before becoming fully active. If establishment fails, the system should remain in RECOVERING or DEGRADED rather than announce success. A status page must reflect observed readiness, not merely successful leader election.

Observe that this is not a distributed transaction across every service. It is a carefully sequenced state machine with durable checkpoints and idempotent or reconcilable effects. In a real design, the coordinator itself must be highly available, and the protected resources must survive their own restarts without forgetting the accepted generation.

PSEUDOCODE
# Pseudocode. A superseded grant cannot activate a shard.
claim = coordinator.claim_if_eligible(shard, version, claim_id)
for target in claim.required_targets:
    target.install_verified_floor(claim)
    journal.record_ack(claim.id, target.id)
reconcile_accepted_operations(claim)
return coordinator.activate_if_current_and_ready(claim)

Failure matrix

Consider four failure points. Before the ownership transaction commits, the candidate has no new authority and must recheck the prior grant before retrying. After the transaction commits but before the new owner fences workers, the system may temporarily refuse new work; do not promise instantaneous availability. After fencing but before state reconstruction, old commands are rejected, while the new owner must discover what already happened. After activation, a new crash simply begins another generation and recovery cycle.

When reviewing this matrix aloud, identify which property you prioritize at each stage. A correct system may pause dispatch rather than risk duplicate execution. Explain the expected recovery time and the observability needed to tell operators whether the system is blocked on coordination, fencing propagation, or external reconciliation.

Recover when deduplication has a retention limit

The provider keeps idempotency records for twenty-four hours. An outage lasts thirty hours. Replaying K1 now falls outside the contract, so the recovery path has to change. A completed audit event bound to K1 and the correct database incarnation may establish success. A read showing only that Phoenix serves traffic is weaker because a separate operator could have promoted it. If the evidence cannot identify the original action, put the plan in an explicit outcome-unknown state. Show the operator which resource, intent, key, and observations are available. Continue independent recovery steps only when they cannot conflict with that unresolved action.

Chapter summary

Resolve ambiguous external work before advancing a dependent recovery step.

07 · Capacity, latency, and failure mathematics

Capacity, latency, and failure mathematics

Fifty thousand owners renew every ten seconds. What changes when twenty thousand of them renew together?

Quorum and availability arithmetic

For N voting replicas under majority consensus, the quorum is floor(N/2)+1. Three replicas require two votes and tolerate one failed voter if the remaining two communicate. Five require three and tolerate two. Seven require four and tolerate three. This tolerance describes crash failures under favorable connectivity, not guaranteed availability during arbitrary partitions. Adding voters increases fault tolerance but may increase coordination and operational costs.

Assume a five-replica coordination group distributed across three zones as 2-2-1. If the one-voter zone fails, four remain and quorum is possible. If one of the two-voter zones fails, three remain and quorum is still possible. But if two zones fail, only one or two remain, so ownership changes stop. A Staff+ design should also consider correlated network failure, not merely independent host failure probabilities.

  • Quorum(N) = floor(N/2) + 1.
  • Quorum math does not replace failure-domain placement analysis.

Lease renewal traffic and capacity

Imagine 50,000 active shard owners, each renewing every ten seconds. That is approximately 5,000 renewals per second, before retries, elections, and reads. If each renewal is a separate consensus write, the coordinator could become expensive. Options include session-level leases covering many shards, renewal batching, watch-based observation, partitioning ownership across multiple coordination groups, and reducing renewal frequency when recovery requirements allow.

Now suppose each lease lasts thirty seconds and the owner renews every ten seconds. There are nominally three opportunities per lease interval, but this is not a proof of safe operation under arbitrary pauses. Measure p99.9 renewal latency and process pause distributions, and choose a margin that accounts for them. Then make downstream safety independent of a perfectly timed renewal by enforcing epochs and fences.

  • 50,000 / 10 seconds = 5,000 renewals per second.
  • Batching changes load but must preserve ownership semantics.

Recovery time budget

Consider a hypothetical requirement that a scheduler shard recover within sixty seconds. Allocate fifteen seconds for detecting lost renewals, five seconds for coordination and election, ten seconds for fencing propagation, twenty seconds for reconstructing durable work, and ten seconds for validation and margin. These are illustrative budgets, not measured promises. The actual recovery time is the sum of dependent critical-path stages, while independent tasks may overlap.

A useful interview move is to ask whether the sixty-second target applies to ownership transfer, first successful new assignment, or complete recovery of all in-flight jobs. Those are different milestones. If the user-facing SLO is about first successful scheduling, you can prioritize recovering high-value queues before bulk historical reconciliation. If correctness requires verifying a destructive external operation, recovery may take longer, and the system should expose that limitation honestly.

  • Define what “recovered” means before quoting RTO.
  • Measure end-to-end failover, not only election latency.

Hotspots and scaling architecture

If all resources share one global owner, election is simple but the leader can become a bottleneck and failure blast radius grows. If each resource independently elects an owner, metadata overhead and complexity can explode. A middle ground is consistent shard partitioning with a bounded number of ownership records and stable worker agents. Each shard has one active coordinator and its own epoch, allowing independent failover and horizontal scale.

At Staff+ level, justify the sharding key. GPU topology, locality, tenant isolation, and placement constraints may matter more than even shard counts. Avoid moving ownership too frequently because handoffs require reconciliation and cache warming. Observe the system under skewed workload, not just average throughput. Measure ownership churn, stale-command rejection, and recovery queue depth as leading indicators of control-plane instability.

Budget for correlated renewal traffic

Fifty thousand owners renewing every ten seconds produce five thousand renewals per second on average. Suppose a host outage synchronizes twenty thousand renewals into the same half second. Those renewals alone briefly demand forty thousand requests per second. At a service capacity of ten thousand per second, five thousand complete within that half second and fifteen thousand remain queued, even before normal traffic arrives. Retries at the front of that queue make the original deadline less likely to be met. Randomize renewal phases, cap retry concurrency, and reserve admission capacity for grants approaching expiry. During a load test, measure remaining lease time at completion as well as requests served.

08 · Production reliability, security, and observability

Production reliability, security, and observability

A worker correctly rejects epoch 80, restarts, then accepts it. Which durable record should have survived?

Metrics that reveal ownership bugs

Instrument election count, election duration, active-owner cardinality, lease renewal latency, renewal failures, epoch progression, rejected stale commands, fencing-establishment latency, and reconciliation backlog. Each metric answers a different question. Election count alone cannot tell you whether resources are protected. A surge in stale-command rejections may indicate slow shutdown, network partitions, or clients retaining old credentials. A backlog of ambiguous operations may reveal an external dependency that is not safely idempotent.

Trace every ownership transition with a correlation ID, resource ID, old owner, new owner, epoch, and reason. Propagate operation IDs through downstream API calls. Do not log sensitive credentials or entire customer payloads. For incident analysis, you want a timeline showing when ownership changed, when the fence was established, when an old command was rejected, and when the new owner became operational.

  • Measure enforcement and recovery, not only leader election.
  • Trace ownership epochs across service boundaries.

Security and authority

Fencing tokens are ordering evidence, not authentication credentials. A malicious actor who can submit arbitrary large epochs could bypass a naive comparison unless the resource authenticates the caller and validates token provenance. Use mutually authenticated service identities, scoped authorization, and a trusted issuer for generations. Protect coordinator writes with least-privilege permissions and audit every forced transfer.

In multi-tenant AI infrastructure, ensure a token for tenant A cannot authorize operations on tenant B’s GPU reservation. Bind the token to a resource namespace and validate that namespace. If a gateway is the enforcement point, its own high availability and durable state become part of the threat and failure model. Consider compromised workers separately from ordinary stale workers: crash-fault fencing alone is not a Byzantine security mechanism.

  • A fence is not a bearer credential by default.
  • Bind authority to resource scope and authenticated identity.

Failure injection test plan

Create tests that pause an owner after it obtains a lease, partition it from the coordinator while leaving its connection to workers intact, delay its outgoing command, and then elect a new owner. Verify that the old command cannot change protected state after the new generation is established. Restart a worker after it has accepted a high generation and verify that it does not forget the floor. Simulate duplicate operation IDs and confirm the result is returned without reapplying the side effect.

Also test coordinator restore from backup, forced region failover, clock jumps, and retry storms. A particularly revealing test pauses the old leader immediately before a destructive external call, performs a handoff, then resumes the old leader. If the external API cannot fence the operation, document the remaining risk and mitigation. Chaos testing should validate stated invariants, not merely whether a dashboard turns green again.

  • Inject stale-owner scenarios intentionally.
  • Test durable fence floors after resource restart.

Operational playbook

When the system reports conflicting ownership, first determine whether the conflict is in leader belief or in accepted resource effects. Inspect coordinator history, resource-side generation floors, and operation journals. Do not manually reset epochs to make the system appear healthy. If the coordinator has lost durable history, isolate dangerous mutations until a safe monotonic recovery path is established.

Investigate a rejection after a resource restart

At 09:10 the coordinator reports epoch 81 and a worker rejects a command from epoch 80. That is expected if the worker installed 81. At 09:12 the worker restarts and accepts a second command from 80. Look for the transaction that durably installed 81, the identity of the disk mounted after restart, and the origin of the command. A replay trace containing only timestamps cannot establish the worker’s serialization order. Store its durable mutation sequence, resource incarnation and operation key alongside each accepted transition. Recovery should refuse writes until the agent has restored its floor and reconciled its reservation state.

09 · AI infrastructure applications

AI infrastructure applications: schedulers, agents, and checkpoints

Compare the point of enforcement for a GPU reservation, an agent tool call, and a checkpoint publication.

GPU scheduler ownership

An AI training platform may have multiple scheduler replicas and thousands of GPU worker agents. The control plane assigns jobs, maintains reservations, and reacts to node failures. Use consensus-backed ownership for scheduler shards and an epoch per shard or resource group. A worker agent validates the scheduler generation before accepting a new reservation. Job IDs and command IDs provide deduplication. A lease lets the platform detect failed schedulers and initiate a handoff.

The hard part is not electing a leader. It is reconciling jobs that may already be running. Killing every job during an election wastes expensive accelerator time. A stronger design reconstructs reservations from worker reports, preserves valid running jobs, and reassigns only work whose ownership is truly lost. For multi-node training jobs, placement and gang scheduling may require an additional atomic or staged reservation protocol. Fencing prevents stale dispatch; it does not automatically solve distributed gang scheduling.

  • Separate scheduler ownership from job execution ownership.
  • Avoid needless termination of healthy expensive workloads.

Agent execution and durable workflows

An AI agent may execute a workflow that lasts minutes or hours, calling tools that change real-world state. Multiple workers can race to resume the same workflow after a timeout. Give each workflow execution an ownership generation and a durable operation journal. Before issuing a tool call, persist an operation ID and intended action. If the worker crashes after the call, the successor queries the tool or uses its idempotency key rather than blindly repeating the action.

A stale agent worker might still attempt a tool call after another worker has resumed the workflow. A gateway can enforce workflow epoch and operation preconditions. But if the tool has already accepted an irreversible action, a new owner must reconcile rather than assume cancellation. This is the same principle as disaster recovery orchestration: ownership transfer protects new decisions; durable execution handles uncertain effects.

  • Workflow ownership and tool idempotency are complementary.
  • A new owner must recover, not simply restart from scratch.

Checkpoint publishing and model serving

In distributed training, checkpoint writers may run for minutes and upload large immutable blobs. Use content-addressed object names and a small authoritative manifest that references a complete checkpoint. Fence manifest publication by generation and validate expected training step. This avoids allowing a stale writer to replace the latest checkpoint pointer. The blob uploads themselves may finish after lease expiry without compromising correctness if unreferenced blobs are harmless and eventually garbage collected.

For model serving, ownership epochs can protect routing configuration or model deployment generation. A stale rollout controller must not restore an older traffic split after a new rollout takes effect. However, data-plane requests should not synchronously consult consensus on every inference request. Push signed or authenticated versioned configuration to serving nodes and use local validation and bounded propagation strategies. This preserves high-throughput serving while keeping control-plane changes ordered.

  • Fence publication points, not necessarily every immutable data write.
  • Keep consensus off latency-critical inference request paths.

Company relevance as engineering preparation

OpenAI’s published Kubernetes scaling account gives us a concrete control-plane load example. Anthropic’s writing on agents identifies tool interaction as a consequential boundary. Meta describes interruptions during large training runs, NVIDIA documents checkpoint recovery, and Google’s Chubby paper describes advisory locking. The research notes connect each observation to a separate design exercise. All five exercises are original practice.

A serving rollout that races a rollback

Suppose rollout 24 moves ten percent of inference traffic to model M2. Elevated error rates cause a new controller to roll traffic back to M1 under revision 25. One serving node receives revision 25 first, then a delayed revision 24. It compares the revision and publisher grant for the same routing namespace, keeps 25, and acknowledges its applied revision. The payload for a rollback can reference an older model while the configuration revision moves forward. A restart must reload a sufficiently current configuration before admitting traffic. For an urgent safety rollback, route around nodes that have yet to acknowledge the required revision. Fleet-wide activation latency and ordinary request latency now have separate budgets.

10 · Complete Senior Staff architecture exercise

Complete Senior Staff architecture exercise

Design safe placement for 10,000 GPUs across three zones. Decide which devices can reopen when some workers cannot acknowledge the handoff.

Problem and requirements

Design a scheduling control plane for a hypothetical fleet of 10,000 GPUs across three availability zones. The platform supports long-running training jobs and short interactive jobs. It must survive one zone failure without double-assigning a GPU, recover scheduling authority for a shard within sixty seconds under defined conditions, and provide auditable ownership transitions. Assume a small coordination cluster, horizontally scalable scheduler shards, and GPU node agents that can enforce generation checks.

Clarify what double assignment means. Two scheduler processes may both send a command, but only one valid reservation should be accepted by the worker for a given resource and allocation generation. Clarify whether already running jobs must continue through control-plane failover; assume yes when worker health is unaffected. Clarify whether the platform guarantees that every training job runs exactly once; it does not, because process crashes and external effects require checkpointing, deduplication, and recovery semantics.

  • Safety: no conflicting accepted GPU reservations.
  • Availability: restore new dispatch under specified failure conditions.

Architecture and APIs

Use five coordination voters spread across three zones, scheduler replicas assigned to shards, a durable job metadata store, a reservation ledger, and GPU worker agents. Each shard has a coordination record with owner ID, epoch, and session. A worker agent stores the highest accepted epoch for each relevant scheduling namespace and enforces conditional reservation state transitions. The scheduler records an operation ID before dispatch and reconciles outcomes after timeouts.

The core APIs might be ClaimShard(shardId, expectedVersion), EstablishEpoch(shardId, epoch), ReserveGpu(gpuId, jobId, operationId, epoch, expectedState), GetReservation(gpuId), and ReportWorkerState(workerId). All mutating operations must authenticate the caller and validate the resource namespace. The worker should reject stale epochs and return the recorded result for a matching duplicate operation; it should also reject incompatible same-epoch reservations based on reservation state.

  • Control plane: ownership and desired state.
  • Data plane: worker-local execution and validated reservations.

Normal execution and failover timeline

In normal operation, scheduler B holds shard S17 epoch 106. It selects a job, writes the intended reservation operation to the durable ledger, and sends the worker a request with epoch 106 and an operation ID. The worker atomically checks its epoch floor and reservation state, persists the accepted reservation, and replies. The scheduler updates the ledger and reports the job as assigned. If the reply is lost, the scheduler queries by operation ID instead of issuing a fresh conflicting reservation.

During failover, B becomes unreachable. After session expiry, scheduler C claims epoch 107 through the coordination service. C establishes epoch 107 with worker agents before issuing new reservations, then reads the durable ledger and queries workers for ambiguous operations. Existing healthy training jobs remain running under their accepted reservation records. New work is dispatched only after the shard reaches ACTIVE. If a worker is unreachable, its GPUs remain quarantined from reassignment until the platform can establish safe ownership or use a documented failure policy.

  • Persist intent before dispatch; reconcile uncertain outcomes.
  • Do not reallocate unreachable GPUs without a safe policy.

Scale, security, and cost analysis

Assume each GPU runs one primary allocation and scheduling decisions average two per GPU per hour. That is 20,000 reservation changes per hour, about 5.6 per second on average; bursts can be far higher during mass restarts. Control-plane sizing should use burst and tail measurements rather than average rate. If 500 shards renew sessions every ten seconds, that is fifty renewals per second, much cheaper than 10,000 independent leases. The shard count is illustrative and should be tuned to locality and hot-spot behavior.

Use authorization scopes that bind scheduler identity, shard, and epoch. Audit forced transfers and protect the coordinator from accidental mass reassignment. Track scheduling latency, rejected stale commands, renewal failures, reservation conflicts, and recovery time. Define separate SLOs for scheduling availability and existing-job continuity. A cost-aware design preserves running GPU workloads during transient control-plane outages instead of restarting expensive training jobs unnecessarily.

  • Average assignment rate is not peak recovery load.
  • Protect expensive running work during control-plane disruption.

Architecture defense: the interviewer challenges you

Question: Why not put every reservation in one global Raft log? Answer: that offers a straightforward serialization point but may create unnecessary latency, operational coupling, and a large failure blast radius. I would shard ownership and keep worker-local reservation enforcement, while using a durable metadata store for cross-shard visibility. Question: What if a worker restarts and forgets its epoch? Answer: the worker must persist the accepted floor or recover it from an authoritative service before accepting commands. Question: What if the new scheduler cannot reach a worker? Answer: quarantine that resource rather than risk double assignment.

Question: Can a five-node consensus group guarantee sixty-second recovery? Answer: no. It provides a foundation for ordered ownership, but end-to-end recovery includes detection, election, fencing propagation, reconciliation, and external dependencies. I would define a measured recovery SLO, test failures at each stage, and expose degraded states. This kind of explicit qualification is a strength, not a weakness, in a Senior Staff interview.

Defend the admission boundary during partial recovery

The product owner wants all healthy GPUs available within sixty seconds. The reliability owner wants a proof that no customer ever shares an exclusive GPU. Ask whether a powered-on host with an unreachable agent counts as healthy. Suppose eighty of a thousand workers cannot acknowledge the fence. Mark those eighty unavailable to new placements. The other nine hundred twenty can reopen after their floors and reservations reconcile if the placement ledger supports partial readiness. A gang job spanning both groups must wait or select an entirely eligible placement. Report usable capacity and time to the first safe placement separately from time to restore the entire pool.

Persist a grant row keyed by shard and immutable incarnation, a reservation row keyed by physical GPU and device incarnation, and an intent row keyed by tenant and client request identifier. Enforce uniqueness of an active exclusive reservation at the GPU boundary, even when two independent shards submit valid commands. A shard split changes the mapping of GPUs to scheduling authorities. Freeze admissions for the moving range, publish the mapping version, install the new binding at each agent, reconcile existing allocations, and reopen the range. Dropping the old mapping before the binding reaches a node creates an interval in which two namespaces both appear legitimate.

Measure the fraction of eligible shard recoveries reaching the first safe placement within sixty seconds over thirty days. Classify causes of missed targets, and report quorum loss and unavailable hosts as separate impact counts even if the narrower recovery objective excludes them. Introduce the design on a small pool, compare shadow decisions against the actual admission log, and require an evidence trail for every apparent conflict. Once a pool enforces generations, a software rollback must continue honoring its durable floor. Rolling back an application binary cannot roll back authority already granted.

11 · Interview masterclass

Interview masterclass: explain and defend the design

Practice the short explanation, then open each interview answer after you have defended your own design.

Thirty-second explanation

Leader election chooses which process should coordinate a resource, but a stale process can continue running after losing leadership. Leases help detect failures and transfer authority. Ownership epochs assign a new logical generation to each handoff. Fencing tokens carry that generation to protected resources, which reject commands from older owners. Together with durable operation IDs and reconciliation, these mechanisms let a control plane recover from crashes without accepting conflicting side effects.

Two-minute explanation

When I design a distributed controller, I start with the safety invariant: only commands from the current authorized generation may mutate a protected resource. I use a coordination service with linearizable ownership transitions to elect an owner and issue a monotonically increasing epoch. The owner holds a renewable session or lease, but I do not rely on the lease alone for correctness. A paused or partitioned old owner may resume and send commands after the lease has expired.

To prevent that, I place a fencing check at the resource boundary. Each command carries the epoch, and the resource durably remembers the highest generation it has accepted. The check and mutation must be atomic. I also use operation IDs for idempotent retries and a durable workflow journal to recover calls whose outcomes are uncertain. During failover, the new owner establishes its epoch, reconciles in-flight operations, and only then resumes normal work. This pattern applies to GPU schedulers, agent execution, and disaster recovery orchestration.

Five-minute explanation: the architectural narrative

I would open by separating coordination from side effects. A consensus service can decide that scheduler B owns shard S17 in epoch 106, but it cannot forcibly stop scheduler A from sending a packet. This distinction is the root of stale-owner bugs. The lease provides a failure-detection and renewal mechanism, while the epoch provides logical ordering. The resource-side fence is where we enforce the invariant. For a worker agent, a conditional transaction checks that the epoch is current and the reservation state is compatible before accepting an assignment.

I would then draw a timeline: A owns epoch 105, pauses, B claims epoch 106, B establishes the new floor, and A resumes with an old command. The worker rejects A. Next I would explain the harder case: an operation already accepted before the handoff may finish afterward. A fence does not cancel it. Therefore we persist operation intent and identifiers before external calls, query actual resource state during recovery, and use idempotent retries or compensation. For long-running GPU jobs, we preserve healthy executions rather than restarting them unnecessarily.

Finally, I would discuss tradeoffs. Short leases speed takeover but increase churn and renewal load. A global leader simplifies serialization but limits scale. Sharded ownership improves availability and throughput at the cost of more complex reconciliation. I would select the design based on failure domains, recovery objectives, consistency requirements, and the ability of downstream systems to enforce fences. I would validate it with chaos tests that pause leaders, partition networks, delay commands, and restart workers. The goal is not just to elect a leader quickly; it is to maintain correctness while restoring useful service.

I would ask the interviewer to choose the next failure. Suppose the worker crashes just after installing the new floor. A successful acknowledgment means that the floor survives the crash. A missing acknowledgment leaves two possible outcomes. The controller retries installation of the same verified grant and reads the resulting floor. An equal value confirms installation, a greater one means this claimant has already lost the race, and an unreachable worker remains unavailable for new admissions. None of those branches requires terminating every running job.

Now consider the business cost. If the worker hosts eight GPUs near the end of a long training step, an unnecessary restart throws away useful computation and may interrupt peers. Continuing their accepted reservation while withholding new placements is a defensible compromise. I would expose the number of working devices, the number accepting new reservations, and the oldest unresolved operation. An executive can then see customer impact while the on-call engineer can see which part of recovery still blocks progress.

Twelve original Senior Staff interview questions — part one

Question 1: Why does leader election not guarantee exclusive execution?

Evaluation: distinguish process belief from accepted effects. Strong answer: old leaders can remain alive or paused; enforce generations at resources. Follow-up: what if the old command was already accepted? Reconcile the effect. Common mistake: assuming a lease instantly kills a process. Draw the old request in the network before the election starts. If the target commits it before installing the new generation, the successor must account for that committed result. If it arrives after installation, reject it. Placing the boundary here allows an available target to explain both outcomes.

Question 2: What makes a fencing token safe?

Evaluation: monotonic issuance, durable comparison, and atomic enforcement. Strong answer: use a serialized authority and atomic resource-side check. Follow-up: what happens after coordinator backup restore? Preserve generation monotonicity. Common mistake: using a random UUID as an ordered token. A restore that might reuse generation 18 must stay isolated until authority is re-established. Recover a strictly greater generation from trustworthy durable evidence or provision a new incarnation and install it at every participating destination. A faster restore without that barrier can resurrect a previously valid writer.

Question 3: How would you choose lease duration?

Evaluation: quantitative reasoning. Strong answer: measure tail renewal latency, pauses, false failovers, and recovery objectives; choose margin and test. Follow-up: can a lease guarantee a long external call finishes safely? No, use fencing or reconciliation. Common mistake: assuming fixed timing is universally safe. Try the proposed duration against a recorded overload event. Count how many owners lose authority together and add the time required to install successor floors. Reducing a lease by five seconds can actually lengthen recovery if synchronized acquisitions overload the coordinator.

Question 4: Can two processes both believe they own a shard?

Evaluation: safety versus belief. Strong answer: yes, during pauses or partitions, but resource-side checks prevent both from making conflicting accepted changes. Follow-up: how do you audit this? Log epochs and rejected stale operations. Common mistake: treating split belief as automatically equivalent to data corruption. Sample the admission records at the target. Two heartbeats saying leader indicate a disagreement in belief. Two conflicting reservations accepted for the same exclusive GPU indicate a safety violation. Alert differently because the second case requires isolating the affected allocation.

Question 5: How does a resource enforce a fence atomically?

Evaluation: concurrency and storage isolation. Strong answer: compare generation and mutate in one linearizable transaction, with operation-level preconditions. Follow-up: how do same-epoch commands avoid conflict? Use state transitions and idempotency keys. Common mistake: separate read and write checks. A serializable local transaction suffices only when the protected effect lives inside it and the required real-time ordering holds at that boundary. An HTTP call inside a database transaction escapes its rollback. For such calls use a durable intent, downstream deduplication, and an explicit uncertain-outcome recovery path.

Question 6: Why might you shard leadership?

Evaluation: scaling tradeoffs. Strong answer: reduce contention and blast radius, improve locality, and bound coordination overhead. Follow-up: what if one shard is hot? Rebalance carefully while preserving epochs. Common mistake: creating an expensive consensus group per individual task. Choose a shard boundary that matches the unit of exclusive allocation. A shard per tenant may spread queue load well while two tenants still compete for one device. Keep that device’s reservation authority common to both paths, then balance scheduler locality against cross-shard contention.

Twelve original Senior Staff interview questions — part two

Question 7: What if a GPU worker cannot be reached during handoff?

Evaluation: safe degraded operation. Strong answer: quarantine the resource until authority can be established or a safe recovery policy is satisfied. Follow-up: how do you meet availability targets? Reserve spare capacity and distinguish scheduling recovery from job continuity. Common mistake: immediate blind reassignment. Quarantine means excluding that device from admission, including cached placement candidates and manual bypass paths. Preserve the existing training process if its allocation is still valid. Reusing a spare elsewhere costs capacity, but avoids paying for a whole gang restart merely because the scheduler changed.

Question 8: How do you recover a timed-out external API call?

Evaluation: durable execution. Strong answer: persist a client-generated request key before submission, query status, retry idempotently when supported, or reconcile observed state. Follow-up: what if the API offers neither query nor idempotency? Acknowledge weaker guarantees and use safeguards. Common mistake: assuming timeout means failure. Persist the client-generated idempotency key before the first submission. A server-generated handle may be unavailable if the response was lost. A conditional replay can recover the handle under the provider’s documented retention window. Outside that window, stop and inspect evidence before repeating a destructive action.

Question 9: What is the difference between a Raft term and ownership epoch?

Evaluation: abstraction boundaries. Strong answer: a term orders consensus elections; an epoch orders application resource ownership. They may correlate but need not. Follow-up: can an epoch advance without a Raft leader change? Yes. Common mistake: using them interchangeably. Schedule a planned move of shard S17 while the coordinator’s Raft leader remains stable. Only S17 needs to change generation. Then fail the Raft leader while its committed grants survive. Invalidating every shard would waste capacity and turn a metadata failover into a fleet-wide incident.

Question 10: How would you test stale-owner safety?

Evaluation: operational rigor. Strong answer: pause an owner, transfer ownership, delay its command, and assert resource rejection; restart the resource and repeat. Follow-up: what metrics detect failures in production? Epoch floors, stale rejections, and recovery timelines. Common mistake: only testing clean process crashes. Put an explicit barrier between the check and the commit in a deliberately broken test implementation. Deliver the new floor while the old writer waits. Verify the suite catches the stale commit there, then verify the production operation either serializes before the fence or fails.

Question 11: How do you handle a coordinator outage?

Evaluation: availability versus safety. Strong answer: existing safe operations may continue only within documented lease and enforcement rules; new ownership changes may pause. Follow-up: what about a minority partition? It cannot commit a new majority-backed owner. Common mistake: promising uninterrupted progress under arbitrary partitions. List individual operations the service can still perform. A GPU can continue its already admitted computation. A scheduler cannot claim another owner’s shard without the grant service. Reporting those states independently lets users distinguish sustained training throughput from temporarily unavailable new placements.

Question 12: How would you migrate an existing service to fencing?

Evaluation: cross-team delivery. Strong answer: add epoch fields and observability, introduce enforcement gateways, run compatibility mode, inject failures, stage rollout, and define rollback. Follow-up: what about legacy clients? Gate or quarantine them until compatible. Common mistake: enabling strict rejection without a migration plan. Cut off direct legacy access before declaring the invariant active. A mixed fleet can shadow comparisons for measurement, but one unfenced writer defeats the guarantee. Roll back performance changes independently while keeping the minimum accepted protocol version and durable floor intact.

Important concepts to remember

  • Election selects a coordinator. A successful election gives the controller a place to start recovery while delayed messages may still arrive.
  • A quorum authorizes a protocol step. Five voters need three, so voter placement determines which zone outages permit a new grant.
  • A lease expires according to its grantor’s protocol. Its deadline permits reclamation while a client process may still be running.
  • An epoch orders grants for one ownership domain. Comparing numbers across unrelated shard identities has no useful meaning.
  • A resource incarnation separates a deleted object from a later object with the same name. Bind grants to the immutable identity.
  • A fence rejects obsolete authority at the protected mutation. Checking only at the dispatcher leaves queued work unprotected.
  • A linearization point is the instant an operation takes effect in the serial history. It determines which side of a handoff owns a racing write.
  • An idempotency key identifies one intended operation across retries. Bind it to payload and tenant to catch incompatible reuse.
  • A version precondition orders competing updates within one epoch. Two commands from an authorized owner can still conflict.
  • Reconciliation compares durable intent with observed effects. A timeout leaves the outcome unknown until evidence resolves it.
  • Quarantine temporarily removes a resource from new admissions. Existing accepted work may continue under its documented contract.
  • A readiness barrier records which resources can accept a successor. Election success alone cannot measure usable capacity.

Speaking practice and final cheat sheet

Practice one: explain the difference between leader election, lease, epoch, and fence in thirty seconds without looking. Practice two: draw a paused-leader timeline and narrate exactly why the old command is rejected. Practice three: explain how a durable operation ID complements fencing during disaster recovery. Practice four: defend a sharded GPU scheduler against a global-leader alternative. Practice five: describe one situation in which your design deliberately pauses work to preserve safety.

Remember these core ideas: leader selection is not resource enforcement; a lease is time-bounded authority under assumptions; an epoch orders ownership generations; a fence rejects stale commands at the resource; the fence check must be atomic and durable; same-epoch commands still need preconditions; external operations may outlive ownership; idempotency handles retries; reconciliation resolves ambiguous outcomes; quorum availability depends on connectivity; and observability must measure accepted effects as well as elections. A strong Staff+ answer identifies where each guarantee is enforced and where it stops.

  • Final interview sentence: “I separate who is elected from which effects a resource will accept.”
  • Do not claim exactly-once external execution from a lease or fencing token alone.
